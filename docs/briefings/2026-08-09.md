## Flagged, not yet resolved

1. **A hold recorded only in memory/prompt prose is not enforced by
   `promotion_gates`.** BL-826's hold lived in the coordinator's own standing
   notes and `coordinator.prompt`, not as a ticket-level `hold:` field. When
   the operator revoked it in the ticket's own `notes:`, the automated
   promotion pick correctly promoted BL-826 — and the coordinator, trusting
   the stale standing note instead of the ticket file, reverted a *correct*
   promotion. No lasting damage (re-promoted within the same cycle,
   stray/duplicate handoffs cleaned up), but it cost a cycle and is a
   pattern worth naming: when a tool's automatic choice conflicts with a
   remembered hold, check the target ticket's own `notes:`/`source:` before
   overriding the tool.
2. **`route_backlog_to_coder.sh` with no BL-id argument routes the first
   `backlog/active/*.yaml` alphabetically, not a dispatch-gap-aware pick.**
   While fixing item 1, a bare invocation intended for BL-826 silently
   re-routed BL-574 a second time instead, producing a byte-identical
   duplicate handoff to the specifier that had to be found and abandoned by
   hand. Always pass the BL-id explicitly for a specific ticket; reserve the
   bare form for "whichever active item sorts first" cases.
3. **BL-861 (sibling-deferral survives blocker closing) is real and
   unfixed.** BL-574 was the live victim tonight; the coordinator worked
   around it by hand (direct QA re-entry) rather than waiting on the
   structural fix, per the ticket's own explicit scope note that says the
   coordinator routes BL-574's re-verification separately. Any other ticket
   currently sitting in a sibling-deferral could be stranded the same way if
   its blocker has already closed — worth a `qa-sibling-check.js list` sweep
   once BL-861 ships the "make stranded deferrals discoverable" listing it
   proposes.
4. **Transient `git index.lock` contention and `commit_integrity_cli`
   `add-failed`/`commit-failed` retries recurred twice tonight** on the
   shared master checkout, both resolved by a short wait-and-retry (a live
   concurrent git process, not a stale lock). BL-856 (shipped this shift)
   directly addresses the failure-mode half of this (no more staged
   leftovers on a failed commit); the lock contention itself is expected
   behavior on a shared checkout with concurrent writers, not a new bug.
