**New failure class: "landed but never handed off"** — a parcel's git work
merges cleanly into `main` (via a role's own merge-up commit), but the
*next* role never receives an actual mailbox parcel for it, so the ticket
sits stuck at its old stage indefinitely with no live work anywhere. Found
in two distinct flavors tonight, five instances total:

1. **QA approved and landed, but never notified the coordinator**: BL-1043,
   then BL-1083 and BL-1086 together. Each time, `build_freshness_cli sync`
   or a coder note surfaced the ticket sitting in `active/` with real,
   already-landed QA-approved work and no coordinator mailbox trail. Fixed
   each time by asking QA to resend the approval note, then bookkeeping
   normally once it arrived.
2. **Documenter passed to QA, but QA never received a parcel**: BL-1063 and
   BL-1088. Both show a full coder→cleaner→architect→hardener→documenter
   chain in git history, landed on `main`, but no handoff ever reached QA's
   mailbox or QA's own worktree branch. Routed both by hand with a
   `git_handoff` citing the documenter-pass commit. (BL-1063's attempt
   correctly bounced itself — a live parcel already existed for it at
   architect from a bounce/refix cycle, so my ancestry read was one stage
   stale; no harm done, nothing double-dispatched.)

The specifier independently minted **BL-1100** tonight for exactly this
pattern ("QA-landed ticket never closed strands in active") — recurring
enough now (5 instances, 2 flavors) that it should stop being a per-instance
coordinator workaround and get a real fix.

**A live bug in my own promotion tooling reintroduced a human-reserved
ticket three times.** `promote_and_route_next.sh`'s auto-picker promoted
**BL-1082** into an open active slot despite an explicit human/Cursor
directive on file twice today ("BL-1052/1053/1082 reserved for human/Cursor
build, swarm must not promote/dispatch... resume after 1078/1079/1080/1081
land"). The park was recorded only as prose in the ticket's `notes:` field —
no `depends_on`, no `status: blocked` — which nothing in the promotion
chokepoint reads. Reverted it twice by hand; it came back a third time
(evidently promoted by concurrent activity on the shared checkout, not my
own session). **Root-caused and fixed**: moved BL-1052, BL-1053, and BL-1082
into `backlog/hold/`, which every promote-picker structurally excludes from
its scan (Article 3.1) — the first correct, tooling-respected home for a
"reserved, do not auto-promote" ticket, rather than a prose note in
`paused/`. Should not recur.

**Same script's opposite bug, also found and worked around**: its
`is_do_not_promote()` check is a bare case-insensitive grep for the phrase
"do not promote" anywhere in a ticket file, and false-positived on BL-1071
and BL-1030 — both contain that exact phrase in unrelated prose ("do not
promote them/the two concurrently"), describing something else entirely.
Both are genuine, approved, high-severity defects; promoted manually
(`git mv` + `commit_integrity_cli` + `route_backlog_to_coder.sh <id>`)
rather than fighting the false refusal. Two independent false positives on
the same naive-grep pattern — worth a real fix if a third turns up.

**Heavy `.git/index.lock` contention observed repeatedly this session** —
routine `git mv`/`commit_integrity_cli`/`git commit` calls collided with
concurrent writers on the shared master checkout more often than on a
typical day, sometimes needing several retries. All cleared within seconds
each time and nothing was lost, but it's a signal of real concurrent load on
the shared checkout tonight (consistent with the parallel promotion of
BL-1082 above, which was not this session's own doing).

**Two `main`/`origin/main` reconciles**, both clean, both excluded
