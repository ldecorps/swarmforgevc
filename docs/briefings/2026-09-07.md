## The story of this window: an 8-hour swarm-crash loop, now landing its real fix

**GH-24** ("coordinator activity surfaced as a compact live feed on its
Telegram topic") landed 2026-09-06 21:45Z and, in its own words, ran its
Telegram-posting sweep with "no separate timeout." With no cursor file on
first run, the sweep tried to walk and post all 6,463 queued handoffs plus a
500-commit `git log` window in a single tick, one Telegram-send subprocess
per trace, overrunning the supervisor's sweep budget (225s) every time. The
supervisor called that `stalled`, and BL-144's halt policy killed every one
of the nine role tmux sessions.

That is exactly what happened, repeatedly: **35 full swarm deaths** logged
between 21:52Z on 9/6 and 06:04Z on 9/7 — roughly one every 13 minutes for
over eight hours overnight, babysitterd faithfully restoring all nine
sessions each time only for the same unbounded sweep to kill them again a
few minutes later. Every agent lost its in-flight context on every death.
This is the swarm-starved/GH-24 kill-loop the operator escalated via SUP-17.

**It stopped this morning.** A human-applied hotfix at ~06:00–06:04Z UTC
(`c5f3e9490b` / `0e96c01906` / `2b8cc2d644`) made the activity feed
config-gated and **default OFF**, restoring the two code halves of the kill
switch that a prior revert had split. No swarm deaths since.

**The durable fix, BL-1454, is now at the finish line.** Human-approved
directly (2026-09-06 ~22:48Z) to run through the BL-567 expeditor with the
stack stopped rather than ride the pipeline it was breaking, it has already
passed coder → cleaner → architect → hardener → documenter, and QA is
running as of this morning (08:06Z). The fix: seed the cursor at the newest
trace on first run and post nothing historical, cap each tick to ~20 posts
inside a ≤30s (never more than a quarter of the supervisor budget) deadline,
and persist the cursor after every successful post instead of only at the
end of a batch — so an interrupted tick resumes instead of restarting from
item 0. It is not yet re-enabled; that is BL-1454's call once QA passes.
