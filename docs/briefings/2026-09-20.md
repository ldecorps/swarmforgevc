## The story of this window: five different "is this safe to land" signals turn out to have been broken, some for weeks, and a duplicate coder seat kept reproducing already-forwarded tickets

The pattern this window: gate after gate that exists specifically to
catch a bad land was itself silently wrong. **BL-1657** found
`check_art_director_tip.sh` comparing every tip against the literal
branch `primary/art-director` — a name that only exists on the nested
pack's frozen checkouts and has never existed on this host, so the guard
has refused **every live art-director tip since it shipped on
2026-09-06**; QA has been hand-verifying the lane on every land since,
undetected because the guard's own acceptance fixture built the wrong
branch too (the BL-1445 shape: a fixture that satisfies its own anchor by
construction gates nothing). The fix resolves the branch from the roster
row for the seat, falling back to the `swarmforge-<seat>` convention,
never a hard-coded literal — the same shape BL-1459 already gave its
sibling documenter-briefing guard. **BL-1668** found the QA-ancestry
predicate (`is_qa_ancestor.sh`) resolved only one hop of a land-approval
record chain, so a hand-built commit QA builds to replace its own stale
replay — done twice overnight — read as unapproved pipeline code and
escalated three false Article 4.2 CRITs to the operator between 04:22Z
and 05:39Z; it now walks a bounded, cycle-safe three-record chain, and
`record_land_approval.bb`'s exit code finally matches the verdict it
prints (it used to exit 0 even on `not approved`, so QA's own recipe step
"verify it exits 0" passed unread). **BL-1662** found the merge-deletion
guard attributing a removed path to whichever commit touched it most
recently — including an untagged removal commit BL-1617's own
closed-ticket-subject rule *requires* to be untagged — making its own
remedy ("name the ticket in the message") unsatisfiable for exactly that
shape; it now walks the path's full history to the first tagged commit.
**BL-1650** took three rounds to land: an already-applied cherry-pick
treated as a real conflict (escalating every later parcel whose ancestry
carried an already-hand-landed stray), a rework regression that reverted
a sibling ticket's own fixture-path fix, and a tip-whose-content-already-
equals-main case that tried a doomed cherry-pick instead of recognizing
nothing was left to land.

Underneath several of these, the same root cause kept resurfacing: a
**duplicate `coder@2` seat** independently re-implementing tickets the
real `coder` branch had already built, reviewed, and forwarded —
confirmed for BL-1652 (kept a stray artifact against explicit
instructions to drop it), implicated in BL-1650's D1 regression (its
rework was built on a branch lacking the original cleaner's fixture fix),
and suspected-then-cleared for BL-1663 (a specifier ruling confirmed that
instance was actually the reviewed lineage, not a duplicate). The
specifier's standing fix so far is procedural, not structural: parcels no
longer edit `backlog/standing-reds.tsv` at all — only the land step
retires a row — recorded in `coder.prompt` after a premature row-removal
from the stale coder@2 lineage twice blocked ordinary merges this window
with a genuinely unresolvable git conflict (a real-content deletion vs.
keep, requiring an explicit `This reverts commit <sha>` trailer per
BL-1576's own exemption mechanism to clear).

## Operator watch items

- **A standing register file cannot safely be hand-edited by a parcel
  mid-flight, and the merge-drop guard that catches a dropped edit has a
  real (documented) escape hatch, not just a symptom to route around.**
  `backlog/standing-reds.tsv` row removals from a stale/duplicate coder
  lineage twice produced a genuine git conflict this window — one side's
  branch kept an unlanded ticket's row, the other side had already
  (prematurely) deleted it — that no ordinary "take theirs" or "take
  mine" resolution can satisfy the merge-drop guard (BL-1576) on, because
  either choice necessarily discards the other side's uncontested
  content. The guard's own remedy works: a follow-up commit whose message
  contains `This reverts commit <the sender's own prior full-sha commit
  that touched the path>` (`-F` fixed-string grep, checked via `git log
  --grep`) satisfies its exemption. The specifier's procedural fix
  (`coder.prompt`: a parcel never edits this file) should make this rare
  going forward, but it is worth knowing the mechanism exists the next
  time a bookkeeping file produces an unresolvable-looking conflict.
