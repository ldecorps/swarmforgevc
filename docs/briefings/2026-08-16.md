**Finding #1 (self-caught, fixed): a human fast-tracked ticket sat active
but unrouted, then turned out to be duplicated.** BL-900 (epic-priority-
before-ticket-priority ordering) was minted to `paused/` at 00:58 via the
normal specifier drain, then fast-tracked straight into `backlog/active/`
at 04:15 by direct human chat approval (`c6da717bb`, commit message says
"Expedite" but this is **not** the Article 3.2.4 severity-expedite lane —
BL-900 is `type: feature`; this was a human queue-jump via the topic-
approval flow, worth naming precisely so the two mechanisms don't blur).
That direct-to-active write left the ticket with no `assigned_to` and no
handoff ever sent — it sat unrouted in `active/` for over 3 hours before
this coordinator noticed on a routine sweep, assigned it, committed
(`b854dbe13`), and routed it. Chasing that down surfaced a second bug:
BL-900's original `paused/` copy (from the 00:58 mint) had never been
removed when the active copy was created — a genuine stray duplicate sat
committed in git, with an unrelated session's uncommitted local deletion
of it dangling in the working tree since before this shift's coordinator
picked it up. Committed that removal (`61f96380a`). A side effect while
this was unresolved: the coder's own worktree, still lagging `main`, read
the pre-fix state and correctly declined to start the routed Work
(`approval: pending`, ticket "still in paused/" from its point of view) —
textbook worktree staleness (BL-317/325), resolved with a merge-and-retry
note. Net: no code defect, but a real gap in how a human fast-track bypasses
the normal promote+route+commit sequence — worth a structural look (see
Flagged #2).

**Finding #2 (swarm-caught, now BL-901): a commit silently deleted a
ticket it didn't own.** `c9f888d14` ("Accept rule_proposal (engineering)")
swept a staged delete of `backlog/paused/BL-893-approvals-ambulance-
choice.yaml` into an unrelated commit at 02:28 — no gate caught it, no
error, no log line. BL-893 (and the human approval recorded on it) was
recoverable only because an untracked copy happened to still be sitting in
the master checkout; a `git clean` at any point in that ~3-hour window
would have destroyed it with nothing left to notice by. Restored
(`0405f5d4e`) and specced as BL-901 (defect, proposed severity `high`,
`human_approval: pending` — see Asks #1) to add a `check_commit_size.sh`-
style pre-commit guard against a commit deleting a ticket file it doesn't
otherwise reference.

Both findings share a root cause worth naming once rather than twice:
**a write to `backlog/` outside the normal promote/close/mint choreography
has no gate checking it stayed self-consistent.** BL-901 closes that gap
for silent deletion specifically; the promote-without-route gap from
Finding #1 does not yet have a ticket (see Flagged #2).
