## The story of this window: a self-inflicted merge-drop gate cascade, caught and closed within the day

BL-1576's merge-drop send gate (landed the previous window to stop a
one-sided merge from silently reverting already-landed work) turned out to
scan too much: for a coordinator-routed `git_handoff` — whose commit is
main's own tip — the scan covered the sender's ENTIRE off-main history,
not just the merges it made for that parcel. The coder's BL-1606 send was
refused first (six historical, already-superseded merges); BL-1610 bounded
the scan to merges since receipt. That bound alone still re-admitted any
merge an UPSTREAM role made that only the received commit's own ancestry
carried — the documenter's own four sends were refused on a cleaner merge
this way — so BL-1610 was bounced and amended a second time to exclude the
received commit's ancestry too. Both amendments landed today. Along the
way, one hardener merge resolution silently re-added a register row
BL-1608 had deliberately removed (BL-1604, a live instance of the same
merge class BL-1576 exists to catch) — caught by QA before landing, not by
any automated gate, and BL-1604 now restores such rows at land time. A
newly-observed root cause: coder@2's stage-queue-dir reads the SHARED
coder mailbox rather than its own, so mail addressed to that seat never
dequeues — this independently produced two functionally-identical, fully
superseded coder rebuilds (BL-1604, BL-1610) stranded on that branch,
recorded as `abandoned_commits` rather than lost or re-litigated.
