# Backlog Item Schema

Every backlog item is a YAML file in `backlog/active/` or `backlog/paused/`.
The coordinator reads these to route work.

## Required Fields
| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique identifier (e.g., `BL-042`) |
| `title` | string | Short description of the work |
| `description` | string | Detailed requirements |
| `priority` | int | Lower = higher priority (e.g., `0` for critical) |
| `mutation_cost` | string | Estimated mutation testing cost: `low`, `medium`, or `high`. Used by the coordinator to sequence promotion. |
| `epic` | string | (BL-341; required on live non-epic items as of 2026-07-19) Which multi-slice epic this item belongs to, as data — never inferred from `notes:` prose. The epic id namespace is separate from `BL-###` ticket ids. One ticket per epic id also carries `type: epic` (see below) and *is* that epic's own definition, self-referentially declaring the same `epic:` id. Every live ticket under `backlog/active/`, `backlog/paused/`, or `backlog/hold/` that is **not** `type: epic` must set a non-empty `epic:`. |
| `milestone` | string | Required on every `type: epic` tracker (e.g. `M8`). Ordinary slices may also carry `milestone:` for display; epics must not omit it. |

## Optional Fields
| Field | Type | Description |
|-------|------|-------------|
| `slice_size_envelope` | string | (BL-634) The slice's declared SIZE band: `low`, `medium`, or `high`. Read by `slice_size_envelope_gate_lib.bb` at promotion, and **preferred over `mutation_cost:`** — the gate falls back to `mutation_cost:` only when this field is absent, and to `medium` when both are. Declare it explicitly whenever `mutation_cost:` is set for a reason other than size: Article 3.6 requires every deprecator build/run ticket to carry `mutation_cost: high` so BL-1001 keeps it off an easy seat, and that seat-tier declaration would otherwise be read as a size estimate and demand a `size_envelope_decision:` the ticket does not need. The two are different axes and are never conflated. |
| `size_envelope_decision` | string | (BL-634) The specifier's split-or-justify record, required when the gate flags a slice — i.e. when the declared band (above) is `high`, or `size_envelope_insertions:` is at or above the p90 threshold (`slice_size_p90_flag` in `swarmforge.conf`, default 514). Any non-blank value discharges the gate; write `justify not split - <reason>` or `split into <ids>` and put the full reasoning in `notes:`. **Single-line scalar only.** A block scalar (`size_envelope_decision: >` with an indented body) reads as ABSENT and the gate still refuses — the same trap as `acceptance:` (BL-922), because the gate's `read-field` rejects a bare `>` or `|` indicator. Keep the value free of ` #`, which is stripped as an inline comment. |
| `size_envelope_insertions` | integer | (BL-634) Estimated inserted lines, when the specifier has a number. At or above `slice_size_p90_flag` (default 514) it flags the slice for split-or-justify exactly as a `high` band does; absent means the band alone decides. |
| `workflow_pin` | list[string] | Override the default pack for this item (e.g., `[coder, cleaner]`). |
| `roles` | list[string] | (BL-317) The routing manifest: which pipeline roles this ticket actually needs, as either a flow-style list (`roles: [coder, QA]`) or a block-style list (`roles:` followed by `  - coder` / `  - QA` lines) — both are read identically. Absent means the full standard chain (`specifier, coder, cleaner, architect, hardender, documenter, QA`) — today's behavior, unchanged. A `roles:` field that IS present but cannot be parsed in either form is a validation error rejected before promotion, never silently treated as absent. `coordinator` is never a valid member (bookkeeping only, not a pipeline chain role); `coder` and `QA` are always required even in a declared list. This slice only decides/validates the list — it does not yet bring a role's session up or down based on it (a later slice). |
| `depends_on` | list[string] | IDs of items that must complete first. **Enforced at promotion since BL-957**: `promotion_gates_lib.bb`'s `depends_on` gate (between `human_approval` and the depth cap in `evaluate`'s fixed chain) refuses any candidate naming a dependency that is not in `backlog/done/` — an ACTIVE dependency still refuses, and the refusal names every unsatisfied id (`REFUSE|depends_on|depends_on not yet landed in backlog/done/: BL-620`). Both promotion modes inherit it from the one BL-663 chokepoint, so the auto-picker skips a blocked candidate rather than promoting it. The gate reads this field with its OWN reader, not `read-field` (which returns nil for a blank value and would read a block-style list as no dependencies at all): every `BL-<n>`/`GH-<n>` token in the field's value and its indented continuation lines, inline `#` comments stripped — so `[]`, a flow list, a block list, and a bare scalar with trailing prose are all read, and prose around the ids is ignored without being parsed. Fails CLOSED: an id resolving to no ticket anywhere, and a present-but-unparseable value, both refuse rather than promote. `depends_on: []` and an absent field promote unchanged. Transitive cycles are NOT traversed here (`makeTopPrioritySafety.ts` owns cycle detection for the make-top primitive). |
| `acceptance` | string | A path to the item's Gherkin feature file under `specs/features/` (e.g. `specs/features/BL-042-add-oauth-login.feature`) — the feature file is the durable acceptance contract and outlives the backlog item. **Single-line pointer only — a block scalar is NOT read (BL-922).** Some older items still carry the criteria inline (`acceptance: \|` followed by a Gherkin block); that form is unreadable by the pre-QA gates and must be migrated before the item is promoted. The gates' ticket-yaml reader (`pre_qa_gate_gather_lib.bb`'s `read-yaml-field`) captures only the `acceptance:` LINE's own tail, so a block scalar collapses to the bare indicator `|`: the BL-761 acceptance-contract gate then fails CLOSED at the documenter->QA hop (`declaration-readable? false`), and the BL-880 pointer gate skips the ticket silently at every earlier hop — so the defect surfaces only after five stages of work have been spent (BL-624, BL-625). Prose that used to ride inside the block belongs in a sibling field (e.g. `qa_e2e:`), never on this one. |
| `human_approval` | string | `pending` or `approved` (BL-251). Set by the specifier to `pending` when it authors or re-specs a feature file that needs human review; a human flips it to `approved`. Unset/absent means not applicable (no approval needed, or a legacy item). This structured field is the SINGLE source for the "needs human approval" lists surfaced in the PWA and the daily briefing — both read this field directly, never the free-text `# HUMAN APPROVAL: ...` comment some items still also carry. Only meaningful on live items (`backlog/active/`, `backlog/paused/`); not read from `backlog/done/`. (BL-357) A ticket's own `BL-###` Telegram topic also gets asked directly on the not-pending → pending transition; replying "approve" in that topic flips this field back to `approved`. |
| `type` | string | (BL-341) E.g. `feature`, `defect`, or `epic`. The one item per epic id carrying `type: epic` is that epic's own definition (its `title` plus `remaining_slices` / `decomposes_into` below), distinct from an ordinary slice merely declaring the same `epic:` id. |
| `severity` | string | **Required on every `type: defect` ticket** (Article 3.2.4, ratified 2026-07-25): one of `critical`, `high`, `medium`, `low`. Drives the expedite lane - a `critical`/`high` defect is promoted ahead of every non-expedited candidate regardless of its `priority:` number. The lane **fails closed**: a defect carrying no `severity:` is NOT expedited and is surfaced for triage instead, so omitting the field can never buy priority. Reserve `critical` for swarm-down or data-loss, `high` for a live fault degrading behaviour or a broken safety/health signal, `medium` for real-but-contained defects, `low` for cosmetic ones. A distinct scale from `priority:` and never conflated with it: expediting a ticket never bumps its handoff `priority:` to `00`, which stays reserved for genuinely blocking decisions. |
| `status` | string | Lifecycle marker, set at mint and - measured 2026-08-23 - never written again by any script (`swarmforge/scripts/` contains no writer for it). Live values: `todo` (the mint default), `needs_design`, `superseded`, `paused`, `blocked`. **Only `blocked` changes behaviour**: `promote_and_route_next.sh`'s `is_blocked_status` refuses a promotion candidate whose line matches `^status:[[:space:]]*blocked[[:space:]]*$` - anchored to the field, so prose that merely mentions the word is never mistaken for it (BL-1100: the unanchored prose check that sat beside it was wrong on 5 of the 8 tickets it uniquely decided). Use `blocked` to park a ticket under a stated condition the **coordinator** may later clear; use `backlog/hold/` for a human-only park no coordinator may release (Article 3.1). Marking a ticket `blocked` never replaces the human sentence that explains the park - that sentence stays in `notes:` verbatim (Article 5.3). The remaining values are advisory and gate nothing today. |
| `remaining_slices` | list[string] | (BL-341) Only meaningful on the epic-defining item (`type: epic`). Free-text descriptions of work known to belong to the epic but not yet ticketed — human/specifier-authored, since nothing in the backlog can derive an unticketed slice's existence on its own. Read as either a flow-style or block-style YAML list, same as `roles`. |
| `decomposes_into` | list[string] | On `type: epic` trackers: child `BL-###` ids. |
| `required_wiring` | list[string] | (BL-531) Call sites this ticket's own mechanism must be wired into, checked by `swarm_handoff.bb`'s pre-QA gate at the moment a `git_handoff` addressed to QA is sent. Each entry is `path::pattern`, with an optional third `::why` segment (split on the first two `::` occurrences, so `::` may appear inside `why` but not in `path`/`pattern`) — either a flow-style list (`required_wiring: [a/b.bb::some-fn]`) or a block-style list (`required_wiring:` followed by `  - "a/b.bb::some-fn"` lines), read identically to `roles`. `path` is read **at the commit cited in the draft**, never the sender's working tree; a missing path or a path present without `pattern` (a fixed-string, non-regex, `str/includes?` check) refuses the send. An entry that cannot be parsed also refuses the send (a `manifest`-class finding) — a typo fails loud, never silently passes. Absent means the ticket declares no required wiring; the gate then only runs its ancestry check. |
| `abandoned_commits` | list[string] | (BL-531) Sha prefixes (10-char abbreviations are enough) the pre-QA gate's ancestry check must NOT flag as stranded, even though they name this ticket and sit off the parcel's lineage — the documented override for a commit deliberately dropped rather than forwarded. Read as either a flow-style or block-style list, same as `roles`/`required_wiring`. |
| `required_stages` | list[string] | (BL-606) Declare which pipeline stages this ticket actually needs, as a single-line flow-style list: `required_stages: [coder, qa]`. Stages NOT listed are skipped at routing time if `required_stages_routing_enabled` is true in `swarmforge.conf` (default false for safety). Stages omitted must have `stage_skip_reasons` entries explaining why. Valid stages are `coder`, `cleaner`, `architect`, `hardender`, `documenter`, `qa` (in that canonical order). Unknown stages, duplicates, or `qa` omitted while `coder` is present are rejected and default to full-chain (all stages). Absent field means the ticket runs the full canonical chain (safe default). |
| `stage_skip_reasons` | mapping | (BL-606) Provide human-readable reasons for each stage omitted from `required_stages`, keyed by stage name: `stage_skip_reasons: { cleaner: "style-only commit", architect: "no architecture changes" }`. One reason per skipped stage. These are committed to git alongside `required_stages` for auditability — `git log` shows both the intent (which stages are needed) and the justification (why others were skipped). Absent or incomplete reasons are a warning; rejecting a ticket with incomplete reasons is a future evolution. |
| `invariants` | list[string] | (BL-633) Properties that must hold across the WHOLE slice — every scenario, including the ones nobody wrote down — each phrased so a violation is checkable. Distinct from `acceptance:` by kind, not by detail: Gherkin scenarios are EXAMPLES (concrete input → concrete expected output); an invariant is a PROPERTY quantified over the whole surface, which no enumeration of examples can express. Worked example: BL-590 slice 1 took four architect send-backs, each surfacing one more violating site of one never-stated property — as an invariant it is a single line, `"Every durable write is idempotent under redelivery of the same Telegram update"` (now declared on BL-590's own ticket). **Cap: at most 3 entries.** Beyond three the list degrades into prose nobody reviews against, and needing more is a signal the slice is too big — split the slice, not the list (see BL-634). Absent or empty is a legitimate outcome, not a failure: most small slices genuinely have none, and a manufactured invariant is worse than no field. Primary consumer is the **coder** (BL-654): for each declared invariant the parcel must carry a coder-authored executable property test — asserted generator-reach into the states the invariant quantifies over, not hoped-for coverage — in the same parcel as the behavior change; the coder's own prompt names this the Invariants section. The **architect** consumes it second, but never as first author: its Invariants Review checks that test's existence and non-vacuity FIRST (a missing or vacuous test is its own send-back, failure class `invariant-unencoded`, distinct from a violated property), then reviews the parcel against each declared invariant as its own distinct pass, sweeping ALL violating sites before one bounce per property — never one bounce per site. Read as a flow-style or block-style YAML list, same as `roles`. |
| `bounce_count` | int | (BL-608) Number of times this ticket has been bounced back during review. Always equals the length of `bounce_history`. Set automatically by `record-bounce` (BL-635 generalised this from the QA-only `record-qa-bounce`; every reviewing role's send-back now calls it) when a bounce is recorded; always recomputed from the list, never manually edited. Absent means zero bounces. |
| `bounce_history` | list[mapping] | (BL-608) Ordered list (oldest first) of bounce events. Each entry is a single-line flow mapping: `{ at: 2026-07-23, by: QA, blamed: coder, class: behavior, commit: 1f7987dd4a, evidence: backlog/evidence/BL-606-qa-bounce-20260723.md }`. Fields: `at` (date), `by` (bouncing role), `blamed` (role held responsible), `class` (failure classification), `commit` (abbrev hash of the bounced commit), `evidence` (path to the bounce evidence file). Append-only; managed by the `record-bounce` CLI (BL-635; `record-qa-bounce` is the legacy QA-only predecessor, still used for its own BL-608 acceptance suite but no longer invoked by any role prompt). Absent means no bounces recorded. |

## Hygiene rules (open backlog)

1. **Every non-epic live ticket has a non-empty `epic:`.**
2. **Every `type: epic` tracker has a non-empty `milestone:`** (and self-declares the same `epic:` id).
3. Audit: `bb swarmforge/scripts/backlog_epic_milestone_audit.bb [project-root]` (exit 1 on violations).

## Example
```yaml
id: BL-042
title: "Add OAuth login"
description: "Implement OAuth2 login with Google and GitHub providers."
epic: auth-onboarding
milestone: M8
priority: 10
mutation_cost: high  # Heavy: new auth flow, many edge cases
depends_on: [BL-041]  # Depends on user table migration
```
