# BL-2064 coder evidence (2026-10-08)

Built the restart half (BL-2064's own build, on top of the already-landed
warn-half hotfix 9b89a6e5db): at the 24th qualifying read since the last
reset, the seat is restarted the way a missed write restarts it (BL-1991),
drawing on the same per-parcel restart count (BL-1992); once both restarts
are spent, the overrun releases the parcel instead. `depends_on` BL-2055
and BL-2056 are both closed on main.

## Production changes (swarmforge/scripts/local_model_repeat_guard.bb)

- `transcript-entries` now also emits `{:kind :user :text ...}` for a
  `"type": "user"` record, and `session-first-message` reads the first
  one - the human's own fallback ("the latest compaction's next_step,
  else the session's first message") for a seat that overruns the read
  budget before any compaction has run.
- `read-restart-at` (24), `read-budget-step`, `read-budget-override-message`,
  `read-budget-overrun`, `read-budget-restart-decision` and
  `read-budget-release-decision` - the read-budget-side counterparts of
  `missed-write`/`restart-decision`/`release-decision`, sharing the exact
  same `restart-count`/`max-restarts` gate and the same durable state file
  (`restart-state-file` keys only on the in-process handoff name, never on
  the restart's reason).
- `write-restart-request!` is now a thin wrapper over a new
  `write-restart-state!`, which also backs the new
  `write-read-budget-restart-request!` - one place bumps the shared count
  and writes the pending `.msg`, whichever reason triggered it.
- `answer`'s `cond` gains `read-restart`/`read-release` branches, checked
  only once the missed-write branches (`restart`/`release`) have already
  said no - the ticket's own direction: "restart and release keep their
  precedence, the read-budget restart joins them."
- `read-budget-note`'s own guard now also requires `(< total read-restart-at)`,
  so the 24th read's own call takes the restart branch in `answer`'s cond
  (which returns before `notes-response` runs) rather than double-firing
  the warn note too.

## Invariant correction (ticket's own direction)

The ticket's own notes (amended 2026-10-07) found a bug in its own
`invariants:` text: it named `resets-window?` (which includes a bare
compaction) as the read-budget's reset rule, but the corrected rule - the
one actually shipped in hotfix 9b89a6e5db and carried forward here - is
`read-budget-resets?`, which drops the compaction clause on purpose (a
compaction is exactly when the seat is most likely to re-read everything
to rebuild lost context; resetting the budget there hands it a fresh 12
reads at the worst moment). Corrected invariant 1 in the ticket YAML to
name `read-budget-resets?` instead, per the ticket's own instruction
("Whoever builds it should also correct invariant 1 above in the same
pass").

## Logic verification before writing the step handler

Confirmed directly against the real functions (`bb -e`, scratch, not
committed):
- 23 prior reads + the in-flight call = 24th read -> `read-budget-overrun`
  fires.
- 11 prior reads + in-flight = 12th read -> `read-budget-note` fires,
  `read-budget-overrun` does not.
- 20 reads, a bare compaction, 3 more reads, in-flight = 24 total ->
  `read-budget-overrun` fires (compaction does NOT reset) - matches the
  spec-gap finding above.
- 20 reads, an edit, 3 more reads, in-flight = 4 since the edit -> no
  overrun (edit DOES reset).
- `session-first-message` returns the FIRST user-type entry's text, not a
  later one.
- When a missed-write condition AND a read-budget overrun both hold on
  the same call (22 reads, a compaction naming a real write path, 1
  non-matching read, in-flight read = 24th read AND the missed-write's
  own 2nd non-matching call, one short of its own 3-strike trigger).
  Rebuilt with a realistic multi-segment named path (a single-segment
  absolute path does not match `named-write-path`'s own regex, which my
  first attempt at this check used by mistake) - missed-write's own
  override message won, confirming precedence is respected.
