# BL-693 coder pass

## Declared invariants - encoding

Both invariants are property-tested (coder's first authorship, BL-654) in
`extension/test/bl693DocsDuplicateParagraphInvariants.property.test.js`,
driving the real `findDuplicateLines` the standing guard and the
acceptance handler both consume:

1. "No line whose content is markdown structure ... is ever reported as a
   duplicate, however many times it repeats." Encoded by generating
   realistic, bounded-length structural markdown lines (fences, rules,
   headings, table separators, list/blockquote markers, box-drawing
   glyphs) via `fc.oneof`, repeated 2-50 times, asserting zero findings.
   Deliberately generates REALISTIC structural markdown (bounded under the
   threshold, matching real documents), not adversarial 300-character
   "horizontal rules" no real file would contain - the ticket's own design
   states the exemption is threshold-only, by construction, never a
   separate structural-pattern classifier (see "What was wrong" below).
2. "A substantial paragraph repeated ... turns the guard red inside the
   parcel that introduces it." Encoded by generating substantial
   (threshold+1 to threshold+300 char) ASCII lines repeated 2-12 times,
   asserting the guard finds exactly one group with the exact count and
   every line number, every time - not just the two fixed examples (2,
   286) the acceptance Scenario Outline covers.

**Non-vacuity** (staged-first restore, run 2026-09-18, recorded in this
commit): `findDuplicateLines` temporarily made to always return `[]` (the
exact BL-692 failure mode). Property 2 failed immediately, naming the
generated duplicate it should have caught (`0 !== 1`). Property 1 passed
vacuously - an always-empty result cannot be told apart from "never
reports a structural line" by that property alone, which is exactly why
property 2 exists as an independent check rather than relying on property
1 in isolation. Restored byte-for-byte; both properties hold again
(verified: `git status --short` shows no diff on the helper file after
restore).

## What was wrong, and the fix

`docs/reference/Specification.MD` carried 830 KB of one paragraph
repeated 286 times for 17 days and ~25 documenter commits before BL-692
caught it by hand. Nothing in the repo lints prose.

**The guard** (`extension/test/helpers/docsDuplicateParagraphGuard.js`,
required by no ticket wiring but factored out per the ticket's own "still
welcome" note): `findDuplicateLines(content, threshold=200)` (pure) finds
trimmed lines over the threshold repeating within one file's content;
`scanDocsTree(docsDir)` (impure) walks every `.md` file under `docs/`
via the shared `walkFilesTolerant` helper (BL-1443's tolerant-ENOENT
walk, already proven against the exact race class this codebase has hit
before) and checks each file ONLY against its own content - never across
files, per the ticket's explicit within-file-only constraint.
`formatFinding` renders one readable line naming the file, truncated
text, count and every line number.

**Deliberately no structural-pattern classifier.** The ticket's own
design: "Structural markdown is exempt by construction ... all short, and
the substantiality threshold excludes them without an enumerated
allowlist." The 200-character threshold alone is the whole mechanism -
verified against real structural markdown (scenario 03's seven kinds, and
the property test's generated ones) and against the real docs tree
(scenario 01 and the standing guard's own real-tree assertion, both
green).

**The standing guard**
(`extension/test/docsDuplicateParagraphGuard.test.js`, the
`required_wiring`-pinned filename): 22 unit tests over the pure scanner
plus the real docs tree assertion and the no-exemption-list check, riding
`npm test` - the suite every parcel already runs, per the ticket's
explicit rejection of a documenter-invoked script that can be (and was,
for 17 days) forgotten.

**Draft conversion, in this same commit** (BL-1340/BL-233): renamed
`BL-693-repeated-paragraph-gate.feature.draft` to `.feature`, repointed
the ticket's own `acceptance:` field, and wrote
`specs/pipeline/steps/bl693DocsDuplicateParagraphGuardSteps.js` -
registered by discovery (BL-1371), no `DOMAINS` list to edit. All 13
scenarios (Scenario Outline 02's 2 examples, Outline 03's 7 examples,
01/04/05/06) drive the real `scanDocsTree`/`findDuplicateLines`/
`formatFinding` functions over real mkdtemp fixtures.

**The guard's first catch** (constraints, 2026-09-18 triage): the
specifier's freshness scan found `docs/index.md` carrying two accidental
duplicate how-to bullets - the BL-1370 bullet at lines 162 and 169, and
the BL-1056 bullet at lines 324 and 326 (each appended twice by two
separate parcels, exactly the defect class this guard exists to catch).
Removed the SECOND copy of each (lines 169 and 326 as of the pre-edit
tree; re-located by content, not by number, since earlier tickets in this
same parcel session also touched the file) - two lines removed, nothing
else in `docs/`.
