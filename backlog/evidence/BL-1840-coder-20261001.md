# BL-1840 — coder pass, 2026-10-01

## What was built

- `swarmforge/scripts/swarmforge.sh` (`write_local_model_qwen_settings`):
  the static `.qwen/settings.json` the swarm writes for every local-model
  seat now sets `"context": {"autoCompactThreshold": 0.8}` — qwen's
  CURRENT key (`context.autoCompactThreshold`, a 0–1 fraction of the
  model's own `contextWindowSize` that `computeThresholds()` multiplies
  against, read directly from the installed `@qwen-code/qwen-code`
  package's bundled source and settings schema — never from memory, per
  the ticket's own direction). The OLDER `model.chatCompression.
  contextPercentageThreshold` this seat's settings never set is REMOVED
  in the installed build and silently ignored (no startup warning) —
  exactly the BL-1841 failure shape the ticket warns against, so this is
  deliberately NOT the key used. 0.8 of a 49152-token window floors to
  39321; of 32768 to 26214 — the two numbers the ticket's own outline
  names. Confirmed the key survives BL-1838's own provider-entry merge
  unchanged (manually, with a real endpoint): `context` sits beside the
  later-added `modelProviders.openai` key, untouched.
- `specs/pipeline/steps/bl1840QwenCompressionThresholdSteps.js` (new):
  the acceptance driver. Scenario 01 drives the REAL
  `write_local_model_qwen_settings` (sourced from swarmforge.sh, same
  posture as BL-1838's own handler) against a fake Ollama `/api/show`
  probe and reads back `floor(autoCompactThreshold * contextWindowSize)`.
  Scenario 02 drives the REAL pinned `qwen` binary (`--auth-type openai`,
  a throwaway `HOME`, cwd the written worktree) against a combined fake
  endpoint on one port — `/api/show` for the settings-write probe,
  `/v1/chat/completions` (SSE) for qwen's own runtime call — with a
  padded ~20,000-token-scale prompt, and asserts NO request body contains
  qwen's own compaction-request marker text (`"First, reason in your
  <analysis> block"`, found in the installed package's compiled source) —
  never a raw request COUNT, since a real turn also fires an unrelated
  `managed-auto-memory-extractor` subagent call even for a trivial prompt
  (measured live while building this handler). A key qwen silently
  ignored would still pass scenario 02 alone (20,000 tokens sits well
  under even qwen's own 85% default of a 49152 window) — scenario 01 is
  the one that catches a wrong/ignored key, by reading the settings file
  back and asserting the exact numeric threshold.
- `extension/test/bl1840QwenCompressionThresholdInvariants.property.test.js`
  (new): a coder-authored property test (BL-654) for the declared
  invariant, driving the REAL `write_local_model_qwen_settings` +
  `local_model_qwen_provider_cli.bb` against served windows generated
  across 4096–262144 (not just the outline's two fixed examples:
  32768/49152), asserting `autoCompactThreshold` is always exactly 0.8,
  the provider's `contextWindowSize` always equals the generated served
  window, and the resulting threshold is always `floor(0.8 * window)`
  and strictly below the window itself.

## Invariant (ticket's `invariants:` list, BL-654 coder-first authorship)

"A local-model seat's qwen never compresses a history below 80% of the
window its model is served with." Encoded by the acceptance feature's
own outline (exact numeric check at two windows) and by the property
test (the same check generalized across a wide window range).
**Non-vacuous, verified by hand** three times: (1) changed the written
fraction to `0.5` — the acceptance feature's scenario 01 failed
immediately (`got 24576`, expected `39321`); reverted, reran 3/3 green.
(2) same break, property test — failed on the very first generated case;
reverted, reran green. (3) changed the fraction to `0.9` — property test
failed immediately (`0.9 !== 0.8`); reverted (clean diff after, confirmed
via `grep`), reran green.
