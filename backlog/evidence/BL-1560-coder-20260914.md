## Goal 7 (PROBE only - BL-1561 owns the fix): reproduced, general defect CONFIRMED, exact symptom differs from the mint-time narration

Re-ran the mint-time reproduction on this parcel's commit: a file `t.log`
holding the line `no such file or directory: ./ready_for_next.sh`,
composed through the REAL `build-healing-wrapper-command` with
`grep -n 'no such file or directory: ./ready_for_next.sh' t.log` as the
original command, executed for real over bash.

Traced with `bash -x`:
- The first attempt (the grep as issued) matches `t.log`'s line, exits 0,
  and its own output is captured.
- Because that captured output itself matches the `:missing-script-path`
  pattern, the masked-exit-0 OR-clause reopens the chain even though the
  first attempt already succeeded - exactly the mechanism goal 7 names.
- `healed-command` rewrites the `./ready_for_next.sh` token INSIDE the
  grep's own search pattern (the token regex is text-level, not
  shell/quote-aware) to `./swarmforge/scripts/ready_for_next.sh`, and the
  healed grep re-runs against the same `t.log`.

**Where this run diverges from the mint-time narration**: the mint-time
report said the healed re-run "printed the line with the token ALREADY
REPOINTED... and exit 0." In this reproduction the healed grep searches
`t.log` for the REWRITTEN pattern, which is not present in `t.log` (only
the original, unrewritten line is), so the healed attempt finds no match:
exit 1, empty output - not exit 0 with the rewritten line printed.

**Disposition**: the underlying defect stands - a data token embedded in a
command (here, a grep search pattern) gets silently rewritten by a
text-level regex that cannot distinguish "this `./x.sh` is being invoked"
from "this `./x.sh` is being searched for" - and the healed re-run's
result genuinely diverges from what the operator's original command would
have reported (in this exact reproduction, from "found, line N" to "no
match", a different but equally wrong outcome from silently swapping the
grep target). BL-1561's premise stands; this note records that the
*exact* symptom (exit code / printed vs. empty output) is input-shape
dependent, not the fixed exit-0-with-repointed-text the mint-time report
described. No note to the specifier is needed - BL-1561 already owns
fixing "a data token is never rewritten" regardless of which concrete
symptom a given input produces.
