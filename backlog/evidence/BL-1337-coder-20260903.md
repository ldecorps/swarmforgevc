# BL-1337 — coder pass (2026-09-03)

Human ruling followed exactly: **cast plus ModelFactory overlay only, reusing
the apply path BL-1181 already ships.** No second generator, no second door,
no pack-conf renderer.

## What changed

- `swarmforge/scripts/bob_starting_cast_lib.bb` (extended, not forked):
  - `parse-profile` — a steward-owned JSON profile (name, roles, quality
    floor, provider allow list, handshake bar). It REFUSES a profile with no
    name, no roles, or an unrecognised bar rather than defaulting; quietly
    weakening the bar is the failure this ticket exists to prevent.
  - `handshake-role` — walks the role's ranked recommendations in order and
    returns the first candidate that passes the provider allow list, the
    quality floor, registry eligibility AND (unless the profile says
    `registry-only`) host reachability. Every rejected candidate keeps the
    reason it lost, so the note can say why a seat took its second choice.
    Deliberately asks for `include-uncertified?` candidates so an uncertified
    top pick is SEEN and recorded as `not-assignment-eligible` rather than
    silently never ranked.
  - `generate-cast-from-profile` — the cast, plus `runnable?` and the named
    `unstaffable` seats. A seat nothing can staff produces NO cast entry.
  - `generation-failure-text` / `evidence-note-text` — loud by seat name, and
    the note records the bar that was applied (with `registry-only` marked as
    the WEAKER bar in words, per the ticket).
  - `apply-via-modelfactory-overlay` — **the required_wiring anchor, now
    gated**: given a generation result it REFUSES a cast that is not runnable.
    BL-1181's own single-argument call site is unchanged and still works.
- `swarmforge/scripts/bob_starting_cast_cli.bb`: `export`/`apply` take
  `--profile <name>`, reading `.swarmforge/model-steward/profiles/<name>.json`.
  Host reachability is answered HERE, not in the lib: the lib takes an
  injected predicate, and the adapter only asks whether a provider's
  credential is PRESENT and non-blank — the value is never read into a cast, a
  note or a message. A provider the map does not know is not assumed
  reachable (fail closed).

## qa_e2e_procedure walked

Fixture steward store seeded exactly as the procedure describes: `coder`'s top
pick eligible and reachable; `cleaner`'s top pick registered but NOT certified;
`architect`'s top pick certified but unreachable on this host; `QA` with
nothing above the floor.

- The profile drives selection, and seats two and three fall through to the
  next model that handshakes (`cleaner` → `cerebras/qwen3.8-max`, `architect`
  → `anthropic/claude-opus-5`).
- The evidence note records each seat's handshake result, including the
  rejected candidate and its reason (`-> not-assignment-eligible`,
  `-> unreachable`).
- A fourth seat with nothing above the floor fails the whole cast loudly,
  names `QA`, emits no entry for it, and exits non-zero.
- The live pack conf is byte-unchanged across generation (propose, never
  install).
- Every file the run wrote, plus both verbs' stdout and notes, swept for
  credential material — including the fixture's own deliberately fake key
  value, so a leak would be visible as that exact string.

The fixture scrubs `MISTRAL_API_KEY`/`OPENROUTER_API_KEY` and friends from the
child environment: a real key on a developer's host would otherwise make the
"unreachable" seat reachable and turn the negative scenarios green for the
wrong reason.

## Note for the reviewer

`qwen` is a provider in the steward registry's namespace but NOT a launch
agent this repo resolves (`require-launch-agent!` knows anthropic, cerebras,
cursor, local, mistral, openai). The fixtures therefore stage the Token Plan
model under `cerebras`. That is a fixture choice, not a claim about the live
pack — and it is worth someone deciding whether the launch-agent map should
learn `qwen`, since a profile naming it would fail at cast time rather than at
handshake time. Recorded here rather than widened silently.
