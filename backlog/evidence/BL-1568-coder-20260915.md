## Known acceptance gap — flagged to the specifier, not worked around

The file still does NOT print `ALL PASS`. Case 04 (the idempotency guard)
fails independently, for a reason unrelated to `:status` and predating
this ticket - masked until now because case 01 always failed first and
exited the script before case 04 ever ran.

Root cause: case 02 constructs its draft via
`chase-sweep-lib/dispatch-gap-draft-lines` called with **no commit**
(1-arg form), which falls back to the "legacy soft-note" path - per that
function's own docstring, production `auto-route!` always supplies a
commit and gets a `git_handoff` instead (confirmed in `handoffd.bb`'s
`auto-route!`, which always calls the 2-arg form with `head-commit-10`).
The resulting note's message ("BL-217 is active with no dispatch on
record...") does not match `spec-work-ticket-id-pattern`, so
`dispatch-trail-ticket-id` (BL-1223's narrowed message-only predicate)
returns `nil` for it - it is never counted as a dispatch trail. Case 04's
second `dispatch-gap-items` call therefore still sees the gap, and
`(empty? gaps)` fails.

Confirmed by direct repro:
```
(dispatch-trail-ticket-id {:task nil :message (dispatch-gap-note-message "BL-217")})
=> nil
```

`chase_sweep_lib.bb` (forbidden by scenario 02 / the ticket's "Not in
scope" section) or changes case 02's draft construction to supply a
commit (which would then hit the `git_handoff` two-call self-audit,
BL-1529, and break case 02/03's own exit-0/queued-note assertions - the
ticket says cases 02 and 03 are unchanged). Sent a `note` (priority `00`)
