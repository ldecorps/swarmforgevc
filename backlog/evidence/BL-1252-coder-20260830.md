# BL-1252 — coder pass, 2026-08-30

The pre-commit guard chain aborts at the first refusing guard.

## 1. What changed

`swarmforge/git-hooks/pre-commit` no longer runs four guards as four
sequential commands under `set -euo pipefail`. It resolves `REPO_ROOT` and
`exec`s the new `swarmforge/scripts/run_commit_guards.sh`, which:

- runs the three index-inspection guards under `set -uo pipefail` with NO
  `-e`, one `guard || st=$?` per call, so a refusal never stops the guards
  after it;
- emits ONE refusal naming every guard that reported a violation;
- exits the combined status;
- reaches `check_property_suite_drift.sh` only when those three pass, so an
  already-refused commit never pays for `npm run test:properties`.

Same shape as the sibling `commit-msg` hook (BL-1242, `61735035f`), which
the ticket names as the proven precedent. Guard order is the hook's original
order, unchanged: a committer with exactly one violation sees the same one
they see today.

Nothing about what a guard DECIDES was touched. No predicate, threshold,
exemption or escape hatch in any of the four guard scripts was edited.

`SWARMFORGE_COMMIT_GUARD_DIR` is a seam naming where the guard scripts live
— used by the shell test and the acceptance fixture. It never changes what a
guard decides, and it is not a `*_FORCE_RESULT` bypass.

## 2. required_wiring

- `swarmforge/git-hooks/pre-commit::run_commit_guards.sh` — the hook's only
  remaining command is `exec "$REPO_ROOT/swarmforge/scripts/run_commit_guards.sh"
  "$REPO_ROOT"`. Case 10 of the shell test asserts BOTH halves: that the hook
  names the runner, AND that it no longer calls any of the four guards
  directly. A runner shipped but uncalled (the BL-419 shape) fails that case.
- `specs/pipeline/steps/index.js::bl1252CommitGuardCompleteInventorySteps` —
  registered; the acceptance run below would not resolve a step without it.

## 4. Declared invariants (BL-654) — all three executable

`extension/test/bl1252CommitGuardAggregationInvariants.property.test.js`,
`npm run test:properties` lane. 5 properties, all pass.

Generator reach was a real failure, not a formality: the first version drew
each guard's state uniformly from `{0, 1, 2, 127, missing}`, which makes an
all-passing plan 1-in-625 — `assertReach` caught it and failed with
`clean: 0` and `suiteOnly: 0` over 80 runs, meaning the tiering assertions
were never exercised. Fixed by weighting `0` heavily AND mixing the two
corner plans in as named constants, so the clean and suite-only states are
reached by construction rather than by luck. The floor is asserted every run.

The refusal-predicate property (invariant 2) does not assume the predicate
is unchanged — it models the pre-BL-1252 `set -e` chain independently in
`legacyChainRefuses` and asserts the runner's refusal set matches it.

Non-vacuity, three deliberate breaks, each run and restored:

| deliberate break | properties that FAIL |
|---|---|
| `set -euo pipefail` + bare guard calls (the defect) | inv 1 both, inv 3 (3 of 5) |
| non-refusal exits treated as a pass (`-eq 1` instead of `-ne 0`) | inv 1 naming, inv 2 both, inv 3 (4 of 5) |
| tiering removed — suite guard always runs | inv 2 tiering (1 of 5) |
| none (fixed tree) | 0 of 5 |

## 5. Acceptance (BL-112)

`specs/pipeline/scripts/run_acceptance.sh
specs/features/BL-1252-commit-guard-chain-reports-every-violation.feature`
— 9 scenarios, 9 pass, 0 fail.

Each scenario makes a REAL `git commit` in a throwaway repo whose
`core.hooksPath` is the REAL `swarmforge/git-hooks`, with the real runner
copied to the real relative path beneath the fixture root. Only the four
guard scripts are stubbed, through the seam: what a guard decides is
explicitly out of this ticket's scope and is pinned by that guard's own
tests, while the chaining is what this feature is about. The `<violations>`
column resolves through an explicit `KNOWN_GUARDS` lookup, and scenario 01
asserts each named guard actually RAN, not merely that it was mentioned — a
violation named but never reached would be the same defect with a better
message.

The fixture also no-ops the three `commit-msg` guards, which share the hooks
directory and are explicitly out of scope; without that, an unrelated gate
decides this feature's outcome.
