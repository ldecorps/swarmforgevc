# BL-1382 — coder evidence, 2026-09-04

Ticket: a crontab line the swarm did not write is never the swarm's to remove.
Human ruling, recorded 2026-09-04 (SUP-17, 14:13:07Z): **option 1, marker-only
ownership everywhere.**

## What shipped

**One ownership rule, in terms of the markers the swarm itself writes.** Both
readers dropped the three path clauses that caused the loss:

- `swarmforge_cron_lib.sh::swarmforge_cron_line_belongs_to_root` and
  `reconcile_shift_schedule_crontab.bb::strip-schedule-lines` no longer claim a
  line for containing `<root>/.swarmforge/operator/`, `<root>/start-swarm.sh`
  or `<root>/stop-swarm.sh`. What remains is the freshness marker, the
  operator-schedule marker, the shift-schedule begin/end markers, and
  `FRESHNESS_ROOT=<root> ` — the freshness line's own signature, which the
  swarm writes itself.
- The BL-1162 intent was to sweep the **legacy presets**, which are themselves
  hand-installed files naming operator scripts by path and carrying no marker.
  To the old predicate "the human installed it" and "a legacy preset installed
  it" were the same line. That is the defect, and it is gone.

**Unmarked lines are surfaced, never swept.** New
`swarmforge_cron_line_names_root` and `swarmforge_cron_report_unmarked` print
`left in place (no swarmforge marker for this root): <line>`; the **uninstall**
reports before its early exit (the "no swarmforge lines for R" case is exactly
where a human's line naming R is most likely present), and the **install**
reports too, because it writes `stripped + rendered` and so is a cron writer
owing the same account.

## A second defect, found by the property test's constructed generator

Invariant 1's sibling property failed on its first run: the shift-schedule
begin/end clauses matched a bare substring, so root `/fixture/aaa` claimed
`/fixture/aaa-sibling`'s block. The generator derives the sibling **from** the
root, so the two always share a prefix — a sibling drawn independently would
almost never have found this. Multi-root isolation (BL-783/BL-1162) is what it
breaks, so it is fixed in both readers: the root must end the marker or be
followed by whitespace. The other markers were already bounded, by the `]` on
the two `root=[…]` forms and by the trailing space on `FRESHNESS_ROOT`.

**No test anywhere here touches the live user crontab.** Both suites put a
`crontab` shim on PATH that reads and writes a fixture file, and the e2e's last
check asserts that the shim — not the real binary — is what `command -v
crontab` resolved to, so a suite that lost its shim fails rather than editing
the human's schedule. `qa_e2e` item 6 (a live read-only `crontab -l` around a
`./swarm` start) is deliberately **not** run here: it belongs to QA on the live
host, and its own text warns against the stop path.

Item 5 is run rather than argued: the agreement suite copies the reconcile
script, gives the copy back one of the removed path clauses, and requires the
two readers to **disagree** — a marker list edited in one reader and not the
other makes the suite fail. The copy sits beside the original (the script
load-files its siblings relative to its own path) and is removed in the trap,
named with the run's pid so concurrent runs never share one.

## Declared invariants (BL-654) — both encoded

`extension/test/bl1382CronOwnershipMarkerOnly.property.test.js` drives the
**real** readers as subprocesses. A JavaScript reimplementation of the
predicate would be a third reader with exactly the drift problem this ticket
exists to end.

Reach is constructed: every generated line is built from a root and a shape —
a marker the swarm writes, or a path under the root carrying none — so each
case is a genuine owned/unowned decision rather than a random string that
happens to miss every marker. Both classes are asserted reached, the sibling
root is derived from the root, and invariant 2 asserts its corpus reached
**both** verdicts, because two readers agreeing that nothing is owned would be
agreement about nothing.
