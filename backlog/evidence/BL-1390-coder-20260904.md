# BL-1390 — CODER PASS, 2026-09-04

Push while it is still cheap: a commit on the shared `main` checkout goes to
origin at once, and only while a fast-forward is possible, so local main sits
at ahead zero and a QA landing arrives as pure lag.

## What was built

- `swarmforge/scripts/push_sweep_lib.bb`
  - `post-commit-decision` — the pure decision over `{branch linked-worktree?
    ahead behind}`. `:not-shared-checkout` is decided FIRST and needs no
    counts, so a role-branch commit costs no fetch at all. The ahead/behind
    question is NOT restated: it delegates to the existing `push-decision`, so
    the hook and the sweep cannot disagree (invariant 3). Unknown counts fail
    CLOSED.
  - `push-main!` — the ONE `git push origin main`, never `--force`, now shared
    by the daemon and the hook. `handoffd.bb`'s `push-sweep-push!` delegates to
    it rather than shelling its own (invariant 3, BL-1198).
- `swarmforge/git-hooks/post-commit` — a thin wrapper: bounded `timeout`,
  exits 0 unconditionally, names `push_sweep_lib.bb` as the adapter it must go
  through and shells no push of its own.
- `swarmforge/scripts/post_commit_push.bb` — gathers the four facts and does
  what the decision says.

## Three defects this parcel's own tests caught before anything ran for real

These are worth reading: each was working code by inspection and wrong in fact.

1. **The hook asked git about the wrong repository.** `core.hooksPath` is
   SHARED by every worktree, so the hook file always sits in the master
   checkout. Resolving the repo from the hook's own location judged a
   role-worktree commit as if it were a commit on main. The hook now passes
   `git rev-parse --show-toplevel` — the repository git ran it IN.
2. **A failed fetch still pushed.** The counts were read whether or not the
   fetch succeeded, and stale counts say "ahead, not behind" in exactly the
   case where origin has moved and we could not see it. Now a failed fetch
   pushes nothing (invariant 1 says the counts follow a FRESH fetch).
3. **The fetch did not refresh the ref the counts are read from.** `git fetch
   origin main` updates FETCH_HEAD and only opportunistically `origin/main`;
   the counts read `origin/main`. Scenario 02 caught it pushing over another
   checkout's tip. The refspec is now explicit:
   `+refs/heads/main:refs/remotes/origin/main`.

## One incident this parcel caused and repaired, reported not buried

While this test was being written, a broken fixture setup left `$root` empty
and the harness ran `git -C "" add -A` followed by a commit. **`git -C ""` does
not fail — it operates on the current directory**, so a commit meant for a
throwaway fixture landed on this worktree's own branch as
`b52bbab7d0 "BL-9390: fixture commit a.txt"`, sweeping in four untracked files
belonging to nobody's parcel. That is the BL-506 violation, committed by a test.

Repaired in full before this parcel was committed: the stray commit was
un-committed (`git reset --soft`, it was never pushed and no branch but this
one contained it), the four foreign files were unstaged back to untracked and
left exactly as found, and the `coder-fixture` branch and leaked worktree
registration the same run created were removed (`git worktree prune`,
`git branch -D`). `git worktree list` shows no fixture entry and the branch tip
is the merge it was before.

The test now cannot do it again: every git call goes through a guard that
refuses any directory not under the fixture root, the worktree scenario names
its branch for this fixture and removes the registration itself, and the setup
asserts its own success rather than failing silently.
