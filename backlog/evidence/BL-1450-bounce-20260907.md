## Root cause

The coder's own comment at lines 231-237 explains the timeout choice:
"Measured 44-50s alone on this host across eight runs under the live
swarm's own concurrent load (6 spawns, was 96), one transient spike to
110s under a heavier moment — 120s keeps margin over both." Every one of
those measurements is a SOLO run (the file run alone, per qa_e2e step 1,
which I independently reproduced three times at 50-55s each). The full
`test:properties` LANE runs this file as ONE OF 375 CONCURRENTLY POOLED
files, competing for the same worker slots — a materially different
timing regime than solo execution, and not represented anywhere in the
120000ms choice's own measurement basis.

## Why this is not the deeper defect BL-1450 exists to fix — scoped narrowly

The ticket's real target (BL-676's refusal) is `check_property_suite_drift.sh`'s
RERUN-ALONE step under its 180s ceiling — the mechanism that actually
gates a commit. I independently verified that mechanism is sound and
unaffected: bl968 passes reliably ALONE (three runs, 50-55s; hardener's
own evidence: three runs, one 67s outlier) — comfortably under both its
own 120s internal timeout and the guard's 180s rerun ceiling in the
UNCONTENDED case a rerun-alone actually is. `test_property_suite_drift_guard.sh`
(verified ALL PASS 25/25 earlier this session, unrelated ticket) already
covers exactly this "red in the pool, green alone → treated as a flake,
commit allowed" path generically, for any file. So this bounce is
**not** the BL-676 problem recurring — the commit-time protection is
intact.

What IS a real defect against this ticket's own stated acceptance: the
raw, unscoped `npm run test:properties` invocation qa_e2e step 3 names
literally still shows bl968 among the timed-out files, twice in a row, on
this host, at the commit under review. Everything else in this ticket's
own checklist is clean (per-file budget, no-deletion/no-weakening,
acceptance 5/5, BL-968/BL-1062 sibling features unaffected, standing-reds
row correctly retired, mutation manifest, wiring) — this is the one item.

## Suggested remediation (direction, not mandate)

Raise the internal `testTimeout` margin to comfortably cover pooled-run
contention as well as solo-run variance — e.g. something in the 180-250s
range (still well under the ORIGINAL 300s, and the 180s figure is not a
hard ceiling for THIS value specifically, only for the guard's separate
rerun-alone check, which this file already clears with room to spare).
Re-measure under a live full-lane run (not solo) before re-forwarding,
since that is the condition that actually broke here.
