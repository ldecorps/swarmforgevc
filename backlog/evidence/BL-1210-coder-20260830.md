## 2. Root cause confirmed, not assumed (step 2)

`git show 35daa5054^:extension/src/concierge/blTopicStore.ts` shows
`recordSwarmIconId` writing unconditionally — `readRecord`, set
`swarmIconId`, `atomicWrite`, commit — with no classification step. The
current file (pre-fix) branches on `classifyTopicThread`: `'supervisor'`
to its own untracked store, anything else `maybeReportUnbound` and
`return`, having written nothing. The claimed regression is the real one.

## 3. What changed

- `topicThreadKind.ts` — the supervisor store's read/write pair is
  generalised into `readIconMap`/`recordIconInMap`, parameterised by
  filename. Supervisor keeps `.swarmforge/supervisor-topic-icons.json`
  (unchanged, so BL-695's migration code that names it still works); epic,
  standing and role ids share a new `.swarmforge/topic-icons.json`. Both
  untracked. `isStorableTopicId` names the one shape no store can key by
  (a blank id). `reportMarkerRefusedToStderr` is a NEW reporter for the
  refusal; `reportUnboundThreadToStderr` keeps its BL-695 wording and its
  `appendMessage` caller untouched.
- `blTopicStore.ts` — `readSwarmIconId` routes `'unbound'` to the new
  store. `recordSwarmIconId` now returns `IconMarkerWriteOutcome`
  (`'recorded' | 'refused'`) on every path.
- `topicIconSync.ts` — the adapter's `recordSwarmIconId` returns that
  outcome, and `syncTopicIcon` returns the new
  `'icon-set-marker-unrecorded'` when it is anything but `'recorded'`.
  Not a throw (constraint 5): the live tick's icon sync stays best-effort.

Nothing in `classifyTopicThread` moved. `TICKET_ID` is unwidened, no new
kind returns `'ticket'`, no call site's `isNewTopic` argument changed, no
icon value or pool changed, and none of the five original assertions were
relaxed or deleted.
