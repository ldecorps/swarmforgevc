# BL-1408 — coder pass

Commit: this parcel · 2026-09-07 · worktree `swarmforge-coder`

## The fix

Four hand-written copies of the commit-guard chain list, all now read
through BL-1398's helper (`extension/test/helpers/commitGuardFixtureSet.js`)
at run time instead of being enumerated in the test:

1. **`swarmforge/scripts/test/test_run_commit_guards.sh`** (standing red,
   register row since 2026-09-04) — `ALL_GUARDS=` (5 hand-named guards, the
   runner names 10 today) replaced with `DERIVED_GUARDS="$(derive_guards
   swarmforge/scripts/run_commit_guards.sh)"`, a `node -e` call into
   `deriveCommitGuardFixtureSet({ repoRoot, runnerRel, hookRels: [] })`.
   `hookRels: []` scopes the derivation to the runner alone — the default
   (both hooks) would have pulled `check_art_director_tip.sh` (a
   pre-merge-commit-only guard, BL-1444) into this fixture, which the real
   runner never runs; caught by case 01 failing "never ran
   check_art_director_tip.sh" during development, fixed by the explicit
   `hookRels: []`. Case 01 now asserts every derived guard ran (was: the
   property guard alone); case 04's cheap-tier list is `DERIVED_GUARDS`
   minus `check_property_suite_drift.sh` computed by a loop, not a
   hardcoded 4-guard string; case 10's wiring regex is the guard-name-class
   `check_[a-z_]+\.sh`, naming nothing by hand. Added an optional `$1` seam
   argument (a scratch runner copy's path) for scenario 02.
   Variable renamed `ALL_GUARDS` → `DERIVED_GUARDS` so the qa_e2e grep for
   the literal hand-list name (step 4) returns 0 even though the RHS is now
   a derivation, not a literal.

2. **`swarmforge/scripts/test/test_pre_merge_commit_hook.sh`** —
   `MERGE_GUARDS="check_pipeline_code_on_main.sh
   check_feature_handler_registration.sh check_art_director_tip.sh"` (a
   sixth hand edit, per the ticket's own "Since mint") replaced with
   `DERIVED_MERGE_GUARDS="$(derive_merge_guards "$HOOK")"`, which calls
   `parseRunGuardEntries` directly over the real hook's text (no
   filesystem-existence walk needed here, per the ticket's own "How": the
   hook's own entries are the whole answer). Case 01 asserts every derived
   guard ran. Added an optional `$1` seam argument (a scratch hook copy's
   path) for scenario 03.

3. **`extension/test/helpers/bl1252CommitGuardFixture.js`** — the
   `required_wiring` anchor names
   `extension/test/bl1252CommitGuardAggregationInvariants.property.test.js`,
   which BL-1349 (landed 2026-09-06, after this ticket's mint) split into
   five independent files sharing this one fixture helper; the anchor is
   stale, this is where `INDEX_GUARDS`/`SUITE_GUARD` actually live today.
   `INDEX_GUARDS` (the sixth hand-enumerated copy, edited for BL-1385,
   BL-1395, BL-1428, BL-1440) is now `ALL_GUARDS.filter(g => g !==
   SUITE_GUARD)`, where `ALL_GUARDS = deriveCommitGuardFixtureSet({
   repoRoot, hookRels: [] }).guards` (scoped to the runner alone, same
   reasoning as file 1). `SUITE_GUARD` stays the one named constant per the
   ticket's "How", with a module-load-time `assert.ok(ALL_GUARDS.includes(
   SUITE_GUARD))` — invariant 3, that the one hand-named guard cannot drift
   from the derived set.

4. **`swarmforge/scripts/test/test_pipeline_code_on_main_guard.sh`**
   (standing red, register row since 2026-09-04, the "fourth copy" the
   ticket's "Since mint" section documents) — the eleven hand-written `cp`
   lines replaced with a loop over
   `deriveCommitGuardFixtureSet({ repoRoot: LIVE_REPO_ROOT }).files`
   (default `hookRels`, i.e. BOTH hooks — this fixture installs both
   `pre-commit` and `pre-merge-commit`, so it needs the union of both
   chains' guards, the runner itself, both hook files, and every lib either
   chain sources; verified by reading `deriveCommitGuardFixtureSet`'s own
   implementation that the default already unions both). `is_qa_ancestor.sh`
   stays a hand copy — it is invoked as a subprocess by
   `check_pipeline_code_on_main.sh`, never `run_guard`'d or `source`'d, so
   it is outside the "chain list" class this ticket is about (a single
   fixed dependency, not a list that grows). The separate `cp` calls for
   `PRE_COMMIT_HOOK`/`PRE_MERGE_COMMIT_HOOK` were removed as redundant —
   the derived `.files` set already includes both hook files via
   `hookRels`.

5. **`specs/pipeline/steps/bl1408CommitGuardTestsDeriveTheirSetSteps.js`**
   (new, `required_wiring` anchor) — drives the four scenarios by running
   the REAL shell test files (files 1, 2, 4 above) against either the live
   chain (scenarios 01/04) or a scratch seam this handler builds itself
   (scenarios 02/03): a modified copy of the real runner/hook with one
   extra `run_guard <name>` line spliced in just before the tier-1
   early-exit check (an append at EOF lands after the runner's own
   unconditional final `exit` and is unreachable dead code — confirmed by
   hand during development), plus placeholder guard files for the runner
   seam (needed because `deriveCommitGuardFixtureSet`'s existence check
   runs there; not needed for the merge-hook seam, which derives via the
   existence-check-free `parseRunGuardEntries` alone). Nothing greps a
   label — every assertion reads the real shell test's stdout/exit status.
