## Two bugs found and fixed while building the acceptance fixture

Both are real, independent of this ticket's own feature — a real swarm
running `route_backlog_to_coder.sh` under a mailbox-only pack (no live
tmux pane, a documented mode — `swarmforge.sh` itself prints "Mailbox-only
mode: handoffd delivers files without tmux wake") would hit them today,
with or without BL-1846.

1. `route_backlog_to_coder.sh` defaults `SWARMFORGE_SKIP_DAEMON=1` (a
   human/script caller has no daemon of its own to rely on). Combined with
   a mailbox-only pack, `swarm_handoff.bb`'s own sync-delivery path cannot
   complete immediately and, under that default, treats the resulting
   outbox-queued file as a hard failure — `promote_and_route_next.sh`
   exits non-zero even though the promotion already committed. Fixed at
   this ticket's own new call site: `deterministic-promote-and-route!`
   explicitly sets `SWARMFORGE_SKIP_DAEMON=0` in the subprocess env, since
   the caller here — handoffd itself — genuinely is a live daemon that
   will pick the queued file up on its own next `poll-once!` cycle.
2. Even with (1) fixed, `route_backlog_to_coder.sh`'s own post-send check
   (`compgen -G "${INBOX}"/*_for_${ROLE}.handoff`) still refuses when
   delivery is deferred rather than instant — a real behavior gap in that
   script under mailbox-only mode, out of this ticket's own scope
   (`route_backlog_to_coder.sh` is not named anywhere in BL-1846's "How").
   Worked around, not silently trusted: `deterministic-promote-and-route!`
   never trusts the script's own exit code alone. `paused-ticket-still-
   present?` re-reads `backlog/paused/` after the attempt — ground truth,
   independent of any downstream step's own wording — to decide promoted
   vs refused. Flagged to the specifier by note (see below); not fixed in
   `route_backlog_to_coder.sh` itself, which is outside this ticket's
   "How".

## Invariant check (BL-654)

Two invariants declared on this ticket:

1. *"handoffd holds no ranking of its own: every ticket it promotes is
   chosen and gated by promote_and_route_next.sh, and it never moves a
   ticket file from paused to active itself."* — **no executable property
   encoding**, stated reason: this quantifies over the SHAPE of
   `handoffd.bb`'s own implementation (delegating the whole promote/route
   decision to a real subprocess, never a parallel git-mv of its own)
   rather than over a pure, generator-drawable input space. It is proven
   by (a) inspection — `deterministic-promote-and-route!` has exactly one
   write path into `backlog/`, the subprocess call to
   `promote_and_route_next.sh <project-root>` with no ticket id; there is
   no second, handoffd-authored rename anywhere in that function — and (b)
   the acceptance feature's own four real end-to-end scenarios (a refused
   candidate never moves; a promoted one moves exactly as the script
   decided). A property-test encoding would need to stub the real
   subprocess to observe a negative ("nothing moves without it"), which
   for this architecture-level claim reads as manufacturing a test around
   the absence of code rather than encoding a computable property.
2. *"A pack whose conf does not declare coordinator_mode deterministic
   behaves exactly as today..."* — encoded in
   `extension/test/bl1846CoordinatorModeInvariants.property.test.js`: a
   generator builds six distinct near-miss shapes (wrong case at a random
   letter position, suffix noise appended to the literal, a different real
   mode word, a blank value, an absent key, and a differently-spelled key)
   BY CONSTRUCTION from the one literal that flips the gate true, and
   asserts `deterministic-coordinator?` reads false for every one, with a
   reach-floor per shape (90 runs across 6 equally-likely kinds, driven up
   from an initial 24 after a real reach-floor flake surfaced running the
   full `npm run test:properties` lane rather than this file alone).
   Non-vacuity, production code: loosening the comparison from `=` to
   `str/includes?` failed on the very first generated near-miss
   (`"deterministic-ish"` read true); restored to `=`. Non-vacuity, this
   test's own generator: the full lane run also caught two authoring bugs
   in the generator itself, both false positives against the CORRECT
   implementation — an empty suffix-noise draw and 'deterministic' left in
   the other-real-mode value pool each accidentally built the exact
   literal while still asserted false. Both fixed, plus a standing per-run
   guard against a third instance of the same shape. The full end-to-end half of this invariant (handoffd actually promotes
   nothing on such a pack) is covered by the acceptance feature's own
   scenario 02, not re-encoded here.
