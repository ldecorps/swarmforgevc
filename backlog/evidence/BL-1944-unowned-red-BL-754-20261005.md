# Unowned red: BL-754's own feature, found while building BL-1944 (2026-10-05)

While binding BL-1944's four features, reused the fixture shape
`specs/pipeline/steps/bl754StageSkipReasonsSteps.js` already established
for driving `swarmforge/scripts/swarm_handoff.bb` (same pair of scripts
BL-661 needed). Ran BL-754's own feature as a sanity check and found it
is currently red on main:

```
node specs/pipeline/cli.js specs/features/BL-754-stage-skip-reasons-never-silently-loses-a-stage.feature
```

3 of 5 pass; 2 fail:

- Scenario "an unquoted reason containing a comma is reported instead of
  silently losing a stage" - fails at step "And the routing-skip record
  carries that report".
- Scenario "a malformed declaration never blocks the handoff it
  describes" - fails at step "Then the parcel is delivered to its
  recipient".

Both fail for the same reason: `bl754StageSkipReasonsSteps.js`'s own
`sendHandoff` helper calls `bb swarm_handoff.bb draft.txt` exactly ONCE.
Since some point after this handler was written, `swarm_handoff.bb`
gained the Article 2.3 self-audit protocol: the first invocation for a
given draft fingerprint always prints `AUDIT_REQUIRED` /
`HANDOFF_NOT_QUEUED` and queues nothing; an identical SECOND invocation
is required to actually submit. A single-call fixture now always gets
the challenge, never the delivery, so `send.status` is 1, not 0, for
every scenario whose assertion expects a successful send.

Not this ticket's fix: BL-754 is a different, already-closed ticket, not
one of the four BL-1944 names (`required_wiring` only covers BL-111,
BL-112, BL-544, BL-661). No standing-reds.tsv row names BL-754, so this
is unowned. Confirmed the fix shape works (my own BL-661 handler's
scenario 05 drives the same `sendHandoff` pattern, calling twice, and
passes) - the remedy for `bl754StageSkipReasonsSteps.js` is almost
certainly the same: call the send twice, asserting the challenge on the
first call and the real result on the second, the way BL-661's handler
now does.
