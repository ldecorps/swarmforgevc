# BL-1385 — CODER PASS, 2026-09-04

## What the guard is

`swarmforge/scripts/check_handler_module_graph.sh <dir|tree-ish|—>` proves
every discoverable `specs/pipeline/steps/*Steps.js` ON A GIVEN TREE has a
module graph that resolves on that same tree.

Three call shapes, because the two consumers differ and neither should have to
adapt to the other: a materialised tree ROOT directory (plus the `--assume-main`
the land passes), an explicit tree-ish, or no argument at all — in which case
the tree under test is the STAGED tree (`git write-tree`), which is exactly
what a hand-land is about to carry.

## The design decision, and why the obvious one was wrong

The ticket offered static resolution or materialise-and-require. I surveyed the
require forms first:

    require('S')                                    3767
    require(path.join(EXT_DIR, 'S','S','S'))         302
    require(path.join(EXT_OUT, 'S','S'))             180
    ... and six more constants (EXT, REPO_ROOT, OUT, EXTENSION_DIR,
        EXTENSION_OUT, EXT_TEST) plus __dirname forms

A static resolver would need to evaluate nine different computed constants and
would false-positive across 947 files. So node evaluates them: the tree is
materialised with `git archive` into a mkdtemp root and each handler is
required in a child process rooted THERE, with `Module._resolveFilename`
hooked.

**No `tsc`.** `extension/out/` is gitignored, so a materialised tree never has
it, and compiling would make a commit guard cost a full TypeScript build.
Instead resolution of `extension/out/<p>.js` is answered by asking whether
`extension/src/<p>.ts` exists ON THE TREE — which is precisely the question
that separates "will exist once built here" from "this module's source is on
somebody else's branch", and is the exact class of the incident.

## Invariant 2 is structural, not a discipline — and proved BOTH ways on real data

The verdict cannot consult the checking worktree because the child is rooted in
the archive and the out/→src/ mapping reads that root.

- **Present in checker, absent on tree → REFUSES.** `extension/src/tools/bubbleSeat.ts`
  IS in my worktree today (BL-1296 landed), and `git ls-tree a93aa4a18f` shows
  it absent there. The guard still refused that tree. This is the exact failure
  of QA's hand-check on 2026-09-04, which was answered by the wrong tree.
- **Present on tree, absent in checker → PASSES.** A module built only into a
  scratch tree, with no such file anywhere in my worktree, passes.

## It catches the real incident

    $ check_handler_module_graph.sh a93aa4a18f .
    HANDLER_LOAD_BLOCK
    handler-load-failed: bl1296BubbleSeatSteps.js - .../extension/out/tools/bubbleSeat (no extension/src source on this tree)
    handler-graph: 1 handler(s) on this tree cannot load; ...
    exit 1

and passes the repaired tree (947 handlers, exit 0).

## Two false-positive classes found and closed before wiring

The first run against a known-good tree refused it — which would have blocked
every commit in the repo. Both causes were mine and are worth recording:

1. **Relative requires bypassed the out/ check.** The incident's own handler
   reaches the module as `../../../extension/out/...`, not as an absolute path,
   so an absolute-only check saw nothing. Requests are now resolved to absolute
   against the parent's dir FIRST.
2. **`node_modules` is not tree content.** Handlers compute absolute paths into
   `<tree>/extension/node_modules/{jsdom,fast-check,js-yaml}`; node_modules is
   gitignored and never archived, so checking it false-positived. Dependencies
   are the manifest's business, not this guard's.

A third, subtler one: requiring a handler runs its top-level code, which broke
on the shape of my stand-in module. The stub is now callable, iterable,
constructible and self-returning, and a handler that resolves everything but
throws for its own reasons is NOT a finding here — that is BL-1371's registry's
question, and refusing on it would block unrelated behaviour.

## A 27s tax on every commit, found by running the guard I had just wired in

The first working version spawned one node process per handler. Measured on
this repo's 947 handlers: **27 seconds**, paid by every commit AND every land,
for a question that is almost always "yes". I only noticed because the guard
was already in `run_commit_guards.sh` and ran on my own commit - 11 node
processes visible mid-hook.

Collapsed to ONE process that walks every handler itself, clearing
`require.cache` between them and scoping the missing-module list per handler.
Per-handler isolation is preserved to the extent this guard's question needs:
it asks whether modules RESOLVE, not whether handlers can coexist. A handler
calling `process.exit` at load is intercepted, because otherwise it would end
the sweep and silently pass every handler after it.

**27s -> 2s**, with the incident still caught and acceptance still 9/9. Both
re-verified after the change rather than assumed from the first run.

## REWORK 2026-09-04 — invariant 3 and scenario 07, after the guard refused two valid commits

The cleaner reproduced two runs deleting each other's tree; the specifier added
invariant 3 and scenario 07 (cf2ea583c7). Both are right, and the defect was
mine.

**The mistake, precisely.** BL-971 asks that a killed run leave nothing behind
forever, and the sweep it prescribes — `rm -rf <prefix>.*` before the run — is
written for TEST FIXTURES, which never run concurrently. I applied it to a
production guard invoked from a commit hook, where invocations overlap
constantly. It deleted a live run's materialised tree; every file then read as
absent, and the guard "found" first ~20 and then 528 phantom missing modules,
refusing two valid commits. Applying a fixture rule to a concurrent guard was
the whole of it.

**A second cause, found only by fixing the first.** With the sweep tamed, a
concurrent pair still failed — but differently: `could not determine a tree to
examine`. `git write-tree` needs `.git/index.lock`, and this guard runs from a
commit hook where another git is very often mid-write. Transient contention,
never a property of the tree.

**Fixes, matching the invariant's own words** ("no run removes a directory it
did not create, and any reaping of leftovers is scoped to directories no live
run owns — a recorded owner pid that is dead, or an age bound"):

- Each run writes `.owner-pid` into its root immediately after `mkdtemp`, so a
  concurrent reaper can see the root is live before anything of value is in it.
- Reaping asks `kill -0` on the recorded owner: a live owner's root is never
  touched whatever its age; a dead owner's is removed at once. An age bound
  (60 min) remains the fallback for a root killed before its owner file was
  written.
- `git write-tree` gets a bounded retry, then reports the examination as not
  performed and exits 0 rather than refusing.
- A refusal must still prove the tree survived: if the sentinel that was
  definitely extracted is unreadable at the end, the run reports INCONCLUSIVE
  instead of trusting its findings.

**Verified, both directions of the invariant rather than one:**

- Six concurrent runs, three pairs: all exit 0.
- A sibling root owned by a LIVE pid survives a run.
- A sibling root owned by a DEAD pid is reaped.
- The a93aa4a18f incident is still caught, marker naming handler and module.
- Acceptance 10/10 on the amended feature, including scenario 07, which plants
  a live-owned probe root and asserts it survives — the invariant stated
  directly rather than inferred from two passes.

**What I got wrong before this, recorded because the reasoning matters more
than the fix:** I diagnosed the first false refusal as file-descriptor pressure
and wrote that into a commit message as established. It was a guess that fit
the symptoms. The ENOENT/could-not-tell distinction it produced is worth
keeping on its own merits, but it was not the cause, and I should have said
"unknown" until I had evidence.
