# BL-1385 — CODER PASS, 2026-09-04

## What the guard is

`swarmforge/scripts/check_handler_module_graph.sh <dir|tree-ish|—>` proves
every discoverable `specs/pipeline/steps/*Steps.js` ON A GIVEN TREE has a
module graph that resolves on that same tree.

Three call shapes, because the two consumers differ and neither should have to
adapt to the other: a materialised tree ROOT directory (plus the `--assume-main`
the land passes), an explicit tree-ish, or no argument at all — in which case
the tree under test is the STAGED tree (`git write-tree`), which is exactly
what a hand-land is about to carry.

## The design decision, and why the obvious one was wrong

The ticket offered static resolution or materialise-and-require. I surveyed the
require forms first:

    require('S')                                    3767
    require(path.join(EXT_DIR, 'S','S','S'))         302
    require(path.join(EXT_OUT, 'S','S'))             180
    ... and six more constants (EXT, REPO_ROOT, OUT, EXTENSION_DIR,
        EXTENSION_OUT, EXT_TEST) plus __dirname forms

A static resolver would need to evaluate nine different computed constants and
would false-positive across 947 files. So node evaluates them: the tree is
materialised with `git archive` into a mkdtemp root and each handler is
required in a child process rooted THERE, with `Module._resolveFilename`
hooked.

**No `tsc`.** `extension/out/` is gitignored, so a materialised tree never has
it, and compiling would make a commit guard cost a full TypeScript build.
Instead resolution of `extension/out/<p>.js` is answered by asking whether
`extension/src/<p>.ts` exists ON THE TREE — which is precisely the question
that separates "will exist once built here" from "this module's source is on
somebody else's branch", and is the exact class of the incident.

## Invariant 2 is structural, not a discipline — and proved BOTH ways on real data

The verdict cannot consult the checking worktree because the child is rooted in
the archive and the out/→src/ mapping reads that root.

- **Present in checker, absent on tree → REFUSES.** `extension/src/tools/bubbleSeat.ts`
  IS in my worktree today (BL-1296 landed), and `git ls-tree a93aa4a18f` shows
  it absent there. The guard still refused that tree. This is the exact failure
  of QA's hand-check on 2026-09-04, which was answered by the wrong tree.
- **Present on tree, absent in checker → PASSES.** A module built only into a
  scratch tree, with no such file anywhere in my worktree, passes.

## It catches the real incident

    $ check_handler_module_graph.sh a93aa4a18f .
    HANDLER_LOAD_BLOCK
    handler-load-failed: bl1296BubbleSeatSteps.js - .../extension/out/tools/bubbleSeat (no extension/src source on this tree)
    handler-graph: 1 handler(s) on this tree cannot load; ...
    exit 1

and passes the repaired tree (947 handlers, exit 0).

## Two false-positive classes found and closed before wiring

The first run against a known-good tree refused it — which would have blocked
every commit in the repo. Both causes were mine and are worth recording:

1. **Relative requires bypassed the out/ check.** The incident's own handler
   reaches the module as `../../../extension/out/...`, not as an absolute path,
   so an absolute-only check saw nothing. Requests are now resolved to absolute
   against the parent's dir FIRST.
2. **`node_modules` is not tree content.** Handlers compute absolute paths into
   `<tree>/extension/node_modules/{jsdom,fast-check,js-yaml}`; node_modules is
   gitignored and never archived, so checking it false-positived. Dependencies
   are the manifest's business, not this guard's.

A third, subtler one: requiring a handler runs its top-level code, which broke
on the shape of my stand-in module. The stub is now callable, iterable,
constructible and self-returning, and a handler that resolves everything but
throws for its own reasons is NOT a finding here — that is BL-1371's registry's
question, and refusing on it would block unrelated behaviour.

## Wiring — both consumers, per required_wiring

- `land_step_lib.bb`'s `replayed-tree-guards`, beside the registration check.
- `run_commit_guards.sh`, because a hand-land bypasses the land replay
  entirely — which is exactly how `a93aa4a18f` reached main.

Refusal exits **1**, not 3: `commit_guard_chain_lib.sh`'s `run_guard` reads any
other non-zero status as UNEXPECTED rather than as a refusal, which would
report the guard as broken instead of as having found something. Pinned by its
own acceptance assertion.
