# BL-1874 — coder pass, 2026-10-05

## What changed
- `emit-throttle-recommendation.ts`: `main` now wraps `refreshReworkSignal`
  in a try/catch. On a throw (a write failure under `.swarmforge/telemetry`,
  a full disk, a git failure, ...), it captures the error message, logs it
  to stderr (the depth CLI's own non-zero-exit reporting path no longer
  fires for this cause, since the CLI now always exits 0 on a successful
  publish), and still calls `emitThrottleRecommendation` — now threading a
  `reworkRefreshFailure` reason through to `computeThrottleRecommendation`.
  When set, `computeThrottleRecommendation` never reads the persisted
  signal (an earlier run's, since this run's own refresh never persisted
  a fresh one) — `recommendedCap`/`severity`/`reworkRate`/`baselineRate`
  all come out null, `standingRed` is computed exactly as on a successful
  run. The recommendation always carries a new `refreshFailureReason: string
  | null` field, naming the failure (null on an ordinary successful run).
  The file on disk and stdout are always THIS run's own output, never an
  earlier run's left standing.
- `bl1874ThrottleRefreshFailureSteps.js`: step handlers for the new feature,
  registered per BL-233/BL-1371 (own file, discovered automatically). The
  two steps shared with BL-432's own text ("the coordinator decides whether
  to promote the next item", "the effective active-depth cap is the
  configured value") are registered via `registry.defineScoped(...,
  FEATURE)` per BL-425, so BL-432's own unscoped steps are untouched. The
  refresh failure is forced with a real `fs.mkdirSync` failure (a FILE sits
  where the telemetry directory must be), never a chmod.
- Unit tests added to `emitThrottleRecommendationCli.test.js`:
  `computeThrottleRecommendation`/`emitThrottleRecommendation` ignore a
  persisted signal and carry the failure reason when passed one; `main()`
  still publishes and exits 0 when the refresh genuinely throws (same
  ENOTDIR/EEXIST seam as the feature), overwriting an earlier severe
  recommendation.
- New property test `emitThrottleRecommendationRefreshWrite.property.test.js`
  encodes the declared invariant ("the recommendation file on disk was
  written by that run, whether the refresh succeeded or failed") against
  the real compiled CLI as a subprocess, over randomly drawn combinations
  of an earlier recommendation (present/absent, cap 0 or 1) and whether
  this run's own refresh is made to fail. Non-vacuous: verified by
  temporarily reverting `main()` to the pre-fix bare
  `refreshReworkSignal(...)` call (no try/catch) — the property then failed
  on every draw where the telemetry write was blocked (counterexample
  `{hasEarlierRecommendation:false, earlierCap:0, refreshFails:true}`,
  `Fatal error: EEXIST...`, exit 1, nothing written). Restored and
  re-verified green before commit.
