# BL-1634 coder pass

## What was fixed

`specs/features/BL-829-bubble-remote-page-pager.feature`'s scenario
`bundle-pages-rejected-whole-02` demanded an EMPTY offered pages list on a
malformed operator manifest, where the scenario's own text only says no
page FROM the malformed manifest is offered. Since BL-1166 (2026-08-27)
the bridge always merges its built-in pages (health, host, operator-docs,
and now BL-775's `live`) in after the operator manifest resolves — so the
list was never empty and the assertion had been red for three weeks
(unseen because no lane runs landed features, BL-1625).

Two hunks, one file (`bl829BubbleRemotePagePagerSteps.js`), per the
ticket's own direction:

- The malformed-manifest fixture step now writes id `malformed-operator-page`
  (was `live` — the exact id BL-775 was about to collide with) and records
  the written ids on `ctx.malformedManifestPageIds`.
- The "no page from it" step now asserts none of `ctx.malformedManifestPageIds`
  appears among the offered pages — nothing about the list's length.

## New feature/handler

`specs/features/BL-1634-a-rejected-manifest-offers-no-page-from-it-built-ins-still-offered.feature`
(specifier-authored, already on `main`) gets its handler,
`bl1634RejectedManifestOffersNoPageFromItSteps.js`:

- Its own scoped Background text ("...for BL-1634") — a deliberate copy,
  not a reuse of the shared unscoped Background text, per BL-1277's
  collision guard (the direction explicitly calls this out).
- Both scenarios drive the REAL bridge (`startBridge`) against a real
  written operator manifest file, same posture as BL-829's own handler.
- Built-in ids/shapes are read from `letsTalkRoutes.ts`'s own exports
  (`operatorDocs`, `bubbleHealth`, `bubbleHostPage`, `bubbleLivePage`) at
  run time — never a hand-typed id list — so a fifth built-in added later
  is picked up automatically, and scenario 02's colliding fixture always
  targets a REAL current built-in (`BUILT_IN_PAGES[0]`, currently
  `operator-docs`) rather than a literal that could go stale.

## Invariant encoding (BL-654)

The one declared invariant ("a page id from a rejected operator manifest
never appears among the pages offered... built-ins offered regardless")
gets a property test,
`bl1634RejectedManifestBuiltInsInvariant.property.test.js`, generalizing
past the two acceptance scenarios' fixed examples over an arbitrary
malformed page id crossed with an arbitrary missing required field
(`title`/`entryPath`/`order`), driving the REAL
`getLetsTalkUiBundleManifest` + the REAL merge chain
(`mergeOperatorDocsIntoUiBundleManifest` →
`mergeBubbleHealthIntoUiBundleManifest` →
`mergeBubbleHostIntoUiBundleManifest` →
`mergeBubbleLiveIntoUiBundleManifest`, the exact order `bridgeServer.ts`
applies) rather than reimplementing their logic.

The two cells (a malformed id colliding with a built-in's id, and one
that doesn't) are reached by CONSTRUCTION (`i % CELLS.length` over 40
draws, `runsPerCell`/`assertReachFloor` from `test/helpers/reachFloors.js`),
never sampled and hoped for — a random string colliding with one of the
4 real built-in ids by pure luck is astronomically unlikely, the exact
BL-1620/BL-1281/BL-1584/BL-1589 reach-floor lesson. First submission drew
the colliding id via `fc.oneof` and asserted `sawColliding`/`sawNonColliding`
booleans by hand; `swarm_handoff.sh`'s SAMPLED_REACH_FLOOR gate (BL-1584)
correctly refused it as a hoped-for floor and named the fix (`runsPerCell`
+ `assertReachFloor`) directly — rewritten to the construction-based
shape before this parcel's first send.

**Non-vacuity** (2026-09-18): temporarily broke
`mergeBubbleHealthIntoUiBundleManifest` to unconditionally return its
input unchanged (never merging in `health`). The property failed on its
first generated case: `expected built-in id "health" offered, got:
["live","host","operator-docs"]`. Restored byte-for-byte
(`git diff --stat` showed no diff on the file after restore, recompiled);
the property holds again.
