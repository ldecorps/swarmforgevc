## 1. The third consumer now has BL-1020's rule

`babysitter_check.bb` read `(active-role-marker)` unconditionally three lines
after resolving `rotation-router?`, so on a standing pack the sweep reasoned
about a resident that does not exist, named by a file nobody clears. It now
routes through `mono-router-lib/resolve-resident-role` — the SAME shared
decision the hotfix used — rather than a fourth copy of the mode check.

Two details the ticket implies and the code needed:

- when the marker must not be honoured the sweep gets **nil, not the home
  role**. Every consumer downstream asks "which role is the resident right
  now", and on a standing pack the answer is none; handing them `home-role`
  would swap one fiction for another.
- **invariant 3's unknown-role case**: `resolve-resident-role` honours any
  non-blank value on a router pack (it is a cache of a role the swarm rotates
  through), so "is this actually one of our roles" is asked against the pack's
  own `ordered-roles` — never a hardcoded list (BL-804 invariant 1).

## 2. The recheck now sees the wrong role in a pane

`assigned-role-mismatch` (new, in `remote_control_health_lib.bb`) compares the
observed RC name against the role **the pack assigns the pane**, not against
whatever role the check was pointed at. That is exactly why
`rc:specifier: HEALTHY` printed over a pane running the coordinator's script:
the check had been aimed at the coordinator by the stale marker and so compared
that role against itself.

It is deliberately silent in three cases that would otherwise cry wolf: a
rotation-router pack (a rotated resident legitimately runs another role's
script — BL-1020/BL-648 untouched), no observed name (the pane-liveness check's
job), and no expected name (a role whose launch script carries no RC flag).

**Placement matters and a test proved it.** My first version checked the
mismatch *before* `actionable?`, which turned every ordinary degraded-RC repair
into a failure report — `test_swarm_ensure.sh` RC-2 caught it immediately. It
now applies only when the RC check is otherwise content, which is the actual
outage shape: healthy-looking, wrongly staffed.

## A weakness in my own acceptance, found and fixed before forwarding

The first version of the standing-pack Given asserted only that
`babysitter_check.bb` *mentions* `resolve-resident-role`. Reverting the sweep
to the raw marker read still passed all 7 scenarios, because the handler
composed the rule itself in JS and the grep matched the leftover binding. That
is a test proving something about the test. It now asserts the sweep DERIVES
`resident-active-role` from the decision and does not bind it straight from
`(active-role-marker)` — and with that, the reverted sweep reds all 7.
