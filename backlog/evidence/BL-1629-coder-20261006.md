# BL-1629 coder evidence (2026-10-06)

## What changed

The pole register (`backlog/suite-poles.tsv`, read by
`check-suite-file-budget.ts`) previously knew only "owned" rows - a file
over budget whose OPEN ticket will cut it. bl968's own two full
step-registry loads (BL-968 invariant 1) will never get fast, so the only
way to keep its row owned was a ticket that never closes. This ticket adds
a `disposition` column: `owned` (default, unchanged) or `accepted` (a
pole that will not be cut; its `ticket` column names the rationale ticket,
which MAY be closed).

- `extension/src/tools/check-suite-file-budget.ts`:
  - `RegisterRow` gains `disposition: PoleDisposition` (`'owned' |
    'accepted'`); `parseRegisterRows` reads an optional 5th column,
    disambiguated by VALUE (an exact `'owned'`/`'accepted'` literal), not
    column count - a row with no 5th field, or a non-disposition 5th
    field, still reads `'owned'` and keeps that field as part of `note`
    (scenario 01).
  - `BudgetVerdictKind` gains `'accepted'`. New `classifyAcceptedRow`:
    an accepted row skips the open-ticket check entirely; it is
    `stale-row` under 80% of budget (exactly like an owned row - FIRM),
    otherwise ALWAYS `accepted` (even comfortably under budget - the one
    place this differs from an owned row, which stays silently unreported
    in the healthy middle band). `FileVerdict` gains `note?: string` to
    carry the rationale's "re-measure: YYYY-MM-DD" through to printing.
  - `formatBudgetOffenders`: an `'accepted'` entry prints `file: Xs
    accepted (rationale TICKET, re-measure: DATE)`, never the
    budget-exceeded wording. Every OTHER entry that carries a `ticket`
    (an owned `'ok'`/`'stale-row'` row) now also names it - matching what
    `unowned-row`'s own separate formatter (`formatGuardReport`'s inline
    `owner TICKET is not open`) already did, so a reader never has to
    cross-reference the register to see which ticket a reported row
    belongs to (required by acceptance scenario 02's stale-row case,
    which the ticket's own description did not call out but the scenario
    itself does).
- `backlog/suite-poles.tsv`: header documents the new optional column;
  bl968's row is rewritten in place - `disposition=accepted`,
  `ticket=BL-1629` (already set by the specifier's earlier amendment),
  note now carries `re-measure: 2026-12-17 or BL-1630's land, whichever
  first` (and keeps the literal phrase "an accepted pole" - see Finding
  below).
- `extension/test/bl968StepRegistryMaterializedTreeGuard.test.js`: the
  shared fixture's prefix now carries its own `process.pid`
  (`bl968-materialized-<pid>-`); the D1 guard's own blind
  `fs.readdirSync(os.tmpdir())` listing is replaced with
  `sweepStaleTmpDirs({prefix})` (BL-1623's own helper) against a
  pid-embedded prefix - removes only a root this exact process (or an
  already-dead owner) created. bl968's assertions, its two registry
  loads and the planted-offender sensitivity test are byte-for-byte
  unchanged.
- `specs/pipeline/steps/bl1629AcceptedPoleNeedsNoOpenOwnerSteps.js`
  (new): binds the feature, landed in the same parcel (required_wiring).

## Invariants

"The register never carries a row the gate ignores: every row - owned or
accepted - contributes a printed line to every run's verdict, and only a
file with no row at all is refused as new-pole." This is a small,
FINITE decision table (disposition x stale/not-stale x open/closed
ticket x row-present/absent), the same "quantified domain is finite and
enumerable" shape BL-968's own invariant 1 already uses to justify an
EXHAUSTIVE, not generative, encoding (its own file header says so
verbatim) - a generator here would explore a space already fully
enumerated by the deterministic cases above, never finding a reachable
state the unit tests do not already cover. Stated reason, not a property
test: `checkFileDurationBudget`/`classifyRegisterRow` are pure and
genuinely testable, but the invariant's own domain has no width left for
a generator to add confidence over the four branches already covered
directly: accepted+fresh-over-budget (`accepted`), accepted+fresh-under-
budget (`accepted`, never silently kept), accepted+stale (`stale-row`,
same floor as owned), and no-row-at-all (`new-pole`, unaffected by other
rows' dispositions).

## Bounce rework (D1, 2026-10-06, commit c51c113e0e)

QA bounce D1 (`backlog/evidence/BL-1629-QA-20261006.md`): `classifyAcceptedRow`
returned `null` when the row's file was not measured this run (renamed,
deleted, or lane-excluded), so an accepted row with a possibly-closed
rationale ticket printed nothing on ANY run - "accepted and forgotten",
exactly the defect this ticket exists to prevent.

- `extension/src/tools/check-suite-file-budget.ts`: `classifyAcceptedRow`'s
  `if (measured === undefined) return null;` now returns `{ file, durationMs:
  row.measuredMs, budgetMs, kind: 'stale-row', ticket }` - a file not
  measured this run costs nothing THIS run, so it reports `stale-row` (the
  register's own "the pole this row named is gone" verdict) using the
  register's last recorded measurement, so the printed line still names a
  real number.
- `extension/test/checkSuiteFileBudgetCli.test.js`: one new test, "an
  accepted row whose file was NOT measured this run is reported stale-row,
  not silently dropped" - covers the exact D1 trigger (the file absent from
  `durations` entirely, not an explicit `durationMs: undefined` entry no
  real vitest report would ever contain).
- `backlog/suite-poles.tsv`: bl968's row removed per the specifier's
  2026-10-06 amendment (S1) - its premise (never under budget) went stale
  once BL-1630 landed 2026-09-21; accepting it now would land a row that
  reads `stale-row` on arrival. The disposition mechanism itself (scenarios
  01-02) is unaffected; scenario 03 (bl968's own acceptance) is retired in
  the feature file, not reworded.
- The invariant declared in the ticket YAML was narrowed by the specifier's
  amendment to the unmeasured-row case specifically (QA evidence S2: the
  original wording over-claimed BL-1598's owned rows, which stay silent in
  the healthy 80-100% band by design - out of this ticket's scope). That
  narrower invariant now DOES get a coder-authored property test (BL-654),
  superseding the "stated reason, not a property test" paragraph above for
  the accepted-row-never-silent claim specifically:
  `extension/test/bl1629AcceptedRowNeverSilentInvariant.property.test.js` -
  `measured` drawn via `fc.option(fc.integer(...), {nil: undefined})` so
  `undefined` (D1's exact trigger) is reached on ~50% of the 200 runs, not
  left to chance across a wider space; `measuredMs`/`budgetMs` drawn
  independently so stale/accepted/over-budget bands are all reached without
  hand-picking. Non-vacuity proven at authoring time: reverting the fix (the
  bounce's own `return null;`) failed the property on the first `undefined`
  draw, every run; restored after confirming the break.
