## Part 1 — the cache is ON DISK, and that is a deliberate departure

The ticket's *"How (direction, not mandate)"* suggested an in-memory cache for
the daemon's lifetime. **It cannot work here.** `babysitterd.sh`'s tick shells
`babysitter_check.sh`, which `exec bb`s `babysitter_check.bb` — every tick is a
**fresh process**, so an atom would never survive one. An in-memory cache would
have passed review and saved nothing.

The ticket's own acceptance settles it the same way: scenario 02 runs two
checks and requires the second to invoke no predicate, and the QA procedure
spells that out as two `babysitter_check.sh` runs. Both are statements about
separate processes. So: `.swarmforge/babysitter/pipeline-code-on-main-cache.json`,
written through a temp file and an atomic move — the daemon being restarted
mid-write is the very failure this ticket is about, and a half-written cache
read back as a hit would be worse than none.

Keyed on all three tips. **An `:ancestry-unavailable?` result is never
written** — a hole frozen as clean outlives the condition that caused it, and
is the one way a cache here could do real harm.

## Part 2 — one process for the whole candidate set

`is_qa_ancestor.sh` gains `--batch`. It is the **same predicate**, not a second
one: BL-925 invariant 2 holds literally, because there is still exactly one
place in the tree that decides approval, and single-SHA mode is now a batch of
one sharing the same code path so the two cannot drift.

The saving is not the process count alone. Each invocation used to re-scan the
whole bounce JSONL store **and** recursively grep the entire `backlog` tree.
Those reads now happen **once** per batch.

## Two things that went wrong, both worth writing down

**1. Store-consultation ORDER is load-bearing.** Reading every store up front
broke a case the original got right: the expedite store was only ever consulted
*after* the bounce stores failed to veto, so a SHA with a bounce on file
answers a clean "no" even when the expedite store is unreadable. My first
version raised the unreadable store immediately and turned that into
`undeterminable`. Fixed by *recording* expedite-store problems and raising them
inside `answer_one`, after the bounce checks — the original ordering, preserved
through batching. Caught by `bl1025_expedite_approval_property_runner.bb`.

**2. `VAR=$(grep …)` aborts under `set -e`.** An expedite store holding only
**bouncing** records makes the collecting grep match nothing, exit 1, and — as
a failed command substitution in an assignment — abort the whole script under
`set -e`. That silently turned an **approved ancestor into a clean "no"**.
Fixed with `|| true` on both collections, and the reason is written at both
sites.

Both were caught by an existing exhaustive property runner, not by mine. That
gap is now closed: **P6** asserts batch/single equivalence over generated
verdict-store shapes — absent, approving, and bouncing — and reinstating the
`|| true` hazard fails it **8** times in 12 runs.

## Declared invariants (BL-654) — all three encoded, non-vacuity measured

`swarmforge/scripts/test/bl1086_cache_and_batch_property_runner.bb`, 40 runs
over **real git repositories** built per run. The subject is a data-access
change over git state, so a simulated fixture would test the simulation.

| property | invariant | breaks that kill it |
|---|---|---|
| P1 | 1 (result equivalence) | — see note |
| P2 | 2 (invalidation) | key on main only **33**; always-unavailable **14** |
| P3 | 2 (a hole is never cached) | cache the hole **24**; unanswered-as-no **12**; always-unavailable **14** |
| P4 | 3 (whole-sweep failure) | unanswered-as-no **35** |
| P5 | armed-ness | always-unavailable **36** |
| P6 | 3 (one predicate, one answer) | drop the `\|\| true` guards **8** |

**P1 is absent from that table, and that is stated rather than hidden.** It
compares two runs of the *same* implementation, so a break that is wrong in the
same way twice slips past it. P1 guards a cache that *diverges* from a fresh
gather — a real hazard, and why it is written as an equality — while P3, P4,
P5 and P6 catch an implementation that is consistently wrong.

Reach: `tip-moved 40, unanswerable 30, cache-hit 40, with-offender 31,
without-offender 9, deep-ahead 14, store-absent 11, store-approving 10,
store-bouncing 9` — all above their floors. The store shape is **derived from
the run index**, not drawn: the LCG correlated with earlier draws and `mod 3`
never landed on the bouncing shape — the very shape a real regression hid in —
zero times in 40 runs. **The coverage floor caught that**, which is what floors
are for.
