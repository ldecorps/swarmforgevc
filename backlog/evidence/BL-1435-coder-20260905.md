# BL-1435 — coder pass, 2026-09-05

## What was wanted

BL-1038's live-repository derivation guard recognizes only
`path.join(__dirname, '..', '..')` as a live-root binding. BL-1317's
hardener (2026-09-02) re-derived `docsStructureRealTree.test.js`'s root
through `git rev-parse --show-toplevel` for sandbox path safety, and the
guard stopped seeing the file entirely - `liveRepoDerivation`,
`violationFor`, and the marker check all returned null, so the "real tree
is clean" verdict was vacuous for every rev-parse-rooted test.

## What landed

- **`extension/test/helpers/liveRepoDerivationGuard.js`**: a new
  `REV_PARSE_TOPLEVEL_SRC` regex fragment recognizes
  `(execFileSync|execSync|spawnSync)('git', [...], {...})` whose args
  array or trailing options object carries `__dirname`, `rev-parse`, and
  `--show-toplevel` (looked for in the window up to the call's own closing
  paren, so `__dirname` is found whether it sits inside the array via
  `-C` or in a trailing `{ cwd: __dirname }` option - both shapes occur in
  the real files). `__dirname` is the load-bearing tell, exactly as it is
  for the `path.join` idiom: a rev-parse against any OTHER root (a
  `mkTmpDir` fixture, `git init`'d separately) resolves that fixture's own
  top level, never the live repository, and correctly does not match.
  Folded into `LIVE_ROOT_BINDING_RE` (the named-binding case) and
  `LIVE_ROOT_INLINE_SRC` (the inline/escape-into-production case) as one
  alternation each - `growthPatternsFor`, `EXEMPTION_RE`, and every other
  rule stay untouched, so the two idioms cannot diverge in which rules
  apply (invariant 1).
- **`extension/test/liveRepoDerivationGuard.test.js`**: five new unit
  tests - the three call shapes (execFileSync/execSync/spawnSync, with
  and without an explicit `-C`), the inline (never-bound) form, the
  fixture-rooted non-match (gitEnvGuard.test.js's own shape), and the
  bare-marker-not-honoured case (BL-1212's invariant carried, per the
  ticket's own instruction).
- **`specs/pipeline/steps/bl1435RevParseRootIsALiveReadSteps.js`** (new):
  drives the real guard against fixture text (scenarios 01-02) and the
  real `extension/test` tree (scenario 03).

## Declared invariants

1. One notion of a live root, one regex, one set of consuming rules -
   `LIVE_ROOT_BINDING_RE` and `LIVE_ROOT_INLINE_SRC` are each a single
   alternation covering both idioms; `growthPatternsFor`/`EXEMPTION_RE`
   are untouched and apply identically to whichever idiom bound the name.
2. `findLiveRepoDerivations('extension/test')` returns `[]` at this
   commit (verified directly, and by acceptance scenario 03) - every file
   the widened guard can now see is either exempt with a reason or reads
   no growth surface; none is silently unreachable the way
   `docsStructureRealTree.test.js` was before this parcel.
3. Widening added no bare exemptions: `docsStructureRealTree.test.js`'s
   pre-existing exemption already carries a real reason (landed by
   BL-1212); no new exemption marker was added by this parcel at all -
   the other files this ticket resolves needed either nothing (no growth
   surface) or were already correctly excluded (no binding).

## Non-vacuity (byte-identical restore confirmed)

`REV_PARSE_TOPLEVEL_SRC` mutated to a pattern that matches nothing
(`` (?!x)x ``). 4 of the 5 new BL-1435 unit tests failed immediately
(the inline-form test, the bare-marker test, and both call-shape
assertions inside the execSync/spawnSync test) - `git-help` this
demonstrates the widening is load-bearing for every new assertion, not
merely present. Restored; `diff /tmp/liveRepoDerivationGuard.js.bak
extension/test/helpers/liveRepoDerivationGuard.js` empty; the real red/
green pair from `qa_e2e_procedure` step 2 (docsStructureRealTree.test.js
with its exemption reason stripped) reconfirmed separately: with the
reason, `violationFor` returns `null`; stripped, it returns the
`computeDocsStructure` production-escape violation.
