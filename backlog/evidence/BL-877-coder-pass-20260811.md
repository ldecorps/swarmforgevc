# BL-877 — coder pass (2026-08-11)

Implements: a portable process-liveness primitive so the sandbox sweep's
keep-guard and the fixture reaper's orphan-kill both get a real answer on
macOS (no `/proc`), not the silent empty-set degrade both previously fell
back to.

## Changes

- `swarmforge/scripts/proc_fd_scan_lib.bb`: new `live-pid-paths!` - the ONE
  shared entry point both consumers now call. `/proc` when present
  (`procfs-available?`, unchanged scanning logic), a single `lsof -F pfn`
  invocation otherwise (Darwin) - never a second call per pid/candidate,
  matching the existing "scan once per sweep pass" cost discipline. Returns
  `nil`, never a coerced-empty map, when NEITHER facility is reachable
  (mirrors `process_table_lib.bb`'s own BL-849 `list-pids!` contract). Two
  small overridable seams for portable testing, both blank-safe and
  defaulting to the real facility when unset: `SWARMFORGE_LSOF_BIN` (which
  `lsof` binary) and `SWARMFORGE_PROC_DIR` (which directory stands in for
  `/proc` - lets the procfs branch be exercised end-to-end even on a host,
  like this one, with no real `/proc`, via a synthetic tree of real
  symlinks). New pure parser `parse-lsof-pfn-output`: only a `cwd` or
  purely-numeric fd id counts, excluding `lsof`'s `txt`/`mem` entries
  (the loaded executable/library image), which `/proc/<pid>/fd` does not
  report - required for invariant 2 (same verdict on both userlands).
- `swarmforge/scripts/operator_runtime.bb`: `sandbox-sweep!`'s
  `live-process-paths!` now delegates to the shared primitive instead of
  its own inline `/proc` scan. Its 0-arity default: `nil` (undetermined)
  makes `:live-process-rooted-in?` answer `true` for every candidate
  (fail-safe keep, the OPPOSITE of the old always-`#{}` default) and logs
  `"liveness could not be determined this pass..."` - invariant 1.
  `live-process-rooted-in?` also now resolves `entry-path` via
  `fs/real-path` before comparing - see the symlink note below.
- `swarmforge/scripts/fixture_reaper_sweep_lib.bb`: same delegation for
  `live-process-paths!`; `nil` passes through unchanged (`pids-rooted-in`
  already treats nil like `{}` - no pids to kill - which is this
  consumer's own pre-existing safe direction regardless of whether
  liveness was determined). `default-adapters` logs the same "could not be
  determined" line for consistency/observability. `pids-rooted-in` also
  now resolves `entry-path` via `fs/real-path`.
- `specs/features/BL-877-portable-process-liveness-without-proc.feature`
  (promoted from `.feature.draft`, unchanged Gherkin - pre-existing, not
  authored this pass) + `specs/pipeline/steps/bl877PortableProcessLivenessSteps.js`
  (new) + `specs/pipeline/steps/index.js`: step handlers driving REAL
  `operator_runtime.bb --tick-once` subprocesses against disposable
  fixture directories (BL-413 scenario-03's own convention), never the
  real `/tmp`.
- `swarmforge/scripts/test/proc_fd_scan_lib_test_runner.bb` (new): pure
  unit coverage for `parse-lsof-pfn-output` (cwd/numeric-fd inclusion,
  txt/mem exclusion, non-path-name drop, multi-pid, malformed-input
  tolerance) plus a same-live-host pin of `live-pid-paths!`'s own contract
  (BL-849's own "cannot force a real enumeration failure portably"
  posture). Verified non-vacuous: breaking the fd-id filter makes 2 of
  these fail; reverted.
- `swarmforge/scripts/test/test_operator_runtime_sandbox_sweep_liveness_undetermined.sh`
  (new): the one case the existing 3 named tests don't cover - a control
  run (real lsof, stale+unrooted entry reaped normally) against an
  undetermined run (`SWARMFORGE_LSOF_BIN` pointed at a nonexistent path -
  `/proc` is already absent on this host, so this removes the only other
  facility) proving the SAME entry is instead kept and the log records why.

## A macOS-specific bug this pass also had to fix

`mktemp -d`/`os.tmpdir()` on this project's own macOS host return
`/var/folders/...` - a symlink to `/private/var/folders/...`. `lsof`
(like `/proc`'s own `fs/real-path` reads) reports the RESOLVED path, so
comparing an unresolved candidate `entry-path` against resolved
live-process paths never matched anything - every candidate looked
unrooted regardless of a genuinely live, correctly-rooted process,
failing invariant 2 outright. Fixed by resolving `entry-path` via
`fs/real-path` in both `live-process-rooted-in?` and `pids-rooted-in`
before comparing. Caught by the existing (unmodified)
`test_operator_runtime_sandbox_sweep.sh` failing 2 of 6 checks before this
fix; both pass after.

## Invariants (BL-654)

Babashka/shell is one of the two stacks with no property-test framework
wired (engineering.prompt's Testability Boundary - Bubble section
documents the same gap class for Android/JVM unit tests; no Babashka
equivalent to `*.property.test.js`/fast-check exists in this repo). Per
the coder role's own instruction for this case, each declared invariant's
verification is recorded here instead of a property test:

1. "Liveness is never silently assumed absent...": `nil`-propagation
   through `live-pid-paths!` -> `live-process-paths!` -> the 0-arity
   `sandbox-sweep!` default, verified end-to-end (real subprocess, real
   log file) by the new `test_operator_runtime_sandbox_sweep_liveness_undetermined.sh`
   and by acceptance scenario 05.
2. "Same keep/kill verdict on macOS as on Linux": verified two ways -
   (a) the pure-parser unit tests pin that the lsof branch's OUTPUT SHAPE
   is semantically equivalent to the procfs branch's (same cwd+numeric-fd
   inclusion, same txt/mem exclusion), both feeding the identical
   downstream comparison logic; (b) acceptance scenario 04 exercises BOTH
   branches against the literal SAME live child process via the
   `SWARMFORGE_PROC_DIR` synthetic-tree seam, asserting the identical
   "still exists" verdict from each.
3. "One shared liveness primitive serves both consumers": structural, not
   behavioral - verified by `required_wiring` (both files call
   `proc-fd-scan-lib/live-pid-paths!`, neither re-implements a `/proc`
   listing loop of its own) and by inspection of the diff itself.

- `specs/pipeline/scripts/run_acceptance.sh` for this ticket's feature:
  **7/7 scenarios pass**, confirmed on 2 consecutive runs (not a fluke).
  One acceptance-harness-specific bug surfaced and fixed along the way:
  the step handlers' own test child processes were spawned
  detached+unref'd, so a process the reaper genuinely killed (confirmed:
  `ProcessHandle.destroyForcibly()` returns `true`, the real workload
  stops) stayed a zombie pid entry until reaped, and `kill(pid, 0)`
  read a not-yet-reaped zombie as "still alive". Fixed by (a) not
  detaching/unref'ing the test's own child processes, so this test script
  stays their real parent, and (b) yielding to the event loop
  (`setImmediate`) before checking aliveness, since `execFileSync` is
  synchronous and blocks libuv's own SIGCHLD processing until it returns.
  This was a test-harness bug, not a production one - `kill-pid!` itself
  was correct throughout; only my own reproduction/step-handler
  methodology needed the fix.
- `npm run compile`: not applicable - no `extension/` files touched this
  pass.
