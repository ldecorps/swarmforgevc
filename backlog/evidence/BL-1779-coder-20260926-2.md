## D1 — `frontDeskHeadlessLauncherSteps.js`, the crash scenario's `ctx.env`

The crash/give-up scenario (`a supervised front-desk process that has
crashed`) built its own `ctx.env` inline, isolating `SWARMFORGE_FLEET_HOME`
but never setting `BRIDGE_PORT` — so it supervised a bridge on the default
live port 8765, exactly like the `-04` scenario would without its own
`freePort()` call. Fixed: the same `ctx.port = freePort()` /
`BRIDGE_PORT: String(ctx.port)` pattern the `-04` scenario already uses.

## D2 — `bl622OnboardingTelegramTokenSeparationSteps.js`, three call sites

## D3 — `frontDeskSurvivesRebootSteps.js` scenario 03, the actual root cause

The prior pass's own note called this "a pre-existing bug this fix
surfaced, not caused" and sent an unowned-red note — but the standing-red
register already attributes it to BL-1779 (row added same pass), and QA's
new bounce confirms it is still red after the port/fleet-home isolation
that WAS already present in `fixtureEnv`. Traced with a real, standalone
reproduction (a throwaway root, the real `launch_front_desk.sh`, the
exact `fixtureEnv` shape): the launch itself is fine — `BRIDGE_PORT` is
honored, the bridge does end up listening on the right port — but only
AFTER several real (failing) Telegram API calls to create onboarding
topics against the fixture's own fake token, each a real network
round-trip. `launchFrontDesk`'s own wait bound
(`waitFor(5000, () => fs.existsSync(statusFile(root)))`) only waits for
the status FILE to exist — written as soon as the supervisor has STARTED
the bridge child process, well before the bridge server has actually
bound its port. Scenario 03's own fetch fires immediately once that
promise resolves, racing a bridge that has not bound yet.

Fixed: `launchFrontDesk` now ALSO waits (bounded, 5s) for the bridge's own
`BRIDGE_LISTENING port=<port>` line, named to the SAME port this run
passed, in the real `front-desk-supervisor.log` — never a fixed sleep,
the same "poll the log for the listening line" technique
`startBridgeHeadlessCli.test.js` already uses for the identical race.
