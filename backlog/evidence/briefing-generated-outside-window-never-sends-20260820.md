# A briefing generated outside the daemon's trigger window is NEVER sent

Reported by the operator: "i did not receive my morning briefing?" — correct.
Coordinator root-caused it. **This is a real defect, and it is NOT the handoffd stall
(that was the first hypothesis and it is wrong).**

## Observed
- `docs/briefings/2026-08-20.md` exists and is committed (`79f1b3f20`, 7481 bytes,
  written 06:01Z).
- `docs/briefings/.sent.json` holds 44 entries ending at **`2026-08-19.md`**.
  `2026-08-20` appears **zero** times.
- handoffd has since been healthy for 35+ minutes, state `R`, **341 completed heartbeat
  cycles** — hundreds of opportunities to send. It still has not.

So the "stalled daemon missed the sweep" theory is disproved: a fully healthy daemon does
not send it either.

## Mechanism (`briefing_generation_schedule_lib.bb`)

    (defn morning-trigger-due?
      "True when now-ms is at/after the configured morning time on its own UTC
       calendar day AND that day's briefing file does not yet exist."
      [now-ms morning-hour morning-minute briefings-dir]
      (and (>= now-ms (scheduled-ms-today now-ms morning-hour morning-minute))
           (not (briefing-already-generated? briefings-dir (utc-day-key now-ms)))))

The trigger is for **GENERATION**, and it **self-disarms on file existence**. Sending is
tracked separately, in `.sent.json`, by `briefing_email_lib.bb`
(`load-sent-briefings` / `record-briefing-sent!`).

**Nothing anywhere asks the one question that matters: "file exists AND not in
`.sent.json` -> send it."** So:

    briefing generated by the daemon's own flow      -> sent
    briefing generated any other way                 -> file exists, trigger disarms,
                                                        never sent, silently

Today's was generated at 06:01Z on an operator prompt (configured window is
`briefing_morning_time_utc 04:30`). The file's existence immediately disarmed the only
trigger. It will never send on its own, and no error is raised anywhere — the operator's
only signal is not receiving it.

## Why this is worth a ticket rather than a hand-send
Hand-sending today's briefing fixes one day and hides the defect. The failure recurs for
**every** briefing generated late, re-generated, or written while the daemon is down —
and it fails **silently**, which is how it went unnoticed until the operator asked.

Suggested direction (specifier's call): make the send predicate key off `.sent.json`
rather than piggy-backing on the generation trigger — i.e. sweep for
`exists(file) AND file NOT IN sent` and send that, independent of the time window and of
who wrote the file.

Related but distinct: the handoffd stall (BL-967, now landed) DID delay generation, which
is how the two got conflated. Keep them separate — this defect survives BL-967 entirely.
