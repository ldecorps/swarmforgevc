## Discovered while wiring

1. **`seat`'s own role check never recognized `coder@2`.** BL-1702's
   amendment (the driver's own state keys on seat id, not role, "because
   the human refined BL-1702 to run the local coder as coder@2 beside the
   Claude coder") requires `seat`'s verb-set gate to treat `coder@2`
   exactly like `coder` - `role_verbs()` did an exact-string `case`
   match, so a driver seat running as `coder@2` would have every `seat`
   verb refused. Fixed with a `${1%%@*}` strip (bash 3.2-safe), mirrored
   in `local_parcel_driver_lib.bb`'s own `base-role`. Both fixes are
   backward-compatible no-ops for any role with no `@` in it - re-ran
   BL-1696's own acceptance feature and property tests to confirm (16/16,
   3/3, unchanged).
2. **`sh!`'s calling convention is opts-FIRST, not trailing** (a real bug
   caught before it did damage - see the "A real risk, caught" section
   below).
3. **`green-gate-decision`'s condition order matters.** My first pass
   checked `acceptance-passes?` before `has-commit?`; the ticket's own
   scenario 02 table expects "makes no commit" to report "no model
   commit", not "acceptance still failing" (which is also technically
   true when nothing changed, but misleading - it reads as "the model
   tried and failed" when it did not try at all). Reordered; the property
   test's exhaustive 16-combination sweep pins this order now.
4. **JSON round-tripping keywordizes `specHashesBefore`'s own path keys**
   (cheshire's `keywordize-keys` recurses into every nested object, and
   `(keyword "/a/b.yaml")` splits on the first "/" into an empty
   namespace and a name that silently drops the leading slash) - every
   gate check compared a keyword-keyed "before" map against a
   string-keyed "now" map and never matched, so `spec-bytes-identical?`
   was always false. Fixed via `(subs (str k) 1)` (the keyword's own
   printed form minus its leading colon - the true inverse of
   `(keyword s)` for any `s`, checked against an absolute path, an
   interior-slash relative path, and a slash-free bare filename).

## A real risk, caught: `sh!`'s opts-first convention

`daemon_cycle_guard_lib.bb`'s `split-sh-args` supports exactly two
optioned call shapes - `(sh! [cmd...] opts)` or `(sh! opts cmd arg1
arg2...)` - never a trailing map after plain string args. My first
`seat!` implementation passed the options map LAST; `split-sh-args`'
`:else` branch then `(mapv str args)` **stringified the options map into
the command's own argv** and silently ran with `sh!`'s own process
default `:dir`/`:env` (the CALLING bb process's cwd/env) instead of the
fixture checkout. During this ticket's own development, before this was
caught, this ran `seat next`/`seat merge` against **this coder worktree's
own live checkout** rather than the throwaway fixture - verified
afterward that no damage occurred (the fixture's own commit shas do not
exist in this repo, so a `seat merge` call would fail cleanly on an
unknown revision, and `seat next` re-serves whatever is already
`in_process` rather than claiming anything new) via `git status`/`git
log` immediately after noticing the anomaly. Fixed to the map-first
form; the fixture's `roles.tsv` also needed a `specifier` row (missing
originally, causing every `seat merge` to fail argument validation) once
the fix let real argument validation actually run in the right directory.
