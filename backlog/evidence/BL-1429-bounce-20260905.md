# BL-1429 — architect bounce, 2026-09-05

## Violated rule

Declared invariant 2: "Every change of the recommended cap is logged with
the signal that caused or cleared it (count, age or unowned), so the
coordinator and the briefing can say why intake is throttled; a
recommendation that persists unchanged logs nothing."

## Commit reviewed

`bcf7d823c9` (cleaner NONE pass — the shared-fixture-writer DRY extraction
is correct and not what's wrong here).

## What is wrong

`extension/src/tools/emit-throttle-recommendation.ts`'s `describeChangeReason`
correctly picks the binding (more restrictive) signal to name while the cap
is ACTIVE — it checks `standingCap <= reworkCap` before crediting
standing-red (so a severe rework diagnosis at cap 0 is correctly named over
a merely-present standing-red signal at cap 1). But the **clearing**
branch does not do the equivalent check:

```js
if (prior?.standingRed) {
  return `${describeStandingRedSignal(prior.standingRed.signal)} cleared - restoring the configured cap`;
}
return 'rework diagnosis cleared - restoring the configured cap';
```

This names the standing-red signal as the cause of a clearing **whenever
it was present in the prior tick's state at all** — regardless of whether
it was actually the binding (lower) cap at that prior tick. When a severe
rework diagnosis (cap 0) was the true binding cause and a standing-red
signal (cap 1) happened to be present but non-binding at the same time,
and both then clear together, the log falsely credits the standing-red
signal for the whole clearing — the rework diagnosis, which was the actual
cause of the cap, goes unnamed.

## Measured, not argued (matching this ticket's own house style)

```
tick1 recommendedCap: 0 severity: severe standingRed: { recommendedCap: 1, signal: 'count' }
tick2 recommendedCap: null
log entries:
{"from":null,"to":0,"reason":"severe rework diagnosis (rate 0.6 vs baseline 0.1) - freezing intake"}
{"from":0,"to":null,"reason":"the red count cleared - restoring the configured cap"}
```

Tick 1: severe rework (cap 0, correctly logged as the cause) with a
co-active but non-binding standing-red count signal (cap 1). Tick 2: both
clear simultaneously. The clearing is logged as "the red count cleared" —
factually wrong; the count was never the binding cap, the severe rework
diagnosis was, throughout. Reproduction used the coder's own test helpers
(`writeStandingRedRegisterFixture`, `persistReworkSignal`) via
`computeThrottleRecommendation`/`emitThrottleRecommendation` directly, no
fabrication.

## Why the parcel's own verification did not catch this

Every test that exercises the clearing branch isolates standing-red-only
transitions with **no rework signal present at all**:

- `bl1429StandingRedThrottleFoldInvariants.property.test.js`'s invariant-2
  property is explicitly commented "Isolated to standing-red-only
  transitions (no rework signal at all)."
- `emitThrottleRecommendationStandingRed.test.js`'s "recovery withdraws the
  recommendation" unit test likewise only ever writes a standing-red
  register, never a rework signal.
- The acceptance feature's scenario 03 ("recovery-withdraws-the-
  recommendation") sets up "a prior recommendation of 1 caused by the red
  count" alone — same isolation.
- Scenario 02 ("the-lower-recommendation-wins") exercises the ACTIVE
  tie-break (rework 0 correctly wins the naming over standing-red 1) but
  never carries that combined state forward into a subsequent clearing to
  exercise the branch this bounce is about.

So nothing in the parcel's coverage can currently distinguish a correct
fix from this bug.

## Scope check — is this the only site?

`describeChangeReason` is the only place a change-log reason is composed;
the active-cap branch's own tie-break logic (`standingCap <= reworkCap`)
is correct and needs no change. One function, one branch, one fix.

## Remedy

Not mine to mandate the shape (direction, not mandate): the clearing
branch needs the same "which was actually binding" comparison the active
branch already does, applied to the **prior** tick's rework/standing caps
(e.g. compare `prior`'s own reworkCap vs `prior.standingRed?.recommendedCap`
the same way `rec`'s are compared today) rather than a bare
`prior?.standingRed` truthiness check. Add a property or unit case that
combines a binding rework severity with a co-active, non-binding
standing-red signal, then clears both together, and asserts the log names
the diagnosis that was actually binding — mirroring the existing tie-break
test's shape but carried through a clearing.
