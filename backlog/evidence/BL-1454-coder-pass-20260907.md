# BL-1454 — coder pass, 2026-09-07 (expedite, stack stopped)

## What was implemented

`coordinator-activity-feed-sweep!` (GH-24) unbounded-walk fix, per the
ticket's "What is wanted" / "How":

- `swarmforge/scripts/coordinator_activity_feed_lib.bb`:
  - `tick!` now seeds (posts nothing, writes both cursors at the newest
    trace of each kind) on the FIRST tick — both sub-cursors nil — instead
    of treating a nil cursor as "everything is new". This was the actual
    kill-loop defect: on 2026-09-06 the cursor file had never been written,
    so every restart replayed all 6463+ handoffs from item 0.
  - `tick!` takes `post-cap` (default 20) and `deadline-ms` (default
    30000) and an injected `now-ms` clock; the loop stops (capped or
    deadline-reached) rather than draining unboundedly.
  - The cursor is now written after EVERY successful post (inside the
    loop), not only when the loop ends or a send fails — a tick killed
    mid-batch (thrown exception, process kill) leaves the disk cursor
    lagging the last success by at most one trace.
  - `new-handoffs` now takes bare filenames, not `{:file :header}` maps —
    `tick!` filters names against the cursor FIRST (`list-sent-handoff-names`,
    no file opened), then calls the new `read-handoff-header` seam only for
    survivors, so I/O is proportional to what's new, never to the total
    count of sent handoffs.
- `swarmforge/scripts/handoffd.bb`: split the old
  `coordinator-activity-feed-list-sent-handoffs` (listed AND slurped every
  file) into `coordinator-activity-feed-list-sent-handoff-names` (bare
  `fs/list-dir` + sort, no `slurp`) and
  `coordinator-activity-feed-read-handoff-header` (slurps exactly one
  file). Added `activity-feed-post-cap` (env `ACTIVITY_FEED_TICK_POST_CAP`,
  default 20) and `activity-feed-tick-deadline-ms` (env
  `ACTIVITY_FEED_TICK_DEADLINE_MS`, default 30000, clamped to at most
  `SUPERVISOR_IN_SWEEP_BUDGET_MS / 4` — the SAME env var
  `handoffd_supervisor.bb` reads, so a misconfigured override can only
  make the tick more conservative, never less — invariant 1).
- GH-24's own acceptance realization updated so its Background persists an
  EXPLICIT starting cursor (sort-key-minimal handoff sentinel `"000"`, a
  listed sentinel commit `seed0`) instead of leaving the cursor file
  absent — an absent cursor now means "seed and post nothing", the
  opposite of what GH-24's scenarios need ("every fixture trace is new").
  Updated: `specs/pipeline/steps/gh24CoordinatorActivityTelegramFeedSteps.js`
  (Background + scenario 05's "cursor unchanged" assertion, now checking
  against the seed sentinel instead of `null`),
  `specs/pipeline/steps/lib/gh24CoordinatorActivityFeedCli.bb` (new
  `list-sent-handoff-names`/`read-handoff-header` wiring). GH-24's Gherkin
  text is untouched; only the handler's realization of "the durable cursor
  starts at the beginning of the traces" changed, per the ticket's own
  direction.
- New: `specs/pipeline/steps/bl1454ActivityFeedSweepFitsBudgetSteps.js` +
  `specs/pipeline/steps/lib/bl1454ActivityFeedSweepCli.bb` — drives the
  real lib through a JSON-in/JSON-out CLI (never a reimplementation), with
  three fixture-only seams the plain GH-24 CLI doesn't need: a
  controllable clock (advances a fixed amount per successful post), a
  post-cap override, and a "throw on the Nth send" interrupt (a daemon
  killed mid-batch, per the specifier's expedite-stage note distinguishing
  this from GH-24-05's returned-false failed-send shape). The IR-DRY pair
  the specifier flagged at mint ("tick runs" / "runs twice";
  "Nth newer trace" / "Nth newer trace after the first tick") is each
  bound as one parametrized regex handler.
- `swarmforge/scripts/test/coordinator_activity_feed_lib_test_runner.bb`:
  rewritten for the new API — seeding, cap, deadline, per-post cursor
  writes (via a write-cursor! spy), and invariant 3 (a `read-handoff-header`
  call-counter proving header reads scale with new-only, not with total
  sent-handoff count).

## Invariants (BL-654)

All three of this ticket's declared invariants got a coder-authored
property test, `extension/test/bl1454ActivityFeedSweepBudget.property.test.js`,
driving the REAL bb lib through the new CLI with `fast-check`:

1. **Deadline bound**: for random `(totalNew, postCap, clockAdvancePerPost,
   deadlineMs)`, every successful post's pre-attempt clock check was under
   the deadline, and — when traces remained and the cap wasn't the reason
   the tick stopped — the NEXT attempt's clock was proven at/past the
   deadline and `result['deadline-reached']` is `true`.
2. **Cursor-lag bound**: for random `(totalNew, failAfter)`, an interrupt
   (throw) at every possible success count from 0 through "never" —
   `writeCount` and `posted.length` both equal `failAfter` exactly, and the
   persisted cursor names exactly the last successfully posted trace (or
   the untouched seed cursor at `failAfter=0`).
3. **Proportional I/O**: for random `(totalOld, totalNew)`, `headerReadCount`
   equals `totalNew` regardless of how large `totalOld` is — proving the
   dependency is on the NEW count only, never the total.

Non-vacuity proven at authoring time (documented in the test file's own
header comment) — each invariant's property was broken and confirmed RED,
then restored and reconfirmed GREEN:
- invariant 1: dropped the `(>= (now-ms) deadline)` cond clause from
  `tick!` → P1 caught it (posted past the deadline).
- invariant 2: moved `write-cursor!` out of the loop's success branch back
  to the terminal-only shape (the pre-fix GH-24 code) → P2 caught it
  (writeCount stayed 0 through an interrupt with successes).
- invariant 3: changed the handoff-trace map to build headers for
  `list-sent-handoff-names()` (everything) instead of just `new-names`
  (the survivors) → P3 caught it (headerReadCount tracked total, not new).
