## Reproduction (the failing text, verbatim)

Both files reproduced under real concurrent load — a background
`npm run test` (full unit-suite, ~620 files) run alongside a direct
`npx vitest run --config vitest.properties.config.mjs <file>` — on the
FIRST attempt, before any fix:

**`bl1343ReplayNeverDropsOwnPathInvariants.property.test.js`**, invariant 1,
host load average ~3.4-3.8 (1-min) on 20 cores:

```
 × test/bl1343ReplayNeverDropsOwnPathInvariants.property.test.js > BL-1343/BL-654 invariant 1: a differing tip is never reported as landed or as nothing left to replay 22167ms
   → Test timed out in 20000ms.
If this is a long-running test, pass a timeout value as the last argument or configure it globally with "testTimeout".
```
Whole-file wall time for that run: 36.53s (vs. an unloaded baseline of
~17-18s for the same file). This is a load-time timeout, not a floor miss:
1 fail / 19 pass over the first 20 alone-under-load attempts, all 19
passes landing at 16-18s — a few seconds of jitter away from the 20s cap
even when the run "passed".

**`bl1323StampOffInvariants.property.test.js`**, invariant 2, same class of
load (a separate background `npm run test` loop, host load ~7-10 1-min):

```
 × test/bl1323StampOffInvariants.property.test.js > BL-1323/BL-654 invariant 2: no green suite writes a decision into the hotfix ledger 22022ms
   → Test timed out in 20000ms.
```
4 fails / 15 loaded-alone attempts (27%) on this invariant specifically,
with passing runs ranging 8-19s — also a few seconds from the cap.

Both match the specifier's hypothesis exactly: the failure is the
property lane's fixed 20000ms `testTimeout` under real concurrent load,
not a sampled reach floor (every SHAPE loop in both files iterates its
corners by construction, confirmed unchanged by this pass).

## What landed

**Fewer subprocesses per draw** (`bl1343...property.test.js`,
`buildRepo`): the per-case fixture used to pay `git init` + 3x `git
config` + an `--allow-empty` seed commit + `rev-parse` + `update-ref` — 6
spawns — before a single one of the ticket's own commits was made, once
per property case (27 cases across the two invariants' three SHAPES ×
`numRuns: 9`). Switched to the existing BL-1039 shared-repo-fixture
(`test/helpers/sharedRepoFixture.js`'s `checkoutSeededRepo`), which hands
back an identity-configured one-commit repo for one `fs.cpSync` and NO git
spawn. Only `update-ref refs/remotes/origin/main` (needed per checkout,
since the template doesn't know about that ref) plus a `rev-parse HEAD` to
resolve the seed sha remain — down from 6 spawns to 2 per case.

The sha is re-resolved fresh every case rather than cached at module
scope: the shared template can legitimately reseed itself mid-run (its
own `templateIsHealthy` check, documented against BL-1124/BL-1175), so a
cached sha from an earlier checkout can silently stop existing in a later
one. Caught this empirically before shipping it — a first cached-sha
version failed immediately with `git update-ref ... trying to write ref
... with nonexistent object <sha>` on the second checkout of a fresh run,
confirming the template really does reseed under this workload.

**Load-relative per-test budget** (new
`extension/test/helpers/propertyLaneContentionBudget.js`, wired onto
`bl1343...` invariants 1 and 2, and `bl1323...` invariants 2 and 3 — the
four subprocess-per-draw tests in these two files): reuses
`specs/pipeline/steps/lib/contentionBudget.js`'s `resolveUnitLaneTimeout`
(the SAME BL-871/BL-1007 shape the unit lane's `contentionBudgetSetup.js`
already uses) unmodified, via its own supported `cpuCountFn` injection
point — no copy of its math, no edit to the shared module.

The unit lane's own `cpuCountFn` default is the host's real core count
(20 on this box), calibrated for sizing a worker POOL. That denominator
never engages for a single subprocess-heavy test: the reproductions above
happened at 1-minute load 3.4-10, i.e. a `load/cores` factor of 0.17-0.5 —
under the module's own `factor > 1` scaling threshold — so wiring the
unit lane's exact default would have changed nothing at the load levels
that actually reproduced the red. Measured this host's own idle band
across several `uptime` samples taken between reproduction batches this
session: 1-minute load 2.34-3.63 quiet, climbing to 7-13 with one or two
concurrent `npm run test` runs alongside — a real, repeatable swing. This
lane's helper therefore injects `cpuCountFn: () => 4` (documented in the
helper as `QUIET_LOAD_CEILING`, this session's own measured idle
ceiling) instead of the raw core count: the denominator this specific
population is actually sensitive to. A quiet host (load <= 4) still gets
the strict 20000ms budget unchanged; a loaded one scales, capped at the
module's existing 120000ms ceiling.

## Non-vacuity / effectiveness proof

The reproduction above (both files' verbatim `Test timed out in 20000ms.`
reds) was captured against the tree BEFORE either fix landed. After both
fixes, ran BOTH files 15 times each (30 runs total), back-to-back, against
a repeating background load generator (`npm run test` looped 10x
consecutively, peak observed 1-minute load 12.87 — heavier than either
original reproduction's load) — **30/30 green**. Several individual test
durations in that same loaded run landed at 20017ms-23568ms — wall time
that would have hit the OLD fixed 20000ms cap and failed exactly as
reproduced above — and passed, because the effective per-test timeout
scaled with load. The subprocess-count fix alone was checked separately:
an interim version with the reduced-subprocess `buildRepo` but before the
budget helper was wired in still hit `Test timed out in 20000ms.` once
during a loaded run (22742ms observed), confirming both parts of the fix
are load-bearing, not just one. Log: `extension/tmp/bl1579-verify.log`
(gitignored, not part of this commit; kept locally for QA's own re-run if
wanted).
