# BL-1341 — coder pass (2026-09-02)

`check_merge_deletion.sh` guarded one direction and was structurally blind to
the mirror case. On `main` the blind direction is the incoming one — where
`origin/main` carries QA-landed work — so the guard protected the unreviewed
side and waved losses through on the approved one.

## The fix — one guard, two directions

`collect_deletions <against> <side>` is called twice, against `HEAD` and
against `MERGE_HEAD`, into ONE list:

- a path seen from both sides is recorded **once**, with both sides named —
  one finding, not two (BL-1242 scenario 04's discipline carried across);
- each refusal line now says which side the path came from, so a resolver can
  tell an intended drop from an accident;
- one refusal, one name-it-to-mean-it exemption, both directions. **Not** a
  second script — the ticket is explicit that a fourth sibling would worsen the
  very shape (a guard family complete member-by-member, holed at the union).

One subtlety the ticket did not name, found while implementing: attribution
had to learn the second side too. `ticket_id_for_path` asked `HEAD` only, and
`HEAD` knows nothing about an incoming-only path — it would have reported
`(unattributed)` and thereby lost the ticket id the exemption matches against,
making the refusal **unexemptable even by naming the right ticket**. Both
`ticket_id_for_path` and `introducing_commit_for_path` now fall back to
`MERGE_HEAD`.

This is NOT a wiring change: the guard was already called from
`swarmforge/git-hooks/commit-msg` and ran on the offending merge. The predicate
was the defect, exactly as the ticket's note warned a first pass might misread.

  13 cases. Four new ones written RED first (10–13): an unaccounted
  incoming-side drop refused naming path/ticket/side; the same drop allowed
  when the message names the ticket; a merge keeping every incoming path
  allowed; a path dropped from both sides reported once. Before the fix, case

  deletions; `git diff --name-status 0a5bffe057 b71c941a19` → **9**. The
  second comparison is the one the guard now makes, so that merge's shape is
  refused going forward.
- `run_acceptance.sh specs/features/BL-1242-…feature` — **12/12 pass** (was
  7 scenarios, now 12).
- **Declared invariant (BL-654)**, coder-authored, in
  `extension/test/bl1341MergeDropsEitherSideInvariants.property.test.js` — 1
  passed. Each side gets its own property run, so "did we test the blind
  direction" is settled by construction, not by a lucky draw; the run fails
  unless it reached receiving-only, incoming-only, both-sides, and both message

- **Non-vacuity, shown not claimed**: removing the second `collect_deletions`
  call fails the invariant. Restored; the shell suite is ALL PASS again.

  branch carries";
- narrative gains the second direction and the `b71c941a19` incident;

One step text differs from the parked draft: scenario 04's `When the merge
would remove a path both branches carry` became `When the merge **omits** a
path both branches carry`. As written it was captured by BL-1242's existing
`the merge would remove <path>` outline step, which resolved first and failed
with "unknown path for double-report fixture". The scenario's meaning is
unchanged; only the verb moved to keep the two steps distinguishable.

does not own and whose manifest may never be hand-edited (Guardrails). Left
