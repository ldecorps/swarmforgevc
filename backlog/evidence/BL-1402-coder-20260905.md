## Scope decisions

- **Only the three call sites inside `processMessageUpdate` itself carry the
  saved-path annotation** (`postToBridge` for an existing subject,
  `deliverOperatorContext`, `openSubjectAndRecord`) — not the steering
  (`processSteeringUpdate`), onboarding, agent-questions, approvals-reject,
  or recert-amend surfaces that also call `annotateRoutedMediaText`
  elsewhere in this file. The feature file's own scenarios only exercise
  "the front desk routes the message" generically (Background: a plain
  bound group, no role/bridge/onboarding topics wired), and the ticket's
  own INVEST note says "one observable outcome... no unbuilt sibling."
  Threading the outcome through those other surfaces (each its own
  multi-parameter function chain) would have meant a materially bigger
  diff than this ticket's `slice_size_envelope: low` calls for. BL-620's
  and BL-955's own features (13/13, 8/8) still pass unchanged, confirming
  those other surfaces are untouched and their annotation stays exactly as
  before.
- **Persistence is gated on `decision.action !== 'drop'`**, computed AFTER
  `decideUpdateAction` rather than before it. The ticket's "before any
  routing decision" phrasing is about being before the caption is POSTED
  anywhere (matching invariant 1's framing: a photo that "cannot be kept"
  never blocks a caption that IS being routed) — gating this way means an
  unauthorized, wrong-chat, or captionless message never triggers a
  network fetch at all, which is both correct (out of scope per the
  ticket's own "Explicitly NOT in scope": a photo with no caption) and
  cheaper.
- **`persistRoutedPhoto` takes injectable `getFileFn`/`downloadFn` deps**
  (the same `DownloadTelegramPhotoDeps` convention
  `cursorBridgeTelegramMedia.ts` already uses for the bridge's own photo
  path), so both the unit tests and the acceptance steps drive the REAL
  store/prune/idempotency logic against a real temp directory without a
  real network call — never a hand-rolled parallel implementation of the
  store logic in the fixture.
- The `telegramCursorBridgeLive.ts`/cursor-bridge photo route (BL-696) is
  untouched — confirmed empty `git diff --stat` on that path.

## Declared invariants (BL-654)

All three have a coder-authored, non-vacuous property test in this parcel
(`bl1402FrontDeskPhotoPassthroughInvariants.property.test.js`), each shown
to fail against a deliberately broken implementation and then restored:

- **Invariant 1** (a fetch failure never blocks the caption, one audit
  line, no file written) — broken by suppressing the
  `adapters.logDropAudit?.(...)` call in `persistPhotoIfRouted`; the
  property failed on "expected exactly one audit line, got: []", the other
  two properties still passed. **Reachability floor**: asserts the
  generator drew all three named failure modes (`getFile`, `download`,
  size-cap) by name across the run.
- **Invariant 2** (BL-620's note stays byte-identical; the saved path
  always rides its own trailing line) — broken by making
  `annotateSavedPhotoPath` always append a `[image saved: ...]` line
  regardless of outcome kind; failed immediately on a `failed`-outcome
  draw. **Reachability floor**: asserts the generator drew all four
  outcome kinds (`saved`, `already-saved`, `failed`, `not-applicable`).
- **Invariant 3** (bounded + idempotent store) — has two independent
  breaks, both confirmed: (a) disabling `pruneMediaStore`'s call site
  → "store exceeded its bound: 51 > 50"; (b) disabling the
  `existingMediaFile` idempotency check → a redelivered update returned
  `'saved'` instead of `'already-saved'`. **Reachability floor**: the
  generator's `preCount` range is centered on `ROUTED_PHOTO_STORE_BOUND`
  so most draws exceed it, and `numRuns: 30` makes missing a `redeliver`
  draw astronomically unlikely; the test asserts both counters (`pruned`,
  `redelivered`) were actually reached.
