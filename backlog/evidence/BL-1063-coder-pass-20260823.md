## Defect 2 first, because it is the one that was visible

`bl796NvmNodePathFollowUpAdoptInvariants` invariant 1 is named *"both bb and
node RESOLVE, however minimal the caller PATH"* — a claim about resolvability —
and asserted node came from the **fake nvm tree**, a claim about which branch
answered. `operator_path_lib.sh` reaches nvm only as a fallback and is
*required* never to shadow a node the caller already resolves (BL-796 invariant
3). Every generated PATH contains `/usr/bin`, and this host has
`/usr/bin/node`. **The test was red exactly because production was correct.**

Now: node must resolve to a real path, and *which* branch supplied it is
checked against the dimension that decides it, not against the host.

The generator gained that dimension — `callerResolvesNodeArb` — because without
it the nvm branch was unreachable on this host and the assertion was a coin
flip about what someone had installed. The "does not resolve" half needs a PATH
with every ordinary command **except** node, so it symlinks the real search
path minus `node`/`nodejs` rather than curating a list of commands the scripts
need: a curated list goes stale silently, and its failure looks nothing like
the thing under test. The farm asserts its own premise (`command -v node` must
fail on it) before use.

Measured reach over two runs of 16: **7 caller-resolves / 5 nvm-fallback**, and
**7 / 5** again. Both branches are reached by construction.

## Defect 1: the race, reproduced rather than asserted

`start_handoff_daemon.sh` backgrounds the daemon, so `spawnSync` returning says
nothing about whether the child has run — but a plain slow child does **not**
reproduce it, and that is worth writing down. The launcher waits for
`handoffd.pid`, and the old stub wrote its marker *before* its pid, so the
launcher's own wait absorbed the delay. The real window is **after** the pid is
claimed, which is also the real daemon's shape: claim the pid, do work, report.

With the child reordered to pid → work → marker and a 0.5s delay in that window:

| | verdict |
|---|---|
| the OLD unwaited `existsSync` read | **1 failed** — *"expected the launched daemon to have run at all"* |
| the new bounded wait, same child | **3 passed** |

That is the ticket's central claim, demonstrated in both directions rather than
argued. It also explains why the flake was intermittent rather than constant.

`extension/test/helpers/waitForFileSync.js` polls and returns the instant the
marker is **complete**, with a declared deadline. Two details that matter:

- **Not existence — readiness.** The child writes through a shell redirect, so
  the file appears before its contents do. Waiting on existence alone swaps the
  race for a subtler one.
- **Synchronous on purpose.** fast-check's callbacks here are sync;
  `boundedWatchWait.js` is await-based, races a promise rather than polling a
  path, and BL-1008 records a defect in its inner deadline — so reuse would
  have been a change, not a shortcut. The inter-poll sleep is `Atomics.wait`,
  a real blocking wait with no child process.

**No fixed sleep** (QA step 5): the only `sleep` in the diff is `sleep 0.5`
inside a temporary probe that was reverted, and the stub's pre-existing
`sleep 3`. Bounded (step 3): with the stub never writing, the file fails at
exactly **10000ms** with *"…/resolved.log did not appear (or was not complete)
within 10000ms — the backgrounded child never wrote it"*. Returns early (step
4): the clean file runs in **3.5s** for 16 cases; a fixed 10s wait would be
160s.

## Declared invariants (BL-654) — both encoded, non-vacuity measured

`extension/test/bl1063BoundedWaitInvariants.property.test.js`. Invariant 1 is
quantified over the two things that actually vary — how late the child writes,
how long the deadline is — with a fake clock, so lateness no real run would hit
costs no wall-clock.

| property | clause | breaks that kill it |
|---|---|---|
| P1 | bounded | overshoot 3× |
| P2 | returns early | sleep-the-deadline-first; always-not-ready |
| P3 | never accepts a partial file | overshoot 3×; accept-mere-existence |
| P4 | armed-ness | always-not-ready |
| P5 | invariant 2: resolvability, not origin | restore the old nvm-tree assertion |

Each clause needs its own property because each is satisfiable while another is
violated: a **fixed sleep** satisfies P1 perfectly, and waiting on **existence**
satisfies P1 and P2. P4 is not optional — a wait that reports "not ready"
forever satisfies P1, P2 and P3 and does not wait at all.

**A non-result worth recording.** Removing the deadline check entirely — the
obvious break — does not fail the properties, it **hangs** them: the poll clamp
goes negative and the fake clock runs backwards. A hang is not a caught
property; the lane reports a bare framework timeout naming nothing. The break
was reshaped into a finite overshoot, which is the same defect in a form the
property can name. That is also a small lesson about the helper: the
`Math.min(pollMs, timeoutMs - elapsed)` clamp is load-bearing, not tidiness.
