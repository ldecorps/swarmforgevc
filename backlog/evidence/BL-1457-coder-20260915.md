## Invariants (BL-654)

Both declared invariants are encoded by the new handler's scenarios, not a
`*.property.test.js` file. Stated reason (same posture as BL-1486, this
ticket's acceptance-lane sibling): invariant 1 quantifies over an
enumerated, fixed set of files named in the ticket (not a generated
domain a fast-check arbitrary would range over), and the encoding is
deterministic, structural verification — running each real file twice
under a controlled child env and asserting both runs pass — rather than a
property over a pure function; there is no generator-reach concern to
assert. Building the new handler is itself "the acceptance-pipeline
components ... is regular coder work" (coder role prompt's own
exception).

- Invariant 1 ("verdict with unset equals verdict with set to 1"):
  scenario 01's four rows run each of the two fixed files, alone, with
  the hatch removed and with it forced to `'1'`, and assert full pass
  both ways — proving verdict-equality by construction for the two named
  files; scenario 03's five rows extend the same real-run proof to the
  rest of the class named in the ticket (hatch removed only, since those
  already passed both ways before this parcel per the ticket's own
  reproduction).
- Invariant 2 ("gate's own refusal untouched, no lane-wide export"):
  scenario 02 asserts no vitest config under `extension/` mentions
  `PACK_STAFFING_SKIP_GATE`; `swarmforge.sh` and
  `pack_staffing_gate_lib.bb` are untouched (`git diff` confirms no
  production line changed); the gate's own regression suite
  (`test_pack_staffing_gate.sh`) still passes unchanged.
