Then the stronger check, because two changes that cancel out survive a set of
*module names* just as a count survives a set: **per-step resolution parity**.
Every `Given/When/Then/And/But` line of every feature file was resolved against
a registry built in the OLD array order and one built in the new sorted order,
with each definition tagged by the file that registered it:

```
features 1059   steps 19693   unresolved in both 2783   MISMATCHES 0
```

Zero steps changed which FILE and which PATTERN answers them. (The 2783
unresolved-in-both are Scenario Outline placeholders my crude line extractor
does not substitute — identical on both sides, so parity holds over them too.)

Function-reference equality is NOT usable here and was not used: most step
files build their handler closures inside `registerSteps`, so two
registrations of the same module produce different function objects. The first
attempt at this comparison reported 16892 false mismatches for exactly that
reason.

## Load order: checked, not assumed

The ticket asked. Resolution is FIRST-match over registration order
(`stepRegistry.js:resolve`), so order can only matter to two DIFFERENT files
registering the same pattern **unscoped** — and BL-1277's standing guard
refuses precisely that state. A scoped registration is resolved by feature
name, never by position. The 19693-step parity run above is the empirical half
of the same answer. Discovery sorts by file name, so the order is
deterministic, just not the old append order.

## Eager, not lazy — a deliberate correction mid-pass

The first implementation loaded handlers on the first `registerSteps()` call.
That silently broke BL-968's guard: its probe decides loadability by
`require`-ing `index.js`, and BL-968 invariant 1 is a statement about what a
step file may do **at module load**. A lazy registry left that probe green on a
tree that cannot load — `bl968StepRegistryMaterializedTreeGuard` invariant 2
caught it. Discovery is now eager at module load, exactly as the array was.

## The trade this makes, stated rather than glossed

The array was explicit and greppable, and a file only joined the suite when
someone added a line — so a half-finished handler on a branch could not affect
a run. Under discovery it joins by existing. Invariant 2 is what makes that
acceptable: a file the directory cannot require fails the run loudly, naming
it, with the underlying cause preserved on the stack (a lib module several
requires deep is named too). The trade is real: a branch carrying a broken
`*Steps.js` file now breaks that branch's acceptance runs immediately instead
of at the first ticket that added a require line for it. That is a louder,
earlier failure attributed to the branch that created it — which is the
opposite of the BL-1253 shape this ticket is about — but it IS a new way for a
work-in-progress file to stop a run, and it should be known rather than
discovered.

## Decision: `check_feature_handler_registration.sh` is NARROWED, not retired

The ticket asked for a decision and said not to delete a gate as a side
effect. **It stays, narrowed.** Every offender kind survives; what narrows is
what can make a handler unreachable.

- The specifier's stage-00 reading is confirmed: `collectUnregisteredHandlers`
  skips a feature whose own handler file does not exist at all
  (`own.length === 0`), so the gate catches "handler file present but
  unreachable from the registry", never "feature file with no handler".
  Discovery retires the first kind for a CONFORMING file and leaves the second
  untouched.
- What is still refused, and is not hypothetical: a handler placed in a
  subdirectory of `steps/`, or named outside the `*Steps.js` predicate, that
  nothing discovery reaches requires. `steps/lib/androidJvmDecisionSteps.js`
  and the eleven `*Only.js` focused entry points are exactly those shapes
  today.
- `missing-registry-module`, `unreadable-handler`, `missing-sibling-script`
  and `unreadable-step-registry` are all untouched. BL-1253's second half (a
  registered handler executing an absent lib script) is not addressed by
  discovery at all.
- Left as it was: the gate had to change or it would have refused every
  commit to `main` after this lands — with no require lines in `index.js`,
  nothing would have been reachable and every feature with a handler would
  have been reported unrunnable. Verified green on this tree:
  `node out/tools/check-feature-handler-registration.js <repo> → exit 0`.
- `unreachableStepHandlerCheck` is NOT retired, as the ticket said: it asks
  whether a registered regex matches any feature step, which is a live
  question however handlers are found. Untouched.
