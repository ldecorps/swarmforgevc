# BL-1069 — coder pass (stamp-off of the landed tmux hotfix)

Reviewed commit `61c62f579` ("Land Cursor hotfix: prefer tmux >=3.7 on WSL to
stop control-plane segfaults"). This is the gate that hotfix never passed. The
landed diff is NOT re-implemented: three of its five review goals confirmed a
real defect, and each is fixed narrowly in place.

## Goal 1 — CONFIRMED, and it was the whole blind spot

`warn_if_tmux_too_old` ran `tmux -V`, which reports the client on PATH. The
incident state is precisely a client that is already fine (3.7b) in front of a
server that is not (3.4), because the server predated the install — so the
landed warning was **silent in exactly the state the crash loop lives in.**

Reproduced, not assumed. Reverting the fix to read `tmux -V` and re-running
this ticket's own suite:

```
FAIL - client 3.7b in front of a 3.4 SERVER warns (the incident state) (expected 'warned', got 'silent')
```

**Fixed**: the judgement reads `tmux -S <socket> display-message -p '#{version}'`
— the server the swarm is actually talking to. With no server answering it
falls back to the client, which is the binary the next server will be started
from, and it says which of the two it measured:

```
WARN: the control-plane server on <socket> reports tmux 3.4, below 3.7 - WSL
control-plane segfaults (resize.c NULL window, fault at 0x208) are unfixed
there. Install tmux >= 3.7 and bounce the control plane (docs/...).
```

The `ensure` branch execs before the file-scope socket resolution, so it now
resolves the socket itself — without that, the fix would be absent on
`./swarm ensure`, the one path the incident lives on. Verified against the
live swarm: the socket resolves, `#{version}` reads `3.7b`, and the check is
correctly silent.

## Goal 2 — CONFIRMED

`prefer_local_tmux_bin` prepended `~/.local/bin` whenever a tmux existed there,
with no version comparison at all: a host whose local build was OLDER than the
one on PATH was silently downgraded by the function written to upgrade it.

**Fixed**: compare before preferring. A local build that is older than the one
already on PATH, or whose version cannot be read at all, does not earn the
front of PATH. All four feature rows pass, and reverting to the unconditional
prepend fails the downgrade row immediately.

## Goal 3 — CONFIRMED soft, but ONE STATED SEAM IS NOT THE SEAM

The shell path is soft and `|| true` is the real reason: dropping it fails
this ticket's suite at once.

The bb path is soft too — but **not because of `:continue true`**. Removing
that flag from `harden-server!` changes nothing. `babashka.process/sh` does not
throw on a non-zero exit with or without it (checked directly:
`(p/sh "sh" "-c" "exit 3")` returns `{:exit 3}`; `p/shell` is the one that
throws), and the function reads no exit code. Invariant 3 holds on that path
because of the RUNNER, not the flag.

Left in place as a statement of intent, with the comment corrected to name
what actually provides the guarantee, so the dangerous future edit (swapping
`sh!` for a throwing runner, or starting to check `(:exit …)`) is visible. The
property's break is now the one that actually bites: a `harden-server!` that
propagates the failure.

## Goal 4 — THE CAPTURE PATH IS FINE; THE TILE-HEIGHT PATH IS NOT

`capture-pane -p -e -t` (`extension/src/swarm/tmuxClient.ts:206`) reads the
pane buffer and is unaffected by `window-size`.

**But `window-size largest` directly contends with the extension**, and this is
worth a follow-up. `PaneTailer.applyPaneSettings()`
(`extension/src/panel/paneTailer.ts:226`) sets `window-size manual` **globally
on the same swarm socket**, every time the role set changes, because
`resizeWindow` only sticks under manual sizing — without it "tmux sizes windows
to the latest/attached client and snaps detached windows back to 80x24"
(`tmuxClient.ts:236`). The hotfix sets `window-size largest` globally on that
same socket on every ensure, launch and plane restore. Last writer wins:

- ensure runs last → tiles lose their configured rows until the panel
  re-applies;
- the panel runs last → the server is back in `WINDOW_SIZE_MANUAL`, **which is
  the exact tmux 3.4 crash trigger** ("SIGSEGVs in resize.c on a NULL window
  whenever WINDOW_SIZE_MANUAL is set").

So the option half of the hotfix is not a safety net on a 3.4 server: the
extension re-arms the crashing state on its next `applyPaneSettings()`. That
does not refute the hotfix — the ticket's own words are "option tweaks alone do
not substitute for the version", and the version is the fix — but it does mean
`window-size largest` buys nothing durable while costing tile height. NOT
changed here: scenario 03 requires that option to still be set, and removing it
is a design decision beyond this stamp-off. Narrow follow-up requested from the
specifier by priority-00 note.

## Goal 5 — CONFIRMED on all three counts

The installer was unpinned in effect, unverified, and x86_64-only, and its
guard did not mean what it read as: `[[ -z "$SRC" || ! -x "$SRC" && ! -f "$SRC" ]]`
parses as `-z || (!-x && !-f)` because `&&` binds tighter inside `[[ ]]`, and
`find -type f` already guarantees `-f`, so the second clause was dead and the
whole test was `-z "$SRC"`.

**Fixed, narrowly — a refusal by name, not a wider installer**:

- architecture resolved against a table of builds that exist; anything else is
  refused by name rather than pointed at a URL that will 404 or at a build for
  another machine;
- the download is verified against an expected sha256 **before** anything is
  installed, so a refusal leaves nothing at `~/.local/bin/tmux`;
- the guard says what it meant.

**A deliberate behaviour change the human should know about**: with no digest
the script now refuses instead of installing. The `KNOWN_SHA256` table is
EMPTY by design — a digest is a pin, and pinning is a human commit, never an
agent action — so today the caller passes `TMUX_INSTALL_SHA256=<digest>`. The
how-to is updated to show that. A human who verifies the published 3.7b digest
can add the row and drop the env var.

Restructured into functions with a run guard so it is sourceable, the same
dual-purpose posture as `tunnel_ownership_lib.sh`. BL-971: the scratch root is
removed on the success path, the refusal path, and by an EXIT trap installed
only on the executed path (a sourced library must not trap in the caller's
shell) — caught by the repo's own `tempDirTrapGuard` while writing this.
