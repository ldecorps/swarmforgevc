# BL-1393 — coder evidence, 2026-09-04

Ticket: one closing ceremony, on every sleep after at least one shift, with the
lean pass as a named step inside it.

Human directive (verbatim, from the ticket's `source:`): *"820 should be part
of 658. rhe closing ceremony should happen each time the swarm does at least 1
shift and goes to sleep."*

## What shipped

**One sequence.** `nightClosingCeremonyLive.ts` — the state machine both
triggers share — gained the lean pass as a step and the no-work path as an
outcome:

- `lean-packet` is emitted **after the parcel's fate is settled** (drained or
  parked, so the ledger it folds is complete) and **before the briefing is
  instructed** (the specifier reads the packet while the documenter writes the
  day). It is one step of this sequence, not a second mechanism beside it.
- `record-empty-outcome` + `night-stop` replace the whole ceremony when the
  swarm worked no shift since the last one: promotion still freezes, the swarm
  still sleeps, but no documenter is woken for an empty day and the outcome is
  written rather than left silent.
- `workedAShift` is **optional and defaults to true**: every pre-BL-1393 caller
  meant "a night that is due", and a missing field must never silence a real
  ceremony.

**The runner** (`night-closing-ceremony-run.ts`) imports `runClosingCeremony`
(wiring anchor 2) and drives it as the `lean-packet` step, adds
`--sleep-path <name>`, and computes `workedAShift`:

- `--sleep-path` says *"this stop is a sleep"*. The ceremony then runs whatever
  the hour, while the **daemon's own trigger stays gated by its closure
  window** — which is what keeps this ticket from changing the schedule.
- `shiftWorkedSinceLastCeremony` compares the newest of
  `.swarmforge/shift-started` / `.swarmforge/swarm-identity` against the newest
  file in `.swarmforge/lean/ceremony/`. It **fails OPEN**: a probe that cannot
  tell returns true, because the empty-outcome path is for a swarm that
  demonstrably did nothing, never for a stat that failed.

**Every sleep path drives it.** `finish_shift_lib.sh`'s
`finish_shift_run_closing_ceremony` now runs
`night-closing-ceremony-run.js --sleep-path finish-shift` (wiring anchor 1);
the direct BL-820 CLI call is **removed, not re-shipped beside it** — dead
logic removed, as the ticket directs. `./finish-shift` still calls the same
named step, so BL-820's own acceptance (12/0) is untouched. A missing compile
stays a loud skip, never a bedtime failure (BL-762's contract).

**"Did at least one shift" is checkable** from what the launch already writes:
`.swarmforge/swarm-identity` is rewritten by `swarmforge.sh` on every launch,
so its mtime IS the shift start, and it is compared against the newest recorded
ceremony outcome.

I first added an explicit one-line `.swarmforge/shift-started` stamp beside it
in `write_swarm_identity_file`, because a derived answer breaks the moment
anything else rewrites that file. **`bl1328QwenModelTokenFormsInvariants`
refuses it**: that property requires every executable line added to
`swarmforge.sh` (diffed against `main`) to sit inside BL-1328's own detection
helper — a guard pinned to one parcel's diff that now binds every later parcel
touching that file. The line is dropped rather than fought; the reader still
looks for `.swarmforge/shift-started` first, so whoever lifts that guard need
only add the stamp. Surfaced below, not fixed here.

**Both predecessors' narratives are re-tensed** under the ticket's `retires:`
scope exemption, no scenario retired: BL-658's title said the ceremony "ends
the night" (it now ends any shift) and BL-820's header said the lean pass is
invoked by finish-shift as its own mechanism (it is now a step of the one
ceremony). BL-658's handler `FEATURE` constant moved with its title in the same
commit, or discovery would scope its steps to a feature name that no longer
exists. **BL-658's mutation manifest is left byte-untouched** for the toolchain
to regenerate — never hand-edited (nothing in the commit chain or the
acceptance runner reads that stamp, so it gates nothing meanwhile).

## The property tests found a real defect

Invariant 3 failed on its first run: a ceremony that starts with the day's
briefing **already sent** short-circuited to `freeze-promotion ->
briefing-already-sent -> swarm-stopped` — no packet, no outcome,
**indistinguishable from a ceremony that never ran**, which is exactly what
"every ceremony ends in a recorded outcome" (BL-820's own human decision, "a
silent ceremony is a failed ceremony") forbids. The shift still happened; only
the briefing was already done. Fixed: that path now delivers the lean packet
before stopping.

A second finding was in my own generator, not the code: stepping the clock by
half an hour per tick passed the 25-minute drain budget before any parcel could
finish, so `parcel-drained` was **unreachable** and 30/30 runs parked — the
"deep state is technically reachable but astronomically rare" shape the coder
contract names. The driver now steps five minutes and the draw decides whether
the parcel clears inside the budget; both branches are asserted reached.

## One path this repo cannot reach

The ticket lists `night-stop.sh` among the sleep paths that must drive the one
sequence. **There is no `night-stop.sh` in this repository** — it lives in the
operator directory outside the checkout (`legacy_operator_schedule_lib.bb`
references `<operator>/night-stop.sh`), so this parcel cannot edit it. What is
in reach is done: `finish-shift` is the in-repo sleep verb, and
`wait_for_expedite_then_bedtime.sh` and the crontab bedtimes all go through it,
so every sleep this repo owns drives the one sequence. The feature's
`night-stop` outline row is answered by that same claim rather than by an edit
to a file that is not here, and the operator-dir script needs the same one-line
re-point when someone with that directory makes it — worth its own ticket.
