# BL-677 — coder, 2026-09-18

## What was built

`swarmforge/scripts/epic_backfill_apply_lib.bb` (pure library) +
`swarmforge/scripts/epic_backfill_apply.bb` (thin CLI wrapper), applying a
human-approved epic-backfill mapping (BL-676's own report, amended and
approved by a human) into `backlog/done/` ticket YAMLs, batched through the
shared commit-integrity path.

Behavior implemented per the ticket's `description:`:
- Refuses the whole run, writes nothing, when the mapping carries no
  `human_approval: approved` line.
- Refuses the whole run, before any write, when any non-empty proposal cell
  names a value that is neither in the `type: epic` roster nor the
  documented pre-epic-era sentinel (`refusal` checks in order:
  not-approved → stale-mapping → unknown-epic, so a typo never gets to
  scatter partial writes).
- Refuses the whole run when a mapping row names a ticket id with no file
  under `backlog/done/` (stale mapping against the tree).
- A target ticket that already carries a non-empty `epic:` is skipped and
  reported, never overwritten — `classify-row` treats this the same
  whether the existing value matches the proposal or differs.
- Empty proposal cells (needs-judgment left unfilled) are skipped and
  reported, not treated as refusals — matches the approval_context's
  decision 3 (the backfill can land in waves).
- Writes land as batched commits via the injected `:commit-batch!` seam
  (defaults to `commit-integrity-lib/commit-with-integrity!`), never one
  commit per ticket; `partition-into-batches` defaults to batch size 25.
- Re-running after a successful apply finds every target already tagged
  (`skip-already-tagged`), so it writes and commits nothing — idempotency
  falls directly out of `classify-row`'s logic, no separate special case.
- `epic-roster` is built from the FULL ticket set (every backlog pool via
  `epic-backfill-proposals-lib/epic-roster`), not just `backlog/done/` —
  matching BL-676's own `generate-report!`, since an epic's own defining
  ticket may live outside `done/`.

## `commit_integrity_lib.bb`, not `commit_integrity_cli.bb` — deliberate

The ticket's `approval_context` names `commit_integrity_cli.bb`, but that
CLI's own doc comment says it exists for "shell-driven writers on a shared
checkout" that are not themselves Babashka processes, and it additionally
wires `ticket_close_guard_lib.bb`'s active/→done/ close-move validation —
irrelevant here, since this apply only ever edits tickets already resting
in `backlog/done/`, never moves one there. `epic_backfill_apply_lib.bb` is
already a bb process, so it calls the CLI's own underlying
`commit-integrity-lib/commit-with-integrity!` directly: the same locked,
pathspec-scoped, verify+retry commit, without the inapplicable close-guard
hook. Documented inline at the call site.

## Declared invariants — property tests (BL-654, caught by the pre-forward self-audit)

The ticket's `invariants:` YAML list carries three entries. First authorship
of each rests with the coder (coder.prompt's Invariants section); the
Babashka unit suite alone does not satisfy this — the audit gate caught
that `*.property.test.js` coverage was missing from the first candidate.
Added `extension/test/bl677EpicBackfillApplyInvariants.property.test.js`,
one property per invariant, each driving the REAL `epic_backfill_apply.bb`
CLI (real `apply!`, real `commit_integrity_lib.bb` commit) against a real
fixture git repo under mkdtemp — same posture as
`bl676EpicBackfillProposalsInvariants.property.test.js` (the predecessor
slice) and bl760/bl787/bl797's real-subprocess properties. A fresh `git
init` fixture carries no hooks (this repo's `core.hooksPath` is a
per-checkout `.git/config` setting, never inherited by a new repo), so no
guard chain can fire from inside a draw's own commit.

- Invariant 1 (never overwrite): every pre-tagged ticket's proposal is
  DERIVED to be a different valid value than its current tag (never
  independently drawn), so the property tests the "propose something
  different and see if it sticks" shape, not a coincidental match.
- Invariant 2 (unknown value refuses before any write): the unknown value
  is a fixed constant containing a dash, which `identArb`'s pattern can
  never itself produce and which isn't the sentinel — unknown by
  construction, never by chance exclusion. Its position among the rows
  varies per draw.
- Invariant 3 (re-run is a commitless no-op): every row gets a real
  proposal against an untagged ticket, so the first run is guaranteed to
  write and commit something before the second run's "nothing changes" is
  checked.

Non-vacuity (checked by hand, documented in the file's own header
comment): each property was run against a deliberately broken
`epic_backfill_apply_lib.bb` and observed to fail, then the library was
restored (diffed byte-identical against the pre-mutation copy) and
re-verified green. Invariant 3's first mutation attempt reused the same
mapping text for both runs, so a "differs from proposal" mutation went
uncaught by construction (current-epic ends up equal to the proposal on
the second run either way) — documented as a dead end in the file's own
comment; the mutation that actually breaks the invariant (removing the
already-tagged guard entirely, so `with-epic-line` double-inserts) does
fail it.

Measured cost: ~50ms per real apply+commit cycle on this host (no hooks,
small fixture) — two orders of magnitude below this codebase's
mailbox/tunnel-heavy properties. Full file run: 3 tests, ~6-7s.

## Testability boundary

Kept ALL decision logic (approval check, refusal ordering, row
classification, batch partitioning, epic-line insertion) in the pure
library, unit-tested with no git involved
(`epic_backfill_apply_lib_test_runner.bb`). The real write+commit path
(actual file mutation, actual `git commit` through commit-integrity) is
exercised only by the acceptance suite against a real fixture repo under
mkdtemp — matching this project's testability-boundary convention (a live
git checkout is not a fast unit fixture).
