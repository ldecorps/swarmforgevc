# BL-677 — coder, 2026-09-18

## What was built

`swarmforge/scripts/epic_backfill_apply_lib.bb` (pure library) +
`swarmforge/scripts/epic_backfill_apply.bb` (thin CLI wrapper), applying a
human-approved epic-backfill mapping (BL-676's own report, amended and
approved by a human) into `backlog/done/` ticket YAMLs, batched through the
shared commit-integrity path.

Behavior implemented per the ticket's `description:`:
- Refuses the whole run, writes nothing, when the mapping carries no
  `human_approval: approved` line.
- Refuses the whole run, before any write, when any non-empty proposal cell
  names a value that is neither in the `type: epic` roster nor the
  documented pre-epic-era sentinel (`refusal` checks in order:
  not-approved → stale-mapping → unknown-epic, so a typo never gets to
  scatter partial writes).
- Refuses the whole run when a mapping row names a ticket id with no file
  under `backlog/done/` (stale mapping against the tree).
- A target ticket that already carries a non-empty `epic:` is skipped and
  reported, never overwritten — `classify-row` treats this the same
  whether the existing value matches the proposal or differs.
- Empty proposal cells (needs-judgment left unfilled) are skipped and
  reported, not treated as refusals — matches the approval_context's
  decision 3 (the backfill can land in waves).
- Writes land as batched commits via the injected `:commit-batch!` seam
  (defaults to `commit-integrity-lib/commit-with-integrity!`), never one
  commit per ticket; `partition-into-batches` defaults to batch size 25.
- Re-running after a successful apply finds every target already tagged
  (`skip-already-tagged`), so it writes and commits nothing — idempotency
  falls directly out of `classify-row`'s logic, no separate special case.
- `epic-roster` is built from the FULL ticket set (every backlog pool via
  `epic-backfill-proposals-lib/epic-roster`), not just `backlog/done/` —
  matching BL-676's own `generate-report!`, since an epic's own defining
  ticket may live outside `done/`.
