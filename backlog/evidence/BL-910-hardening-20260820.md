## Hardening changes made

### D1 — the step file required the gitignored build output at module load (BL-968 class)

`bl910BriefingBurndownEtaSteps.js` required `extension/out/metrics/*` at
**module top level**. `specs/pipeline/steps/index.js` requires every domain
eagerly, so in any tree where `extension/out/` has not been built — a tree
materialized from git, which is exactly what the BL-761 acceptance gate does —
requiring the step registry throws at load. That is the defect class BL-968 was
minted for ("three step files bind `resolveMainCheckout` at module load … the
gate is blind on effectively every send").

Its own sibling on this chart, `bl896BriefingOpenTicketChartSteps.js`, already
does this correctly and says why: the compiled module is required **lazily**,
inside the functions that use it. BL-910 now mirrors that. Behaviour is
unchanged (acceptance still 9/9 after the change — the acceptance run above ran
against the edited file).

### D2 — differential complexity regression in `buildNotDoneBurndownSvg`

Measured with the project's own `crapLib` AST walker, each changed function
against `main`'s version of that function:

```

```

The parcel added a guard `if` and a two-branch ternary directly into an
already-large renderer. Both sides were under the CRAP threshold, so the
absolute check reads identically before and after and hides this — the exact
BL-956 shape the differential rule was accepted for. CRAP also grows
superlinearly with complexity, so the new caption would have inherited a score
it did not earn (the BL-866 dispatcher lesson, same mechanism, different file).

Fixed by extracting the guard and the two-branch caption into a pure exported
`formatProjectionLine(projection)` in the same module — a behaviour-preserving
testability split, which is this role's own domain. After extraction:

```

notDoneBurndown.ts:      no function rose; projectNotDoneEta=2, yyyyMmDd=1
```

No function in either changed file is now above its `main` baseline.

### D3 — assertion gaps the existing suite could not see

Five tests added to `extension/test/notDoneBurndown.test.js`. Each closes a gap
where a mutant would have survived, not a restatement of coverage already there:

1. **The eta caption's net-burn figure.** Nothing asserted the `at net burn
   2.0/d` half of the line, so `toFixed(1)` → `toFixed(0)` survived.
2. **The not-shrinking caption in full.** Neither the `(net burn …/d, all open
   tickets)` suffix nor the negative-rate rendering was asserted anywhere.
3. **`netBurnPerDay` on the no-eta path.** Asserted only for the eta branch, so
   the `netBurnTenths / 10` reconstruction was unguarded when there is no date
   — including the rounded-from-noise case.
4. **The guard as its own unit.** `formatProjectionLine(undefined)` throws,
   testing the required wiring at the function that now owns it.
5. **Placement — the human's explicit decision.** The ticket chose "the caption,
   not a dashed overlay line". Nothing checked it: the heading, subtitle and
   projection `y` ordinates are now asserted in order, and the projection is
   asserted to sit strictly above the first gridline, i.e. clear of the plot
   area. This kills the layout-constant mutants (`padT`, the caption's `y`)

   decision rather than the literal.

## D4 — BLOCKED / SPEC GAP: this parcel breaks BL-896's acceptance, deterministically

**Not fixed here — it needs a specifier ruling, and it is recorded rather than
worked around.**

`specs/pipeline/steps/bl896BriefingOpenTicketChartSteps.js` implements BL-896's
step `And it projects no completion date` as:

```js
if (/complet/i.test(ctx.burndownSvg) || /\bETA\b/i.test(ctx.burndownSvg)) {
  throw new Error(`expected no projected completion date; got: ...`);
}
```

BL-910 renders `no ETA — backlog still growing` on a not-shrinking chart. That
string contains `ETA`, so the step throws.

Reproduced in-process against BL-896's own fixture (8 tickets filed, 1 closed
over a 30-day window — the fixture asserts `net > 0` by construction, so the
chart is ALWAYS on the not-shrinking branch, never the eta branch):

```

projection = {"kind":"no-eta","netBurnPerDay":-0.3,"reason":"no ETA — backlog still growing"}
/complet/i   -> false
/\bETA\b/i   -> true          <-- step throws
```

This is deterministic, not load-flaky: BL-896 scenario `briefing-open-chart-01`
fails on every run once BL-910 lands. It passed before this parcel (there was no
projection line at all).

**Why this is a spec gap and not a defect I should fix.** The contradiction is
between two human rulings and only the human's later one resolves it. BL-910's
`source:` carries decision 3 verbatim — *"Add a projected ETA the human can read
at a glance"* — and decision 1, *"The chart stays. The 2026-07-26
PWA/milestone-burndown ban does not apply here (recorded on BL-896)."* So the
substance is settled: this chart carries a projection. What is NOT settled is
BL-896's scenario, whose English sentence — `And it projects no completion date`
— is now false of the chart it describes. Narrowing only the handler regex would
leave a green scenario whose text asserts the opposite of what the chart does:
a test that reads as coverage and proves nothing. Rewriting the scenario text is
a requirements change on a landed ticket, which is the specifier's call, not
mine.

**And the obvious dodge is not available.** The colliding string is not the
implementer's wording — it is the human's, verbatim in BL-910's own `source:`
block: *"If net burn ≤ 0, render 'no ETA — backlog still growing' (never
'never', never a fabricated infinity)."* Quietly rewording it to slip past
BL-896's regex would drop a human sentence to make a test green, which
Article 5.3 forbids outright. The collision has to be resolved on BL-896's
side or not at all.

The irony worth naming for whoever rules on it: the string that trips the guard
is BL-910's *refusal* to project — the exact behaviour BL-896's step wanted.

Leaving as a `note` at priority `00` to specifier AND coordinator per Article
4.4 (a spec gap travels by note, never as a parcel, and is not a bounce). The
