## Gotcha (debugged, not a regression)

Batching invariant 3's `land-step-lib/own-paths` calls into one bb process
at first appeared to break case 0 (`shape=merge addTestFile=true`): `land`
came back `nil` instead of `[]`. Isolated it to NOT being a batching
artifact - a single, unbatched `own-paths` call on that exact fixture also
answers `nil`. `own-paths` (BL-1343) legitimately REFUSES (nil + warning)
whenever a commit's full origin-main..tip diff is non-empty but every
path is attributed to an unlanded sibling (here, every non-evil INV3
shape tags its content `OTHER`, a real ticket id) - as opposed to a
genuinely empty diff, which answers `[]`. The ORIGINAL `threeCallers`
never surfaced this because it wraps the answer in `(vec (sort land))`
inside the bb script, and `(sort nil)` is `()`, so `(vec (sort nil))` is
`[]` - silently coercing the refusal into an indistinguishable empty
answer, which happens to satisfy the `authored=[]` assertion by
coincidence for these shapes. My first batched draft returned `land` raw
(preserving nil faithfully) and exposed this pre-existing coercion for
the first time. Since fixing `own-paths`'s refusal semantics or the
test's oracle is explicitly out of scope (`Not in scope`: BL-1297's own
feature/behavior untouched), `threeCallersBatch` keeps the exact original
`(vec (sort ...))` coercion for `gate`/`land` so every existing assertion
means exactly what it meant before this ticket.

## Invariants (BL-654)

This ticket's declared invariant - *"The number of bb processes a run of
this file starts is bounded by its number of invariants, never by its
number of fixture cases or fast-check draws"* - is process/environment
behavior across a real subprocess boundary (bb process count), not a
pure module a `fc.property` could exercise from inside the file itself:
counting it requires a real counting shim wrapped around a real
subprocess run of the LIVE file, which is exactly feature scenario 02 /
step handler `the shim counted at most 3 bb processes`. Same posture
BL-1556 recorded for its sibling class. No separate `*.property.test.js`
encodes it; the acceptance scenario is the executable encoding.
