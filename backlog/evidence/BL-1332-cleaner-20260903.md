## Observation for downstream (not a bounce, not fixed here)

Scenario 04 ("A produced tip satisfies the guard that froze main") asserts
only `r.status !== null` on the spawned `check_feature_handler_registration.sh`
process — that proves the guard process *ran* (was not killed by a signal),
not that it *passed* (exit 0), even though the Gherkin's own Then-text says
"the guard passes." `spawnSync`'s `status` is non-null for any exit code
the guard could return, including a genuine registration failure or an
unrelated crash (checker missing, node absent), so this scenario would
report green even if the guard were broken. It does not currently mask
anything real — `ownPaths.paths === null` is already asserted first, so no
bad tip is ever produced for the guard to react to either way — but the
scenario proves less than its own name claims. Worth a tightening pass
(`assert.equal(r.status, 0, ...)`) whenever an acceptance-owning role is
next in this file. Also noticed: the `SWARMFORGE_ROLE: 'QA'` env passed to
the guard spawn is unused by `check_feature_handler_registration.sh` (it
only reads git branch) — harmless, likely copied from elsewhere.
