# BL-1489 — coder implementation, 2026-09-13

## What changed

`specs/pipeline/steps/bl982SecondSeatSteps.js`: scenario 04's Then handler
("every session, worktree, launch script and prompt path is unchanged from
before this slice") no longer byte-compares the whole `.swarmforge/roles.tsv`
between the live root and the pre-change (blob-pinned) root. It now compares
only the fields the scenario names — role-keyed `worktree` (col 3) and
`session` (col 4), root-normalised the same way the old whole-file compare
was — via two new exported functions, `singleSeatFieldsByRole` and
`compareSingleSeatRolesTsv`. The launch-script-name and prompt-artifact-name
checks are untouched. `bl982SecondSeatSteps.js` also now exports
`SINGLE_SEAT_CONF`, `mkRoot`, `cleanupRoots`, `zshSource` and
`compareSingleSeatRolesTsv` for BL-1489's own handler file to reuse rather
than restate.

New file `specs/pipeline/steps/bl1489Bl982HandlerComparesNamedFieldsSteps.js`
(required_wiring) registers BL-1489's three scenarios:
- Scenario 01 drives the REAL `run_acceptance.sh` against BL-982's REAL
  feature file and asserts `# pass 6` / `# fail 0` (was `# pass 5` / `# fail
  1` before this fix — reproduced below).
- Scenario 02 provisions two real single-seat roots via the real launcher,
  patches a seam copy's roles.tsv to append an extra column to every row,
  and asserts `compareSingleSeatRolesTsv` still passes.
- Scenario 03 (outline: session | worktree) provisions two real roots,
  patches a seam copy's coder row to a different value for the named field,
  and asserts `compareSingleSeatRolesTsv` fails, naming that field.

The seam roots are built from the real provisioning path
(`parse_config; write_roles_file; generate_dormant_role_launch_artifacts`)
and then patched on disk for the one field each scenario names — not a
hand-patched copy of `swarmforge.sh` — so the seam can't silently drift from
what the real launcher actually writes.

`backlog/active/BL-1489-*.yaml` moves with this parcel unedited; the
standing-red register row (`backlog/standing-reds.tsv` line 39, owner
BL-1489) is left for the documenter to remove per this ticket's own "How"
section, not touched here.

## Invariants (BL-654)

The one declared invariant — "BL-982's single-seat comparison asserts only
the fields its scenario names ... and passes when any other roles.tsv
column differs" — is encoded, not left unencoded, but the encoding is
BL-1489's own acceptance scenarios 02/03 above, not a `*.property.test.js`
file. Stated reason: `compareSingleSeatRolesTsv` lives in
`specs/pipeline/steps/`, the acceptance-pipeline module tree, not
`extension/src` — it is outside the testable-module boundary the
`test:properties` lane (`extension/vitest.properties.config.mjs`) covers,
and this ticket's own `acceptance:`/`required_wiring` fields already commit
its invariant to a Gherkin Scenario Outline (arbitrary extra column;
changed session/worktree, constructed to the transformation the invariant
actually quantifies over) built and run against the real launcher, which is
the acceptance-pipeline-work exception in the coder role prompt ("building
or fixing the acceptance-pipeline components themselves ... is regular
coder work"). No fast-check generator applies here since there is no
`extension`-side pure module to attach one to.
