# BL-1554 — coder evidence, 2026-09-16

## The fix (new feature)

`extension/src/quality/qaGather.ts` — the checklist definition, the
sequential runner loop, and the register join, all pure/testable and
driven through one injected `RunFn` seam (`defaultRunFn` wraps
`spawnSync` for production; every test drives a fake):

- `CHECKLIST`: the 8 fixed checks in the fixed order (`stragglers_before`,
  `sibling`, `register`, `wiring`, `unit`, `properties`, `acceptance`,
  `stragglers_after`), each an EXISTING owner CLI/npm script invocation —
  never a reimplementation. `wiring` blocks itself (no `runFn` call at
  all) when `--task` is absent; `acceptance` blocks itself when the
  ticket declares no `acceptance:` path.
- `runChecklist`: a plain sequential `for...of` over the checklist —
  never `Promise.all`/concurrent scheduling — producing one `CheckRow`
  per check (`id`, `command`, `cwd`, `status: 'ran'|'blocked'`, `exit`,
  `duration_ms`, `excerpt`, and `reason` when blocked). No row, and no
  top-level report field, ever encodes a verdict.
- `readAcceptancePath`/`findTicketYamlContent`: mirrors
  `task_scope_gate_lib.bb`'s own `declared-acceptance-path`/id-matched
  lookup exactly (single-line scalar only; id: field match across
  active/paused/done, done nested by milestone) — the one YAML field this
  tool reads for itself, never a second acceptance-path convention.
- `buildRegisterJoin`/`parseFailingFilesFromVitestOutput`/
  `failingFilesFromRow`: parses failing file names from the `unit`/
  `properties` rows' own vitest-shaped `FAIL` lines, and from the
  `acceptance` row's own declared feature path on a non-zero exit: joins
  each against the `register` check's own parsed JSON (`owned`/`unowned`/
  `absent`), never re-deriving ownership itself.
- `gatherQaChecklist`: the one impure entry point — resolves the
  ticket's acceptance path, runs the checklist, builds the join, returns
  `{ticket, task, commit, root, checks, register_join}`. No verdict field
  anywhere in this shape.

`extension/src/tools/qa-gather.ts` — thin CLI wrapper (`main()` only
parses argv via `parseArgs`, resolves `--root`/`--commit` defaults, calls
`gatherQaChecklist`, and prints via `printJsonToStdout`). No branch ever
sets `process.exitCode` on the success path, so the tool exits 0
whenever a report was printed, regardless of what any check returned —
by construction. `parseArgs` returns `undefined` with no `--ticket`,
`main()` prints usage and exits 2 in that case only.

Covers: the fixed checklist shape/order; `runChecklist`'s never-skip-a-

(dedup, clean-output-yields-nothing); `failingFilesFromRow`'s per-id
dispatch (unit/properties via the parser, acceptance via its own declared
path on non-zero exit, nothing from a blocked row); `buildRegisterJoin`'s
owned/unowned/absent classification against a real register-CLI-shaped
JSON object, and its no-register-data-means-everything-absent case;
`readAcceptancePath`'s scalar/block-form/absent handling;
`findTicketYamlContent`'s real-fixture lookup across active/done
(nested by milestone), including the BL-992 filename-prefix-collision
guard (`BL-15540` never resolves a `BL-1554-FIX` lookup); `gatherQaChecklist`
end to end over a fake runner and a real ticket-YAML fixture.

`qaGatherCli.test.js`: `parseArgs` (required `--ticket`, every flag read,
partial-flags left `undefined`); `main()`'s only seam-free branch (no
`--ticket` → usage + exit 2, never a crash) — the happy path is
deliberately NOT exercised here (see note below).

**Why `main()`'s happy path isn't unit-tested**: `gatherQaChecklist`'s
DEFAULT `runFn` is a real `spawnSync` — running it from inside a unit
test would spawn `npm test`/the property lane/a real acceptance run
FROM INSIDE the very suite that's already running them, the nested-suite
problem the engineering rules exist to prevent. That coverage is the
acceptance suite's own job, over an injected fake runner (see Acceptance
below) — exactly the shape BL-1554's own feature file specifies.

## Declared invariants (BL-654)

1. "The report and the tool's exit status never encode a verdict..."
2. "Every check runs the existing CLI or npm script that owns it as a
   child process through one injected runner seam, and the register join
   reads the register CLI's JSON..."
3. "Checks start in the fixed order, each only after the previous has
   ended; a check that cannot start is reported blocked with its reason
   and every later check still runs..."

**Invariants 1 and 3**: coder-authored property test,
`extension/test/qaGather.property.test.js` (fast-check, 200 runs).
Generates, per check, either a runner-cannot-start answer (random reason)
or a started answer with a random exit code (0-255) and freeform output
text deliberately peppered with "pass"/"BOUNCE"/"approve this" etc. (to
prove those words survive harmlessly in excerpt text without leaking into
any STRUCTURAL field), plus independently toggles whether `--task`/the
acceptance path are present (the OTHER way a check can fail to start —
its own build() blocking it before `runFn` is ever consulted). Asserts:
every run has exactly `CHECKLIST.length` rows in exactly `CHECKLIST`'s own
id order (never omitted); every blocked row carries a non-empty reason;
the fake runner's own call log, compared against an INDEPENDENTLY
computed expected sequence of built `(command, args, cwd)` tuples (not a
content-guess made at call time — `stragglers_before`/`stragglers_after`
build an identical command, so identity there is POSITION in the
expected sequence, established before the run), matches exactly, in
order, once each; no row ever carries a `verdict` key.

**Non-vacuity, proven by hand**: commented out the `wiring` check inside
`runChecklist`'s loop (a deliberate omission). Both the property test and
2 of the plain unit tests failed immediately (row count 7 instead of 8;
the strict start/end alternation lost a pair). Restored and reconfirmed
19/19 unit + 1/1 property green.

**Invariant 2** is a structural/process claim about this module's own
source shape, not a generative data claim — recorded with a stated reason
rather than forced into a property: `runChecklist` has exactly ONE call
site of `runFn` (verified by inspection, and implicitly by every test
above, none of which could pass if a check's command were invented
in-process instead of routed through the seam); `buildRegisterJoin` takes
an already-parsed `RegisterReport` and only reads its `owned`/`file`
fields, never re-deriving `real-ticket-state` itself — the register-join
unit tests exercise this parse-then-join path directly against real
register-CLI-shaped JSON.

## Dependency-gate split (found by the pre-commit property lane, fixed same pass)

`.dependency-cruiser.cjs`'s `no-io-from-policy` rule (BL-259 hard gate)
forbids `fs`/`child_process` imports from `src/quality/` - the original
single-file draft had `qaGather.ts` importing both directly (`defaultRunFn`
via `spawnSync`, `findTicketYamlContent` via `fs`), caught by
`bl759CursorOperatorFrontDeskCycle.property.test.js`'s full-repo dependency
gate. Split to the SAME shape as `siblingDeferral.ts`/`siblingDeferralStore.ts`
and `bounceRevertVerdict.ts`/`bounceRevertGitAdapter.ts`:

- `extension/src/quality/qaGather.ts` stays pure - no fs/child_process
  import. `gatherQaChecklist` (the impure entry point) is now
  `composeQaGatherReport`, taking the ticket's already-read YAML content
  as a parameter instead of reading it itself.
- `extension/src/metrics/qaGatherAdapter.ts` (new) holds `defaultRunFn`
  and `findTicketYamlContent` (both real IO) and re-exports the impure
  `gatherQaChecklist(root, ticketId, opts, runFn?)` entry point that
  resolves the YAML then calls `composeQaGatherReport`.
- `extension/src/tools/qa-gather.ts` (the CLI) and
  `specs/pipeline/steps/bl1554QaGatherReportSteps.js` now import
  `gatherQaChecklist` from the adapter, not from `quality/qaGather`.
- `extension/test/qaGather.test.js` splits its imports the same way
  (pure functions from `out/quality/qaGather`, `findTicketYamlContent`/
  `gatherQaChecklist` from `out/metrics/qaGatherAdapter`) - no test
  behavior changed, only the require paths.

Re-verified after the split: 19/19 unit (`qaGather.test.js` +
`qaGatherCli.test.js`), 1/1 coder-authored property test, 9/9 acceptance
scenarios, `tsc --noEmit` clean, and both previously-red property files
(`bl1280MkdtempMigrationInvariants.property.test.js`,
`bl759CursorOperatorFrontDeskCycle.property.test.js`) green.

## Raw-mkdtemp convention fix (same pass)

Two more pre-commit findings, both migration-guard violations, not
correctness bugs:

- `extension/test/qaGather.test.js`'s two `fs.mkdtempSync(path.join(os.tmpdir(),
  ...))` fixture roots now go through the shared `mkTmpDir` helper
  (`test/helpers/tmpDir.js`, BL-420) - caught by
  `bl1280MkdtempMigrationInvariants.property.test.js` invariant 2. The
  `try/finally` + manual `fs.rmSync` teardown these two tests used is
  removed; `mkTmpDir` registers the dir for the shared per-test afterEach
  sweep instead, matching every other test in this suite that uses it.
- `specs/pipeline/steps/bl1554QaGatherReportSteps.js`'s own fixture root
  used the same raw pattern; the steps lane's own required route is
  `mkSocketFixtureRoot` (`specs/pipeline/steps/lib/socketFixtureRoot.js`,
  BL-1226's `pilotMkdtempConventionCheck.ts` gate on touched
  `specs/pipeline/steps/*.js` files) regardless of whether the fixture
  needs a socket - switched, which also picks up that helper's exit-time
  cleanup (the fixture root had no cleanup at all before).
