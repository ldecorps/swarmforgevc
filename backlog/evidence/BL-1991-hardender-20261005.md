  `write|writes|edit|edits`, and the ticket's own FIRM approval text says
  "names a write OR AN EDIT" - but every scenario (acceptance, property)
  only ever phrases a next-step with "Write ...". Hand-removing the
  `edit|edits` alternative left every existing test green. Closed with a
  direct unit-style test driving `named-write-path`/`restart-decision`
  with "Edit ..."/"... edits ..." phrasings; confirmed it fails against
  the mutant, restored green.
- **The missing-event-cwd safety fallback.** The coder's own commit
  message names this as the central safety fix: "restart state now only
  ever reads an explicit event cwd" (never the process's own cwd - the
  exact hazard that already caused one real incident in this worktree
  during the ticket's own trial run). No test ever omits the event's
  "cwd" to prove the fallback stays gone; every fixture always sets one.
  Hand-mutating the guard back to the dangerous fallback shape
  (`(and entries (string? restart-cwd))` -> `(and entries true)`, plus
  re-adding `(or (get event "cwd") (System/getProperty "user.dir"))`)
  left EVERY test green: acceptance 4/4, both shell regressions, both
  property invariants. Closed with a test that omits the event cwd
  entirely - but pins the `bb` SUBPROCESS itself to a disposable sandbox
  (via `spawnSync`'s own `cwd` option, distinct from the event's own
  "cwd" field) so that even a reintroduced `user.dir` fallback writes
  into the sandbox, never this real worktree, making the test safe to
  run against a buggy implementation by construction. The test's FIRST
  draft was itself vacuous - it built an empty sandbox with no
  `.swarmforge/handoffs/inbox/in_process/` fixture, so
  `restart-state-file` returned nil regardless of the mutant (its own
  precondition was never met) - caught by re-running the same hand-mutant
  against the first draft and seeing it still pass; fixed by seeding the
  in_process handoff file the real precondition requires, then
  re-confirmed the mutant fails.
