## Correctness read — the mechanism

Confirmed the root cause by reading the two attribution walks directly:
`task-tagged-changed-paths` (per-sibling, ticket-level verdict) walks
`rev-list --first-parent`, while `path-owner-tickets` (per-path, what
`own-paths` actually excludes on) walks `git log -- <path>` across every
parent. A sibling's exclusively-owned file reaching the tip via a merged
side branch is invisible to the first walk (so the sibling can read
"landed" off its first-parent-visible files alone — a feature file, an
evidence file) while fully visible and correctly attributed to that
sibling by the second walk. The fix is structurally sound: `own-paths`'
exclusion now asks the PER-PATH question (`sibling-path-landed-fn`) as a
second arm, reached only when the cheap per-ticket check says landed —
so the common case (every owner still unlanded) pays nothing extra, and
`delivered-attribution` is deferred behind a `delay` so a clean land with
no entangled sibling never computes it at all. This directly addresses
the property-test timeout regression the coder found and fixed in their
first draft (asking the per-path question unconditionally blew the land
property runners' time budget).

The two invariant halves are correctly separated and independently
testable: invariant 1 (path exclusion, self-sufficient regardless of the
sibling's ticket-level verdict or approval state) and invariant 2 (the
ticket-level verdict itself made per-path-complete via `extra-paths-fn`,
which threads the per-path walk's findings into the per-sibling verdict
computation) are genuinely orthogonal fixes to two different functions,
not one patch wearing two names.
