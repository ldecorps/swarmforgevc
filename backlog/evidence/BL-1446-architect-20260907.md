## Investigated: `land-plan`'s own `candidates`/`lines-of` binding still uses the un-excluded 3-arg walk

**File:** `swarmforge/scripts/land_step_lib.bb`, lines 1063/1068.

`entangled-siblings`' internal candidate walk was correctly updated to
`(ancestry-commits root walk-base commit origin-main)` (excluding anything
reachable from `origin-main`), matching invariant 1's text. `land-plan`
computes its OWN, separately-named `candidates` — feeding `lines-of`
(`sibling-own-line-changes`), which is threaded into `entangled-siblings`
as its `lines-fn` argument — via the OLD 3-arg call:
`(ancestry-commits root walk-base commit)`, with no `origin-main`
exclusion. Textually this is exactly the shape invariant 1 says should
never happen: a "candidates" binding, feeding sibling-landed detection,
that can include commits already reachable from `origin-main`.

Traced whether this can flip a verdict: `lines-of`'s extra (origin-main-
reachable) commits can only ADD entries to a sibling's own added/removed
line sets. `sibling-path-verdict` requires (`every?`) EVERY surviving-added
line to be present on `origin-main` and no surviving-removed line to be
present there — a universal, not existential, check. Extra lines added
from already-landed commits are, by construction, already satisfied by
that check (they're on `origin-main`), so they can only reinforce a
`:landed` verdict already earned by the real (post-boundary) commits, never
manufacture one: a genuinely unlanded line from a real candidate commit
still fails the `every?` regardless of how much benign extra data is
merged in. Confirmed empirically, not just by inspection: scenario 03
(`bounded-and-wide-walks-agree-03`) forces exactly this divergence — the
bounded call's `walk-base` differs from `origin-main` while the wide call's
does not, at syncs 1 and 2 (a landed sibling present in the post-hop sync)
— and both verdicts and both own-path sets are asserted identical; all
three Examples pass. Reverted to pre-fix, the coder's own evidence records
this same scenario failing at syncs 1/2, confirming the test is sensitive
to exactly this class of divergence.

Not bounced: no failing case exists today, and the scenario built to catch
this exact class of divergence passes. Recorded here rather than silently
cleared because it is a genuine textual inconsistency in extremely
safety-critical code (this file caused the incident this ticket fixes) —
worth a coder follow-up for consistency (pass `origin-main` through to this
`candidates`/`lines-of` binding too, even though it costs nothing
behaviourally today), but not a ticket-worthy defect on its own, and not
something this review is entitled to fix directly.
