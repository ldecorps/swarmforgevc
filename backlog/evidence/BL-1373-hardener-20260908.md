## Surviving Mutants Analysis

**Mutant 3: `remove-qa-paths-from-cache-write`**
- Removes `qa-paths` from the cache write: `{:tips tips :result result}` instead of `{:tips tips :qa-paths qa-paths :result result}`
- Effect: Cache reads would always miss (because the read checks for `:qa-paths`), causing the cache to never be used
- Impact: Performance regression (no cache hits), but correctness is preserved (every sweep re-gathers)
- Why it survives: The property tests verify correctness (invariants 1 and 2), not cache performance. The cache mechanism is an optimization, not a correctness requirement.

**Mutant 5: `wrong-cache-field-name`**
- Uses `:qa-path` (singular) instead of `:qa-paths` in both cache write and read
- Effect: Cache reads would always miss (field name mismatch), same as mutant 3
- Impact: Performance regression, correctness preserved
- Why it survives: Same reason as mutant 3

## Why These Mutants Are Not Killed

The surviving mutants test cache optimization details that are difficult to verify through property tests due to fixture complexity:

1. The cache is only written when `:ancestry-unavailable?` is false (babysitter_check.bb:692)
2. The fixture setup does not properly establish git ancestry (no `origin/main` remote tracking branch), so `:ancestry-unavailable?` is always true in fixtures
3. Therefore, the cache is never written in property tests, and cache-related mutants cannot be caught

To kill these mutants, we would need to:
- Fix the fixture setup to properly establish git ancestry (create `origin/main` as a remote tracking branch)
- Or, manually write cache entries in the tests and verify cache read behavior (attempted, but complex due to tips matching)

## Decision

The two surviving mutants are documented as performance-only regressions. The declared invariants are fully tested and pass. The cache mechanism is an optimization that does not affect correctness. Per the hardener role's degraded-fallback discipline, this is recorded and the parcel is forwarded.
