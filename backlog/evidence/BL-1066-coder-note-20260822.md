# BL-1066 — coder pass, implementation note

Parcel: the metrics computation (`extension/src/metrics/swarmMetrics.ts`) and
the panel call site that drives it (`extension/src/panel/swarmPanel.ts`), per
the ticket's SCOPE. BL-1038's live-repo unit-test subjects are cited, not
merged. Vitest worker-pool sizing untouched.

## What changed

1. **One walk, not one per closed ticket.** `computeMeanTicketTime` used to
   shell `git log --follow` once per file under `backlog/done/`. It now runs
   ONE `git log --full-history -M --name-status -- backlog`, indexes every
   arrival (rename or add) by the path arrived at, and reads each ticket's
   activation out of that shared index by walking its rename chain.
   `MEAN_TICKET_TIME_GIT_SUBPROCESS_BOUND = 1` is exported and asserted, not
   just claimed.
2. **The walk is off the 2-second tick.** New `metricsTickGate.ts` owns two
   decisions the panel used to make implicitly: a tick may not start a
   computation while one is running, and may not start one at all until the
   standing value has aged past `MEAN_TICKET_TIME_REFRESH_INTERVAL_MS`
   (5 minutes). `computeSwarmMetricsOnTick` is the entry point the panel
   calls; every tick still publishes a complete metrics object, the mean is
   simply republished rather than recomputed.
3. **The gate is subject-aware.** The panel's `targetPath` is mutable
   (`updateTarget`), so the gate takes the target as its subject: re-pointing
   the panel never serves the previous repo's mean for the rest of the
   interval. Without this, item 2 would have introduced a stale-metric
   regression.

## Two corrections to the diagnosis, both recorded rather than assumed

**A. Ticks cannot literally overlap inside one extension host.** The ticket
says ticks "overlap roughly fifty deep in steady state". They cannot:
`computeSwarmMetrics` is fully synchronous (`execFileSync`), so a blocked
`setInterval` callback prevents the next tick from firing at all. What
actually happened in one host is a poll callback that blocked the extension
host's event loop for ~89s at a time and ran git back-to-back at a ~100% duty
cycle — one child at a time, continuously. The many CONCURRENT
`git ... --follow` children the operator saw therefore came from separate
processes (multiple windows/extension hosts, the `swarm-metrics` CLI), each
one running its own continuous chain. This does not change the fix — the
102-seconds-on-a-2-second-timer ratio is still the defect, and the fix is
still to get the walk off the tick — but the arithmetic in the ticket's
description would not reproduce as stated, and invariant 1 is therefore
encoded as re-entrancy refusal (the only way a tick can reach a synchronous
computation mid-flight) rather than as parallel-tick refusal.

**B. Default history simplification silently drops re-open commits.** A
directory-wide `git log -- backlog` is NOT equivalent to per-file
`--follow`: default simplification prunes a side branch whose net effect on
`backlog/` was nothing, which is exactly the shape of a
reopen-then-reclose that was merged back. On the live repo this dropped both
commits of BL-575's second cycle and would have silently reported a stale,
much longer duration. `--full-history` is load-bearing for correctness here,
not a performance flag. `-M` is likewise deliberate: a host or repo with
`diff.renames=false` would otherwise make every duration unmeasurable.
Both have their own unit tests.

## One PRE-EXISTING correctness observation, deliberately NOT changed

The measured END of a ticket's duration is the file's LATEST arrival at its
current `backlog/done/` path. For a ticket later re-filed under a milestone
directory (and again when that directory was renamed), that is the re-file
commit, not the close — so its reported duration is inflated by however long
the re-file came afterwards. This is the pre-BL-1066 semantics exactly (the
old per-file `--follow` read the newest arrival at the same path), and it is
preserved here on purpose: this ticket is about what the computation COSTS,
and changing what it MEANS is a separate decision with a visible effect on the
reported mean. It is pinned by a test
(`meanTicketTimeWalk.test.js`, "a ticket re-filed twice INSIDE done/...") so
the behaviour cannot drift unnoticed, and flagged here for the specifier to
decide whether it wants its own ticket.

## Invariants (BL-654) — all three encoded, all three shown non-vacuous

| Invariant | Encoding | Non-vacuity check |
|---|---|---|
| 1. a tick never re-enters a running computation | `metricsTickGate.property.test.js` — generated interleavings of ticks that fire further ticks from inside their own compute, over generated refresh intervals, clock advances and subjects; asserts max nesting depth 1 and that every mid-flight tick is told `in-flight` | deleted the `if (inFlight)` guard: both properties fail (`computations stacked 2 deep`); restored |
| 2. cost does not grow with the corpus | `meanTicketTimeCost.property.test.js` — real git repos at generated corpus sizes and shapes; git PROCESSES counted by a shim named `git` first on PATH, so any spawn API is counted; second property closes one more ticket and asserts the count is unchanged | restored the per-ticket walk: fails with `2 closed tickets cost 2 git processes` and `closing one more ticket moved the cost from 200 to 201` ; restored |
| 3. every git child is reaped, none left defunct | `meanTicketTimeReaping.property.test.js` — after each computation (including the failing paths: a non-repo target and a missing path) asserts this process has no surviving child and none defunct, scoped to our own pid via `pgrep -P`, never a host-wide pattern | added an unwaited `spawn('git', ['log'])`: fails with `left a surviving child`; restored. The detector itself is proved by an instrument-check test against a real live child |

Generator reach is ASSERTED, not hoped for, in the two properties where it
matters: invariant 1 counts the cases that actually reached the in-flight
state and fails below a floor; invariant 2 draws corpus size from two explicit
regimes and fails unless the large one (200+ closed tickets) was reached.

**What could not be encoded, and why.** The negative control for invariant 3's
DEFUNCT arm specifically: producing a real zombie among this process's own
children requires blocking SIGCHLD, which libuv does not permit from inside
Node — it reaps automatically. The defunct assertion is therefore live in the
property, but its deliberate-break demonstration covers the surviving-child
arm only. Stated here rather than left silent.
