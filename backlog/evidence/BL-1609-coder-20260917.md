# BL-1609 — coder pass, 2026-09-17

## The fix

`swarmforge/scripts/forward_evidence_lib.bb` (new): the pure decision core,
mirroring BL-1422's `work_note_evidence_lib.bb` split.

- `sent-handoff-names-ticket-since?` moves here from
  `done_with_current_task.bb`'s own private copy (BL-1422's helper), so the
  Work-note gate and this ticket's forward gate share the one outbox/sent
  reader instead of growing a second copy.
- `forward-completion-decision {:forwarding? :master-resident? :evidenced?
  :reason}` → `:complete-plain | :complete-with-reason | :refuse`. A
  non-forwarding inbound (Article 2.4's merge-only handback marker) or a
  master-resident role (`load-role-info`'s `:worktree-name "master"` —
  never a hardcoded role-name list, per the ticket's own FIRM direction)
  always completes plain; otherwise a stated `--no-op` reason always wins
  (recorded, never silent), evidence with no reason completes plain, and
  neither refuses.

`done_with_current_task.bb`: `forward-gate!` beside `work-note-gate!`
(after it in `-main`), stamping `no_op_reason`/`no_op_at` the way
`no_work_reason`/`no_work_at` are stamped for the Work-note gate. The two
gates are mutually exclusive in effect — `work-note-gate!` only engages for
a genuine dispatch note, `forward-gate!` only for a `git_handoff` — so both
run unconditionally and each contributes at most one reason.

`done_with_current_batch.bb`: the same gate applied per item (Article 4.4's
shape) — every forwarding item's verdict is gathered first; a refusal names
every unforwarded one in one message, before any file is touched; a pass
stamps `no_op_reason`/`no_op_at` on exactly the items whose verdict carried
one (the reason, from argv, is common to the whole batch).

`dispatch_lib.bb`: `--no-op "<reason>"` accepted by the same
`refuse-unexpected-args!` family as `--no-work` (`reason-flag-args?`
factored out so both share the blank-reason-refused shape); `no-op-reason`
mirrors `no-work-reason`.

## Existing shell-test fixtures updated (not listed in the ticket's own
## constraints, but broken by this change)

Five pre-existing shell tests fixture a bare, unforwarded `git_handoff` in
`in_process` and drive `done_with_current` expecting a PLAIN completion,
for concerns entirely unrelated to forwarding (idle-clear-respawn, sidecar
tolerance, dispatch receive-mode routing, the lean-ledger CLI wiring, and
worktree-root anchoring). Each now also queues a matching forward (or, for
`test_idle_clear_respawn.sh`/`test_sidecar_tolerant_completion.sh`/
`test_lean_ledger_bb_wiring.sh`, an outbox entry with a fixed 2020
timestamp since those items carry no `dequeued_at` at all) so the fixture
stays an ordinary forwarding git_handoff in every other respect the test
observes:

- `test_idle_clear_respawn.sh` — `queue_task`/`queue_batch` now also drop a
  matching outbox entry.
- `test_sidecar_tolerant_completion.sh` — `make_handoff` does the same;
  harmless for the two "orphaned sidecar, real file already gone" cases
  since the batch is then empty and the gate never engages.
- `test_dispatch_lib_receive_mode.sh` / `test_handoff_state_dir_worktree_root.sh`
  — these dequeue through the REAL `ready_for_next*` first, which stamps a
  real `dequeued_at`, so the added evidence uses a real "+1 hour" (or a
  future-dated `sent/` entry) timestamp instead of a fixed past one.
- `test_lean_ledger_bb_wiring.sh` — `mk_done_fixture` does the same as
  `test_idle_clear_respawn.sh`.

Also retired the sibling gate's own shell test's analogous scenario:
`test_done_with_current_work_note_evidence.sh`'s "04b: a git_handoff
completes exactly as today, no gate" no longer holds, for the same reason
as BL-1422's feature row — removed, comment left explaining why, the
file's remaining scope (the WORK NOTE gate) is otherwise untouched since
every other scenario there already uses a note, never a bare git_handoff,
as its in_process item.
