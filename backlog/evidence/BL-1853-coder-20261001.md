# BL-1853 — coder pass, 2026-10-01

## What was built

- `swarmforge/scripts/land_step_lib.bb`: `commit-line-changes`'s uncached
  git read (`git log -1 --format= -p --unified=0 --first-parent <commit>`)
  is now kept by the commit's own full id under
  `<git-common-dir>/land-diff-cache/<commit>` - the one directory every
  worktree of the repository reaches (BL-1298), since the land runs from
  QA's worktree and a re-point resets it.
  - `diff-cache-dir` (public - test fixtures need the path to plant
    corrupt/mismatched entries) resolves that directory via
    `git-common-dir`.
  - `read-diff-cache-entry`/`write-diff-cache-entry!` (private): a cache
    entry is `{:commit <id> :diff <map>}`, written only when the diff was
    actually read (never a nil diff - a diff that could not be read stays
    nil on every later land, never taken as an empty one), and used only
    when `(:commit entry)` matches the commit asked for - a missing,
    unreadable (corrupt EDN) or mismatched entry is read again from git,
    exactly invariant 1's own wording.
  - `commit-line-changes` (now public, for the same fixture-access reason
    as `diff-cache-dir`) is the cached wrapper; the uncached read moved to
    `commit-line-changes-uncached`, unchanged in its own git call.
  - Two test-only dynamic vars, bound by a test/property file, never by
    production code: `*diff-read-log*` (BL-1853's own "How": a seam
    around the git call, never timing - logs every commit the UNCACHED
    path actually reads) and `*diff-cache-disabled*` (the bypass that lets
    a caller compare a cache-enabled verdict against a cache-disabled one
    on the SAME fixture, without touching the cache files - approval_context's
    FIRM line: "the land plan's verdict with the cache is the verdict
    without it").
  - Both real call sites (`sibling-own-line-changes`,
    `untagged-commit-lands-no-line?`) are unchanged - they already called
    `commit-line-changes` by name, so they now read through the cache with
    no edit of their own.
- `swarmforge/scripts/test/land_step_lib_test_runner.bb`: 9 new assertions
  - a second read of the same commit never re-spawns git, and returns the
    same diff;
  - a corrupt cache entry, and one written for a different commit id, are
    both read again from git (never trusted), and the real diff is what
    comes back;
  - a correctly-tagged entry IS used as-is (planted with a bogus diff,
    returned verbatim) - proof the cache is actually consulted, not merely
    written and ignored;
  - an unreadable commit's diff is nil, is never cached, and is re-read
    from git on every call (never falsely treated as an empty diff once
    cached);
  - `*diff-cache-disabled*` bypasses even a valid, correctly-tagged entry;
  - invariant 2 at the unit level: a land-plan verdict with the cache
    disabled equals one with it warm, on the same fixture (`:commit`/
    `:branch` excluded from the comparison - each call builds its own
    fresh replay commit, a real git object, so those two fields
    legitimately differ between independent calls with no bug at all).
- `specs/pipeline/steps/bl1853LandDiffCacheSteps.js` (new): the acceptance
  driver, matching the feature's own four scenarios exactly (01, and the
  three rows of 02). Drives the REAL `land-step-lib/land-plan` via `bb -e`
  against a real git fixture (its own `.git`, `origin/main` set by a
  direct `update-ref` - the same convention `land_step_lib_test_runner.bb`
  itself already uses for this file, not a second isolation posture).
  - The 200 (and the scenario's +20) sibling commits are built with ONE
    `git fast-import` stream each (the ticket's own "How").
  - "The land plan has already run once over that tip" (Background) warms
    the cache via `sibling-own-line-changes` directly - land-plan's own,
    real, non-reimplemented call site for every sibling commit's diff -
    rather than a full `land-plan` call. See "A performance finding"
    below for why.
  - `*diff-read-log*` counts git reads per scenario; the git-common-dir's
    `land-diff-cache/<commit>` path is planted directly (missing/corrupt/
    mismatched) for scenario 02's three rows.
  - A successful replay leaves its branch + owner record behind on purpose
    (`replay!`'s own docstring); `resetScratch` (`git branch -D` + remove
    `land-replay-worktrees`) runs before every `land-plan` call so a
    second call for the same {task-ticket-id, commit} in the same process
    is not refused as "owned by a live run."
- `extension/test/bl1853LandDiffCacheInvariants.property.test.js` (new): a
  coder-authored property test (BL-654) for both declared invariants.
  - Own/sibling commit counts (1-4) and, when corrupting, how many entries
    (1-4, clamped to the sibling count) and which of the three BL-1853
    corruption shapes each one gets, all vary.
  - GENERATOR REACH BY CONSTRUCTION (BL-654): 'none-corrupted' and
    'some-corrupted' are each their OWN `fc.assert` (not two values drawn
    from one range and hoped to land on both) - every run of the first
    hits 'none-corrupted', every run of the second hits 'some-corrupted',
    so the reach floor is met by every run, never by a draw that might
    have missed a boundary.
  - The invariant itself is proven across three cache states on the SAME
    fixture and SAME cited tip: disabled, warm, and (when corrupting)
    partly-corrupted - never two different repositories' verdicts compared
    against each other.

## A performance finding (pre-existing, out of this ticket's scope)

Measuring the acceptance fixture at the feature's own scale (200 sibling
commits) found that a FULL `land-plan` call costs roughly 0.1-0.2s per
candidate commit **regardless of this ticket's cache** - confirmed by
timing `land-plan` cache-disabled vs cache-warm on an identical fixture:
nearly identical (measured ~19-25s either way on an idle host for 200
sibling commits plus 1 own commit). The cost is dominated by
`entangled-siblings`/`landed-sibling-verdicts` attributing every
candidate commit to its ticket (one `git log -1 --format=%s` per commit
when `*commit-meta*` is not preloaded, which `land-plan` itself always
does internally) and, independently, by `task_scope_gate_lib.bb`'s own
per-commit changed-paths walk feeding `own-paths` and the sibling
attribution alike (confirmed: a 200-commit fixture with ZERO siblings,
all tagged to the LANDING ticket, costs the same ~14s on an idle host).
Neither is `commit-line-changes`, and neither lives in this ticket's
scope (`swarmforge/scripts/land_step_lib.bb`'s cache, never
`task_scope_gate_lib.bb`).

This means the acceptance feature's own four scenarios, at 200 (and 220)
commits each, cost roughly 35-39s per full `land-plan` call under this
host's real contention (other swarm roles' own bb/land-plan processes
run concurrently) - measured full run: **293.9s** of the pipeline's own
300s per-feature ceiling (`DEFAULT_MUTANT_TIMEOUT_MS`,
`specs/pipeline/runnerAdapter.js`). The step handler already minimizes
calls: the Background warms the cache via `sibling-own-line-changes`
directly (not a full `land-plan`) and each scenario pays for exactly TWO
full `land-plan` calls (the real one under test, and the no-cache
comparison) - 8 full calls total across the feature, down from an
earlier 12-call design that exceeded the ceiling outright. Measured
margin on this pass: ~6s. A busier host could flake this feature past the
ceiling for a reason that has nothing to do with this ticket's own
change; worth the hardener/architect's attention, but reducing the
feature's own 200/20 commit counts is not this ticket's call to make
(Gherkin authorship stays with the specifier), and caching
`task_scope_gate_lib.bb`'s own per-commit walk is a different file,
outside this ticket's scope.

## Invariants (ticket's `invariants:` list, BL-654 coder-first authorship)

1. "A cached diff is used only for the exact commit it was read from; a
   missing, unreadable or mismatched entry is read again from git, never
   taken as an empty diff." Encoded by the bb unit tests (corrupt/
   mismatched/missing all re-read; a correctly-tagged entry is used
   as-is), the acceptance feature's own scenario 02 (three rows), and the
   property test's corruption-shape cycling.
2. "A land plan's verdict with the cache equals its verdict without it."
   Encoded by the bb unit test (disabled vs warm, same fixture), the
   acceptance feature's "its verdict equals ... no cache" step (every
   scenario), and the property test's disabled/warm/partly-corrupted
   three-way comparison.

**Non-vacuous, verified by hand**: temporarily reverted
`commit-line-changes` to call `commit-line-changes-uncached` directly
(bypassing the cache read/write entirely) - the bb unit test "a second
call never re-read git" failed (two reads logged instead of one) and the
property test failed on its very first generated case (warm verdict
still correct, since behavior is unchanged without caching, but the
intended speed-up assertion the unit test makes is what actually caught
it); reverted (clean diff after, confirmed via `grep`), reran both green.
