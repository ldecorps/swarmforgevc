## What was implemented

1. **`extension/src/docs/docsTree.ts`** gains `filterSpecTree(tree, query)`,
   right beside `filterDocsTree` (BL-254, left byte-identical -
   `pwa/app.js` mirrors it by hand and must stay in sync). Reuses
   `filterDocsTree` for the ticket-text match (title/description/scenario
   text), and adds the label match itself: a milestone name, an epic
   tracker's title, or a ticket id containing the term - a milestone/epic
   label match keeps that node's WHOLE subtree unfiltered; a ticket-id
   match behaves like the text match (the ticket itself, not a subtree -
   a ticket has none). Rebuilds the milestone hierarchy from the
   UNFILTERED tree (not by post-processing `filterDocsTree`'s own already-
   pruned output), which is the only way to express "keep the whole
   subtree" correctly.
2. **`extension/src/bridge/bridgeServer.ts`**: the `/spec-tree-state`
   route's `compute` becomes `(url) => filterSpecTree(computeDocsTree(...),
   queryParams(url).get('q') ?? '')` - the required_wiring anchor.
3. **`extension/src/bridge/specTreeUiHtml.ts`**: a
   `<input type="search" data-testid="spec-tree-filter">` above the
   crumbs; typing debounces ~250ms then re-fetches
   `/spec-tree-state?...&q=<term>`; a no-results state
   (`data-testid="no-results"`) names the term when the filtered tree has
   no milestones. No client-side text matching at all - the script only
   builds the `q=` query string (invariant 1's own third clause).
4. **`specs/pipeline/steps/bl1412SpecTreeTextFilterSteps.js`** - drives the
   REAL `startBridge()` + the REAL served screen in jsdom (same
   bridge+jsdom shape as `bl592SpecTreeOnLiveConsoleWithEpicTierSteps.js`,

5. Unit tests extended: `docsTree.test.js` (+9 for `filterSpecTree`,

## Non-vacuity (BL-654), all three declared invariants

`extension/test/bl1412SpecTreeFilterInvariants.property.test.js`. Each
break applied by hand to the real source, confirmed via `diff` against a
pre-edit backup empty after restore, all four tests green again
immediately after each restore.

- **Invariant 2** (prune, never regroup): `filterSpecTree`'s final
  `tickets` mapped to append `' MUTATED'` to every kept ticket's title.
  P1 failed (deep-equal check: the kept ticket was no longer byte-
  identical to its unfiltered self).
- **Invariant 1** (ticket match is filterDocsTree REUSED): `textMatchedIds`
  changed to an always-empty set, severing the reuse. Both P1 and P2
  failed - P2 directly (filterSpecTree no longer kept everything
  filterDocsTree's own match decided), P1 as a cascading consequence
  (fewer tickets kept than the oracle expected).
- **Invariant 1's structural half** (no client-side text matching): a
  `.toLowerCase()` call planted in the filter input's own event listener.
  The structural check failed (`toLowerCase` count went from 0 to 1).
- **Invariant 3** (GET-only, no write path): `method: 'POST'` planted in
  the inline script's own `fetch(stateUrl(), {...})` call. **First
  attempt at this check used a naive `/fetch\([^)]*\)/` regex, which
  passed OVER this exact break** - `stateUrl()`'s own parenthesis closes
  the regex's match before ever reaching the options object, so the
  planted `method: 'POST'` sat outside what the regex even looked at. A
  real, if narrow, coverage gap in the check itself, not in the shipped
  code - caught immediately by deliberately re-running this exact
  non-vacuity proof, fixed to a bracket-counting fetch-call extractor,
  reproven to catch the same break.
