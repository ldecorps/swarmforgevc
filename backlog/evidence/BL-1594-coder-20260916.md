# BL-1594 — coder evidence, 2026-09-16

## The fix

`swarmforge/scripts/land_step_lib.bb`'s `path-content-blocked-ids` now
clears a blocking co-owner on `:vacuous` exactly as it already did on
`:landed`: `(cond-> blocked (not (contains? #{:landed :vacuous} verdict)) (conj id))`
in place of `(not= :landed verdict)`. `:unlanded` is unchanged - still
blocks. A content check that cannot complete (`main-lines`/`tip-lines`
unreadable, or any candidate's own line-change read returns nil) still
returns `nil` and the caller still fails closed exactly as before
(invariant 1, untouched code path).

The returned blocked-ids set now carries `{:verdicts {id verdict}}` as
metadata (attached once, at the loop's final return) so a caller can learn
WHICH of the two verdicts cleared a given id without a second content
check. Metadata is invisible to `contains?`/`seq`/`empty?`, so every
EXISTING caller that only asked "does this id still block" — both call
sites in `own-paths` (the default arity and the `:content-blocked-fn`
injection point QA's own recorded content-blocked-fn) — is unaffected.

`own-paths`'s `content-clear` accumulator (the ONLY other line touched in
`land_step_lib.bb`) now reads each cleared id's verdict off that metadata
and carries it in the entry: `{:path path :sibling id :verdict verdict}`
in place of `{:path path :sibling id}`. `sibling-path-verdict`,
`landed-siblings` and `sibling-landed?` are byte-identical to the received
commit — confirmed by `git diff` (below).

`swarmforge/scripts/land_step_cli.bb`'s `CONTENT_CLEAR_SIBLING_PATH` line
now prints which of the two cleared the id: `... reverted` for `:vacuous`,
`... landed` for anything else (only `:landed` reaches this branch
otherwise, since `:unlanded` never clears). The existing acceptance step's
own assertion (`bl1481SharedPathContentCheckSteps.js`) uses `.includes(...)`
on the line's existing prefix, so it is unaffected by the appended word.
