# BL-1431 — coder pass, 2026-09-05

On 2026-09-05 `land_step_lib.bb` resolved `origin/main` by name several
times inside one land-plan (`land-plan` itself, then `entangled-siblings`,
then `own-paths`, then transitively `ticket-approval-state`/
`main-ticket-sources`), while the daemon's push sweep and other live
processes ran `git fetch origin main` on the shared repository throughout
the walk. When the ref moved between two of those reads, `own-paths` diffed
against a newer tip than the attribution map was built on, and a freshly
minted ticket file appeared as a delivered path with no attribution — the
plan escalated with "could not read `<path>`'s attribution", naming an
unrelated ticket that had merely landed mid-walk. This stopped BL-1416's
land twice and BL-1407's once on 2026-09-05.

## What landed

`origin/main` is now resolved by name exactly once per land-step
invocation, at the true entry point, and threaded as an explicit parameter
through every reader:

| function | change |
|---|---|
| `land_step_cli.bb` | resolves `origin-main-sha` ONCE, right after canonicalizing the commit, and passes it as `:origin-main` into **both** `land-plan` and (when the plan replays) `replay!` — the same sha for the whole invocation. Was completely absent from the CLI before this ticket. |
| `land-plan` | `:origin-main` is now an optional key in its input map. Present (even `nil`, the CLI's "entry resolution already failed" case): used as-is, never re-resolved, never retried. Absent (the pre-existing contract for a direct/test caller): resolved once, here, at this function's own entry — unchanged behaviour for every existing caller that never knew about the key. |
| `entangled-siblings` | new 6-arg arity taking `origin-main` explicitly; the pre-existing 5-arg arity now just resolves once and delegates. |
| `own-paths` | new 8-arg arity taking `origin-main` explicitly; the pre-existing 7-arg (`opts`) arity resolves once and delegates. The internal `blocking-for` (sibling-approval lookups) now builds its default `approval-fn` closing over the SAME already-resolved `origin-main` instead of letting `ticket-approval-state`'s own default resolve a second, potentially different, tip. |
| `main-ticket-sources` / `ticket-approval-state` | each gained a 3rd, explicit-`origin-main` arity; the 2-arg convenience arity (unchanged contract) resolves once and delegates. |
| `replay!` | same optional `:origin-main` contract as `land-plan` — `land_step_cli.bb` threads the identical sha it gave `land-plan`, so the replay worktree is built off the exact tip `own-paths` was decided against. |
| `delivered-attribution` / `sibling-path-landed-fn` | already took `origin-main` as a required parameter with no internal resolution — untouched, confirmed correct by reading. |

`land_main_publish.sh` (the publish/rematch mechanism, invariant 2) is
**untouched** except that BL-1431's own acceptance scenario 04 now exercises
it live — per the ticket's own "How" section.

## Declared invariants (BL-654)

- **Invariant 1** ("one plan, one tip... a fetch that moves the ref
  mid-walk changes nothing about the verdict") — **P1**: builds a real git
  fixture with a randomized number of unlanded siblings and own paths, and
  a randomized choice of whether the caller supplies `:origin-main`
  explicitly (mirroring `land_step_cli.bb`) or omits it (mirroring a
  direct/test caller); asserts `origin-main-sha` is called exactly 0 times
  inside `land-plan` when supplied, exactly 1 time when omitted, and that
  the returned plan matches an independent reference model of which
  sibling ids should be entangled. Broken by reverting `land-plan`'s
  `contains?`-guarded threading to an unconditional fresh resolve: failed
  on every `explicit?=true` case (the mutation is invisible to
  `explicit?=false` alone, since both the original and the mutant resolve
  fresh when no value is supplied — a real gap in the property's first
  draft, caught and fixed by adding the `explicit?` dimension before this
  commit).
- **Invariant 3** ("a read that fails mid-walk still refuses rather than
  narrowing") — **P2**: builds a fixture with 1-3 own paths and injects a
  `commits-fn` that fails (returns nil) for a randomly chosen one of them;
  asserts `own-paths` ALWAYS refuses (`:paths nil`, naming the specific
  unreadable path) rather than silently excluding just that path and
  returning a narrowed set. Broken by short-circuiting the
  `(nil? attribution)` refusal branch (`false` in place of the real
  condition): failed on every generated case (the failing path's own read
  was silently treated as "included, no exclusion", producing a full,
  wrongly-narrowed path list with no warning).
- **Invariant 2** ("the publish is unchanged... never `--force`") —
  **no separate property test**, per BL-654's own allowance for a declared
  invariant with no fresh executable encoding to record a stated reason:
  this ticket makes **zero changes** to `land_main_publish.sh` (its own
  "How" section: "Keep land_main_publish.sh untouched except for the
  scenario 04 pin"). The invariant is proven by (a) the pre-existing,
  unmodified `land_main_publish_test_runner.sh` and
  `bl1144_main_land_publish_mutation_sweep.sh` both passing unchanged, and
  (b) this ticket's own acceptance scenario 04
  (`bl1431OneLandPlanOneTipCli.bb moved-at-push`), which drives the real
  script end-to-end against a real rejected-then-rematched push and asserts
  `rematchCount=1`, `published=true`, `forced=false` live. A third,
  redundant test of code this ticket does not touch would encode nothing
  new.

**Reachability**: P1/P2 ran 40 cases each; every dimension (no-siblings/
some-siblings, single/multi own-path, explicit/self-resolved origin-main,
failing-path-first/failing-path-later) measured 14-26 out of 40 — all well
above the 4 (runs/10) floor.
