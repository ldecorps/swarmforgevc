## D1 (blamed: coder) — the standing Intake topic is never actually wired live

- **Class:** scope gap / incomplete implementation (feature not
  functional end-to-end).
- **What's missing:** the ticket's own Scope names
  `extension/src/tools/telegram-front-desk-bot.ts` alongside
  `telegramTopicDecisions.ts`. The coder added the pure decision
  functions (`decideEnsureIntakeTopicAction`, `decideIntakeTopicReply`)
  to the latter, but per the coder's own evidence
  (`backlog/evidence/BL-1732-coder-20260930.md`, "Scope gap" section),
  did NOT add an `ensureIntakeTopic` async function or wire inbound
  Telegram message-dispatch routing for the Intake topic into
  `telegram-front-desk-bot.ts`.
- **Why this isn't acceptable as a deferred follow-up:** the coder's
  stated reason is that the bot's live poll loop is the "unsuitable
  boundary" Design And Testability carves out. But that file already
  contains `ensureOperatorTopic`, `ensureApprovalsTopic`, and
  `ensurePipelineBoardTopic` — each ~20 lines, each calling the matching
  pure `decideEnsure*TopicAction` function, each unit-testable via an
  injected `postFn` (no live Telegram credentials needed), and each
  wired into the startup sequence (`telegram-front-desk-bot.ts:3792-3800`
  region). This is the established, low-risk pattern for exactly this
  kind of glue — the same pattern the coder used as the acknowledged
  model ("mirrors `decideEnsureOperatorTopicAction`'s reuse/create shape
  exactly"). Writing the async wrapper and the inbound-dispatch case does
  not require live testing to write correctly, only to verify live —
  same as the three existing `ensure*Topic` functions.
- **Consequence:** without this wiring, the "Intake" forum topic is never
  created, and a principal message in it gets no reply. The feature's
  entire stated purpose ("A standing Telegram forum topic 'Intake'
  ... opens a Mini App form") does not exist in the live bot — only the
  backend routes and the web form do. `qa_e2e_procedure` step 2 ("send
  any message in the Intake topic. The topic answers with the way into
  the form") will fail as written, since no such topic is ever created.
- **Why acceptance is green anyway:** scenario 05 (the unreachable-form
  reply) drives `decideIntakeTopicReply` directly rather than through the
  live bot (evidence file, "drives ... the topic decision in-process"),
  so the missing wiring has no test coverage that would catch it before
  QA's live e2e check.
- **Remediation:** add `ensureIntakeTopic` (mirroring `ensureOperatorTopic`)
  and wire it into the startup sequence alongside the other standing
  topics; add the inbound-message dispatch case for the Intake topic
  (principal-only per `isFromPrincipal`) that calls
  `decideIntakeTopicReply` with the resolved `/intake-form` URL (or
  `undefined` when the tunnel is down) and posts the result.
