# BL-1705 — coder pass, 2026-09-24

## What landed

- **`swarmforge/scripts/orphan_janitor_lib.bb`**: a new pure classifier,
  `reapable-ollama-ghost?`, plus its three cmdline predicates
  (`ollama-serve-cmdline?`, `ollama-model-runner-cmdline?`,
  `ollama-run-client-cmdline?`) and one combined-candidate predicate
  (`ollama-ghost-candidate-cmdline?`):
  - `ollama serve` itself is always kept (left to the stop paths, BL-1704).
  - A model runner (`llama-server ...` / `ollama runner ...`) is reaped,
    ANY age, once its parent is no longer a live `ollama serve` — no
    grace period, per the ticket's own "reap, any age" direction.
  - An `ollama run <model>` client is reaped only once it has been
    reparented to init (pid 1 / WSL's `/init`) AND its age exceeds the
    grace period; a run client under any other still-live parent (an
    interactive shell, say) is kept regardless of age.
  - `ollama runner` and `ollama run` are disambiguated by a plain regex
    word boundary (`\brun\b` never matches inside "runner" - "run" is
    followed by "n", a word/word non-boundary), not a lookahead.
- **`swarmforge/scripts/orphan_janitor_sweep_lib.bb`**: wires the new
  class into the live sweep -
  `ollama-run-client-grace-threshold-ms` (env `SWARMFORGE_ORPHAN_JANITOR_
  OLLAMA_GRACE_MINUTES`, default 30 minutes - the ticket's own proposed
  number, in MINUTES unlike the other classes' HOURS defaults, since 30
  minutes is the actual ask), a new `parent-live-ollama-serve?!` adapter
  (production impl inlined with raw `ProcessHandle` calls, matching this
  file's own existing style for `live-pid-from-file!`/`kill-pid!` rather
  than adding a new primitive to `process_table_lib.bb` - keeps the diff
  inside the ticket's own declared Scope), and a new `cond` branch in
  `sweep-candidates!` that classifies via `reapable-ollama-ghost?` and
  audits `reaped-ollama-ghost pid=... cmd=... age_ms=...` on a reap.
  `scan-candidate-pids!`'s filter now also matches
  `ollama-ghost-candidate-cmdline?` (including `ollama serve` itself, so
  it is provably seen-and-kept rather than silently unscanned).
- **`specs/pipeline/steps/bl1705OllamaGhostJanitorSteps.js`** (new): both
  scenarios drive the REAL Babashka decision/sweep via a JSON-bridge
  runner (see below) - never a hand-rolled reimplementation of the reap
  decision in JS, same posture as BL-885/BL-886/BL-930's own janitor-side
  step handlers.
- **`swarmforge/scripts/test/bl1705_ollama_ghost_janitor_acceptance_runner.bb`**
  (new, test infra - the ticket's own "How" section explicitly asks for
  "classification rows... plus one sweep over stand-in processes"): two
  subcommands, `classify` (calls `reapable-ollama-ghost?` directly against
  a named parent role - "a live ollama serve" / "init" / "a live
  interactive shell") and `sweep-two-ollama` (drives the real `sweep!`
  over two stand-in numeric pids via fully-injected adapters - no real
  process spawned, same JSON-bridge posture bl885's own runner
  established for this exact ticket family).
