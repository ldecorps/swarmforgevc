## Both holes reproduced first, then closed

Reproduced against the real send path before writing the fix (qa_e2e steps
1 and 3):

```
full-chain          coder->QA        -> to: QA        skipped=cleaner,architect,hardender,documenter
[coder,cleaner,qa]  coder->architect -> to: QA        skipped=architect,cleaner,hardender,documenter
```

The second is the one that is easy to miss and worse than it looks: a coder
addressing **architect** was delivered to **QA** — forward of the stage it was
addressed to, jumping the declared cleaner — because the non-member branch
rewrote to `next-required-stage(effective, literal-to)` and never consulted the
sender at all.

At this commit, same fixtures:

```
full-chain          coder->QA        -> to: cleaner   (no header, no log line)
[coder,cleaner,qa]  coder->architect -> to: cleaner   (no header, no log line)
```

**The fix is one guard ahead of both branches**, exactly the shape the ticket's
"How" describes: `next = next-required-stage(effective, sender)` — computed
from the SENDER, so it is the same answer whichever branch would have run —
and when `next` is strictly before the addressed stage, deliver to `next`.
Everything else falls through to today's logic unchanged, so BL-606's pruning
contract survives.

A binding rewrite is not a skip: it deliberately does not reuse `emit-skip`'s
`rewritten-away` slot, because that would put QA in `skipped=` while QA is
precisely what will still run (invariant 2). Stages the declaration genuinely
prunes are still recorded — `no-cleaner` coder→QA delivers to architect and
correctly records `skipped=cleaner`.

The ticket's `constraints` section names BL-951's feature file. **It missed
BL-623**, which the exhaustive consumer sweep caught. Both are amended here,
in this parcel, and both are green.

**BL-951 feature** — the `full-chain` row removed from scenario 01's outline,
exactly as instructed. `absent` and `invalid` both resolve to default-full and
stay correct, so BL-951's own point still has two live states to make it in.

**BL-951 property runner** (`bl951_stage_skip_recording_property_runner.bb`) —
not named by the ticket either, and it asserted the same thing the feature row
did ("delivery unchanged in every state") over generated hops, so it went red
too. Amended so `:full-chain` expects the bound hop and `:absent`/`:invalid`
still expect literal delivery. The oracle is computed in the runner rather than
read back from the code, so it still fails if the router stops obeying either
rule.

**BL-623 scenario 04** — asserted a coder→QA hop on `[coder, cleaner, qa]`
delivering to QA and recording cleaner as skipped. That is the jump the ruling
now forbids, so the hop skips nothing and there is no record left to inspect.
The scenario's real content is a skip record carrying a MIX of stages with and
without a declared reason, so it is retargeted to a cleaner→QA hop, which
reaches the same mixed record (architect has a declared reason, hardender has
none) without asserting a forbidden jump. Retargeted rather than deleted: no
other scenario covers that contrast. BL-623 scenarios 01/02 use `[coder, qa]`,
where cleaner is undeclared and nothing binds, so they are untouched — which is
the pruning contract still holding.
