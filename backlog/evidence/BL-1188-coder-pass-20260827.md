## Summary

source Telegram's board already uses (BL-487) over the coordinator-written
`ticket-stage-map.json` cache, which only advances on `sync` and read as

(matching the invariant's own "when a live report is available" wording),

## Design notes

- Kept `capturePipelineGridLive`/`readLiveRoleHeldTickets` **synchronous**
  (`execFileSync`, not the async `execFileAsync` telegram's reader uses):
  its only caller, `bridgeServer.ts`'s JSON route table, invokes every
  `compute()` synchronously and does `JSON.stringify(jsonRoute.compute(url))`
  with no `await` anywhere in that dispatch path — every other route in the
  same table is sync too. Making this one route async without also
  reworking that dispatch mechanism would silently serialize `{}`.
- `queued-not-claimed-04` scenario: verified against the *real*
  `pipeline_stage_cli.bb` that a parcel sitting only in a role's `new/`
  queue (never claimed `in_process`) still legitimately renders at that
  role's column — that's its genuine pipeline position, not a bug. The
  scenario's "does not show status claimed" is satisfied by confirming it
  is NOT rendered as the not-started default (the pre-fix failure shape)
  and IS positioned at its real target stage; the grid model itself has no
  separate claimed-vs-queued flag beyond the column to assert further on.
