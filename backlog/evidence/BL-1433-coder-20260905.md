# BL-1433 — coder pass, 2026-09-05

## What was wrong

`post_qa_branch_sweep_lib.bb`'s `decide-role` classified any branch it
could not fast-forward as `:divergent-branch`, including a branch that
already **contains** the landed commit and merely carries the role's own
work on top - the ordinary state of every role mid-parcel after it merged
`main`. BL-1421's "caught up to the told commit" check
(`git merge-base --is-ancestor <told-sha> HEAD`) is trivially true for such
a branch from the moment it is first told, so the standing-surfacing
suppression never engaged and `record-surface!` rewrote the same record
every cycle. Measured: 61 notes to four roles in fifteen minutes on
2026-09-05, each reading "branch behind `<sha>`: branch cannot
fast-forward to landed commit - merge up" with nothing to merge.

## What landed

  a `contains-landed?` fact, checked right after `already-settled` and

## Declared invariants (BL-654)

**Invariant 1** ("A role whose HEAD contains the landed commit is never
told it is behind, whatever else its worktree holds.") — **P1** in
`bl1433_branch_holds_landed_commit_property_runner.bb`: randomizes
`dirty?`/`in-process?`/`can-ff?` (8 combinations, drawn repeatedly) with
`contains-landed? true` and asserts `decide-role` always returns
`{:action :holds-landed}`.

**Invariant 2** ("divergent-branch means exactly HEAD lacks the landed
commit and cannot fast-forward to it; BL-1421's standing surfacing holds
unchanged.") — **P3**: the same randomized flags with `contains-landed?
false`, asserted EQUAL to an independent reference re-implementation of
the pre-BL-1433 `decide-role` cond (kept as a separate copy in the
property file, not a call into `decide-role` itself) - proving the new
fact changes nothing when it is false. BL-1421/BL-1361's own full
regression suites (property + acceptance) continuing to pass unchanged is
the complementary, higher-level proof (table below).

**Invariant 3** ("An unanswerable containment fact never produces a note:
... the role is skipped with a logged reason.") — **P2**: the same
randomized flags with `contains-landed? nil` (`head-sha`/`landed-sha` both
present, so `:missing-ref` never fires) and asserts `decide-role` always
returns `{:action :skip :reason :unknown-containment}`.

**Non-vacuity**, each mutation run for real and restored byte-identical
(confirmed via `diff` against a pre-break backup):
- P1 and P2: removing the `(nil? contains-landed?)` and `contains-landed?`
  branches together failed EVERY generated case for both properties (500
  each) - P1 fell through to `:surface`/`:settle`, P2 fell through
  identically (nil is falsy, so it took the same path `false` would).
- P3: reordering `dirty?` to be checked before `in-process?` (reverting
  BL-1421's own precedence fix) failed every generated case where both
  were true - proving P3 is sensitive to the exact preserved order, not
  merely to `contains-landed? false` being present at all.

**Reachability**: each of `dirty?`/`in-process?`/`can-ff?` is asserted to
be drawn both true and false above a 10% floor (500 runs); the same three
booleans are shared across P1/P2/P3's domains, drawn once and reused for
all three predicates per the generator-reach requirement.

## Scenario 03: the supplier's own argument order, against a real fixture

`bl1433_supplier_git_facts_runner.bb` builds a real git fixture (a bare
`origin`, a role worktree cloned from it, one commit pushed to
`origin/main` as "landed", one further commit made only on the role's own
branch) and computes `can-ff?`/`contains-landed?` via the SAME
`git merge-base --is-ancestor` shell-out `handoffd.bb`'s real supplier
uses - a deliberate, minimal (3-line) duplicate rather than loading
`handoffd.bb` itself (never load-file `handoffd.bb`: it boots daemon
machinery as a side effect - the same reason
`test_invariant2_qa_definition_lib.sh` keeps its own local copy of this
exact check rather than loading the daemon). Measured: `can-ff?: false`,
`contains-landed?: true` - correct, and non-trivially so: an early draft
had the two ancestor-check argument orders backwards (copy-paste from
`can-ff?`), which this same fixture caught immediately (`can-ff?` came
back `true` instead of `false`) before the fix. Every mkdtemp root the
runner creates is verified via `git rev-parse --git-common-dir` to resolve
INSIDE that same root before any mutating git command runs (BL-1390); the
fixture never touches the real checkout.
