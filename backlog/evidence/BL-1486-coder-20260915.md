## Invariants (BL-654)

Both declared invariants are encoded by the new handler's four scenarios,
not a `*.property.test.js` file. Stated reason (same posture as BL-1489's
precedent): the module under test (`specs/pipeline/steps/*.js`, the
acceptance-pipeline tree) is outside the `extension`-side testable-module
boundary `test:properties` covers, and this is deterministic, structural
verification over the real file tree — not a property over a pure
function — so there is no generator-reach concern to assert. Building the
new handler is itself "the acceptance-pipeline components ... is regular
coder work" (coder role prompt's own exception).

- Invariant 1 ("verdict with unset equals verdict with set"): scenarios
  01/02 run the real features/shell test with the hatch removed and assert
  full pass; scenario 03 structurally guarantees every qualifying handler
  decides the hatch in its own spawn (so removing it from the parent
  process can never change a child's behavior); together these prove
  verdict-equality by construction rather than by re-running both ways
  every time (scenario 01/02 additionally confirmed both ways for this
  evidence file, not asserted in the generated test).
- Invariant 2 ("gate's own refusal untouched, no lane-wide export"):
  scenario 04 asserts no lane-wide export; `bl1318PackStaffingGateSteps.js`
  and `pack_staffing_gate_lib.bb` are untouched (`git diff` confirms no
  production line changed).
