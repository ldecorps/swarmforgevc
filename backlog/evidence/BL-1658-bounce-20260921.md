## D2 — BL-1658's own acceptance scenario 01 measures a single sample, not
best-of-three, and reproducibly fails under ordinary host load for four of
the eight handlers

`specs/pipeline/steps/bl1658SevenJsdomHandlersLoadLazilySteps.js` defines
`confirmAloneMs` (best-of-three, `Math.min` of three `censusOneHandler`
calls) with the comment "a single fresh-child reading can land on a sibling
agent's scheduling spike on this shared, continuously-running swarm host" —
but only scenario 02's step (`checkHandlerBudgets(..., { confirmAlone:
confirmAloneMs })`) uses it. Scenario 01's own budget step reads
`ctx.bl1658Row.ms` straight from the single `censusOneHandler(handler)` call
made two steps earlier, with no retry — the exact single-sample fragility
the function's own comment warns against, present in the same file, unused
where the ticket's declared invariant ("a fresh-child require of the
handler alone stays under the guard's budget under any host load") most
needs it.

Confirmed reproducibly (not a one-off flake — ran the whole feature twice in
a row, identical failing set both times):
`node specs/pipeline/cli.js specs/features/BL-1658-the-seven-remaining-eager-jsdom-handlers-load-it-lazily.feature`
→ `# pass 5`, `# fail 4`, all four failures on scenario 01's Examples:

```
bl592SpecTreeOnLiveConsoleWithEpicTierSteps.js cost 666.0ms, expected under 400ms
bl674EpicDrilldownUiSteps.js cost 556.7ms, expected under 400ms
bl686EpicDrilldownSlugMatchSteps.js cost 621.1ms, expected under 400ms
bl687EpicReorderIncludesActiveChildrenSteps.js cost 549.5ms, expected under 400ms
```

The handler file's own comment explains why these four specifically sit
close to budget: "Four of the seven jsdom handlers (bl592, bl674, bl686,
bl687) already require extension/out/bridge/bridgeServer at module scope —
unchanged by this ticket — and bridgeServer's OWN pre-existing dependency
graph transitively reaches cursorBridgeAgentSession ... for reasons that
have nothing to do with jsdom or this parcel." That pre-existing weight is
real and out of scope to remove, but it means these four handlers' true
"confirmed alone" cost is genuinely close enough to 400ms that a single
sample can land over it under normal contention — exactly the shape
`confirmAloneMs` exists to smooth out.

By contrast the ACTUAL production gate,
`extension/test/stepHandlerModuleLoadBudget.test.js` (which does use
`confirmAlone` for every handler, not just an aggregate scenario), passed
green (8/8) run alone moments before this bounce — consistent with D2's
diagnosis: the guard is fine, scenario 01's own measurement is the
inconsistency.

Direction (not mandate): scenario 01's "the cost is under the per-handler
budget" step should use `confirmAloneMs(ctx.bl1658Row.file)` (or re-run
`censusOneHandler` three times itself) rather than the single sample taken
by the earlier "is required alone" step — matching scenario 02's own
methodology and the production guard's.
