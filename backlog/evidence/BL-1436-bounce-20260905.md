## What is wrong

`costFrom` was rewritten from a fixed four-term sum into a per-category
loop that returns `null` for the whole estimate when a category has
nonzero tokens and an undefined rate (`extension/src/metrics/pricingTable.ts`).
This is new behavior this ticket introduces — the honest-null discipline
this file already applies at the whole-model level, now applied
per-category — and the coder's own evidence explicitly credits it as the
mechanism that keeps invariant 1 honest ("no guess, no sibling copy").

I independently measured this rather than argued it: mutated the branch's
`return null` to `continue` (silently costing the category at zero) and
re-ran every test surface this parcel's own evidence names:

- `npx vitest run test/pricingTable.test.js` — **still 30/30 pass**.
- `node specs/pipeline/cli.js
  specs/features/BL-1436-the-pricing-table-prices-every-model-the-swarm-runs.feature`
  — **still 6/6 pass**.
- `extension/test/pricingWindows.property.test.js` — its own
  `cacheCreatePerMTok` generator always produces a defined value
  (`fc.double({ min: 0.1, max: 100, ... })`), never `undefined`, so it
  never reaches this branch either.

Nothing in the automated suite would fail if this exact regression landed
tomorrow. The coder's own "Non-vacuity" section for this mutation says
"confirmed live" — a manual `node -e` probe against the compiled table,
not an assertion in any test file that runs under a gate. Scenario 02's
own Examples table (input/output/cache-read, each priced in dollars)
deliberately excludes cache-creation because it has no dollar figure to
assert — a reasonable scoping call for THAT scenario, but it leaves the
honest-null path itself with no coverage anywhere else in the parcel.

Yes. `costFrom` is the only new logic this parcel introduces; the entry
addition, the display-name map, and the register removal are all
