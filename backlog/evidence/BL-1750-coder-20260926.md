# BL-1750 — coder pass — 20260926

## Cause found

`fixtureReaperAbnormalExitHarness.js` never set `SWARMFORGE_FLEET_HOME`
when spawning `launch_front_desk.sh`. `front_desk_supervisor.bb` defaults
that to the real `$HOME` (`(or (System/getenv "SWARMFORGE_FLEET_HOME")
(System/getProperty "user.home"))`, line 172), so `resolved-telegram-creds`
resolved THIS HOST'S OWN genuinely-populated `~/.swarmforge/fleet/` instead
of a fixture-local one, picking up the real, live swarm's own recorded
bridge port (8765) rather than the harness's `BRIDGE_PORT` (18999)
override. `maybe-adopt-or-spawn-bridge!` then found port 8765 already held
by the real production bridge and freed it - the supervisor log's own
line, quoted verbatim from a manual repro:

    free-port bridge pid= 24261 cmdline= node /home/carillon/swarmforgevc/extension/out/tools/start-bridge-headless.js /home/carillon/swarmforgevc 8765  port 8765

`free-foreign-pid!` (front_desk_supervisor.bb) then sent that real pid
`kill -TERM` (and would have escalated to `-KILL`). The fixture's own new
bridge was then started, ALSO on port 8765 (the wrongly-resolved real
port) - never on the harness's requested 18999, which is exactly what its
own `waitFor` polls. Nothing ever answered on 18999, hence "fixture
bridge never came up" at the 5 s timeout: the real cause was never a
timing shortfall (hypothesis a) or a supervisor pid-claim refusal
(hypothesis b) - it was fleet-creds resolution reading real host state,
hypothesis (c).

**This is not a production defect.** `SWARMFORGE_FLEET_HOME` is an
existing, documented isolation seam (front_desk_supervisor.bb's own
comment: "so a test can point this at its own fixture root rather than
the operator's real ... `~/.swarmforge/fleet/`") that this ONE harness
simply never used - `bl789MacHostSwitchFreshnessBridgeAdoptSteps.js`
already sets it correctly (`SWARMFORGE_FLEET_HOME:
path.join(ctx.bridgeRoot, 'fleet-home')`) for the exact same
adopt-or-free code path. No spec-gap note; STOP RULE does not apply.

**Live-swarm impact acknowledged**: this repo's own real front-desk
bridge (pid 26312 at investigation time) was confirmed alive and
answering (`GET /pipeline` → 401, an expected auth refusal, not a
failure) both before and after the fix was verified - the kill happened
only during my own manual reproduction of the pre-fix bug (immediately
noticed and cross-checked), not from any of the fix-verification runs
below. Every time this scenario ran on a host with a real front-desk
bridge on port 8765 before this fix, it would have briefly killed and
forced a real restart of that bridge.

## Fix

`specs/pipeline/steps/lib/fixtureReaperAbnormalExitHarness.js`: added
`SWARMFORGE_FLEET_HOME: path.join(root, 'fleet-home')` to the spawned
`launch_front_desk.sh` environment - a fresh, empty subdirectory of the
fixture's own throwaway root, same convention as BL-789's own step
handler. With no existing fleet registration there, resolution falls
back to the harness's own `BRIDGE_PORT` override; the bridge now binds
exactly the port the harness's `waitFor` polls.
