# BL-1403 — coder pass, 2026-09-05

`check_merge_deletion.sh` no longer reports a moved path as a deletion, and
attribution now tries either side of a merge whenever HEAD's own subject
names no ticket — not only when it is empty. This is the guard that
refused my own BL-1402/BL-1413/BL-1384/BL-1365 merge-ups earlier today
(worked around each time via the cherry-pick recipe); this ticket fixes it
at the source.

## A real bug found and fixed while writing the tests, not just the fix

The first draft printed `id<TAB>commit`. Test 16 caught it immediately:
the refusal read `(c8af328, introduced at unknown on this branch)` instead
of `(unattributed, introduced at c8af328 ...)` — id and commit had swapped.
Root cause, confirmed by isolated reproduction:

```
$ printf '%s\t%s\n' '' 'ba8f69c' | { IFS=$'\t' read -r a b; echo "a=[$a] b=[$b]"; }
a=[ba8f69c] b=[]
```

Bash's `read` builtin silently swallows a **leading** empty field even when
`IFS` is set to a single explicit tab character — a trailing empty field is
preserved correctly, a leading one is not. This is a genuine, easy-to-hit
shell gotcha, not a git behavior. Fix: reorder the printed tuple to
`commit<TAB>id` (commit is never legitimately empty for a real deletion;
id is the field that can legitimately be empty), and update the caller's
`read -r attr_commit attr_id` to match. Recorded in the script's own
comment so the next person touching this function does not reintroduce it.

A second, unrelated fixture bug surfaced while authoring both the shell
test and the acceptance handler: a one-line intake body drops BELOW git's
default 50% rename-similarity threshold once a short footer is appended
(measured: a bare `D`+`A`, never `R`, for a tiny file). Real intakes are
multi-paragraph documents, so this never fires in production, but the
*test fixture* needed a realistically-sized body to actually exercise the
rename path it claims to test — both new test files use the same
multi-paragraph fixture body for this reason (commented at the point of
use in both).

## Declared invariants (BL-654)

Both have a coder-authored, non-vacuous property test in this parcel, each
shown to fail against a deliberately broken implementation and then
restored:

- **Invariant 1** (a path whose content survives elsewhere is never a
  deletion; a genuine deletion is still reported unchanged) — broken by
  reverting to `--no-renames`: failed on every `:move-plain`/`:move-footer`
  draw (41 failures across 60 runs). The property ALSO checks the other
  half explicitly (a real deletion, content survives nowhere, must still
  refuse) using the SAME `:delete` draws invariant 2 exercises — this
  half never broke because I did not touch that path, which is itself the
  point: the fix is additive to what already worked.
- **Invariant 2** (a refusal is exemptable whenever either side names a
  ticket; `(unattributed)` only when neither does) — broken by restoring
  the pre-fix "only fall back when subject is EMPTY" condition: failed
  specifically and only on `head-names-ticket: false,
  incoming-names-ticket: true` draws (18 failures) — exactly the raw-intake
  shape the ticket exists to fix, never on the other three combinations,
  confirming the property targets the right defect precisely.

**Reachability floors**: the generator must hit both move variants and all
four head/incoming ticket-naming combinations for deletions at least a
few times each; 60 runs measured 20/21 for the move split and 5/3/6/5
across the four deletion combinations in a passing run.
