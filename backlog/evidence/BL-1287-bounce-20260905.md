# BL-1287 — architect bounce, 2026-09-05

## Violated rule

Declared invariant 2: "The sweep still clears every fixture left by a run
that is gone, however that run died - nothing traps SIGKILL, so a killed
run always leaves its fixtures behind and the next run must still find
them."

## Commit reviewed

`97c297608d` (cleaner NONE pass — the wrapper-stays-local judgment is
correct and not what's wrong here).

## What is wrong

`extension/test/helpers/fixtureTunnelName.js:82-89`:

```js
function isProcessAlive(pid) {
  try {
    process.kill(pid, 0);
    return true;
  } catch {
    return false;
  }
}
```

used at line 122 to decide whether a fixture's creating run is still
around: `if (creatorPid === null) return true; return
!isProcessAlive(creatorPid);`

This is the exact discriminator class BL-1292 (landed on `main` earlier
today, same file family — `extension/test/helpers/fixtureLiveness.js`)
identified and fixed: `process.kill(pid, 0)` answers "does some process
with this pid exist and can I signal it?", not "is this process actually
gone?" — a SIGKILLed process stays signallable as an unreaped zombie until
its subreaper collects it. Here, that means: **a creator that has just
been SIGKILLed but not yet reaped is misreported as still alive, so its
leaked fixture is NOT swept** — the exact case invariant 2 promises to
handle ("however that run died").

## Measured, not argued (matching this ticket's own house style)

Reproduced directly, using BL-1292's own zombie-construction technique (a
bash parent that backgrounds a short-lived child and never `wait`s on it,
confirmed via `/proc/<pid>/status`'s `State: Z` line):

```
zombie confirmedZombie: true pid: 627
isProcessAlive(zombiePid): true
fixturePid: 629 selected (should be swept since creator is functionally dead): false
```

A fixture whose "creator" is a confirmed zombie (functionally dead,
awaiting reaping) is **not selected** by `leakedFixtureTunnelPids` —
directly violating invariant 2. Script used for this measurement is
reproducible from BL-1292's own `spawnZombie` helper
(`extension/test/helpers/fixtureLiveness.js`) plus a fixture named to
declare that zombie pid as its creator.

## Why the parcel's own verification did not catch this

Both of this parcel's own invariant-2 checks share the identical blind
spot:

- `bl1287FixtureSweepScopingInvariants.property.test.js`'s `deadPidVia(signal)`
  (lines 53-66) busy-waits on `process.kill(pid, 0)` throwing before
  returning the pid as "dead." A zombie's `kill(pid, 0)` does **not**
  throw — only a fully-reaped pid does — so this loop can only ever
  produce a creator that is dead **and already reaped**. It never
  constructs, and therefore never tests, the zombie window that
  `isProcessAlive` gets wrong.
- `specs/pipeline/steps/bl1287FixtureSweepSparesLiveRunSteps.js`'s
  `deadPid()` (line 59, used at line 81 for the acceptance feature's
  "gone" example) is the same `spawnSync('true', [])`-based
  fully-reaped-pid construction — same blind spot, so scenario 01's
  "gone" Outline row doesn't exercise it either.

So neither the property suite nor the acceptance feature can currently
distinguish a correct fix from this bug — a fix must also add a
zombie-constructing non-vacuity case (BL-1292's `spawnZombie` is directly
reusable) to actually prove invariant 2 holds through the death signal
that matters most for a killed test run.

## Scope check — is this the only site?

`grep -n "isProcessAlive\|process.kill(.*, 0)"` across the parcel's three
changed/new files finds exactly one production call site
(`fixtureTunnelName.js:122`, via `isProcessAlive`). The two other bare
`process.kill(pid, 0)` uses are: the property test's own busy-wait
scaffold (the mechanism of this finding, not a second instance) and the
step handler's scenario-03 check on a fixture known to be genuinely
running (a normal liveness check on a live process, not a
creator-liveness discriminator — not the same failure class). One site,
one fix.

## Remedy

Not mine to mandate the shape (direction, not mandate, matching this
ticket's own style): `isProcessAlive` needs to treat a zombie as gone, the
same way BL-1292's `isAlive` does — reusing or adapting
`fixtureLiveness.js`'s zombie-detection technique (or an equivalent
`ps`/`/proc` state check) is the most direct path since it already exists
in this exact codebase, landed today, for the identical discriminator
class. The property test's `deadPidVia` and the step handler's `deadPid`
scaffolding both need a companion "creator is a zombie" case with a
non-vacuity proof (revert the fix, confirm the new case fails) — mirroring
BL-1292's own non-vacuity discipline — or invariant 2 stays honestly
unverified for the death mode most likely to matter under a killed test
run.
