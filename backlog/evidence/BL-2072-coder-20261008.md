# BL-2072 — coder evidence (2026-10-08)

## What changed

A shared timing helper, `timePhase` (and its adapter-aware wrapper
`timePhaseIfWired`), lives in `telegramFrontDeskBotCore.ts` next to
`pollAndForward` - the one mechanism all three sites below share, so a
phase name/duration line is formatted exactly once:

```
front-desk-phase-slow: <phase> took <elapsedMs>ms
```

written via the EXISTING `logDiagnostic` adapter (`appendFrontDeskDiagnostic`
in production - unchanged, already durable and append-only) whenever a
phase's own elapsed time is `>= FRONT_DESK_SLOW_PHASE_THRESHOLD_MS`
(10000, the coder's own choice per the ticket's "direction, not mandate" -
generous over any single ordinary phase, tight enough to still catch one
eating a meaningful share of the supervisor's 90s kill budget). Under the
threshold, nothing is written.

Three sites, one helper:

1. **startup topic checks** - the ~10-call `ensure*Topic`/
   `runPendingApprovalAnnouncementHook` sequence in `main()`
   (`telegram-front-desk-bot.ts`) is extracted into its own exported
   `runStartupTopicChecks(targetPath, botToken, chatId, postFn?)` -
   every individual topic's own "BEFORE any loop starts polling" ordering
   comment is unchanged, only WHERE the sequence lives moved. `main()`
   now calls it through `timePhase` directly (`Date.now`,
   `appendFrontDeskDiagnostic`). `postFn` threads through every call
   (all nine already accepted an optional `postFn: TelegramPostFn` before
   this ticket) so a fixture can drive the real sequence over a fake
   Telegram without touching `main()` itself (which also reads env vars
   and starts the forever-loops).
2. **getUpdates wait** - `pollAndForward`'s own `adapters.getUpdates(offset)`
   call, wrapped via `timePhaseIfWired`.
3. **handling of one update batch** - the `for` loop over `result.updates`
   (each iteration calling the existing `processUpdate`), wrapped as ONE
   phase around the whole loop, not per-update.

`PollAdapters` gains one new optional field, `now?: () => number`, paired
with the ALREADY-EXISTING `logDiagnostic?: (line: string) => void` -
`timePhaseIfWired` runs a phase untimed unless BOTH are wired (the same
"omitted adapter -> unaffected" posture every other optional adapter here
already has). Production wires `now: () => Date.now()` right beside the
existing `logDiagnostic` wiring in `buildPollAdapters`.

Nothing else changes: the heartbeat write (`writeFrontDeskPollHeartbeat`)
stays exactly where it was (in `pollLoop`, untouched), and every wrapped
function's own return value rides through `timePhase` unaffected - proven
by the property test below, not just asserted.

## Step handler

`specs/pipeline/steps/bl2072FrontDeskStallNamesPhaseSteps.js` drives the
three REAL phases directly: `timePhase(...)` wrapping the REAL
`runStartupTopicChecks` for the startup phase, and the REAL
`pollAndForward` for the other two (one fixture per phase, since each
needs a different fake adapter to be the one that advances the clock -
`postFn` for startup, `getUpdates` for the poll wait, `openSubjectAndRecord`
for the batch - never a sleep: a fake clock (`now`/`advanceMs`) is advanced
BY the fake adapter the instant it is called, so the measured elapsed
time is exactly the scenario's own chosen delay with zero real
wall-clock cost). Never the live token or the live operator directory -
every fixture's `opDir` is `mkTmpDir`'d.

## Declared invariant (BL-654)

"Every startup step, getUpdates wait and batch handling that runs longer
than the threshold leaves exactly one timing line naming that phase and
its duration; nothing else in the bot's behaviour changes." -
property-tested in
`extension/test/bl2072FrontDeskPhaseTimingInvariants.property.test.js`,
driving the REAL `timePhase` directly (the one mechanism shared by all
three real call sites; the acceptance feature above already proves each
site is actually wired to it, so this is the shared helper's own proof,
never a second copy of that wiring).

GENERATOR REACH: `delayMs` drawn from two explicit sub-ranges (`[0,
threshold)` and `[threshold, threshold*2]`, `fc.oneof` with equal weight)
rather than one uniform range spanning the threshold - BL-1062/BL-2083's
own rule: a single uniform draw centered loosely around an asymmetric
boundary could statistically starve the rarer side; two explicit
sub-ranges cannot. 40 runs, reach floor asserted >= 5 on each side (both
comfortably exceeded in practice).

Checks per draw: under the threshold -> zero lines; at/over it -> exactly
one line naming the phase, whose own printed duration is >= the delay;
the wrapped function's own return value is unchanged either way (the
invariant's "nothing else... changes" half).

Non-vacuous, confirmed by hand before this commit: temporarily replaced
the threshold comparison with a bare `true` (every phase always logs,
however short) - the under-threshold case failed immediately
(`delayMs=0: expected no timing line, got [...]`); reverted, reran clean.
