# BL-1289 — coder pass, 2026-09-05

## What landed

`extension/test/tempDirTrapGuard.test.js` scans `swarmforge/scripts` and
flags any `.sh`/`.bb` file that creates a temp root (`mktemp -d` /
`fs/create-temp-dir`) with no recognized cleanup path. At pickup this
reported **27** violations (the ticket's own spec-time count of 21 had
drifted upward — six more call sites landed between 2026-08-30 and today:
`check_bb_scripts_load.sh`, `bl1411_...property_runner.bb`,
`bl1421_one_standing_surfacing_{acceptance,property}_runner.bb`,
`handoffd_supervisor_startup_grace_test_runner.bb`, and
`test/lib/fixture_isolation.sh`; one of the ticket's original 21,
`land_main_publish_test_runner.sh`, had already been fixed elsewhere). The
qa_e2e bar is "the guard reports zero violations run directly," not "the
21 files the ticket happened to name nine days ago," so all 27 are fixed
here — the guard is the acceptance contract, not the snapshot.

Every fix adopts one of the two conventions the guard itself names — an
`EXIT` trap or `lib/tmp_cleanup.sh` for shell, `addShutdownHook` or a
`(try ... (finally ... delete-tree))` for bb — never new machinery. The
per-file shape (single call site vs. several, a shared `mk-repo`/`mkRoot`
helper vs. independent `let`s) decided which of the two bb idioms fit best;
no file's own logic changed.

| `test/lib/fixture_isolation.sh` | sources `lib/tmp_cleanup.sh` itself and registers `$WORK` right after `fixture_isolation_stamp_owner` — on TOP OF, never instead of, the file's own lock/reap/bound machinery (BL-1385/1390/1392), which stays untouched. This gives a normal exit immediate cleanup; the pre-existing `fixture_isolation_reap` (owner-liveness sweep) remains the ONLY defense against a killed run, since a trap cannot catch SIGKILL. |

### Babashka (21 files)

Single-call-site files (`bl1121`, `bl1122`, `bl1134`, `bl1137`, `bl533`,
`daemon_log_freshness_pulse_lib`, `rotation_telemetry_lib`): one
`addShutdownHook` referencing the same `let`-bound root, inserted as a
next binding in the same `let` (the var is already in scope for it).

Multi-site files, using a shared `(def created-temp-dirs (atom []))` +
one `addShutdownHook` that sweeps the whole atom, with a `swap!` at each
creation site: `bl1138`, `bl1141`, `bl615`, `bl683`,
`master_checkout_integrity_lib` (registered once, inside its shared
`mk-repo` helper — covers all 4 call sites), `retirement_registry_lib`
(same, inside `mk-repo`, covers all 5), `self_heal_telemetry_lib`,
`swarm_shift_lib`, `post_hotfix_merge_origin_lib` (7 sites, one of them an
inline value inside a map literal — rebound to a name first so it could be
registered), `post_qa_branch_sweep_lib` (9 sites), `handoffd_supervisor_startup_grace`
(the root was already a top-level `def` created before `failures`/the atom
existed — the atom is seeded with it directly:
`(atom [fixture-root])`).

Exception-shaped files, using `(try body (finally (fs/delete-tree dir)))`
because the create/use/delete-tree were already in the same lexical scope
and the guard's own `HAS_TRY_FINALLY_DELETE_TREE` regex fits directly:
`bl1421_one_standing_surfacing_property_runner.bb`'s P1 and P3 (P3
DELIBERATELY exercises a `tell!` adapter that throws — try/finally is not
just guard-satisfying here, it is the correct shape for a property whose
own subject is exception handling).

Two files needed a design call rather than a mechanical copy:

- **`bl1411_..._property_runner.bb`**: already had named `p1-teardown!`/
  `p2-teardown!` functions called on the normal path (lines 288/292) — an
  exception between setup and its own teardown call would still leak.
  Added one `addShutdownHook` calling both teardown fns (each already
  nil-guarded) as a crash-only backstop, rather than restructuring the
  existing, working two-phase setup/check/teardown shape.
- **`bl1421_one_standing_surfacing_acceptance_runner.bb`**: this file is
  invoked ONCE PER GHERKIN STEP (a separate `bb` process per step), and
  deliberately REUSES the same `dir` across calls — the JS step handler
  (`bl1421OneStandingSurfacingSteps.js`, unmodified) passes the path back
  in via `scenario.dir` and does its own `fs.rmSync` in its own `afterEach`.
  An unconditional shutdown hook here would delete the fixture the moment
  the FIRST invocation's process exits, before the second invocation could
  reuse it — breaking the acceptance feature. Fixed instead with a
  crash-only hook: it only exists on the invocation that created `dir`
  fresh (`(nil? (:dir scenario))`), and is a no-op once this invocation has
  successfully printed the JSON handing the path back
  (`@handed-off?`) — it only fires if THIS process dies before that
  hand-off, which is exactly the gap the JS side cannot itself cover.
  Verified this doesn't regress the reuse behavior: `BL-1421-one-standing-surfacing-per-role.feature`
  still passes 6/6 (run twice).

## Declared invariant (BL-654)

**"Every temp root a runner creates is removed on every exit path it
controls, and a root left behind by a run that was killed is swept before
the next run makes any assertion - nothing traps SIGKILL, so cleanup alone
is never sufficient."**

No new property test is written for this invariant: this parcel introduces
no new cleanup MECHANISM, only applies four already-existing, already-used
patterns (`addShutdownHook`, `try/finally + delete-tree`, shell `EXIT`
trap, `lib/tmp_cleanup.sh`) at 27 call sites, plus registers one more root
with `fixture_isolation.sh`'s own pre-existing owner-liveness reap. Writing
a property test here would either (a) restate the guard's own regex over a
generated file-text domain — already exactly what
`bl948SocketFixtureShortRootSteps.js`-style tests and this ticket's own
acceptance Scenario 01 (Outline, both mechanism directions) do against the
REAL `findTempDirTrapViolation`, or (b) restate the fixture_isolation_reap
sweep — already property/behaviorally proven by `test_bl1370_worktree_strays.sh`
(a real shell suite: "reaping killed this worktree's stray", "the other
worktree's process is STILL RUNNING after the reap", "a prefix-sibling
root's suite is never reported as this worktree's stray" — re-run above,
all pass) from the BL-1390/1392 hardening passes that built that
mechanism, unmodified here. The acceptance feature's three scenarios
instead close the gap this ticket's OWN 27-file adoption could uniquely
get wrong:
- **Scenario 01** (Outline, both mechanism directions) drives the real
  guard against a generated fixture with/without a cleanup mechanism —
  proves the guard's OWN recognition, not this parcel's fix.
- **Scenario 02** drives the real guard over the REAL `swarmforge/scripts`
  tree — proves every one of the 27 adopted sites actually satisfies it,
  today, not a fixture standing in for them.
- **Scenario 03** drives the real `fixture_isolation_reap` against a
  killed-run-shaped fixture (a stale root stamped with a verified-dead
  pid) — proves the SIGKILL-can't-be-trapped half of the invariant holds
  for the mechanism this parcel's one new registration (in
  `fixture_isolation.sh`) now also benefits from.
