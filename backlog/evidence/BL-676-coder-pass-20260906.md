## Two real bugs found by the qa_e2e_procedure's own live-repo step —
## fixed before forwarding, not left for a later stage

The ticket's own qa_e2e_procedure explicitly asks to "run against the real
repo" before considering the slice done. Doing that (not just trusting the
fixture-based acceptance suite, which used absolute temp-dir roots and
could not have caught either bug) surfaced two genuine defects:

1. **Path-normalization bug: every run against the real repo produced
   ZERO rows.** `generate-report!`'s `done-files` filter compared
   `list-backlog-ticket-files`'s returned path strings (no `./` prefix)
   against a re-derived `(fs/path backlog-root "done")` string that DID
   carry one when `project-root` is `"."` (the ordinary invocation shape)
   — `fs/path` preserves the prefix, `fs/glob`'s own output strings do
   not, and even `fs/starts-with?` is Path-textual rather than
   normalized, so it also failed to bridge the two. Fixed with
   `fs/normalize` on both sides before the ancestry check. Verified live:
   0 rows before the fix, 428 after, against this repo's actual 368+
   untagged `backlog/done/` tickets (the ticket's own 2026-07-24 measurement
   was 427 of 497; more closures have landed since, so a higher count is
   expected, not a discrepancy).

2. **Precision defect in `roster-match`: matching a done ticket's title
   against an epic's own free-text TITLE produced spurious matches on
   ordinary English prose.** Spot-checking ten real roster-match rows
   (the qa_e2e_procedure's own instruction) found three clear false
   positives: "Dead tile detection — red tile border when session
   disappears" proposed epic `bubble-thin-shell` on the shared word
   "when"; "Backlog panel — show work items in the webview" proposed
   `stereo-router` on "work"; "Hardened message bus — append-only event
   log per message" proposed `github-auto-intake` on "only". None of
   those words appear in the matched epic's own SLUG — only in its
   verbose title prose, which can contain nearly anything. Fixed by
   matching against the epic's SLUG tokens instead of its title tokens
   (a slug is a curated, compact, deliberately evocative identifier — a
   title is free text), raising the minimum token length from >2 to >=4
   characters, and widening the stopword list with the specific offending
   words plus other common short English words. Re-spot-checked after the
   fix: all three false positives gone; `roster-match` row count dropped
   from 406 to 271, `needs-judgment` rose from 3 to 79 (a far more honest
   split), `pre-epic-era` rose from 4 to 63.

## Known, documented limitation (not fixed — see below for why)

Even slug-only matching is not perfectly precise: several slug words that
name a SPECIFIC epic (`agent-memory-transfer`'s "agent",
`local-llm-swarm`'s "local", `tool-miss-auto-heal`'s "tool",
`github-auto-intake`'s "auto", `disaster-recovery-loop`'s "loop") are
also ordinary, frequent vocabulary in a multi-agent swarm codebase, so a
handful of live roster-match rows are weak-confidence single-word
coincidences rather than strong thematic matches (e.g. BL-002 "Stall
detection... on silent agent" → `agent-memory-transfer` via "agent").
**Not chased further, deliberately**: the ticket's own design already
prices this in — `roster-match` is a PROPOSAL for the report's own
`needs-judgment` sibling and the human review this ticket's
`approval_context` describes ("BL-677 consumes the human-amended,
human-approved report"), never an auto-apply. The evidence column always
names exactly which word matched, so a human skimming the report can spot
and downgrade a weak row in seconds. Building genuine confidence scoring
(word-frequency weighting, requiring multiple overlapping words) is a
materially bigger, still-deterministic-but-far-less-simple mechanism than
what this slice's own description asks for ("title/source keyword match"),
and risks scope creep into a problem the ticket itself hands to human
judgment by design.
