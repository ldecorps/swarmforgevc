## What was wrong

`vitest.properties.config.mjs` sets `globals: true` and collects
`test/**/*.property.test.js`. A file that instead imported `test` from
`node:test` registered its cases with node:test's own runner, invisible to
Vitest's collector ("No test suite found"), while node:test itself ran and
passed every case — the assertions pass and the file fails, simultaneously.
BL-1175 allowlisted the resulting standing reds under time pressure and
landed; every row still read "pending fix" against a closed ticket, so the
repair BL-1175 deferred had no owner.

## Declared invariants (BL-654)

**Invariant 1** ("No file in the vitest property lane takes its `test`
binding from node:test - the lane's globals are the single source of
it.") — **P1 + P2** in
`bl1206PropertyLaneAllowlistInvariants.property.test.js`: P1 proves the new
property-lane walk flags a genuine import wherever it sits in a
property-lane file (any of 6 import forms, any of 3 lane-adjacent
extensions, any of 3 directory depths) and never flags the identical text
in a non-property-lane file or a data-only occurrence; P2 proves the walk
skips no offender across a tree of several. The underlying per-line scanner
(`findNodeTestImportLines`) is BL-1220's own, already proven
data-vs-import-safe by its own 400-run property test — not re-proven here,
to avoid duplicating that coverage; what's new and tested here is the
property-lane file-selection and walk. A real-tree sweep confirming the
invariant actually holds today lives as a plain (non-generative) unit test —
`bl1206PropertyLaneNodeTestImportGuard.test.js`'s "the real extension/test
tree has no property-lane node:test imports" — matching BL-1220's own
precedent of keeping the deterministic real-tree check out of the property
lane.

**Invariant 2** ("A file leaves the standing allowlist only by passing
under the property lane, never by being deleted from the list while still
red.") — **P3**: `findSilentRemovals` is a pure function judging any
before/after file-set diff against a pass/fail record; P3 randomizes which
files depart, stay, or never existed, and whether each departure passed,
and asserts the function reports exactly the departures NOT backed by a
recorded pass. This ticket's own register edit satisfies it directly: all
14 removed files were run alone and confirmed passing (table above) before
their rows were deleted — `findSilentRemovals(before14+hostActivityFeed,
[hostActivityFeed], {14 files: true})` returns `[]` (not run as an extra
test file, since it would just restate the table above; verified by hand
at a REPL during authoring).

**Non-vacuity**, each mutation run for real and restored byte-identical
(confirmed via `diff` against a pre-break backup):
- P1: forcing `isPropertyLaneTestFile` to always return `true` (erasing the
  lane distinction) failed on the very first non-property-lane import case
  — "unexpected violation for..." — proving the property actually
  distinguishes lanes.
- P2: dropping the walk's first directory entry (`.slice(1)`) failed
  immediately — "one violation per offending file, none skipped" — proving
  the property is sensitive to a skipped file, not just to some array
  coming back.
- P3: inverting `findSilentRemovals`'s filter (`=== true` instead of `!==
  true`, reporting legitimate departures instead of silent ones) failed on
  the very first generated case with a departed-set mismatch.

**Reachability**: P1 asserts a floor on all three classes it distinguishes
(property-lane imports, non-property-lane imports, data forms — each drawn
>20 times over 300 runs); P2 asserts a floor on multi-violation trees (>15
of 60); P3 asserts floors on legitimate departures, silent departures, and
stayed files (each >5 of 100).
