## D1 — the new acceptance step handler leaks its fixture git repo every run, never cleaned up

**Class**: `hygiene` (resource leak) — a correctness defect I can see,
bounced per the architect prompt's own standing rule that a concrete
defect spotted during review is a send-back even when the parcel is
otherwise architecturally clean (BL-333 precedent).

**Where**: `specs/pipeline/steps/bl924HotSyncedCopiesDoNotBlockMergeSteps.js`,
Background step (`mkRepoWithDivergedRole()`, called via
`fs.mkdtempSync(os.tmpdir(), 'sfvc-bl924-root-')` at line 38). Every one of
the 4 scenarios re-runs the Background, creating a full disposable git
repo + a `git worktree add` under it. Nothing in the file ever removes
`ctx.root` (or `ctx.wt`, nested under it) — grepped the whole file for
`rmSync`/`cleanup`/`finally`/`afterEach`/`after(`: zero matches.

**Reproduced, not assumed**: ran the acceptance feature myself (twice,
once clean and once as part of the invariant-1 non-vacuity check above) —
`ls /var/folders/.../T/ | grep sfvc-bl924-root- | wc -l` grew from a
baseline already left behind by the coder/cleaner's own dev-time runs to
**32** directories currently on disk, each a full git repo with its own
`.git` and a nested `.worktrees/role` checkout. None are cleaned up by
anything in this parcel.

**Why this is a real defect, not nitpicking**: this is the exact,
already-named class the shared engineering rule addresses directly ("A
fixture dir from `fs.mkdtempSync` is removed in a `finally`, never only
after the last assertion — a test that throws or bounces otherwise leaks
it permanently. Measured 2026-08-18: 236 of 287 step-handler files using
it had no `finally`; one ticket left 45 dirs behind.") — this file is a
**new** instance of exactly that pattern, not a pre-existing violation
inherited from elsewhere. Checked whether the standing sandbox sweep
(`sandbox_sweep_lib.bb`, BL-413) mitigates this: it DOES allowlist the
`sfvc-*` prefix and will eventually bound the stock, but its own header
is explicit that BL-413 (bounding the stock) and BL-420 (bounding the flow
— "fixing the extension test helpers to clean up their own mkdtemp dirs
at the source") are **both required**; the sweep existing does not make
skipping the source-side `finally` acceptable for new code. A full git
repo + nested worktree per scenario per run is also heavier than the
plain scratch files BL-460's own sweep evidence was measuring.

**Remediation**: this repo already has the working shape for this exact
problem — `specs/pipeline/steps/bl413StaleSandboxSweepSteps.js` (lines
163–176) wraps each scenario's terminal-step assertions in
`try { ... } finally { fs.rmSync(ctx.projectRoot, {recursive:true,
force:true}); ... }`, removing every `mkdtempSync` root it created in the
Background, on both pass and throw. Apply the same shape here: wrap each
of scenario 01/02/03's terminal assertion step in
`try { <assertions> } finally { fs.rmSync(ctx.root, {recursive: true,
force: true}); }` (removing `ctx.root` alone is sufficient — `ctx.wt` is
nested under it via `git worktree add`, so it goes with it).
