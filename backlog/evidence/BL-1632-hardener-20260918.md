## Detail

### Leaked-process gap found and fixed in-pass (not a bounce)

Both acceptance scenarios in `bl1632Bl1071ProbeCountsOnlyItsOwnFixturesHangsSteps.js`
spawn a real long-lived process — a detached `sleep 3600` in scenario 01,
a whole process group carrying its own `sleep 3600` grandchild in
scenario 02 — and reaped it ONLY inline, in a terminal Then step's own
`finally`. The acceptance runtime (`specs/pipeline/runtime.js`) has no
After-hook mechanism, so any assertion EARLIER in the same scenario that
throws — and these steps assert the very invariant this ticket exists to
fix, so a real failure here is entirely plausible — skips every later
step, including that `finally`, and leaks the process for real (an hour,
for the plain `sleep 3600`). This is the acceptance-lane sibling of the
"a fixture-creating Given step that throws while validating leaks its
temp dir" hazard: here the leaked resource is a process, not a directory,
but the mechanism (a later step's cleanup never runs) is identical.

Confirmed the gap was real, not theoretical: a standalone probe script
that spawns the same kind of detached `sleep 3600`, registers no cleanup
beyond an inline reference, then throws before reaching any teardown —
nothing reaped it (the file had no `process.on('exit'/'SIGINT'/'SIGTERM')`
registration at all).

Fixed in commit `326022f346` by binding both spawns to
`specs/pipeline/steps/lib/fixtureReaper.js`'s `onAbnormalExit` — the
shared primitive that file's own header says exists exactly for "a
fixture with its OWN kill logic... [needing] the SAME exit/SIGINT/SIGTERM
coverage without adopting [track/reap's] shape",
mirroring the pattern `bl690EnsureDaemonRepairStartsNotHaltsSteps.js`
already uses for its own spawned processes. Re-confirmed the fix closes
the gap: the same probe script, now registering its kill through
`onAbnormalExit` before throwing, WAS reaped — the tracked process died
via the exit handler despite the throw happening before any inline
cleanup ran.

All 4 acceptance scenarios re-run green after the fix; `pgrep -af
"sleep 3600"` empty afterward. BL-1071's own feature (10/10) and the
property file alone (`npx vitest run --config vitest.properties.config.mjs
test/bl1071RecoveryBoundedInTime.property.test.js`, 2/2, 8.93s) both still
resolve. Register rows (`backlog/standing-reds.tsv`,
`swarmforge/scripts/property_suite_standing_allowlist.tsv`) correctly
left in place per the ticket's own note (QA's land step retires them).
