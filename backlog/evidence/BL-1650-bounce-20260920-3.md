  BL-1639 commit), producing a genuine add/add conflict on content the tip doesn't even carry.
- **Failure class**: spec-gap
- **Expected vs observed**: The ticket's own FIRM constraint ("an ancestor whose every path is
  byte-identical to main after the parcel's own edits is reported as landed, never as entangled")
  names the ANCESTOR's paths compared to main, but the correct decision axis is the REPLAY TIP's
  content, not the stray commit's own content — a path can be byte-identical on the tip while the
  historical commit that introduced it differs from main's current (further-evolved) copy. The spec
  as written under-specifies which content to compare, and the implementation (reasonably) read it as
  "the commit's own content," producing this second-order bug.
- **Blamed role**: specifier (the FIRM constraint's own ambiguity, not a coder implementation error —
  per the specifier's own ruling: "QA's own reading of 'subset = identical' is right in effect and
  unnecessary in form: with TIP content there is no subset, only equal or different").
- **Remediation pointer**: amend the stray-cherry-pick loop (and the landed-sibling-verdict it shares
  logic with) to decide by the REPLAY TIP's content at each path versus `origin/main`, never the
  historical commit's own diff; add scenario 06 pinning this exact subset/superset shape (per the
  ticket's own notes, referenced in the specifier's ruling).
