# BL-1076 — coder pass

Commit: this parcel · 2026-08-23 · worktree `swarmforge-coder`

## What changed

Both signals the ticket named, applied to the batch observer.

**Per-role tolerance.** `batch_claim_progress_lib.bb` gains
`role-stale-threshold-ms` (`hardender` → 90 minutes) and
`resolve-stale-threshold-ms`, resolved highest-first: operator override →
built-in role entry → configured base. An override the parser rejected is
simply absent from the map, so an unusable value degrades to the **role's own
built-in** tolerance, never to the tighter base.

**Visible-work gate.** A third label, `:suppressed-visible-work`, reachable
only where a note would otherwise have gone out — fresh progress and a missing
sidecar stay `:silent` even with a dirty worktree, because nothing was
declined. Suppressed and silent both send nothing; suppressed is logged.

**Operator override.** `config batch_claim_progress_role_stale_threshold_minutes
<role> <n>`, repeatable, parsed with the same degrade-to-default posture as the
two keys beside it.

## One design call, stated because a reviewer will ask

`decide-batch-claim-observation`'s dirt-blind 3-arity is **retired**, not left
defaulting `worktree-dirty?` to `false`. A call site that forgot the flag would
silently lose the gate — which is this defect over again in a new place. That
cost four consumer updates (`chase_sweep_lib.bb`, `batch_claim_progress_cli.bb`,
and two test runners), each of which now says "clean worktree" out loud, which
is the condition every one of them always meant. Same reasoning as BL-1043's
retired grace-less arity, landed in the parcel before this one.

`apply-batch-claim-progress-check!` returns `{:suspects :suppressed}` rather
than a bare seq, because the caller must be able to log what it declined to
send.

**Not shared with BL-528**, per the ticket's explicit instruction: both
libraries keep their own 90-minute literal, and both now say in their headers
why merging them is refused rather than merely undone.

## Declared invariants (BL-654) — all three encoded, non-vacuity measured

`swarmforge/scripts/test/bl1076_visible_work_gate_property_runner.bb`, 240 runs.
Each invariant is asserted against the **filesystem after a real sweep**, not
against the pure return value — a third label is exactly the shape that breaks
all three at once.

| property | invariant | what it holds |
|---|---|---|
| P1 | 1 | no label touches the parcel — bytes, path, listing, no inbox/new copy |
| P2 | 2 | full accounting: every stale parcel is surfaced or suppressed, never dropped; every suppression names parcel and reason |
| P3 | 3 | with no HEAD advance the persisted `lastProgressAtMs` is unchanged, whatever the label |
| P4 | — | armed-ness backstop: P1–P3 are all satisfied by suppressing everything |
| P5 | — | the shipped defect, stated absolutely |

**P5 exists because the obvious phrasing is vacuous.** "A hardener inside its
own tolerance is not surfaced" is trivially true once that tolerance has
collapsed to the base — which *is* the bug. Measured: with the per-role map
emptied, the relative phrasing fired **0** times; P5, which names the 90-minute
floor instead of asking the resolver, fires **116**.

Four breaks, each restored, counts measured:

| break | kills |
|---|---|
| suppress by bumping `lastProgressAtMs` instead of declining | P3 156 |
| drop suppressed observations instead of recording them | P2 52 |
| return `:suppressed-visible-work` for everything | P4 68 |
| empty the per-role map (the shipped defect) | P5 116 |

Three also trip a coverage floor — the reach assertions doing their second job:
a break that makes a whole band of states unreachable is caught even where no
property statement covers it.

Generator reach, asserted not hoped for: `defect-band 19, past-tolerance 165,
under-base 71, label-silent 120, label-suspect 68, label-suppressed 52,
role-hardener 123, role-other 117` — all above their floors. The age is
**derived** from the resolved threshold rather than drawn independently;
drawn on its own it would essentially never land in the 20–90 minute band that
is the entire defect.

## One harness change worth flagging to the cleaner

`batch_claim_progress_sweep_harness.bb` now accepts `-` for its optional
positional arguments, meaning "take the default". BL-1076 needs the fourth
argument without pinning the first two, and `-` says so without putting a flag
parser in a test harness. The alternative — computing dirtiness from
`git status --porcelain` in the role worktree, as the daemon does — was
rejected because BL-678's fixture worktree carries untracked `.swarmforge/`
state and would read dirty forever, turning its scenario 04 red for a reason
that has nothing to do with either ticket.
