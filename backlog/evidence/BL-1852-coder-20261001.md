# BL-1852 — coder pass, 2026-10-01

## What was built

- `swarmforge/scripts/land_step_lib.bb`: `post-land-repoint!`'s candidate
  set is no longer `ancestry-commits` (BL-1308's own FULL ancestry walk,
  built for a different caller's different need — detecting an entangled
  tip must see a merge's second-parent lineage). Three new pure helpers:
  - `first-parent-no-merge-range` — oldest-first non-merge commits between
    two refs, walking ONLY first-parent (never a merge's second parent).
  - `first-parent-no-merge-ancestors` — the full SET of non-merge commits
    on a tip's own first-parent line, used only to ask "was this sha ever
    really on this tip's own line" (never walked per-commit).
  - `read-last-repointed-record` — the most recent `:repointed` entry
    `land-repoint.log` holds (the exact `<timestamp> <edn-map>` shape
    `log-repoint!` already writes, unchanged), or nil.
  - `own-line-candidates` — the new candidate-set builder. When the
    previous record's `:new-tip` is still an ancestor of `old-tip` (the
    ordinary case): every first-parent non-merge commit since that
    `:new-tip`, UNIONED with whichever of that record's own `:kept`
    entries were themselves on **its own old tip's** first-parent line
    (re-derived from git each time, by original sha — never a new marker
    field, so an OLD-shaped 2026-09-30 log record reads correctly too).
    Otherwise (no record, or `:new-tip` not an ancestor): every
    first-parent non-merge commit since `old-tip`'s merge-base with
    `origin-main` — a safe superset of QA's own work that still never
    reaches merged-in lineage.
  - `post-land-repoint!` itself: swapped `ancestry-commits` for
    `own-line-candidates`, and dropped the now-redundant `(reverse
    candidates)` (the new function already answers oldest-first).
    `classify-repoint-candidate`'s own bookkeeping-shape/revert/no-ticket-
    id/landed-ticket-own checks are UNCHANGED — they decide what to do
    with a candidate; this ticket only changed which commits ever reach
    them as candidates at all.
- `specs/pipeline/steps/bl1852RepointKeepsOwnLineSteps.js` (new) and
  `specs/pipeline/steps/lib/bl1852RepointKeepsOwnLineCli.bb` (new): the
  acceptance driver. Every scenario drives the REAL `post-land-repoint!`
  against a real git fixture with its own bare origin under mkdtemp.
  Scenario 02 hand-writes a `land-repoint.log` entry in the EXACT
  pre-ticket shape (no new marker field — a timestamp with no embedded
  space, matching `java.time.Instant/now`'s own `toString`, a gotcha
  caught by hand while building the fixture: an `#inst "..."`-tagged
  timestamp breaks the reader's "split on the first space" the real
  `log-repoint!` format relies on) to prove the fix reads a record this
  ticket's own code never wrote.
- `extension/test/bl1852RepointOwnLineInvariants.property.test.js` (new):
  a coder-authored property test (BL-654) for both declared invariants,
  driving the REAL `post-land-repoint!` across TWO consecutive re-point
  rounds with generated counts of QA's own commits (round 1 and round 2)
  and a merged-in parcel's bookkeeping commits (round 1) — proving
  invariant 2's "carried forward" half against a record the code wrote
  ITSELF (the self-consistent repeated-call path), complementing the
  acceptance feature's own hand-written-old-record scenario.

## Invariants (ticket's `invariants:` list, BL-654 coder-first authorship)

1. "A re-point never re-applies a commit that reached QA's tip only
   through a merge." Encoded by acceptance scenario 01 (a merge whose
   lineage holds 40 commits, none kept) and scenario 02 (30 merged-in
   commits a PAST, buggy re-point wrongly carried are excluded going
   forward), and by the property test's `two-round-repoint` cell.
2. "A re-point never drops a commit QA made on its own line that is not
   yet on origin/main, including one an earlier re-point carried
   forward." Encoded by acceptance scenario 01 (3 own commits, all kept)
   and scenario 02 (the 2 genuinely-own commits a past record carried are
   carried again, alongside 1 new one), and by the property test's
   two-round structure (round 1's own commits still present after round
   2's re-point).

**Non-vacuous, verified by hand**: temporarily reverted the candidate-set
swap (`own-line-candidates` back to `(some-> (ancestry-commits root
origin-main old-tip) reverse vec)`) — the acceptance feature failed on 2
of 3 scenarios (33 kept instead of 3) and the property test failed
immediately (a merged-in commit kept on the very first generated case);
reverted (clean diff after, confirmed via `grep`), reran both green.
