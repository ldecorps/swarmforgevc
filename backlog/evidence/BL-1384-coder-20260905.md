## The bridge side needed no change — verified, not assumed

The ticket's own direction says "the bridge side needs no change... verify
that with the fixture in scenario 02 rather than assuming it." Before this
pass, `telegramCursorBridgeLive.test.js` had **zero** tests driving
`runCursorBridgePollOnce` with `qwenLocalTopicId`/`runLocalSeatTurnFn` set —
the exact integration point BL-1235 already implements
(`processInboundUpdates`'s `deps.qwenLocalTopicId` branch) but that nothing
had exercised end-to-end. Two new tests close that gap:

- a live-polled update in the local-seat topic dispatches to
  `runLocalSeatTurnFn`, never to cursor's own decision.
- a **forwarded** update (via `appendCursorBridgeInboundUpdate`, the same
  queue this ticket's front-desk half feeds) drained in inbound-queue mode
  reaches the local seat identically — proving the seam between the two
  processes, not just each side in isolation.

The acceptance feature's scenario 02 goes one step further: it wraps the
REAL `runLocalSeatTurn` (BL-1235's own decision/turn logic) with only the
HTTP call faked (`readEndpoint`/`complete`), so the fixture asserts on the
actual end-to-end behavior, not a stand-in.

## Declared invariant (BL-654)

"A topic the bridge process owns - cursor host, Bubble, or the local seat -
is forwarded whole to the bridge inbound queue and never opens a support
subject, whether or not the bridge is currently draining." Has a
coder-authored, non-vacuous property test, shown to fail against two
independent deliberate breaks and then restored:

- disabling `qwenLocalSeatTopicId` in `hasCursorBridgeTopicAdapter`'s
  short-circuit check → failed on every draw where the local seat was the
  ONLY bound topic (cursor and bubble both unbound in that draw) — the
  gate never even resolved the adapter.
- dropping `qwenLocalSeatTopicId` from the array passed to
  `decideCursorBridgeExclusion` → failed identically, confirming both
  halves of the wiring are independently load-bearing.

**Reachability floor**: the generator must hit all three owned-topic kinds
(cursor, Bubble, local) at least once across 60 runs; measured coverage
confirmed in a passing run. A companion property (30 runs) pins the other
side: a topic none of the three own still opens its subject exactly as
before, so "never opens a subject" cannot be satisfied by a seat that
swallows every topic.
