# BL-1984 evidence — coder, 2026-10-05

## Failure mode

QA's BL-1958 gather ran both property files in the loaded lane (load ~15, 917s wall).
Both files pass alone and pass together at low load, but bl1678 invariant 1
times out under the gather's load.

## Root cause

bl1678 invariant 1 had a **static** `{ timeout: 120000 }` that does not scale
with system load. Under the gather's load ~15 the contention budget factor is
`max(loadavg/4, forks/4) = max(15/4, 11/4) = 3.75`, so the effective budget
should be `120000 * 3.75 = 450000ms` (capped at `max(120000, 120000*3) = 360000ms`).
The static 120000ms is insufficient for the 36.7s-alone invariant under load 15.

bl1375 already uses `propertyLaneTimeoutMs(20000)` on all three invariants and
scales correctly (20000 * 3.75 = 75000ms at load 15).

## Loaded-lane reproduction

Attempted `npx vitest run --config vitest.properties.config.mjs` from the
extension directory. The config path resolves relative to the worktree root
(not the extension/ cwd), causing "Cannot resolve entry module
vitest.properties.config.mjs". The property run never executed under load.
The unit suite background runs succeeded (load 10-19) but the property lane
could not be reproduced in this session.

## Fix chosen

Wire bl1678 invariant 1 through `propertyLaneTimeoutMs(120000)` — the same
pattern bl1375 already uses. This scales the timeout with load (120000 →
360000ms at load 15) without lowering run counts or dropping any invariant.

- Added `require('./helpers/propertyLaneContentionBudget')` to bl1678 file.
- Changed `{ timeout: 120000 }` → `{ timeout: propertyLaneTimeoutMs(120000) }`.
- No changes to numRuns, assertions, or other invariants.

- bl1678: 2 invariants, unchanged.
