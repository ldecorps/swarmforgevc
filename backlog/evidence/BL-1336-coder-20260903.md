# BL-1336 — coder pass (2026-09-03)

The ceiling could not tell a mono-router swarm (one live resident plus the
coordinator) from a full forge (seven live role sessions), because the rotation
mode was written into `swarm-identity` and **never exported** — so nothing
running inside a role could read it. That missing signal was the real content
of the ticket; the number was a preference.

## The signal

`swarmforge.sh` now exports `SWARMFORGE_ROTATION` beside the existing
`SWARMFORGE_PACK` in every role launch script. The value comes from a new
`rotation_signal()` helper that `write_swarm_identity_file` also uses, so
`swarm-identity` and the exported env can never disagree about what "router"
means — one normalisation, two readers, rather than a second copy of the
`ROTATION_MODE` check.

## The ceiling, built to the human's ruling

*"Fixed router ceiling above the current default, with the memory budget still
the binding cap."* So `ROUTER_FORK_CEILING = 10` is a constant, not derived
from the host's core count — deriving would make the function host-sensitive,
which is how a deterministic unit test becomes a flaky one, and the RAM budget
protects a small host either way.

Keyed on **rotation, never on pack names**, as the ticket requires: router
packs are not a fixed enum and new ones are minted regularly, so a name-matching
predicate would silently miss every future one.

Rule order is explicit and deliberate: the full-forge-on-darwin ceiling of 1 is
checked *before* the router rule. The two cannot both apply today, and keeping
the order stated means a future router variant of full-forge could not silently
widen it.

Both lanes read the signal through the SAME `resolveVitestWorkerPool` call
they already shared (BL-935 invariant 3) — no second composition point.

## Not verified here, and why

The live half of `qa_e2e_procedure` — launching a real swarm under a router
pack and reading `SWARMFORGE_ROTATION` out of the resident pane — is not run
from this worktree: `./swarm` kills and relaunches the whole swarm, and the
workflow article forbids running it from an agent worktree. What is checked
instead is that the launcher emits the export line into the generated launch
script, which is the same fact one layer earlier. QA owns the live check.

## Scope kept

The RAM floor and `MAX_WORKERS` baseline (BL-422/BL-792) are untouched, the
full-forge darwin ceiling is untouched, and no pack name is matched anywhere.
