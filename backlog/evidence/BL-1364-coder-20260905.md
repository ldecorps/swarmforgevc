## Three things only the live run found

Each of these made the producer useless in production while every fixture
test stayed green. Recording them because "the tests passed" would have
shipped a mechanism that is reachable and still produces nothing — the
BL-1235 shape this ticket is itself an instance of.

**1. Every stage came back as `unknown`.** `walkTranscriptFiles` attributes a
stage only by time-matching a handoff trail, and the producer had no trail, so
the first live run emitted a single meaningless row. Fixed by walking PER ROLE
GROUP and taking the stage from the worktree the transcript lives in — a
transcript in the coder's worktree is the coder's turn. `runTurnProfileProducer`
now builds `TranscriptGroup`s from `roleWorktrees`.

**2. `RangeError: Maximum call stack size exceeded`.**
`coverageFromIntervals` folded its window with
`Math.min(...intervals.map(...))`, which passes one ARGUMENT per interval.
Every caller before this ticket walked one worktree group at a time and stayed
under the limit; the first caller to walk all 2256 transcripts in one pass hit
it immediately. Replaced with a loop, exported so the fold is testable
directly, and covered with a 300 000-interval assertion rather than a quarter
of a million real files. This is a latent BL-664 defect, not a new one — it
was simply unreachable until a consumer existed, which is the ticket.

**3. The store grew on every tick while claiming to be idempotent.** Keying a
window on its exact start/end looks idempotent and is not: the walk's window
ends a little later on every daemon cycle, so each tick appended a new row.
Now keyed on `window_day` and UPSERTED — one row per UTC day, always carrying
that day's latest numbers, bounded for an every-tick sweep.

## Spec observation — invariant 2, raised not worked around

Invariant 2 says a window containing an "unreadable or partial" transcript is
reported incomplete and contributes no share. Implemented strictly first, then
measured: on the live repo **6 of 2256** transcripts were "partial", and every
one was the same shape — the FINAL line torn, on a transcript whose agent was
mid-append at that moment. Every record before it was whole.

Read strictly, six agents working normally make the entire 2256-transcript
window incomplete, so the producer can never publish a share at all — which is
precisely the outcome this ticket exists to end.

So the parcel distinguishes them:

- a torn **final** line, every earlier line whole → readable; the unfinished
  record is simply not yet part of the window. Named in
  `truncated_tail_transcripts` so the condition is **recorded, not absorbed**.
- a bad line with a complete line **after** it, or a path that cannot be read
  at all → unreadable; the window is incomplete and no stage reports a share.

A file whose ONLY line is unparseable falls in the first class deliberately: a
brand-new transcript's first record can be mid-write, and nothing distinguishes
that from garbage. A fast-check counterexample caught exactly this case and the
test was wrong, not the code.

**This is a coder reading of the specifier's words, so it went to the specifier
as a priority-`00` note in the same pass** rather than being settled here. If
the specifier wants the strict reading, the change is one branch and the
consequence is that the producer publishes nothing while any agent is running.

## Declared invariants (BL-654)

All three have a coder-authored property test in this parcel, each shown
non-vacuous against a deliberately broken implementation, each independent
(breaking one failed only its own property):

- **Invariant 1** (absent, never zero) — broke it by seeding every trail stage
  at zero → `a stage nobody worked is absent` failed; 2 and 3 still passed.
  Generator floors asserted: at least one run leaving a stage unworked, at
  least one working several.
- **Invariant 2** (fail closed) — broke it by walking the readable remainder →
  `one damaged transcript refuses the whole window` failed. Floors: interior
  damage, a missing file, and an unreadable path all generated. A directory is
  used for the unreadable-path case rather than `chmod`, which
  engineering.prompt forbids for failure simulation. The **tolerated** face has
  its own property, so the torn-tail decision does not rest on one example.
- **Invariant 3** (no restated category set) — broke it by restating a
  two-element list in `turnProfile.ts` → `the stored category set is exactly
  the walker's own` failed. It also asserts the shares SUM TO 1, so a category
  the walker emits but the record omits is caught even if the key set were
  faked.

Invariant 3 needed one production change to be encodable at all: `IntervalCategory`
was a TYPE, which vanishes at runtime, so anything enumerating categories had to
restate them. It is now derived from an exported `INTERVAL_CATEGORIES` tuple —
same six members, same order, no classification change.

## Self-audit findings, fixed before forwarding

**1. The window record was assembled twice.** `buildTurnProfileWindowRecord`
(single group, trail-attributed) and `buildTurnProfileWindowForGroups` (the
production path, worktree-attributed) each built the record shape
independently. `window_day` had already had to be added to both copies during
this pass, which is exactly how two builders of one shape drift. Folded into a
single `assembleWindowRecord`; both entry points now differ only in how they
obtain intervals, which is the only thing that genuinely differs between them.
Re-verified: unit 18/18, properties 4/4, acceptance 8/8, BL-664 11/11, and the
live run still RECORDED then UPDATED with one row.

**2. qa_e2e step 6's prefix pre-sweep is deliberately NOT implemented.** The
step asks for a fixture root removed in a `finally` AND a sweep by prefix
before the run (BL-971). The `finally` is there - the property tests use
`withRoot`, and `mkTmpDir` additionally registers every root for the shared
per-test sweep, so roots are double-covered.

The pre-sweep is not, and that is a decision rather than an omission. BL-971's
"sweep the prefix before the run too" is a rule for a suite that runs ONE AT A
TIME, where nothing else owns those roots. These property tests run under
Vitest and several roles run their suites at once; a blind `rm -rf
"$TMPDIR/<prefix>"*` would delete a concurrent run's fixtures mid-test. That is
the BL-1390 storm the shared `lib/fixture_isolation.sh` exists to prevent, and
its own header says so. Recorded here rather than silently skipped - if the
specifier wants the pre-sweep, it should be owner-pid/age based through that
library, not a prefix glob.
