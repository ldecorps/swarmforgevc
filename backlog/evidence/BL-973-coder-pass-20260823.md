### The shell side, and BL-897

Shell fixtures cannot require the JS helper, so `bb_load_closure_lib.bb` is its
Babashka twin, with `bb_load_closure_cli.bb` as the seam and
`lib/bb_closure_copy.sh` as the one shared `copy_bb_closure` both shell
fixtures call. Per BL-897 — *a rule mirrored across a language boundary needs a
test asserting both agree; a "kept in sync" comment is not a gate* —
`bb_load_closure_agreement_test_runner.bb` runs **both** walks over the real
tree for **all four** entry points the fixtures drive, compares the transitive
sets *and* the direct-dependency parses, and asserts non-vacuously that both
parsers actually find edges in a fixture that has them (two parsers that both
returned nothing would otherwise "agree" forever).

### The guard reads behaviour, never source

`specs/pipeline/steps/lib/bbFixtureClosureGate.js` obtains each fixture's
**effective** copy set: the JS three export `BB_FIXTURE_CLOSURE`; the two shell
fixtures are *sourced and run into a scratch dir*, and what lands is the
answer. No source is parsed for a literal — a grep would pass against a
comment, which is exactly the failure mode here.

## Half 2 — no test sits unrun

`suite-manifest.tsv` accounts for all **360** test files in one lane each:
**356 standing, 4 excluded with a dated reason**. `run_bb_suite.sh` runs the
standing rows, so the runner's list *is* the manifest — one source of truth
rather than two that can disagree about what the suite is. It runs the
inventory gate first and refuses to proceed if the tree and the manifest have
diverged.

The four exclusions are evidence-backed, not convenience: each drives real tmux
or `kill_all_swarm.sh`, and a full sweep run from inside an agent pane killed
all eight live swarm sessions on 2026-08-22. **A failing test is never a reason
to exclude** — the manifest says so in its own header, because hiding a red
test here would restore the exact condition this ticket removes.

`suite_inventory_lib.bb` holds every decision (thin-wrapper rule); the CLI just
resolves the tree and renders. `suite_inventory_lib_test_runner.bb` is itself a
row in the manifest — the gate that notices unrun tests is not exempt from it.

## Declared invariants (BL-654) — both encoded, non-vacuity measured

Lane note: both are **bb** property runners rather than `*.property.test.js`,
following the repo's established shape for invariants whose subject is Babashka
source (bl1035, bl1043, bl1076). Still outside the unit lane, still run only on
purpose.

**Invariant 1** — `bl973_closure_guard_property_runner.bb`, 120 runs over
randomly shaped real `.bb` DAGs, with reachability computed by an independent
second implementation so the property is not the code checking itself.

| property | clause | breaks that kill it |
|---|---|---|
| P1 | "the real closure", both directions | depth-1 walk **118**; wrong entry **87**; whole directory **120** |
| P2 | "of the entry point that fixture actually drives" | wrong entry **120**; whole directory **120** |
| P3 | "a new edge upstream fails loudly" | — |
| P4 | armed-ness: not "everything in the directory" | whole directory **120** |

P3 survives the depth-1 break, which is recorded rather than hidden: the probe
edge attaches to the shallowest node, so a depth-1 walk still sees it. P1 holds
the depth. Neither covers the clause alone.

**Invariant 2** — `bl973_suite_inventory_property_runner.bb`, 200 runs, stated
as an **equivalence** because "it rejects bad manifests" alone is satisfied by
a gate that rejects everything.

| break | kills |
|---|---|
| accept any lane string | P1 17 |
| stop requiring a date on an exclusion | P1 11, **P3 66** |
| stop requiring a reason on an exclusion | P1 17, **P3 91** |
| report problems without naming the file | P2 51 |
| ignore files the manifest never lists | P1 19 |

P3 fires far more than P1 on the exclusion breaks, which is the argument for it
existing: P1 only notices when the manifest is otherwise sound. P3 objects per
row — what a gate satisfiable by excluding everything needs held against it.

Reach floors met in both: closure `deep-chain 120, diamond 111, multi-root 95,
unreachable-present 120, edge-added 120`; inventory `all-good 21, unlisted 59,
orphan-row 44, bad-lane 95, undated 80, unreasoned 104, duplicate 33`. Depth is
**derived** (a chain edge k→k+1 always present) rather than left to chance —
uniform edge draws give shallow trees, and transitivity is the whole invariant.

## Acceptance — 13/13, and non-vacuous

Proven by reverting `readLiveRoleHeldTicketsCli.test.js` to a frozen
hand-written array: scenario 02 row [3] and scenario 03 row [3] both go red,
naming exactly `daemon_cycle_guard_lib.bb, prompt_engine_lib.bb` — the two
files the ticket measured as missing. Restored.

Scenario 03 deserves a note. With a derived list nothing can be "missing", so
the guard would be untestable as written. The handler therefore **freezes** the
fixture's list as it stands today and measures that snapshot against a scratch
tree carrying one new load-file edge. That is what a hand-maintained list *is*
— a snapshot — so the scenario shows the guard firing on the event that has
actually caused this defect three times, rather than merely being present. The
scratch edge's presence in the closure is asserted before the check runs, so
the scenario cannot pass vacuously.
