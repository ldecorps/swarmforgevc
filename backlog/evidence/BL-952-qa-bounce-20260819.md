## D1 — acceptance scenario 10 fails only under `SWARMFORGE_ROLE=QA`, the
role that will always be the one running it

**Class**: `acceptance`.

**Failing command** (exactly as run):
```
specs/pipeline/scripts/run_acceptance.sh specs/features/BL-952-a-bounced-parcel-never-reads-as-qa-approved.feature
```
run with the ambient `SWARMFORGE_ROLE=QA` every QA session has set — not a
special flag, just this role's normal shell.

**Commit checked out**: `3d3a68315` (this worktree's merge of documenter's
`aeee53446c` into QA).

**First error excerpt**:
```
not ok 10 - every consumer of the predicate gets the same answer
  error: |-
    Scenario "every consumer of the predicate gets the same answer" failed
    at step "Then every consumer answers that it is not approved":
    check_pipeline consumer: a bounced merge-head must not exempt staged
    pipeline paths, got exit 0:
```
Reproduced identically on a second independent run (deterministic, not
flaky).

**Expected vs observed**: Expected `check_pipeline_code_on_main.sh`, run
against a staged pipeline-code file with `GITHEAD_<bounced-sha>` set (the
merge-head exemption's own env fallback), to REFUSE (non-zero exit) since
the merge head is a QA-bounced commit. Observed exit 0 (exempted).

**Root cause, independently traced, not assumed**: NOT a defect in the
merge-head exemption logic itself. Reproduced by hand in a throwaway
fixture (`/tmp/bl952-repro-*`, removed after): with `SWARMFORGE_ROLE`
unset, the exact same commands correctly refuse (exit 1, names
`extension/src/staged.ts`). With `SWARMFORGE_ROLE=QA` set, `bash -x`
shows the script exits at its own, unrelated, correct-by-design early
exit — `check_pipeline_code_on_main.sh`'s own `if [[
"${SWARMFORGE_ROLE:-}" == "QA" ]]; then exit 0; fi` (a deliberate
allowance for QA's own real git operations, not part of what this
scenario means to test) — before ever reaching the merge-head/bounce
logic under test.

The step handler's own subprocess spawn is the defect:
`specs/pipeline/steps/bl952BouncedParcelNeverApprovedSteps.js:386-390`
(`each consumer of the shared approval predicate is asked about it`,
Consumer 2):
```js
const guard = spawnSync('bash', ['swarmforge/scripts/check_pipeline_code_on_main.sh'], {
  cwd: root,
  encoding: 'utf8',
  env: { ...process.env, [`GITHEAD_${ctx.sha}`]: 'review-merge' },
});
```
`env: { ...process.env, ... }` inherits whatever `SWARMFORGE_ROLE` the
process running the acceptance suite happens to have set, instead of
neutralizing it the way `startDaemon()` elsewhere in this same file
deliberately deletes `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`/
`RESEND_API_KEY` before spawning. Consumer 1 (`askPredicate`, calling
`is_qa_ancestor.sh` directly) is unaffected — that script never reads
`SWARMFORGE_ROLE` — which is exactly why only the second assertion in
this scenario fails, not the first.

**Why this is real and not a QA-environment quirk to route around**: the
architect and hardener both independently ran this same acceptance suite
and reported it green — correctly, in their own sessions, because their
`SWARMFORGE_ROLE` is `architect`/`hardender`, not `QA`, so the leak never
fires for them. But QA is the role whose environment this scenario will
ALWAYS run under from here on — every future QA verification of this
feature file inherits the same false pass/fail depending on which role
happens to invoke it, which defeats invariant 2 ("every consumer... gets
the same answer from one definition") as a *test*, even though the
production code the test is supposed to gate is itself correct. A
regression in the real merge-head exemption logic would currently go
undetected by this scenario specifically when QA runs it, since the test
never reaches the code path it claims to exercise.

**Not the actual production code's fault**: independently confirmed with
`env -u SWARMFORGE_ROLE` that `check_pipeline_code_on_main.sh` and
`is_qa_ancestor.sh` both behave exactly as invariant 2 requires. This is a
test-fixture isolation defect, not a functional regression.

## Remediation (direction, not mandate)
In `bl952BouncedParcelNeverApprovedSteps.js`'s Consumer 2 spawn (and
`askPredicate` too, for defensive symmetry even though it is not
currently affected), delete `SWARMFORGE_ROLE` from the spawned env before
setting the `GITHEAD_<sha>` override — the scenario means to simulate a
generic git-hook caller, not literally re-grant QA's own real bypass.
