# BL-1615 coder pass

## What changed

`handoff_lib.bb` gains two functions beside `stage-queue-dir`:

- `claim-queue-dirs` — `(distinct [(stage-queue-dir state) (my-mailbox-dir state)])`.
  Collapses to one directory exactly when the two already coincide (a bare
  single-seat role, or a master-resident roster row - BL-1515's shape),
  since `mailbox-base-dir` resolves identically for either in that case.
- `claim-stage-handoff-files` — `stage-handoff-files` unioned across every
  directory `claim-queue-dirs` names, each file offered once (deduped by
  basename), sorted by the one filename order across both.

`ready_for_next_task.bb`'s fresh-dequeue path now reads `new-files` from
`handoff-lib/claim-stage-handoff-files :new` instead of
`stage-handoff-files new-dir` alone, and the create-dirs loop creates every
directory `handoff-lib/claim-queue-dirs :new` names (so a seat's own new/
is created even on its very first turn). `new-dir` itself (still
`stage-queue-dir :new`) is UNCHANGED as the resume path's and
`requeue-and-refuse!`'s single target - a BRANCH_CLAIM_MISMATCH requeue
still lands in the shared stage queue; this is safe because
`stage-handoff-files`'s own `recipient` filter (not directory placement)
is what keeps a sibling seat from ever LISTING seat-addressed mail (a
requeued file addressed to seat X is never offered to seat Y regardless of
which of the two directories physically holds it) - constraints explicitly
scope this parcel to the claim path, never the guard/requeue functions.

`ready_for_next_batch.bb` does not read `stage-queue-dir` at all (grepped,
confirmed) - out of scope, per the ticket's own direction ("say so in the
evidence and leave it").

## Why not a bb unit runner too

`claim-queue-dirs`/`claim-stage-handoff-files` (and `stage-queue-dir`
before them) resolve through `current-role`, which reads
`SWARMFORGE_ROLE` from the process environment - there is no in-process
seam to flip that for a second case inside one bb invocation, so unit
coverage isn't practical without a real subprocess per case. That
coverage instead lives in the acceptance feature's real-subprocess
scenarios below (the same posture every other roles.tsv-dependent
`handoff_lib.bb` function in this codebase already has - none of
`stage-queue-dir`, `difficulty-allows-claim?`, `stage-sibling-seats` etc.
carry a bb unit runner either).

scenario 03's "two directories coincide" case.

- Scenario 01 (4 rows): a stage-addressed `git_handoff` sent to `coder` is
  claimed by `coder@2` from the stage queue; a non-forwarding copy and a
  plain note addressed straight to `coder@2`'s own `new/` are each claimed
  by `coder@2` from its own box; the same seat-addressed copy is NOT
  listed when `coder` (not `coder@2`) asks - `coder` prints `NO_TASK` and
  the file stays untouched in `coder@2`'s own `new/` (invariant 2).
- Scenario 02: a priority-10 note in the stage queue and a priority-00
  seat-addressed copy in `coder@2`'s own `new/` - the priority-00 copy is
  claimed first, the one filename sort spanning both directories
  (invariant 1).
- Scenario 03 (2 rows): `cleaner` (bare) and `specifier` (rewritten to a
  master-resident row sharing `coordinator`'s checkout path) each see
  their one seat-addressed note exactly once and claim it - their two
  candidate directories coincide, so nothing is offered twice.
