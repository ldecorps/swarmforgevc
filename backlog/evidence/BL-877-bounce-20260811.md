## D1 — the reaper's "liveness could not be determined" message bypasses the caller's own `:log!` override

- **File**: `swarmforge/scripts/fixture_reaper_sweep_lib.bb`
- **Failing test**: `swarmforge/scripts/test/test_operator_runtime_fixture_reaper_sweep_liveness_undetermined.sh`
  (new, committed with this evidence) — check "undetermined: the reaper
  records its own distinct liveness-undetermined message" fails.
- **Commit hash**: `729a4e9445`
- **Class**: behavior

`default-adapters` (lines ~140-163) computes `pid->paths` and, when it is
`nil` (neither `/proc` nor `lsof` reachable), logs the warning **eagerly,
using its own local `default-log!` (`println`)** — before returning the
adapters map:

```clojure
(defn default-adapters []
  (let [log! default-log!
        pid->paths (live-process-paths!)]
    (when (nil? pid->paths)
      (log! "liveness could not be determined this pass (no /proc, no lsof) - killing nothing this pass"))
    {:list-entries! ...
     ...
     :log! log!}))
```

`operator_runtime.bb` (the only real daemon caller) does:

```clojure
(fixture-reaper-sweep-lib/sweep!
 (assoc (fixture-reaper-sweep-lib/default-adapters)
        :log! (fn [msg] (log! "fixture-reaper-sweep" msg))))
```

`assoc` runs *after* `default-adapters` has already returned — so the
liveness-undetermined message has already fired via `default-log!`
(`println` to stdout) by the time the override takes effect. Every other
log line this sweep produces (e.g. `sweep!`'s own "reaped N of M scanned")
goes through the overridden `:log!` and lands in `runtime.log` with a
timestamp and the `fixture-reaper-sweep` component prefix. This one message
does not — reproduced directly:

```
$ SWARMFORGE_LSOF_BIN=/nonexistent/... bb operator_runtime.bb "$PROJECT" --tick-once
fixture-reaper-sweep: liveness could not be determined this pass (no /proc, no lsof) - killing nothing this pass
{"state":"dispatching",...}

$ cat "$PROJECT/.swarmforge/operator/runtime.log"
2026-08-11T07:48:18.142037Z sandbox-sweep liveness could not be determined this pass (no /proc, no lsof) - treating every candidate as potentially live
2026-08-11T07:48:18.160159Z fixture-reaper-sweep reaped 1 of 1 scanned
...
```
— note the sandbox-sweep sibling's equivalent message (right above it) is
timestamped and structured; the reaper's own message is neither, and is
missing from `runtime.log` entirely under the project's own test/verify
convention (`--tick-once ... > /dev/null`, used by every existing wiring
test in this file), because that convention captures the daemon's real
stdout redirect (`start_operator_runtime.sh`'s `>> "$LOG" 2>&1`) which the
tests deliberately discard to isolate `runtime.log`'s own content.

This is not cosmetic: `default-adapters`'s own docstring states its purpose
is so "a caller ... that wants its own `:log!` (writing into its own
runtime.log instead of stdout) can override just that one key without
hand-duplicating every other real adapter here" — that promise is false for
this one message. It also means the exact class of gap this ticket exists
to close (BL-877's own notes: "a check whose only consumer is a test that
cannot run on this host") reproduces one level down, inside BL-877's own new
code: no test using this project's own established wiring-test convention
can ever see this message, because that convention's `--tick-once ...
> /dev/null` is exactly what discards it. Confirmed non-vacuous: the two
sibling checks in the same new test (process survives, root still removed)
pass — only the log-content check fails, isolating this to the log-routing
defect specifically, not a broader wiring break.

**The safety-relevant behavior itself is correct** — `pids-rooted-in`
already treats a `nil` `:pid->paths` the same as an empty map (Clojure's
`filter` over `nil` is a safe no-op returning `()`), so the reaper kills
nothing when liveness is undetermined, independent of this logging defect.
Verified directly: the new test's other two checks pass.

**Suggested fix** (not applied — outside hardener's remit to change
production behavior): move the `(when (nil? pid->paths) (log! ...))` check
out of `default-adapters` and into `sweep!` itself, using `(:log!
adapters)` — the same pattern `operator_runtime.bb`'s own sandbox-sweep-tick
code already follows (checks `determined?` and logs via its own `log!`
*before* calling into the pure sweep, using the final, already-resolved
logger). `sweep!` already receives the fully-assoc'd adapters map by the
time it runs, so this closes the gap without changing the message content,
the invariant, or either consumer's safe-direction behavior — only *which*
logger a caller's override actually reaches.

## Verdict

One real defect (D1), isolated to logging/observability, not to the safety
invariant itself. The five pre-existing required-wiring tests and the full
7-scenario acceptance suite (independently re-run this pass) all still
pass; this gap was invisible to every existing test because none of them
exercised the reaper's own undetermined-liveness path end to end through
`operator_runtime.bb`. Bouncing to coder — this ticket's own new code,
requires a production `.bb` change outside hardener's remit ("does not
introduce new product behavior").
