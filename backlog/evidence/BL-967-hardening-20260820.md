### The leak check, and why the raw number lied

The step file spawns a REAL `handoffd.bb` per scenario and reaps tracked pids
with `SIGKILL` in `afterEach`. The daemon spawns its own `bb`/`node` children,
which SIGKILL on the parent does not reach — the BL-928 "reap the parent too"
hazard, inverted. So the acceptance run was instrumented with a process-table
and fixture-dir count before and after.

The raw counter came back `AFTER_COUNT=1`, which looks like a leak and is not:
it piped `ps` into `grep -c`, and in a pipeline grep's own command line is in
`ps`'s output and self-matches. The `grep -v grep` variant printed nothing, 0
fixture dirs remained, and a live check afterwards found nothing. **No leak** —
the teardown is sound. Recorded because the misleading number is the kind of
thing that gets copied forward as a finding.

Fixture roots are under `os.tmpdir()`, not the repo, so the live
`handoffd_supervisor.bb` does not reap them (the role article's BL-321 trap).

### M2 was real, and is now closed

Deleting `(process/destroy-tree proc)` passed the whole unit AND property
suite. The existing tests prove a timeout HAPPENS — caller freed, `124`
returned, `on-timeout!` fired — but none proved the wedged child DIED.

That is invariant 1's second half. "A wedged tmux/git process may cost one
bounded wait, never the heartbeat" holds only if the process is reaped;
otherwise every timeout leaks a live child into a daemon whose entire failure
mode is a restart storm, and it compounds silently because the caller sees an
ordinary failure and moves on.

Closed by a BEHAVIOURAL assertion rather than pid bookkeeping: the child would
write a marker file shortly after the bound, so a destroyed tree never writes
it and a surviving orphan does. Only `destroy-tree` distinguishes the two.
Non-vacuity verified — unit runner exit 0 unmutated, exit 1 against the M2
mutant.

### M3 was a FALSE survivor — my harness, not the code

M3 ("a timeout reports success, exit 124 -> 0") was first reported as a
survivor. It is not: the runner already asserts `124` on the timeout path.

The mutation had matched the FIRST occurrence of the literal
`{:exit 124 :out ""`, which is a **comment on line 9**; the code site is line
81. The file's bytes changed, so the harness's no-op guard passed, while the
code was untouched — a byte-level diff cannot tell prose from code. Mutating
the real code site kills it immediately (`exit 1`).

Recorded because it cut both ways: it invented a defect that did not exist,
and it meant the sweep was not measuring what it claimed. The harness now
strips `;;` lines before deciding whether a mutation landed, and the sweep
was re-run from scratch under the corrected rule.
