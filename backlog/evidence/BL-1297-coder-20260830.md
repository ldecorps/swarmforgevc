# BL-1297 — coder pass, 2026-08-30

A merge commit's own changed paths are computed, not silently empty.

## 1. The change

`task_scope_gate_lib.bb`'s private `own-commit-diff` ran

```
git diff-tree --no-commit-id --name-only -r --first-parent <commit>
```

which prints NOTHING for a merge: git suppresses a merge's diff unless
`-m`/`-c`/`--cc` is given, and `--first-parent` is a `log`/`rev-list`
traversal flag with no effect on `diff-tree`'s own diff output. It is now
public `own-commit-changed-paths`, and diffs the commit's FIRST PARENT
against the commit:

```clojure
(let [parent (git! root "rev-parse" "-q" "--verify" (str commit "^1^{commit}"))
      diff (if (zero? (:exit parent))
             (git! root "diff-tree" "--no-commit-id" "--name-only" "-r"
                   (str/trim (:out parent)) commit)
             (let [resolves (git! root "rev-parse" "-q" "--verify" (str commit "^{commit}"))]
               (if (zero? (:exit resolves))
                 (git! root "diff-tree" "--no-commit-id" "--name-only" "-r" "--root" commit)
                 resolves)))]
  (when (zero? (:exit diff))
    (remove str/blank? (str/split-lines (:out diff)))))
```

Three deliberate choices, each of which the tests can tell apart from its
alternative:

- **First-parent, not `-m`.** The ticket wrote this as direction rather than
  mandate and the two answers really do differ. `-m` unions the per-parent
  diffs, which attributes the RECEIVING branch's own prior work to the
  incoming parcel — a different question, and a stricter gate than any of the
  three callers asked for. Every merge fixture here carries a path on the
  first parent that a `-m` implementation would name and this one does not,
  so the choice is asserted, not just documented (break table in §5).
- **`diff-tree` plumbing, not `git diff`.** The ticket's measurement used
  `git diff --name-only <c>^1 <c>`, which is the same first-parent semantic,
  but porcelain `git diff` has rename detection ON by default while
  `diff-tree` does not — a rename would report one path instead of two and
  scenario 04 would be quietly false. The two-tree `diff-tree` form is the
  same plumbing walk the code already used.
- **A root commit reports the tree it introduced (`--root`)**, never nothing.
  Answering nothing there would pass the gate open on a foreign path in
  exactly the way the merge blind spot did. An unreadable commit still
  answers `nil`, which is the distinct "the walk failed" signal all three
  callers already branch on.

`land_step_lib.bb`'s `diff-readable?` probe was a SECOND, independent
invocation of the old command. It now asks through
`own-commit-changed-paths` too — a probe that reads a commit differently
from the walk it vouches for can call a commit readable whose paths the walk
then silently drops, which is invariant 2's own failure shape one door down.

## 4. Declared invariants (BL-654) — both executable

`extension/test/bl1297MergeOwnPathsInvariants.property.test.js`,
`npm run test:properties` lane. 2 properties, both pass.

**Invariant 1** builds a real repository per case across five commit shapes —
`single-parent`, `merge`, `octopus-merge`, `empty-merge`, `root` — and
compares the reported paths against the set the GENERATOR CONSTRUCTED, never
against another `git diff-tree` invocation. An oracle that re-ran git would
be tautological with the code under test.

**Invariant 2** pins both bases to the same boundary (a recorded origin/main,
no handoff archive) and asserts caller 1 (`parcel-own-changed-paths`, the
seam both send-time gates share) and caller 2 (`land-step-lib/own-paths`)
return byte-equal answers, that the answer equals the constructed set, and
that caller 3 (`unregistered-test-gate-lib/findings-for-git-handoff`) finds
the parcel's unregistered test file exactly when the shared walk contains it.
`empty-merge` — a merge whose two sides reach byte-identical content
independently — is the case that separates an HONEST empty answer from the
defect's artefact, and it is generated on purpose.

**Generator reach is constructed, not hoped for.** Every shape is run
outright before any random draw, and each has an asserted floor. This is not
theoretical: the first green run of this file drew `empty-merge` zero times
in 16 random runs and the floor assertion caught it. A purely random draw
over five shapes misses one at these run counts often enough to matter.

## 7. A consequence downstream roles will meet immediately

With this fix, a merge commit whose SUBJECT names a ticket puts everything
that merge carried in into that ticket's scope. That is correct for the hop
merge every role does to receive a parcel — the incoming content really is
the parcel. It is NOT correct for a bookkeeping sync of `main`, which carries
every other ticket's landed backlog moves.

This parcel's own `main` merge (`dd581cb7cd`) therefore carries a subject that
names no ticket, and says so in its body. Naming BL-1297 there would have made
BL-1210, BL-1218, BL-1225, BL-1240, BL-1252, BL-1253, BL-1264, BL-472 and
BL-692's backlog files this parcel's own foreign scope, and the gate would
have refused this very send — correctly, under the repaired rule.

Nothing in the gate was weakened to make that go away, and no
`abandoned_commits` or `retires:` entry was added: both would have put a
false statement in a durable ticket contract to buy one send.
