## The fix (ruling B, replacing option 2's raw-core-count default)

`extension/src/tools/vitest-worker-memory-budget.ts`: new
`resolveFreeCoresCeiling(cores, loadAvg5min)` — `max(1, min(cores,
floor(cores - loadAvg5min)))`. Pure, no os/env read (both read by the
caller, per this module's own testability rule). Both
`vitest.config.mjs` and `vitest.properties.config.mjs` now pass
`defaultCeiling: resolveFreeCoresCeiling(os.cpus().length,
os.loadavg()[1])` in place of option 2's flat `os.cpus().length` — the
one composition point (`resolveVitestWorkerPool`) and its own contract
are otherwise untouched; ruling B only changes what value the two
callers compute and pass in.

`PER_WORKER_HEAP_MB` (1280→640, measured 298 MB peak) and `MAX_WORKERS`
(6, unchanged fallback) are unaffected by this pass — they were already
correct under every ruling option per the ticket's own notes.

## Why the acceptance feature needed no change

`resolveVitestWorkerPool`'s and `resolveVitestForkCeiling`'s own
contracts are unchanged by ruling B — only the VALUE the two real config
files compute for `defaultCeiling` changed, and the acceptance handler
(`bl1348ForkPoolSizesToTheRealHostSteps.js`) never passes `defaultCeiling`
at all (confirmed by reading it), so its scenarios exercise the pack/
platform/override/RAM rules only, unaffected either way. A "full-forge on
linux" *outline* row was floated in the ticket's approval_context, but
`resolveFreeCoresCeiling`'s own input (a live 5-minute load average)
cannot be pinned into a deterministic Gherkin Example without either
faking `os.loadavg()` (a second os-read seam this module deliberately has
none of) or measuring a real, unstable host signal in an acceptance run —
exactly why the ticket's own IR-DRY notes already declined to pin a
resolveVitestWorkerPool-level number "this ticket has no authority to pin
yet". `resolveFreeCoresCeiling` is instead unit- and property-tested
directly against explicit, deterministic `(cores, loadAvg)` pairs (below).

## Addendum: spec-gap bounce, scenario 03 added (2026-09-07, same day)

The reasoning above ("Why the acceptance feature needed no change") was
half right and half a missed option: `resolveVitestWorkerPool`'s contract
genuinely didn't change, but the ticket's own `approval_context` had
promised a feature amendment once ruled ("the feature gains one Examples
row for full-forge on linux"), and that promise was never kept — the
Given-step objection above (faking `os.loadavg()`) turned out to be a
false constraint: the ruled fix is to INJECT `cores`/`loadAvg5min` as
explicit Given-step values, exactly the shape `resolveVitestWorkerPool`'s
own `hostRamMB` parameter already uses, never a live `os.loadavg()` read
inside the acceptance run. The specifier caught this as a spec-gap
(`4822211fbc`) after the parcel had already reached the documenter, and
per BL-1385's routing (a spec-gap re-enters the parcel at the coder, not
on `main`) sent it back here as a `note` rather than a `git_handoff`
(nothing to merge - the parcel's code was already correct; only the spec
was incomplete). Added, verbatim per the specifier's notes:

- `specs/features/BL-1348-fork-pool-sizes-to-the-real-host.feature`:
  Scenario Outline `no-override-follows-free-cores-03` (3 Examples rows:
  20/12→8, 20/17→3, 20/19.5→1, each `max(1, floor(cores - load))`, all
  well under the RAM cap so scenario 02 alone owns that bound), plus one
  narrative sentence stating ruling B's rule in prose.
- `specs/pipeline/steps/bl1348ForkPoolSizesToTheRealHostSteps.js`: new
  Given step `a full-forge pack on linux with <cores> cores, <ram> MB of
