# BL-1684: the pipeline board's caption cap budgets the escaped length — coder

## What changed

`extension/src/concierge/pipelineBoard.ts`:

1. `truncateCaptionDescription` now budgets `escapeHtml(text).length` (the
   RENDERED length), never `text.length` (the raw one). When the escaped
   length already fits, the text is returned unchanged, byte-identical to
   before (no behavior change for the common case — including
   `deriveListEntryText`'s own kebab-slug callers, whose output can never
   contain `&`/`<`/`>` at all). When it doesn't fit, a binary search on the
   cut index finds the largest raw-char prefix whose escaped length still
   fits the budget — escaped length is monotonic non-decreasing in the
   number of raw chars kept, so this is well-defined and never cuts
   mid-entity.
2. `composePipelineBoardHtml` gains a last-resort fallback: if the body is
   STILL over `maxLength` even after every link is dropped (every
   existing cap now bounds this in practice, but the FIRM invariant is
   unconditional), it returns a minimal, well-formed, visibly-marked
   `<pre>` message naming the row count, rather than the old unconditional
   return of whatever `buildPipelineBoardHtml` produced — a truncated
   mid-tag HTML string would risk Telegram rejecting it on malformed-
   markup grounds on top of the length one.
3. The `PIPELINE_BOARD_MESSAGE_MAX_LENGTH` comment corrected: the safety
   margin was never what absorbed HTML entity expansion (it couldn't,
   against an unbounded escapable-row count) — the caption cap and the
   compose-level fallback are the actual two-layer defence.

`extension/test/bl956PipelineBoardCaptionCapInvariants.property.test.js`:
added a pinned `{ seed: 10, numRuns: 1500 }` regression test alongside the
existing unpinned invariant-1 property (per the ticket's own instruction)
— the specifier's own recorded counterexample now runs every lane pass,
not roughly once in two hundred.
