# BL-1427 — coder pass, 2026-09-05

## What landed

`swarmforge/scripts/check_bb_scripts_load.sh`'s probe (`analyse_one`) used
to run `bb -e "(load-file \"$file\")"` inside a `while read < <(process
substitution)` loop reading `changed_bb_files`' output. Two real defects:

1. **Drained loop.** The probe's stdin was the loop's own file list. A
   script whose load-time code reads stdin (`harness_env_scrub_names.bb`)
   swallowed the rest of the list; `--all` analysed 107 of 286 scripts on
   2026-09-05 and reported the other 178 as clean, `post_qa_branch_sweep.bb`
   among them (BL-1426).
2. **Executed entry calls.** `load-file` runs a script's trailing entry
   call too, so a healthy CLI whose `-main` has a fixed, non-zero arity
   (`check_swarm_detached.bb`, `clear_identical_untracked_and_merge.bb`)
   threw `ArityException` under the probe's empty argv and was refused
   although it loads and runs correctly with real arguments.

### The fix

- **`swarmforge/scripts/bb_load_analyse_driver.bb`** (new): reads the
  target's forms one at a time with a `LineNumberingPushbackReader` and
  `eval`s each EXCEPT a call whose head is `-main` (bare, with
  `*command-line-args*`, or through `apply`) — read, never run. Every
  `def`/`defn` is still evaluated eagerly (SCI's own eager analysis is
  unchanged), so a missing symbol or forward reference inside `-main` or
  any other `defn` still refuses exactly as before. `*file*` is bound to
  the target's own path (213 scripts in this tree compute their own
  location via `*file*` at load time, not only inside `-main`). The
  target path travels through an env var (`BB_LOAD_ANALYSE_TARGET`), never
  a positional `*command-line-args*` entry — `*command-line-args*` is one
  var for the WHOLE bb process, and a positional arg here leaked into
  `post_commit_push.bb`'s own top-level `(load-file (first
  *command-line-args*))`, which then load-filed the driver's OWN
  invocation path recursively to a `StackOverflowError` (found and fixed
  during this ticket's own testing, not a pre-existing defect in that
  script). This driver's own real work lives inside `-main` too, since
  `--all` analyses it like any other `.bb` file under `swarmforge/scripts`
  — the first version ran its loop as bare top-level code, so
  self-analysis re-entered the same loop on the same file, to a second
  `StackOverflowError`; wrapping it in `-main` is this driver dogfooding
  the exact convention it exists to read.
- **`analyse_one`** now invokes the driver (`BB_LOAD_ANALYSE_TARGET="$file"
  ... bb "$SCRIPT_DIR/bb_load_analyse_driver.bb" </dev/null`) instead of
  a bare `load-file`. `boot_handoffd`'s own `bb` invocation also gains
  `</dev/null`.
- The main loop is captured into a bash ARRAY (`mapfile`) before iterating,
  never streamed through a pipe a probe could still drain by some future
  spelling; the listed count and the analysed count are compared, and a
  gap refuses naming how many scripts the loop never reached (invariant 1,
  belt-and-suspenders alongside `</dev/null`).

## Declared invariants (BL-654)

New property test: **`extension/test/bl1427LoadGuardCoversEveryScriptInvariants.property.test.js`**,
mirroring `bl1395BbScriptsLoadGuard.property.test.js`'s own fixture shape
(real git trees, real `spawnSync` on the real shell guard, never a
reimplementation).

- **Invariant 1** ("the guard's verdict covers every script it lists...
  analysed count equals the listed count") — **P1**: randomizes 0-4 filler
  scripts plus one stdin-reading script (always sorted first) and,
  independently, whether a reader-error script (always sorted last) is
  ALSO present. Asserts: no broken script → pass with the exact analysed
  count; a broken script present → refusal naming it, regardless of the
  stdin-reader's presence ahead of it. 30 runs.
- **Invariant 2** ("the probe executes no script's entry point... a
  script's runtime behaviour never decides the verdict") — **P2**:
  randomizes among the 3 entry-call shapes and `-main`'s own declared
  arity (0-2 fixed params). Asserts the guard passes (an arity mismatch
  under empty args would refuse a healthy script if it were EVER called)
  and a marker file `-main` would write never appears. 24 runs.
- **Invariant 3** ("recall is not lowered... still refuses naming the
  file, the line and the symbol") — **P3**: randomizes the entry-call
  shape wrapping an undefined-symbol `-main`. Asserts the refusal still
  names both the file and the unresolved symbol, whichever shape sits
  after the defect. 18 runs.

**Non-vacuity**, each mutation restored byte-identical (confirmed via
`diff` against a pre-break backup) before this commit:
- P1: reproducing the ORIGINAL bug required BOTH mutations together
  (reverting the loop to `while read < <(process substitution)` AND
  removing `</dev/null` from the probe) — either alone left the property
  passing, since the array-loop and the redirect are independently
  sufficient fixes for the scenarios this property generates. The
  combined mutation reproduced the exact defect: "check_bb_scripts_load: 1
  changed Babashka script(s) analysed, handoffd booted - all clean" on a
  tree that genuinely had a broken script sorted after the reader.
- P2: `entry-call?` mutated to always return `false` (never skip) — the
  marker file was written (`true !== false`), confirming the entry call
  ran.
- P3: `entry-call?` mutated to always return `true` (skip everything,
  including the `defn -main` form and its own analysis) — the guard
  silently passed a script with a genuine unresolved-symbol defect,
  reproducing the exact "recall lowered" failure mode.

**Reachability**: P1 (30 runs) covered both the has-broken/no-broken and
0-4-filler dimensions; P2 (24 runs) covered all 3 shapes × 3 arities; P3
(18 runs) covered all 3 shapes — all well above the `runs/10` floor.
