# BL-1390 — CODER REWORK 2, 2026-09-04

Second incident accepted in full: 1156 concurrent copies of this suite
exhausted the host. The established mechanism is mine — each copy began with a
**blind prefix sweep**, so every copy deleted every other copy's fixture
mid-run.

That is BL-971 misapplied. Its "sweep the prefix before the run too" is a rule
for a suite that runs ONE AT A TIME; the moment a suite can be invoked
concurrently the same line is a cross-run delete.

## Part of the multiplier, established rather than guessed

The amendment records the multiplier as unknown. I can name one factor and have
fixed it: **the acceptance handler ran the whole suite once per SCENARIO.** The
runtime hands each scenario a fresh ctx, so my per-ctx memo never hit — 7
invocations per feature, times every role running acceptance at once. The memo
is now at module scope: one run per process, shared by every scenario.

I am not claiming that accounts for 1156. It is the factor I could measure.

## What changed

New `swarmforge/scripts/test/lib/fixture_isolation.sh`, sourced by this suite
(and by BL-1363's and BL-1392's, which had the identical defect):

- **A lock.** At most one instance runs; a second waits up to a bound and then
  exits cleanly naming the holder's pid.
- **Reaping only what no live run owns.** Every root records its owner pid; a
  root whose owner is alive is never touched, and an unstamped root is removed
  only past a generous age. Never a blind prefix `rm`.
- **A wall-clock bound.** The suite re-execs itself once under `timeout`, so a
  wedged run ends by itself.
- **An invoker log line** (`SUITE_INVOKER pid= ppid= parent=`), so a future
  storm names its source.
- `FIXTURE_ISOLATION_NO_REAP` for a probe invocation: an instance that only
  wants to reach the lock decision can never delete anything, whichever path it
  takes. Closing the mechanism beat reasoning about whether it was reachable —
  and it was: with reaping merely "unreachable in theory", the suite still went
  red 3 times in 12.

Also, from the same red runs:

- The scripts tree is copied ONCE per run and symlinked per fixture. Six deep
  copies per run was heavy enough to race git's own object writes — observed as
  `fatal: object … cannot be read` during a fixture's push.
- The bare origin's HEAD is pinned to `main` at creation, so a clone can never
  land on an unborn branch.
- A failed seed aborts the run immediately: a broken fixture otherwise cascades
  into a page of failures that all describe the same one problem.

## Non-flakiness, measured rather than asserted

The architect's bounce was right that a single green run proves nothing, and my
previous evidence said "ALL PASS" from exactly one. Measured this pass:

| when | standalone runs | green |
|---|---|---|
| before the no-reap fix | 12 | 9 |
| before, earlier batch | 12 | 10 |
| **after** | **14** | **14** |
| **after** | **20** | **20** |

34 consecutive green standalone runs after the fix, and the acceptance path
(the other invocation shape) 3 for 3 at 7/7.

I am not claiming flakiness is impossible — a real-git suite on a loaded host
never earns that word. I am reporting 34/34 after a change that removes the one
mechanism I could prove was destroying fixtures, against 19/24 before it.
