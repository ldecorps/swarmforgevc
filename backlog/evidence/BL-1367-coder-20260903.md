## Declared invariants (BL-654)

`extension/test/bl1367ApprovalCarriesItsRuling.property.test.js` — the
TypeScript lane's standard home (`npm run test:properties`), which is the right
one here because this ticket's code is TypeScript.

| # | Invariant | Property | Non-vacuity |
|---|-----------|----------|-------------|
| 1 | never approved with `ruling_options` and no `human_ruling` | **P1** — for every declared/undeclared option set and every ruling, either the approval is recorded with a ruling or the file is byte-identical afterwards | let a bare approval through for an option-bearing ticket → **1 of 2 property tests failed** |
| 2 | an existing ruling is never overwritten or cleared | **P2** — a recorded ruling changes only when a **declared** option was just chosen, and is never cleared outright | cleared the ruling on a plain approval → **both property tests failed** |
| 3 | a ticket declaring no options approves exactly as today | **P3** — a bare approval always succeeds and writes no ruling; a ruling nobody offered is refused | (same breaks) |

**Generator reach is asserted.** A ruling drawn independently of the options
would match one essentially never, so the accepted case — the only one that
writes a ruling at all — is **constructed**: the chosen label is drawn *from*
the generated option list. The run then fails unless all five outcomes
(`options:ok`, `options:ruling-required`, `options:unknown-option`,
`no-options:ok`, `no-options:unknown-option`) were actually generated.

## Decisions worth the reviewer's eye

- **Validation is the caller's job, not the writer's.** `recordApprovalReply`
  is told what to write; a caller that has not asked
  `classifyApprovalRulingRequirement` is not silently rescued inside the
  writer. Rescuing it there would hide exactly the class of surface this
  ticket exists to catch — one that records without asking.
- **A ruling offered for a ticket that poses no choice is refused**, not
  silently written. Nothing declared it, so nothing can validate it, and a
  `human_ruling` on an optionless ticket is the same unanswerable state in the
  other direction.
- **Blank is not an answer.** A surface sending an empty `ruling` field trips
  the same refusal a missing one does.
- **A non-string `ruling` is rejected rather than coerced** at the request
  shape: a ruling is written into the ticket, and a coerced one would be a
  fabricated answer.
- The acceptance handler drives the **real HTTP route**, not the classifier.
  A scenario that called the classifier alone would report green for a
  decision that is right and not reached — which is this defect's own shape,
  one surface having the writer and the other not.

## Surfaced, not swept: a second surface with the same shape

`/paused-pager/expedite` (`handlePausedPagerExpediteRoute`,
`bridgeServer.ts:783`) also calls `recordApprovalReply` with no ruling, so an
Expedite tap on an option-bearing ticket still leaves it approved with the
choice unanswered — invariant 1's shape, on a route this ticket does not name.

**I did not change it, deliberately.** BL-1083 records that this route must
record the approval *before* the gates are consulted, precisely so Expedite
satisfies the `human_approval` gate rather than being blocked by it, and warns
in the code that a fix letting approval refuse an expedite "would leave the
verb dead — the over-correction this ticket explicitly warns against". Copying
the refusal there would reverse a recorded decision, which is not a coder call.
The ticket's `required_wiring` names `computePausedPagerApproveOutcome` and its
description scopes the fix to the Approve route.

**For the specifier**: closing invariant 1 across every surface needs a ruling
on which wins — BL-1083's "expedite is never blocked" or BL-1367's "never
approved with the choice unanswered". A middle path exists (expedite records
consent *and* leaves the ticket pending its ruling) but it is a new state, not
an adjustment.
