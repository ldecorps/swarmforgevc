# BL-1626 coder pass

## Declared invariant - encoding

"A fixture that copies a Babashka entry point carries that entry point's
whole transitive load-file closure, derived from the sources at build time -
never a hand-maintained list." Encoded directly: `bl803PromoteRouteSedBsdPortabilitySteps.js`
and `bl1028PromotionRefusalSteps.js` no longer hand-list the promotion chain's
`.bb` files; both now call `copyScriptClosure(SCRIPTS_DIR, targetDir,
['promotion_gates_cli.bb'])` (BL-1538's helper), which derives the closure by
reading each load-file form at fixture-build time. `bl1100PromotionProseNeverBlocksSteps.js`
already used `computeClosure` - untouched on that front. Coverage: acceptance
scenario 01 (Scenario Outline over both fixed handlers) diffs each real
built fixture directory against `computeClosure(SCRIPTS_DIR,
'promotion_gates_cli.bb')` and asserts nothing is missing; scenario 03 is
the census, asserting every handler that copies the promote chain requires
one of the closure-deriving helpers, so a future hand-list regression on any
copier is caught, not just these two.

## What was wrong, and the fix

Three landed acceptance features were red on main with no lane running them
(BL-1625/1628 fix that separately):

- **BL-803** (`bl803PromoteRouteSedBsdPortabilitySteps.js`): hand-copied
  `promotion_gates_cli.bb`, `promotion_gates_lib.bb`, `backlog_depth_lib.bb`,
  `swarm_identity_lib.bb` - missing `daemon_cycle_guard_lib.bb`
  (`backlog_depth_lib.bb` load-files it since BL-966, 2026-08-20). Fixed by
  replacing the hand list with `copyScriptClosure`.
- **BL-1028** (`bl1028PromotionRefusalSteps.js`): same shape, `GATE_DEPS`
  hand list missing `acceptance_pointer_gate_lib.bb`
  (`promotion_gates_lib.bb` load-files it since BL-626, 2026-08-25). Same
  fix.
- **BL-1100** (`bl1100PromotionProseNeverBlocksSteps.js`): already used
  `computeClosure` correctly for its own copies, so this one was never a
  closure problem.

Fixing the two closures alone did not turn BL-803/BL-1028 green: once the
gates a fixture's own eligibility check depends on stopped throwing on load,
both fixtures hit the freshness gate (`promote_and_route_next.sh`'s BL-1173
block) fail-closed, because neither fixture's root carried an `extension/`
tree for the gate's `deprecate_check_cli` resolver to find - the exact shape
the ticket's description attributed to bl1100 alone, but the two-stage
failure (eligibility first, freshness second) meant bl803/bl1028 never got
far enough to show it until the closure fix landed. All three fixture
builders (`bl803`, `bl1028`, `bl1100`) now `fs.symlinkSync` the real
`extension/` into the fixture root; bl1100 already did this via
`installExtensionLink` (added here), bl803/bl1028 gained the same call. The
gate then resolves the repository's real compiled `deprecate-check.js` and
answers on its own - never bypassed, per the ticket's FIRM constraint.

bl1028's fixture also asserts a clean index in one scenario
(`Given the index holds nothing staged`); the untracked symlink and a
`.gitignore` entry for it (`/extension`) both needed staging into the
fixture's own init commit (`git add ... .gitignore`) so the working tree
reads clean afterward.
