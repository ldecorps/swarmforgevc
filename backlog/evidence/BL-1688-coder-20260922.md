## Why python3, not bb, for the status read-merge-write

`test_start_handoff_daemon.sh` (and `test_bl785_freshness_deliberate_stop.sh`)
already put a FAKE `bb` binary on `PATH` that intercepts every `bb`
invocation this script makes, matching only the two daemon-launch
patterns and falling through to `exec true` (a silent no-op) for
anything else. A read-merge-write via a `bb` subprocess would have gone
through that same interception, silently no-op'd under those existing
fixtures, and broken their own `state=healthy` assertions. `python3` is
already a project-wide dependency in this script family (`install_aps_tools.sh`,
`ancillary_provider_lib.sh`, and this same test file's own JSON
assertions already shell out to it) and sits outside that interception
entirely.

## A regression I found and fixed

`test_bl785_freshness_deliberate_stop.sh` scenario 04 invokes the real
`start_handoff_daemon.sh` directly (simulating `./swarm`'s own launch,
proving "the real start script re-arms handoffd") without setting the
new required `SWARMFORGE_DAEMON_START_CALLER` signal. Under my new
caller gate this now (correctly) refuses, and `set -euo pipefail`
aborted the whole test file at that line. Fixed by setting
`SWARMFORGE_DAEMON_START_CALLER=swarmforge.sh` on that one invocation -
the scenario's own intent (a deliberate launch re-arms watching) is
unchanged, it just now has to say so explicitly, same as the real
`swarmforge.sh` already does at its own call site (line 2426). Full
suite re-run green after the fix (18 checks, `ALL CHECKS PASSED`).

## A coverage gap I found and closed

None of the four acceptance scenarios exercise the read-merge-write fix
against the REAL shell script: scenario 03 drives the in-process
`bl1492RestartInPlaceCli.bb` fixture, whose ledger accumulation was
already correct before this ticket (the supervisor's own `restart-daemon!`
writes an immutable in-memory snapshot merged with the new entry, which
already survives an interleaved subprocess's blind write within a single
tick - verified by reasoning and by deliberately breaking the real
script's fix and re-running the acceptance feature, which stayed 4/4
green). Only a SEPARATE, INDEPENDENT caller's blind write between two of
the supervisor's own ticks reproduces the real incident's mechanism, which
a single-process acceptance fixture cannot represent. Closed with a
dedicated real-script regression test,
`test_bl1688_status_ledger_survives_start.sh` (3 cases: an existing
ledger and every other field survive the start owner's own write; a
status file with no ledger still ends up healthy; no pre-existing status
file still creates none) - break-then-restore confirmed it catches the
regression (`KeyError: 'restart_history'` when reverted to the blind
overwrite).

## Invariants (BL-654)

1. "While the handoffd.stopped marker stands, an invocation... by any
   caller other than a deliberate launch... launches nothing and leaves
   [everything] byte-identical; the refusal is one audit line naming the
   marker." A finite, binary state space (caller deliberate or not, ×
   marker present or not) - the acceptance feature's own scenarios 01/02,
   driven against the REAL script via the new shell runner, are this
   invariant's coder-authored executable test. No separate property test
   adds anything.
2. "A restart_history entry the supervisor appends survives until it ages
   out of the budget window: no writer of handoffd.status.json... drops
   an entry another write appended..." Scenario 03 (three ticks through
   the real `respond-to-verdict!` wiring, the budget exhausting exactly as
   specified) plus the new `test_bl1688_status_ledger_survives_start.sh`
   (the real shell script's own write, in isolation) together cover three
   of the four named writers (the start owner's rewrite, `restart-daemon!`,
   `alarm-and-halt!`). The fourth (`check!`'s own healthy-write,
   `(write-status! (assoc status :state "healthy"))`) was never touched by
   this ticket and was already correct by construction before it - it
   `assoc`s onto a status map read fresh in the same call, so it cannot
   drop anything by design; not separately re-verified here since nothing
   about it changed. Same disposition as BL-1658's own precedent: a
   fast-check property adds nothing over these real, exhaustive scenarios
   for a state space this small; no separate property test added.
