## D1 — the "changed files" detection is the wrong technique, two ways

`rescue_orphaned_work.bb:62` computes the files a rescue commits from
`git diff --name-only HEAD` taken AFTER `stash apply` — i.e. "what is
currently uncommitted in the whole tree", not "what this specific stash
entry contains". This directly contradicts the coder's own stated design
(commit message: *"COMMIT onto the role's branch. Only the paths the
source touched - a rescue never sweeps whatever else the tree was
carrying"*) and violates **invariant 2** ("No role finds uncommitted
changes in its worktree that nothing accounts for... its owner is told
what and why") two independent ways:

**D1a — pre-existing uncommitted work on an already-tracked file is
silently swept into the rescue commit.** Reproduced end-to-end against the
real compiled CLI: a fixture repo with its own pre-existing uncommitted
edit to `mine.ts` (simulating a role's own in-progress ticket work already
sitting in its worktree), then a rescue of an unrelated stash touching only
`seat.ts`. The CLI reports `RESCUED ... (2 file(s))`, the commit's `Files:`
line lists `mine.ts, seat.ts`, and `git show HEAD:mine.ts` contains the
role's own unrelated edit — committed under a "Rescue orphaned work:
BL-981 seat-fold stash" message that does not describe what actually
happened. The note sent to the role's owner also mis-states "rescued 2
file(s)" when only one was the actual rescue target. This is a silent
sweep of legitimate, unrelated work under a misleading commit message —
the same class of harm invariant 2 exists to prevent, now automated rather
than manual.

**D1b — a stash whose orphaned work is a brand-new (never-staged,
untracked) file is missed entirely, and the CLI's own refusal leaves an
unaccounted-for file behind.** `git diff --name-only HEAD` does not report
untracked files at all. Reproduced end-to-end: a stash created with
`git stash push -u` carrying only a new untracked file. The CLI applies
the stash successfully (the file lands on disk), then `changed` comes back
empty, and the `(when (empty? changed) ...)` guard at line 66-67 fires:
`REFUSE nothing to rescue: applying the source changed no tracked file` —
factually wrong (something WAS applied) — exits 1, correctly leaves the
stash undropped (invariant 1 intact here), but leaves the newly-applied
file sitting **untracked and unaccounted for** in the target worktree with
no note, no cleanup, and a misleading error message. This is exactly the
state invariant 2 is written to forbid.

**Root cause, one fix for both:** derive the rescued path set from the
STASH ITSELF (e.g. `git stash show --name-only --include-untracked <ref>`,
read BEFORE or independently of applying it) rather than from a blanket
post-apply `git diff --name-only HEAD`. That would never pick up unrelated
pre-existing tracked-file edits (D1a) and would correctly include a
brand-new untracked file the stash carries (D1b).

**Why the current suites never caught this:** every fixture in
`test_rescue_orphaned_work.sh` and `bl1041RescueNeverReducesDurabilitySteps.js`
starts from a perfectly clean tree and stashes an existing tracked file
with a plain pathspec (`git stash push -- seat.ts`), so neither the
pre-existing-dirty-tree case (D1a) nor the untracked-new-file case (D1b) is
ever constructed. Recommend the fix add scenarios for both when it lands.
