# BL-1075 — coder pass

The swarm applied and documented `window-size largest` as a mitigation it could
never keep. It no longer applies or claims it; nothing else changes.

## The premise, measured before touching anything

The specifier's reading is sharper than the one I filed from BL-1069, and it is
right. I verified it against a real tmux server rather than accepting it:

```
global                     : largest
window option before resize: []            <- inherits the global
window option AFTER resize : [manual]      <- resize-window armed it
global still               : largest       <- and the two now disagree
```

tmux(1) on `resize-window`: "This command will automatically set window-size to
manual **in the window options**." A window option beats the server global, so
on every window the extension tiles, `largest` is unreachable **by
construction** — not a race, not an ordering bug, and not fixable by changing
who writes last. My BL-1069 note described it as two writers of the global
fighting; that was the wrong mechanism.

That measurement is not a one-off: the property runner re-measures it every run
(`:mechanism-measured`), so if a future tmux changed the scope rule this file
fails rather than quietly enforcing a decision whose premise had gone.

## Two repo guards caught real defects in my step handler

Both are the guards working, and both were genuine:

1. **`socketFixtureShortRootGuard`** — I rooted the fixture at `os.tmpdir()`.
   On macOS that resolves under `/var/folders/<hash>/<hash>/T/` and the socket
   path overruns `swarm_socket_lib.bb`'s 100-char guard, so scenarios would die
   on the refusal instead of on what they assert. I hit exactly that error by
   hand earlier in this session and worked around it instead of recognising the
   rule. Now uses `lib/socketFixtureRoot.js`'s `mkSocketFixtureRoot`.
2. **`tmuxReaperGuard`** — the fixture starts a tmux server that DETACHES and
   outlives the runner, with no `fixtureReaper` tracking. Now tracked.

Adopting `track()` was not sufficient on its own, and measuring showed why:
`reap()` finds a fixture's tmux server through the `<root>/.swarmforge/tmux-socket`
pointer file, and it **refuses** to kill anything matching the live swarm's own
socket shapes (`.swarmforge/tmux/<name>.sock`) — the BL-817 guard that stops a
fixture reaping the running swarm, since these fixtures deliberately reuse real
session names like `swarmforge-coder`. My first attempt named the socket in
exactly that refused shape and wrote no pointer file, so nothing was reaped:
**six leaked tmux servers, measured.** The socket now has an arbitrary fixture
name and the pointer file is written. Verified after the fix: acceptance 7/7
with **0** surviving servers and **0** surviving directories, and the live
swarm still at its 8 sessions throughout.

The six servers my earlier fixture leaked were killed by PID, each verified to
name `/tmp/bl1075-` in its own `/proc/<pid>/cmdline` first — never by session
name, which would have reached the live swarm.

The bb property runner got the same two fixes (short `/tmp` base, and a
shutdown hook that kills every socket it started on the throw and signal paths).
