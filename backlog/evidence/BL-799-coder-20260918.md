# BL-799 — coder, 2026-09-18

## What was wrong and what replaced it

`record-bounce.js --role` validated against `KNOWN_PRODUCING_ROLES`
(`extension/src/quality/qaBounce.ts`), which omitted `specifier` even
though `--by` (`KNOWN_BOUNCE_ROLES`) already accepted it and `--class`
already accepted `spec-gap`. specifier.prompt's own "Recording A
Send-Back (BL-635)" rule requires exactly this recording for a spec
defect the specifier remediates itself — three live occurrences
(BL-795 2026-08-03, BL-1184 2026-08-27, BL-1305 2026-08-31), all refused
by the CLI, all invisible to the bounce-rate store the daily briefing
reads.

**Fix**: added `'specifier'` to `KNOWN_PRODUCING_ROLES` (one array, the
shared closed set both `record-bounce.js` and the legacy
`record-qa-bounce.js` validate `--role` against via
`bounceArgsCore.ts`'s `validatedCoreFields`); updated `record-bounce.js`'s
own `USAGE` text (`recordBounceArgs.ts`) to list it.

## Scope note: record-qa-bounce.js's own usage text left as-is

`KNOWN_PRODUCING_ROLES` is genuinely shared between the two CLIs
(`bounceArgsCore.ts`'s `validatedCoreFields` is the one `--role`
validator both call), so `record-qa-bounce.js --role specifier` now also
validates — but that CLI's own hardcoded `USAGE` string
(`recordQaBounceArgs.ts`) still lists only the original five roles. The
ticket's text frames this as `record-bounce.js`'s own fix and explicitly
scopes `record-bounce-correction.js` out; `record-qa-bounce.js` is
elsewhere documented as "a separate, still-tested CLI" left untouched by
the BL-635 generalisation it was superseded by, and no existing test
asserts its usage text's exact role list, so left unchanged rather than
expanding scope on a severity-low ticket. Flagging here in case a future
pass wants it for consistency.
