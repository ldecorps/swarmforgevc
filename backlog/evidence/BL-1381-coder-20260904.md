## CORRECTION to the ticket's item 3, with evidence

The ticket says a reconcile that exits zero but prints nothing "leaves
scheduling/changed/mode empty, and the wrapper prints 'No shift schedule
configured' and exits 0". **That does not reproduce on this shell, and the
difference matters.**

Measured, pre-fix wrapper, empty reconcile output:

    exit=1
    out=[Traceback (most recent call last): ... json.decoder.JSONDecodeError]

`read -r ... < <(python3 ...)` gets EOF when python dies, `read` returns
non-zero, and `set -e` aborts the script. So the exit CODE was already
non-zero. What was actually broken is invariant 2's other half: the failure
**did not name its cause** — it emitted a raw interpreter traceback and
stopped. An operator reading launch output sees a Python stack, not "the
reconcile gave no verdict".

I could find no input that produces the described exit-0 silent success:
`{}` yields a legitimate "no schedule configured" (correct), and every
non-object or non-JSON input dies in the parse. Recording this so the next
reader does not go looking for a bug that is not there.

The fix is unchanged by the correction and still needed: an empty result is
rejected before parsing, the parse runs where its status is visible, and each
refusal names its cause and touches nothing.

## Why my own first test was VACUOUS, and how I found out

My first three rows asserted the exit code and the absence of the "no schedule
configured" message. All three passed against the PRE-FIX wrapper — because it
already exited non-zero, by aborting. A test that passes against the code you
are fixing proves nothing, and from the inside it looks exactly like success.

Found by running the suite against the reverted wrapper, which is the check
I was bounced for skipping on BL-1386. The discriminating rows are now:

- the failure NAMES its cause (fails pre-fix)
- no interpreter traceback reaches the operator (fails pre-fix)

Verified in both directions: FAIL/FAIL pre-fix, ok/ok post-fix.

## The acceptance found two more gaps in my own fix

I nearly forwarded this parcel without running the declared `acceptance:`
feature at all - the send-time self-audit caught it. Writing the fixture then
surfaced two failures in the wrapper hardening I had just called done:

1. **A reconcile that EXITS NON-ZERO was still unnamed.** My empty-output check
   sat after `result="$(bb ...)"`, and `set -e` aborted on the non-zero exit
   before reaching it - exit non-zero with no message, which is invariant 2's
   naming half unmet all over again. The reconcile's own failure is now
   captured and named, and its output echoed.
2. **The parser's traceback still reached the operator** on non-JSON input. My
   own shell-suite row asserted no traceback leaks, and passed - because the
   EMPTY case is caught before parsing and that was the only case it drove. The
   acceptance drove the non-JSON case and found it. Python's stderr is now
   suppressed so the named cause stands alone.

Both are the same lesson from a different angle: a test that exercises one
input of a class proves nothing about the others, and my confidence after the
first fix was not earned.

The fixture's own conf format was wrong too (`swarm_shift day` rather than
`config swarm_shift day`), which made the live-install scenario silently take
the "no schedule configured" path - a fixture that looks like it exercises the
install path while never reaching it. Read off
`legacy_operator_schedule_lib.bb`'s own regex rather than guessed.
