## Architecture / correctness review

- `collect_deletions`'s `--no-renames` → `-M` is the minimal correct fix:
  git's default similarity threshold already distinguishes a real move
  (reports `R<NNN>`, already excluded by the existing `status == "D"`
  filter) from a rewrite-that-keeps-the-name (still `D`+`A`, correctly still
  flagged) — confirmed by reading the diff directly, not just trusting the
  evidence's claim.
- `ticket_id_for_path`/`introducing_commit_for_path` merged into
  `attribution_for_path`, resolving id+commit TOGETHER from whichever side
  actually names a ticket. This removes a genuine duplication risk: the two
  original functions had independently-drifted fallback conditions (id's
  narrower than commit's), which was the root cause of the original defect
  — merging them is a correctness fix, not just tidying.
- The `commit<TAB>id` field-order fix is backed by an isolated, reproduced
  bash `read` gotcha (a leading empty field with `IFS=$'\t'` is silently
  swallowed; a trailing one is not) — verified the claim myself:
  `printf '%s\t%s\n' '' 'x' | { IFS=$'\t' read -r a b; declare -p a b; }`
  reproduces exactly as described. The fix (id last, never first) is
  correct and the reasoning is preserved in a comment for the next editor.
- No anchor gap: the ticket's own notes correctly identify that a
  `required_wiring` anchor inside the guard itself would be the BL-1235
  fail-open shape (the commit-msg hook already calls it unconditionally) —
  confirmed by reading `swarmforge/git-hooks/commit-msg` calls this script
  regardless of parcel content, so the shell/acceptance tests exercising
  the real hook path are the correct reachability proof instead.
- BL-1242's original protection (an inherited deletion with no exemption
  still refuses) is explicitly NOT weakened — confirmed both by the
  regression feature (12/12 unchanged) and by reading that
  `attribution_for_path`'s neither-side-names-a-ticket branch still returns
  an empty id, which still refuses as `(unattributed)`.
