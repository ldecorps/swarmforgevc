# BL-1981 coder evidence (2026-10-05)

## What changed

Article 3.5's amendment (2026-10-05): a cleared throttle signal no longer
restores the effective cap by itself - it holds at the lowest cap the
episode reached until a human releases it.

- `extension/src/tools/emit-throttle-recommendation.ts`: new
  `ThrottleEpisode`/`ThrottleEpisodeAnswer` types, `heldCap`/`episode`
  fields on `ThrottleRecommendation`, and the pure
  `updateThrottleEpisode`/`heldCapForEpisode` state machine. `recommendedCap`
  itself is untouched - still the raw, honest signal (BL-1429's own "the
  recommendation is withdrawn" contract unchanged); `heldCap` is the new,
  separate floor. `describeChangeReason`'s clearing branch now says "held
  at N for a human release (<prior-binding-signal> cleared)" for an open,
  unanswered episode, preserving the existing which-signal-cleared naming
  verbatim inside the new wording (every existing substring-matching test
  - `/cleared/`, `/red count/`, `/rework diagnosis cleared/`,
  `doesNotMatch /red count/` - still passes unchanged; confirmed by
  running `emitThrottleRecommendationCli.test.js` and
  `emitThrottleRecommendationStandingRed.test.js`).
- `extension/src/tools/release-intake-throttle.ts` (new): the release CLI,
  `node release-intake-throttle.js <project-root> --by <who> (--release |
  --keep <N>) [--reason <text>]` - exactly the interface
  coordinator.prompt/BL-1982 call. Records the answer onto the currently
  open episode; refuses (throws, `runCliMain` exits non-zero) when none is
  open.
- `swarmforge/scripts/backlog_depth_lib.bb`: new `read-held-cap` (same
  degrade-never-crash posture as `read-recommended-cap`) and
  `min-recommended-cap`; `read-effective-max-depth` now folds
  `read-recommended-cap` and `read-held-cap` together before the existing
  `effective-max-depth` call - a one-line composition, `effective-max-depth`
  itself untouched.
- `specs/features/BL-432-auto-tune-intake-throttle.feature`: scenario 03
  ("When the diagnosis clears, the effective cap returns to the configured
  value") retired per requirement 6 - it tested the now-superseded
  behavior. Header comment re-tensed. The two step registrations unique to
  that scenario removed from `bl432AutoTuneIntakeThrottleSteps.js`;
  BL-432's other 5 scenarios, all still green, are untouched.
- `specs/pipeline/steps/bl1981ThrottleHumanReleaseSteps.js` (new): binds
  the feature. "the register has fallen back under every threshold"
  repeats BL-1429's own step text - registered with `defineScoped` (BL-425)
  so it answers only this feature; BL-1429's unscoped registration is
  byte-for-byte untouched.
