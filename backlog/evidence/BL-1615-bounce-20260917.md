## D1 - CONFIRMED correctness defect: a refused claim requeues seat-addressed
mail into the shared stage queue, violating invariant 2 and the ticket's own
FIRM requirement

`ready_for_next_task.bb` binds `new-dir` once, at line 369:

```
new-dir (handoff-lib/stage-queue-dir :new)
```

Before this parcel, EVERY claim candidate came from `new-dir` alone, so
`enforce-branch-claim-guard!`/`requeue-and-refuse!` (lines 240-292) moving a
refused claim's file back to `new-dir` was always correct - the file's
origin and its requeue target were the same directory.

This parcel's `claim-stage-handoff-files` (handoff_lib.bb) now draws
candidates from the UNION of `stage-queue-dir` and `my-mailbox-dir` (the
seat's own new/) - exactly the fix the ticket asks for. But `new-dir` at the
two call sites that can requeue a claim (line 405, the in-process resume
path, and line 524, the fresh-claim path) is STILL the single
`stage-queue-dir` binding, never the file's actual origin directory.

Concretely: a branch-behind merge-up note delivered to coder@2's OWN new/
(exactly the shape this ticket exists to drain) is claimed into in_process
by the new union-based candidate list, then on a dirty-worktree or
uncorrectable-branch guard refusal, `requeue-and-refuse!` moves it into
`stage-queue-dir :new` - the SHARED coder queue - where the bare `coder`
seat's dispatcher (reading `stage-handoff-files new-dir` - `stage-queue-dir`
unchanged) can now claim mail that was addressed to coder@2 alone.

This directly contradicts:
- The ticket's `approval_context` FIRM clause: "seat-addressed mail stays
  seat-specific - it is never redirected into the stage queue and never
  offered to a sibling seat (a branch-behind merge-up note names the seat's
  own branch; a reverse-hop merge-only copy syncs the seat's own tree)."
- Declared invariant 2: "A file delivered to a seat's own new/ is offered to
  that seat only: a sibling seat's dispatcher never lists it."

The branch-claim guard's dirty/uncorrectable path is not a rare edge case
here - a "branch behind" merge-up note exists specifically because the
seat's branch state is unusual, so claiming one of these notes is a
plausible trigger for exactly the guard refusal that mis-routes it.

No scenario in the feature (7/7, all passing) exercises a guard refusal on a
seat-addressed candidate - scenario 01's four rows and scenario 02 never
touch a dirty/mismatched worktree, and scenario 03 has no candidate from a
non-coincident pair of directories interacting with the guard at all.

### Remediation direction (not mandate)
`requeue-and-refuse!`/`enforce-branch-claim-guard!` need the candidate's
OWN origin directory (its `fs/parent`, or the directory it was actually
read from) as the requeue target, not the single `new-dir` binding - so a
file claimed from the seat's own new/ is ever only returned there, and a
file claimed from the stage queue is ever only returned there. A new
scenario driving the guard's dirty-worktree refusal on a seat-addressed
candidate (row: seat-addressed note, worktree dirty, refused, file lands
back in the SEAT's own new/, never the stage queue) closes the coverage gap
this defect hid in.
