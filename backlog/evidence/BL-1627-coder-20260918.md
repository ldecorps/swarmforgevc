## What was wrong, and the fix

`BL-937-shell-scripts-run-on-stock-macos-bash-32.feature` was red on main
for two independent reasons:

1. **Real regressions.** Scenario 02's static scan correctly flagged
   `mapfile` (a bash-4 builtin, stock macOS bash 3.2 lacks it - BL-801's
   target) at `check_bb_scripts_load.sh:140` and
   `check_constitution_doc_citations.sh:41,67`. Both are commit guards in
   the BL-1242 chain - the first thing a macOS operator's commit runs.
2. **A host-premise scenario.** Scenarios 01 and 03 both `Given the stock
   system bash reports version 3.2` - true on the macOS host BL-937 was
   minted on, never true on the WSL/Linux host this swarm runs on now.
   Proves nothing about the scripts either way.

### The two scripts

Every `mapfile -t NAME < <(cmd)` became `NAME=(); while IFS= read -r
__line; do NAME+=("$__line"); done < <(cmd)` - the same process
substitution, same full materialization into an array before any
consuming loop runs (BL-1427's own invariant in
`check_bb_scripts_load.sh` is unchanged: the array is fully built before
either `for` loop over it, so no shared-stdin drain risk). Every later
`"${NAME[@]}"` expansion of a possibly-empty array under `set -uo
pipefail` became `${NAME[@]+"${NAME[@]}"}` (this repo's established BL-801
idiom - `harness_env_scrub.sh`, `check_ticket_deletion.sh`,
`is_qa_ancestor.sh` all use it). `${#NAME[@]}` (length only, never `[@]`
expansion) needed no change - safe on an empty array under bash 3.2's
`set -u` either way (`check_constitution_doc_citations.sh`'s `TOUCHED`).
