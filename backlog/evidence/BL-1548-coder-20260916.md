## Declared invariants (BL-654) — stated reason, no property test

1. "Every invocation ... appends exactly one `start_handoff_daemon
   invoked root=<root>` line ... whether or not SWARMFORGE_SKIP_DAEMON=1
   is set."
2. "Under SWARMFORGE_SKIP_DAEMON=1 the launcher mutates nothing under
   `<root>` except creating `.swarmforge/daemon/` and appending to that
   audit log: no pid file, no handoffd.log, no stopped marker cleared, no
   process started."

No coder-authored property test is added for either. Reason: this is a
bash script performing real I/O (mkdir, file writes, process spawning),
never a pure, testable module in the generative-property sense the
codebase's TS/bb property lanes target — and, per the ticket's own
`mutation_cost` note, "Shell has no mutation/CRAP/DRY wired (BL-472)."
More load-bearing: BOTH invariants' actual variable is `SWARMFORGE_SKIP_DAEMON
== "1"` versus not, a genuinely BINARY state space with no other input
this script's own behavior branches on — a random sampler over that
2-point space adds no coverage a generator could reach that the two
acceptance scenarios do not already assert EXHAUSTIVELY, not
statistically: scenario 01 (skip="1") asserts invariant 1's exactly-one
line AND invariant 2's every named mutation-absence in full; scenario 02
(skip="") asserts invariant 1's exactly-one line for the other branch.
Together the two scenarios are a complete enumeration of the invariants'
own domain, which is what a property test exists to approximate when full
enumeration is not feasible - here it already is the acceptance suite.
