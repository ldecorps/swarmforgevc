## D1 — BL-1198's own acceptance feature now asserts the exact behaviour BL-1310 removes

`specs/features/BL-1198-main-rematch-reset-must-attempt-push-before-discarding-local-ahead-commits.feature`,
scenario `genuinely-colliding-ahead-still-recovers-02` ("A local-ahead commit
that collides with origin still falls back to today's reset recovery"):

```
Given origin/main has diverged such that pushing local main is rejected
When the rematch path runs
Then it attempts the push first
And only after that push is rejected does it reset local main to origin/main
```

This is real-git, and it still passes (verified: `node specs/pipeline/cli.js
specs/features/BL-1198-...feature` → 2/2 green). It passes because its driver,
`specs/pipeline/steps/lib/bl1198RematchPushFirstCli.bb`, wires
`rematch-with-push-first!`'s `:reset!` directly to a raw `git reset --hard
origin/main` — never through `refuse-reset-if-local-ahead!`. The CLI's own
header comment says so explicitly ("that ticket's own driver, unmodified, has
no BL-1310 gate at all") and the coder deliberately left it unwired rather
than update it.

The precondition this scenario arranges — local main ahead by one commit
(Background: "local main holds one or more commits not yet present on
origin/main"), origin diverged, push rejected — is *exactly* the case
BL-1310's invariant 1 says must now refuse at every real call site. The
scenario's own title and `Then` step assert the opposite: that today's
behaviour is still to reset local main onto origin's tip, discarding the
ahead commit. That is no longer true anywhere in production. This is the
same "the name promises something the code does not do" trap the ticket's
own description calls out about `:replay-bookkeeping` — a reader auditing
BL-1198's feature file for current behaviour is told the discard still
happens, and stops there.

Same defect as D1: a genuinely local-ahead, rejected-push case is asserted to
end in `discarded`, which BL-1310 makes false at every real call site.

## Why this is a send-back, not a rule_proposal (BL-333's lesson)

Both are concrete, verifiable defects visible right now in the parcel's own
regression surface, not a hypothetical or a durable-rule question. The
ticket's own `qa_e2e_procedure` step 6 says BL-1288's "push-rejection
precondition is what this ticket narrows, not removes" — the narrowing exists
in code but was never reflected back into BL-1198's or BL-1288's own feature
text, so both now describe stale, misleading acceptance criteria that will
mislead the next reader (exactly BL-1310's own complaint about
`:replay-bookkeeping`'s name).

## Remediation

For each of D1 and D2: either (a) point the scenario's raw `:reset!` at the
same `refuse-reset-if-local-ahead!` composition the real call sites use (so
the scenario proves current behaviour, and the two now-doubly-covered rows/
scenarios collapse or gain a companion "…but not when local-ahead" row), or
(b) if the isolated-primitive framing is intentionally kept, rewrite the
scenario title/Given/Then text so it no longer reads as a claim about current
production behaviour for a local-ahead commit — e.g. scope it explicitly to
`rematch-with-push-first!`'s raw-adapter contract and cross-reference BL-1310
for the wrapped, production-current behaviour. Either fix belongs with the
BL-1310 parcel's own coder, since it is BL-1310's own change that made the
existing text stale.
