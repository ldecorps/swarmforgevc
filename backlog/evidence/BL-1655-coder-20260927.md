# BL-1655 — coder pass, 2026-09-27

## What changed

A reclaimed claim now travels with the identity of the seat that held it,
and every reader of the cross-seat deferral mechanism (the claim path, both
stall sweeps) treats that identity exactly like a BL-1004 sibling-rework:
deferred to the holder inside the cross-seat deadline, released to any seat
past it, self-affinity always wins immediately.

- `swarmforge/scripts/orphan_claim_sweep_lib.bb` (`reclaim-file!`): stamps
  the re-delivered file with `held_by_seat: <role>` and refreshes
  `enqueued_at` to the reclaim moment (the same "a redelivered parcel is
  fresh here" semantics `rework-claim-decision`'s own docstring already
  documents for a bounce - the age source every reader below consults).
  `claim-reclaim?` itself (BL-648's own decision), and the target
  directory, are untouched - the constraint's own words.
- `swarmforge/scripts/handoff_lib.bb`: new `remove-header!` (mirrors
  `set-header!`'s temp-file-then-move write; a no-op when the header is
  absent) - the mechanism `ready_for_next_task.bb` uses to make
  `held_by_seat` "gone once claimed."
- `swarmforge/scripts/seat_affinity_lib.bb`:
  - `rework-claim-decision` gains `:held-by-seat`/`:my-seat`. A second,
    independent deferral candidate (`reclaimed-elsewhere?`) is OR'd
    alongside the existing sibling-rework candidate: ANY type reclaimed
    from a seat other than `my-seat` defers/cross-seat-claims on the SAME
    age/deadline arithmetic; `held-by-seat = my-seat` (or absent) leaves
    the existing rework logic as the sole decider, byte-identical to
    before.
  - `deferral-hold?` gains `:held-by-seat`. Holds for a reclaim on any
    stage with more than one seat (`(count seat-worked-task-sets) > 1)`);
    a single-seat stage's own set has exactly one entry, so this is
    structurally false there with no extra branch, per the existing
    invariant 3.
  - Two new line renderers, `reclaimed-deferral-line` /
    `reclaimed-cross-seat-claim-line`: same invariant 2 (never render a
    seat id) as the existing pair, worded for "reclaimed from" rather than
    "worked by" (a reclaimed note has no task to name either).
- `swarmforge/scripts/ready_for_next_task.bb`: the claim loop reads
  `held_by_seat` per candidate and passes it (with `my-seat =
  current-role`) into `rework-claim-decision`; the deferred-line and
  cross-seat-claim-line print sites pick the reclaim-flavored renderer
  when the file carries `held_by_seat`, else the existing rework one;
  every successful claim (self-affinity, cross-seat, or an ordinary
  never-reclaimed parcel) drops `held_by_seat` via `remove-header!`
  unconditionally - "gone once claimed."
- `swarmforge/scripts/flow_watchdog_lib.bb` / `chase_sweep_lib.bb`: both
  `deferral-hold?` call sites (via `parcel-record`+`parcel-deferral-held?`
  and `item-deferral-held?` respectively) now pass `:held-by-seat` read
  from the same header - the identical `deferral-hold?` the claim path
  itself decides with, never a second, drifting notion.
- `swarmforge/scripts/swarm_handoff.bb`: `held_by_seat` added to
  `reserved-fields` - tool-stamped audit metadata, same class as
  `from_seat`/`received_at_head`; a draft supplying it is refused.
- `swarmforge/handoff-protocol.md`: `held_by_seat` added to both Reserved
  headers lists and a lifecycle-ownership bullet describing who writes,
  reads, and drops it (mirrors the existing `from_seat` bullet).
- `specs/pipeline/steps/bl1655ReclaimedClaimSeatAffinitySteps.js` (new):
  drives the REAL `relaunch_resume_cli.bb sweep`, `ready_for_next_task.bb`,
  and `handoffd.bb --sweep-once` over one shared fixture (BL-1004's simple
  single-git-init style; the flow-watchdog piece follows BL-679's own
  `--sweep-once`/operator-outbox invocation exactly). The feature file
  itself is the specifier's own, unchanged.
- `swarmforge/scripts/test/orphan_claim_sweep_lib_test_runner.bb`: new
  case asserting the reclaimed file's `held_by_seat` and refreshed
  `enqueued_at`.
- `swarmforge/scripts/test/handoff_lib_test_runner.bb`: new cases for
  `remove-header!` (removes only the named header, leaves neighbors and
  the body untouched, no-ops when absent).
- `swarmforge/scripts/test/bl1655_seat_affinity_property_runner.bb` (new,
  BL-654 Invariants): generative coverage for the ticket's own two
  declared invariants, over `rework-claim-decision`'s and
  `deferral-hold?`'s new `held-by-seat` input specifically - BL-1004's own
  property runner keeps its existing coverage of the sibling-rework
  dimension untouched (measured: it still passes byte-for-byte, since its
  generator never sets `held-by-seat`/`my-seat` at all). Invariant 1: the
  holder claims at ANY age (even past the deadline - self-affinity wins
  unconditionally) and a sibling defers a fresh reclaim, whatever the
  parcel type. Invariant 2: a sibling releases (claims out loud) past the
  deadline or on an unreadable age, and a single-seat stage's
  `deferral-hold?` never holds regardless of `held-by-seat`. Verified
  NON-VACUOUS: reverting `deferral-hold?`'s single-seat guard

  `reclaimed-cross-seat-claim-line`) are not calls BL-1004's own runner

  no-seat-id sweep over both is included here instead, verified
  NON-VACUOUS the same way (a deliberate seat-id leak into
  `reclaimed-deferral-line` was caught immediately, then reverted).

## A finding: the default flow-watchdog thresholds make a 20-minute-old parcel un-alarmable either way

Building scenario 06's fixture, a plain default-conf fixture (no
`flow_watchdog_warn_ms` override) never alarmed a 20-minute-old parcel
regardless of `held_by_seat` - measured directly: with zero calibration
samples the GLOBAL fallback pair is 15m warn / 1h escalate, and
`flow_watchdog_lib.bb`'s own `calibrated-warn-slack-factor` (2x, every
resolved pair) doubles both, landing warn at 30 minutes - above the
scenario's own 20-minute age either way. A green scenario 06 against that
fixture would have proven nothing. Fixed by giving the fixture its own low
`config flow_watchdog_warn_ms 300000` (5m raw, 10m resolved) - comfortably
under 20 minutes - and verified NON-VACUOUS two ways: (1) an A/B fixture
pair, identical except for `held_by_seat`, where the WITHOUT-header case
genuinely alarms (`⚠️ WARN flow-stall: ... aged 20m ... Threshold 10m via
global.`) and the WITH-header case does not; (2) `git stash`-ing the
`flow_watchdog_lib.bb` change alone and re-running the real acceptance
feature: scenario 8 fails exactly as expected
(`AssertionError: expected no stuck-parcel alarm for bl1655-reclaim-8`),
then passes again once the change is restored.
