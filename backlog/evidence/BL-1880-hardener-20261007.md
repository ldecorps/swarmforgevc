## A real Stryker/vitest coverage-attribution bug on this file — do not trust "Survived" at face value here

Per the project's own "false 0%"/"false Survived" measurement-bug class
(BL-1015 and its sequels): **the tool's own `coveredBy` list for several of
its 19 "Survived" mutants is simply wrong**, confirmed directly, not
inferred. Example: mutant 146 (`out/182:122`, the `formatBounceWindowLine`
"none" fallback StringLiteral) lists `coveredBy: ["21","28","30"..."37"]`
(10 tests) and **omits test id 22**
(`formatBounceWindowLine names the 24-hour fallback and "none" when no
role bounced in the window`) even though that test's own body directly
calls `formatBounceWindowLine` with `windowByProducingRole: []`, which
executes exactly this line. Hand-mutating `out/tools/qa-bounce-line.js` at
that exact location and running `npx vitest run test/qaBounceLineCli.test.js`
(the full file, not a Stryker-selected subset) fails that test
immediately — this mutant is a real kill, not a survivor.

This was not a one-off: re-running the same scoped Stryker config five
times (including once with `coverageAnalysis: "all"` instead of
`"perTest"`, and once after clearing `node_modules/.vite` +
`node_modules/.vite-temp`) reproduced the IDENTICAL 19-Survived set and
the identical `"Ran 2.63 tests per mutant on average"` figure every time
— `coverageAnalysis: "all"` should have run every test against every
mutant (no selective `coveredBy` narrowing at all) and did not change a
single number, which rules out an incremental-cache explanation (BL-1015's
usual cause) and points instead at this project's custom vitest Stryker
runner wiring (`vitest.bl1880.stryker.config.mjs`'s `related: false` /
`appendPlugins`) computing `coveredBy` independently of the
`coverageAnalysis` setting. Filed as a tooling observation for the
specifier below; not chased further here — it is out of this ticket's own
scope and the workaround (direct hand-mutation) is cheap.

**Every one of the 19 "Survived" mutants was individually hand-verified**
by patching the exact AST location in `out/tools/qa-bounce-line.js`,
running `npx vitest run test/qaBounceLineCli.test.js` (the whole file,
never a Stryker-selected subset), confirming the result, then restoring
from a saved original. 13 are genuinely killed by a test (9 by tests this
pass added, 4 the tool had simply mis-scored from the start); 6 are
confirmed accepted equivalents. The 3 Timeout mutants (`i--` on the
`parseArgv` loop counter, producing a genuine infinite loop) are not
silent — a hung loop IS the test suite catching the mutant, just via
timeout rather than an assertion; no action needed.

  killed by the pre-existing "names the 24-hour fallback and 'none'" test
  — the tool's own `coveredBy` list for this mutant omits that test,
  which is the measurement bug above, not a real gap.
- `out/208:21` (the `dayKeys` chain's `.filter(day => Boolean(day) &&
  day < todayKey)` dropped entirely): killed by the new "a committed file
  for TODAY is excluded by the filter, not merely sorted before an earlier
  valid day" test — deliberately built with NO non-matching filename
  alongside the real files, because a stray name maps to a real JS
  `undefined`, which `Array.prototype.sort()` always moves to the end
  regardless of the comparator, silently masking a dropped filter (see the
  dayKeys.length===0 equivalent below for the same masking effect).

- `out/246:84` (`modelForRole`'s `'model unknown'` fallback → `''`):

### Accepted equivalents (confirmed empirically, never by shape alone)

- `out/212:9`/`out/212:31` (`if (dayKeys.length === 0) { return undefined;
  }` forced false/emptied): when `dayKeys` is genuinely empty, skipping the
  early return falls through to `path.join(dir, \`${dayKeys[dayKeys.length
  - 1]}.md\`)` — `dayKeys[-1]` is `undefined`, so the template produces the
  literal path `"undefined.md"`. That path is vanishingly unlikely to exist
  on disk with git history, so `gitLog` returns `undefined` just as the
  skipped early return would have — same final outcome
  (`findPreviousBriefingSentAtIso` returns `undefined`, 24-hour fallback)
  through a different path. Confirmed by hand-mutation against the full
  test file: no failures.
- `out/225:16` (`.trim()` dropped from `execFileSync(...).trim()`):
  `git log --format=%aI` output for one commit is the ISO string plus a
  single trailing newline; the caller already does
  `out.split('\n').filter(Boolean)`, which discards a trailing empty
  string from an untrimmed value identically to a trimmed one. Confirmed
  by hand-mutation: no failures.
- `out/225:107/108/118/126` (the `stdio: ['ignore', 'pipe', 'pipe']` array
  replaced with `[]`, and each string replaced with `''`, four separate
  mutants): confirmed empirically (same finding BL-1676's hardener
  recorded for an identical construction) that this Node runtime (v22)
  treats `stdio: ''` and `stdio: []` identically to `'pipe'`/`'ignore'` for
  these slots — the captured stdout is byte-identical either way. Four
  hand-mutations, no failures.
- `out/233:9`/`out/233:16` (`if (!file) { return undefined; }` forced
  false/emptied): when `file` is `undefined` (no previous briefing file
  found), skipping the early return calls
  `gitLog(targetPath, [..., undefined])` — passing a non-string argument
  array element to `execFileSync` throws synchronously, caught by
  `gitLog`'s own `try`/`catch`, which returns `undefined` — the identical
  final value the skipped early return would have produced. Confirmed by
  hand-mutation: no failures.
- `out/240:19` (`.filter(Boolean)` dropped from `out.split('\n')`): by the
  time this line runs, `out` has already passed the `if (!out)` guard
  (truthy) and is `.trim()`-med `git log` output; `--format=%aI --follow`
  never emits an embedded blank line between commit entries (one ISO
  timestamp per line, newline-separated, no blank-line separators), so
  `split('\n')` produces no empty entries in any reachable case for the
  filter to remove. Confirmed by hand-mutation across the whole suite,
  including the two-commit "oldest commit" test: no failures.
- `out/241:12` (the `lines.length > 0 ? lines[lines.length - 1] :
  undefined` ternary's condition forced `true`, and separately `>`
  weakened to `>=`): by the time this runs, `out` passed the `!out` guard
  (truthy, non-empty after trim), so `out.split('\n')` yields at least one
  element and (per the equivalent above) `.filter(Boolean)` removes none of
  them — `lines.length` is therefore always >= 1 whenever this ternary is
  reached, making its `: undefined` branch dead code reachable by no real
  input. Confirmed by hand-mutation (both the forced-true and the
  weakened-comparison variant): no failures.
- `out/227:11` (`gitLog`'s `catch { return undefined; }` block emptied to
  `catch {}`): a function with no further statement after a `try`/`catch`
  implicitly returns `undefined` when control reaches its end — an empty
  catch block and an explicit `return undefined;` inside it are the
  identical outcome. Confirmed by hand-mutation: no failures.
- `out/258:21` (`for (let i = 0; i < argv.length; i++)` weakened to `i <=
  argv.length`): the one extra iteration runs with `i === argv.length`,
  where `argv[i]` is `undefined` for every access inside the loop body —
  `valueFlagAt(argv, argv.length, '--target')` evaluates
  `undefined === '--target'` (false) and returns `undefined` the same way
  it would for any non-matching position, and
  `argv[argv.length] === '--json'` is likewise false. One harmless no-op
  pass through the loop body, no different from the args object already
  built. Confirmed by hand-mutation across the whole suite: no failures.

Filed as a tooling observation (not a ticket — out of this parcel's own
scope, and the cost of confirming one false Survived by hand is a few
seconds): the specifier may want to track that this project's scoped
`coverageAnalysis: perTest` (and, per the five-run check above,
apparently `"all"` too) can under-report `coveredBy` for this vitest
Stryker wiring shape, independent of the documented BL-1015 incremental-
cache cause. No ticket minted; a hand-mutation + full-file re-run is cheap
enough that this evidence records the workaround rather than opening a
new investigation.
