# BL-1912 coder evidence

## The new bound's value and why

`land_step_lib.bb/default-replay-commit-bound-ms` = `600000` (10 minutes),
overridable via `SWARMFORGE_LAND_REPLAY_COMMIT_BOUND_MS`.

- The ticket's own measurement: the replay commit of BL-1893's two evidence
  files took 69s at load average 14.3 (source: BL-1870 merge-path census).
  600000ms is ~8.7x that, comfortable headroom for a busier host or a
  heavier commit than the measured one.
- "Land-scale" per the ticket's own direction: `lander_lib.bb/overdue-ms`
  gives a WHOLE land an hour (3600000ms) before reporting it overdue. The
  replay commit is one step inside that land, not the whole thing, so its
  own bound stays a small fraction of the land's overall budget (1/6th) -
  real headroom over the 69s measurement without letting one step consume
  the land's entire overdue allowance should it ever genuinely hang.
- Every OTHER git call in `land_step_lib.bb` is untouched (still the
  generic `SWARMFORGE_SUBPROCESS_WAIT_BOUND_MS` / 60s default) - only the
  replay's own `git commit` call site passes `{:bound-ms (replay-commit-bound-ms)}`.

## What changed

- `git!` (private helper every call in this file goes through): now passes
  a trailing opts map through to `daemon-cycle-guard-lib/sh!` as its own
  SEPARATE second positional arg (the shape `sh!`'s `split-sh-args`
  expects), rather than appending it into the command vector where it
  would have been stringified into a bogus git argument. This was a real
  latent bug, not exercised until this ticket's own commit call needed to
  pass `:bound-ms` for the first time - caught and fixed by this
  parcel's own unit tests (`land_step_lib_test_runner.bb`, "git! passes a
  trailing opts map through to sh! correctly" cases) before it ever
  reached a real git call.
- `replay-commit-refusal-reason`: now a 2-arity fn. The 5-arg form adds a
  `timed-out?`/`bound-ms` case reporting a timeout by name
  ("timed out after N second(s)"), checked BEFORE the generic stderr
  branch so daemon-cycle-guard's own "bounded-wait timeout after Nms" text
  is never read as an ordinary hook refusal. The original 3-arg form is
  kept (defaulting `timed-out?` false) for backward compatibility -
  `bl1474ReplayCommitRefusalReasonInvariants.property.test.js` calls the
  3-arg form directly and would otherwise have broken on an arity
  mismatch; verified it still passes after this change.
- The replay's escalate-map construction: a timeout (`:timeout?` true on
  the replay result) now omits `:unlanded` from the `:escalate` map, so
  the CLI's existing `(when (contains? plan :unlanded) ...)` gate never
  prints the entanglement note / specifier-adjudication text for a
  timeout - no CLI change needed, this was already the exact mechanism
  that text was gated on.
