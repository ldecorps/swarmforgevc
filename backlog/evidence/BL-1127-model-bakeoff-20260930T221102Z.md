## Caveats

- iq3's 222s wall time reflects ollama's default scheduler loading it at its
  Modelfile's baked-in 49152 context, NOT the seat's actual production
  launch flags (explicit `--flash-attn on` + `--cache-type-k/v q8_0`), which
  per standing memory notes achieve full 65/65 GPU-layer residency at that
  same context in real production. This run likely understates iq3's true
  production throughput; noted rather than silently normalized away. The
  staffing battery's own "model" phase DID use the seat's real production
  launcher flags and passed.
- The swarm's own babysitter/supervisor auto-healed iq3 back onto the GPU
  twice during testing (once after an initial `kill -TERM`, once mid-test
  on the 30B Q3_K_M attempt), which is expected self-healing behavior but
  interfered with clean sequencing. This is why Q3_K_M's in-vivo result is
  missing rather than a hard failure of the model itself.
- Config propagation gotcha (new, worth a ticket): updating
  `swarmforge/packs/full-forge.conf` in master and in the seat's own
  worktree copy was NOT sufficient to change what a respawn actually runs.
  The swarm caches a fully-generated per-seat launch script at
  `.swarmforge/launch/coder@iq3.sh` with the `--model` flag baked in
  literally; `./swarm ensure` respawns FROM THAT CACHED SCRIPT, not by
  re-reading the pack conf. All three copies (master pack conf, worktree
  pack conf, and the generated launch script) had to be updated by hand to
  actually change the model. This is the same shape as the already-known
  "pack switch leaves stale launch scripts" hazard.

## Winner and action taken

**Qwen2.5-Coder-14B-Instruct Q5_K_M** — correct output (same as iq3 on the
shared problem), passed the staffing battery, ~5x faster than iq3's
measured run (45s vs 222s), and fits the 16GB GPU alone with comfortable
headroom where iq3 at full context does not (on the naive scheduler path).
The 30B-A3B variants are not viable replacements: IQ4_XS is disqualified
outright on VRAM fit, and Q3_K_M (the smaller/lower-quality fallback
quant) was not confirmed to fit either and is unlikely to beat a clean,
fully-fitting, already-faster 14B win even if it does.

**Deployed**: `swarmforge/packs/full-forge.conf`'s `coder@iq3` window,
its worktree copy (`.worktrees/coder-iq3/swarmforge/packs/full-forge.conf`),
and the generated launch script
(`.swarmforge/launch/coder@iq3.sh`) were all updated to
`--model qwen2.5-coder-14b-q5km:latest` (an `ollama cp` alias of
`hf.co/bartowski/Qwen2.5-Coder-14B-Instruct-GGUF:Q5_K_M`, created to avoid
the battery script's slash-in-filename bug on the full hf.co tag). The
`coder@iq3` seat was stopped and respawned; its pane status line now
confirms `qwen2.5-coder-14b-q5km:latest` is live. The window/seat name
`coder@iq3` is now a legacy label, not a claim about which model is
loaded.

coder@2 was kept offline throughout per a separate standing human
directive; all testing ran as standalone scratch probes against the
Ollama API directly, never through a live pipeline seat.
