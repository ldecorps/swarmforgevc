## Review findings on the patch

Read line by line before applying. The design holds up: the pure/live split is
right, the dispatch step is in the correct place (after the cursor-bridge
exclusion, before the side-channel and subject-opening steps), and the live
adapter mirrors `forwardCursorBridgeUpdate`'s shape — core decides whether to
call and stop, the live side performs.

One change made:

- **`chatCompletionsUrl` had two identical branches.** `/\/v1$/` and the
  fallback both returned `${root}/chat/completions`, so the `/v1` test decided
  nothing. Folded to one ternary with a comment saying why the two cases are
  the same suffix. Behaviour is unchanged and the unit tests pin all three
  inputs (bare root, `/v1` root, already-full endpoint).

Two things checked and deliberately left alone:

- The `answer` turn carries the raw `apiKey` in its return value. That is
  in-memory only, never logged, and never posted — there is a unit test and a
  property assertion that nothing the seat posts contains the key. Passing it
  as a value rather than re-reading env at the call site is what keeps
  `completeWithProviderChat` injectable.
- A refusal returns `'handled'` to core, not `'not-mine'`. That is correct and
  load-bearing: invariant 1 says no subject is opened whether the provider
  answered, **refused**, or failed.

## Declared invariants (BL-654)

Both have a coder-authored property test in this parcel, each shown
non-vacuous and independent:

- **Invariant 1** (a bound topic never opens a support subject) — broken by
  deleting the seat step from `processMessageUpdate`, so a bound topic falls
  through to `openSubjectAndRecord`. `a bound topic never opens a support
  subject` failed; the other three passed. The property drives the REAL
  `runPollCycle` and asserts against the REAL `openSubjectAndRecord` adapter,
  never the absence of a log line — the ticket's qa_e2e step 2 is explicit
  that the subject store is the evidence. **Reachability floors** assert the
  generator reached all three endings the invariant names by name: answered,
  refused (no key), and provider-failed. A run that only ever answered would
  pass the invariant without testing what it claims.
  A companion property pins the other side — an unbound topic still opens its
  subject and the seat stays silent in it — so "never opens a subject" cannot
  be satisfied by a seat that swallows everything.
- **Invariant 2** (credentials from env and the gitignored map only) — broken
  by merging a `.env` parsed out of the target working directory into the
  seat's env. BOTH invariant-2 properties failed; both invariant-1 properties
  passed. The fixture plants decoy credentials in three plausible
  working-tree places — `.env`, a feature file under `specs/features/`, and
  `.swarmforge/swarm-identity` — and the decoy is **derived from the generated
  value** so a leak is unmistakable rather than coincidental. It asserts the
  key came from the process env, the endpoint from the map, and that nothing
  posted carries either secret.

Both broken files restored and confirmed byte-identical by `diff`; no `BREAK`
marker survives under `extension/src/tools/`.

6. **Fixture roots** — unit and property fixtures remove their root in a

   `rm -rf <prefix>*` is the BL-1390 storm shape when several roles run suites
   at once, and BL-971's sweep-by-prefix is a rule for a suite that runs one
   at a time.

## Scenario Outline handling

Both Outline examples validate against explicit `KNOWN_FAILURES` /
`KNOWN_REASONS` maps and the handler throws on an unrecognised example rather
than passing the text through — no binary/passthrough check. Each example maps
to the REAL failure shape the seat would see (`... answered 401: invalid api
key`, `connect ECONNREFUSED 127.0.0.1:9`), so the assertion is about the
seat's reporting rather than about the feature file's own words.

The "not a bare status code" step is BL-572/BL-662's rule made executable: the
posted message must not be bare digits and must carry readable prose.
