# BL-1631 coder pass

## Declared invariant - encoding

"A registry row whose owner is the ticket being landed does not survive
that land: after the replay commit is built, no row in
backlog/standing-reds.tsv, swarmforge/scripts/property_suite_standing_allowlist.tsv
or backlog/suite-poles.tsv names the landing ticket as owner (an accepted
pole row excepted)." Encoded directly: `rows-to-retire` (pure,
`land_step_lib.bb`) is the counterpart of BL-1604's `rows-to-restore`, run
in the same pass by `restore-other-tickets-registry-rows!` over the same
`registry-specs`, now covering all three registries. Coverage: bb runner
cases BL-1631 (01)-(09) exercise the pure function directly and the real
orchestrator against real fixture trees (including the pole register's
accepted-row exception, BL-1629's disposition); acceptance scenarios 01-03
drive the real function and the real `land_step_cli.bb` end to end.

## What was wrong, and the fix

Three lands on 2026-09-17 (BL-1605 10:04, BL-1613 13:14, BL-1623 16:44)
closed with their own standing-red/allowlist rows still present in the
replay, each read `unowned` within minutes and throttled intake to one
(BL-1429), costing a specifier round trip each time to retire by hand.
`land_step_lib.bb` had the restore half of this shape (BL-1604: an open
sibling's row a tip-pure replay would otherwise drop is restored) but no
retire half at all.

- **`rows-to-retire`** (new, pure): given a registry's data lines,
  `owner-fn` and `task-ticket-id`, returns the lines whose owner is the
  landing ticket AND whose own `retirable?-fn` (a per-line predicate,
  default always-true) says yes.
- **`registry-specs`** gains a third entry, `backlog/suite-poles.tsv`
  (row-key = file column, owner = ticket column), each with a new
  `:retirable?-fn` key (absent on the other two = always retirable; the
  pole register's is `(not (re-find #"(?i)accepted pole" line))`, matching
  the one live accepted row's own note text - BL-1629's disposition has no
  dedicated column to read instead).
- **`restore-other-tickets-registry-rows!`** now computes both `restore`
  and `retire` for each registry in the same pass (a restore candidate's
  owner is guaranteed never the landing ticket by `rows-to-restore`'s own
  filter, so the two sets never contend for the same row) and rewrites the
  replay tree's file via the new `rebuild-registry-content` (header/comment
  lines preserved verbatim and in place, kept data lines in original
  order, restored rows appended - byte-identical to the prior append-only
  behaviour in every existing BL-1604 case, verified by the unchanged bb
  runner). Returns `:retired` alongside `:restored`.
- **`land_step_lib.bb`**'s replay orchestrator (`replay!`) now `git add`s
  every registry touched by EITHER restore or retire, and threads
  `:retired-registry-rows` through to `land-plan`'s `:replay` result
  alongside the existing `:restored-registry-rows`.
- **`land_step_cli.bb`** prints one `REGISTER_ROW_RETIRED <registry> <file>
  <owner>` line per retired row, next to the existing
  `REGISTER_ROW_RESTORED` block (`register-row-retired-prefix`, the mirror
  of `register-row-restored-prefix`).

## Fixture note (acceptance handler)

The new handler (`bl1631LandRetiresOwnRegisterRowsSteps.js`) reuses
BL-1604's own fixture idiom (`mkSocketFixtureRoot`, an entangled unlanded
sibling committed AFTER `origin/main` is marked to force `land-plan`'s
`:replay` path) directly, per the ticket's own "How" direction. One
non-obvious ordering requirement surfaced building scenario 02: the
landing ticket needs a genuine own-path committed after `origin/main` is
marked (`writeActiveTicket` for its own backlog file) even though its
registry row content is otherwise unchanged from origin - without it,
`own-paths` reads empty and `land-plan` refuses the whole replay as
"nothing of this ticket's own contribution to land" (own-paths is a diff
against origin/main, and a row identical on both sides is, correctly, not
a diff).
