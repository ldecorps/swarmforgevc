# BL-1678: a land never ships an unapproved forward — coder

## What changed

1. `swarmforge/scripts/land_step_lib.bb` — `land-plan`'s `:land` verdict
   (no entangled sibling found) no longer short-circuits to a bare
   `{:action :land}` that trusted the caller-cited commit verbatim. It now
   runs through the SAME `own-paths` + `replay!` build the `:replay`
   verdict always did — `:unlanded` is empty, so nothing is excluded, but
   the result is a FRESH, single-parent commit built off `origin-main`,
   never the cited commit itself. `:action` is `:land` when there was no
   entanglement and `:replay` otherwise; both carry `:commit`/`:branch`
   from the same build. This closes the TOCTOU gap the incident actually
   exercised: QA's `LAND_CLEAN` check for BL-1666 was accurate for the
   commit it was asked about, but the later manual `git push origin
   HEAD:main` pushed whatever QA's branch had grown to by then
   (`bbeb70f408`, a 2-parent merge carrying BL-1640's bounced content) —
   never re-checked, never re-built.
2. Added `land-step-lib/verify-push-safe` (item 3's publish-step backstop):
   given a commit, refuses when it has more than one parent, or when its
   diff against `origin-main` touches a path attributed (via the existing
   `delivered-attribution`) to a ticket that is neither the commit's own
   (from its subject) nor already `closed-on-main?`.
3. `swarmforge/scripts/land_step_cli.bb` — new `verify-push <commit>
   [repo-root]` verb (`LAND_PUBLISH_OK <commit>` / `LAND_PUBLISH_REFUSED
   <reason>`). `:land`'s case now prints `LAND_CLEAN <(:commit plan)>`
   (the built commit, not the cited one) and shares the same
   stray/registry/entangled-report printing `:replay` already had (a
   clean land can carry stray-evidence/registry bookkeeping too, now that
   it goes through the same build).
4. `swarmforge/scripts/land_main_publish.sh` — `land_push_ff_only` runs
   `verify-push-safe` before every push it makes (exit 9 is its own
   sentinel, never rematched — rematching a merge commit or a foreign path
   fixes neither). New standalone `--push <commit>` mode/`run_push`: the
   entry point for a commit that never went through `--land` at all (the
   literal 2026-09-21 shape).

## What did NOT change

- `entangled-siblings`' candidate selection was already a full
  `origin-main..commit` ancestry walk, not path-filtered (BL-1461, already
  landed) — re-verified directly against the real BL-1666/BL-1640 commits
  (`git merge-base --is-ancestor 1a46af4fd1 <BL-1666's own checked
  commit>` — yes) and via a live `bb` run of `entangled-siblings`. Item 1's
  "what is wanted" is satisfied by existing code; the defect was items 2/3.
- The replay/own-paths content rules (BL-1272/BL-1354/BL-1389) are
  untouched, per the ticket's own FIRM constraint.

## Side effects of unifying :land/:replay (fixed in this parcel)

`:land` now also builds a real `land-replay/<task>-<short-commit>` branch
(deterministic, keyed on task+commit alone, same as `:replay` always did).
Several existing tests called `land-plan`/`landPlan` twice for the SAME
(commit, task) pair expecting `:land`'s OLD no-op shape — these now collide
on the branch name the first call claimed. Fixed by dropping the first
call's branch before the second, the same discipline already used
elsewhere in both files for repeated `:replay` calls:
- `swarmforge/scripts/test/land_step_lib_test_runner.bb`: 4 sites (BL-1446
  scenario 01 bounded/wide, the `:origin-main c1` case, BL-1446 scenario 03
  doseq).
- `specs/pipeline/steps/bl1446LandWalkNeverCountsLandedHistorySteps.js`: 2
  sites (same shapes, JS side).

Also: two existing fixtures (`land_step_lib_test_runner.bb`'s BL-1650 item
0 test, and `bl1650LandStepPureEvidenceStraySteps.js`'s scenario 04) put an
abandoned sibling's own content at a path (`sibling.txt`) outside
`backlog/evidence/`/`docs/` — BL-1650's own pure-evidence-stray carve-out.
Under the old bare `:land`, `own-paths` was never consulted for these, so
the ambiguity was invisible; now that `:land` genuinely builds, BL-1546's
existing closed-owner refusal correctly fires (the path's only owner is
closed but its content isn't demonstrably on `origin/main`). Moved the
path under `backlog/evidence/` in both fixtures — the realistic shape
BL-1650's own commit text describes, and now a real stray-cherry-pick
instead of an escalate.

## Invariants (BL-654)

Both of BL-1678's declared invariants have coder-authored, non-vacuous
property tests in
`extension/test/bl1678LandNeverShipsUnapprovedForwardInvariants.property.test.js`:

- invariant 1 ("no unapproved forward ever rides"): drives the real
  `land_step_cli.bb` over a generated matrix of the sibling's own path
  count (1–3) × its ancestry position relative to the landing ticket's own
  commits (before/between/after — the BL-1461 shape). Non-vacuity: broke
  `own-paths`' exclusion clause to `false` (nothing ever excluded) and
  confirmed the property fails, naming the sibling's own path as present
  in the built commit; restored the real code, re-verified green.
- invariant 2 ("origin/main never gains a merge commit"): drives the real
  `land_main_publish.sh --push` over 4 shapes (2-parent merge, 3-parent
  merge, a single-parent tip whose ancestry still carries a foreign path
  via an earlier merge — the actual incident shape, and a genuinely clean
  commit that must be ACCEPTED). Non-vacuity: short-circuited
  `verify-push-safe`'s refusal in `land_push_ff_only` and confirmed the
  merge-tip shape then pushes a 2-parent commit to `origin/main`; restored
  the real code, re-verified green.

Both restores verified against a clean `bb -e '(load-file ...)'` load and
a full re-run of both property tests (green).
