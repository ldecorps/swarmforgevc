# BL-1083 — coder pass

Commit: this parcel · 2026-08-23 · worktree `swarmforge-coder`

## The fix, in one sentence

`promoteToActive` — the mover, not either of its callers — now takes its
verdict from `promotion_gates_cli.bb` and refuses when a gate says no.

## Why the mover and not the callers

Both live callers reached the same bare file move: the Telegram Expedite verb
and the paused-pager endpoint, whose own comment called the semantics
*"force-promote"*. A check in one would have left the other, and every future
one, open — which is this defect exactly, with one caller fewer. So the gate
sits at the single point both pass through, and the paused-pager comment that
said "force-promote" no longer says it, because it is no longer true.

## Not a second copy of the rules

`backlogWriter.ts` contains no reference to `depends_on`, `hold`,
`human_approval` or the depth cap. It knows three words: **ALLOW**, **REFUSE**,
**NOT_FOUND**. Verified mechanically, not by reading — scenario 01 strips
comments and asserts no gate-rule name survives as live code in any promotion
path, and asserts the same names *are* live code in `promotion_gates_lib.bb`,
so the check cannot pass by looking for the wrong strings.

One new bb subcommand carries the composition:
`promotion_gates_cli.bb gate-promotion <root> <BL-id>` does locate → cap
resolution → evaluate and prints `ALLOW|<file>`, `REFUSE|<gate>|<reason>` or
`NOT_FOUND`. Everything that decides anything stayed in Babashka.

### A BL-973 lesson applied the same day it was learned

The cap resolution first shelled to `effective_backlog_depth_cli.bb`,
`backlog_depth_conf_path_cli.bb` and `backlog_depth_cli.bb` — three siblings
reached by name, none of them in this CLI's load-file closure. The depth-cap
test caught it: a fixture copying the CLI's *real* dependencies still lacked
them, so the cap silently fell back to the default instead of refusing. That is
precisely the class of defect BL-973 had just removed from five other places.

The configured cap now comes from `backlog-depth-lib` **directly** — already in
the closure. The one remaining shell-out, `effective_backlog_depth_cli.bb`, can
only make the cap **tighter** (it is `min(configured, throttle)`), so its
absence degrades to the configured cap and never to a looser one; Article
3.2.4's rule that expedite never overrides the circuit breaker holds wherever
it is present.

## Expedite is still a real verb

Both paths now record the human's approval **before** the gates are consulted,
so `human_approval` is *satisfied* rather than skipped. The Telegram path
already did; the paused-pager path did not, and now does. Without that, this
fix would have killed the verb — the over-correction the ticket's own QA step 5
warns about, and what P4 below exists to catch.

## The operator is told, in the topic

A refusal returns the gate's own words. The Telegram verb posts them to the
Approvals topic (`"BL-x: Expedite refused by the depends_on gate — …"`) and
dispatches **no build**, because the ticket is still paused. The paused-pager
endpoint answers **409** with `{ gate, reason }` — 409 rather than 500 because
the request was well formed and the system is healthy; a rule said no
(BL-572/662: never a bare status).

The approval itself is still committed on a refusal: it is a real human
decision that landed on disk, and leaving it uncommitted is the durability
hazard BL-490-VIOLATION describes.

## The gates fail CLOSED

An unreachable CLI refuses, naming itself. A gate that fails open is not a
gate — and this one exists because a bypass promoted BL-1078 onto an unlanded
BL-713. The consequence is real and is paid for honestly: every fixture that
expects a promotion now carries the gate, through one shared
`installPromotionGates` helper whose copy list is **derived** from the CLI's own
closure (BL-973's helper). Three consumers share it rather than three
near-identical setups.

## Declared invariants (BL-654) — both encoded, non-vacuity measured

`extension/test/bl1083PromotionGateInvariants.property.test.js`.

Invariant 1 is a claim about the **source tree**, not about inputs, so P1/P2
state it that way — generating fake movers would test the detector rather than
the tree. Invariant 2 **is** quantified: over every gate that can refuse, so a
fifth gate added later inherits the guarantee by construction.

| property | invariant | what it holds |
|---|---|---|
| P1 | 1 | every mover into `backlog/active` consults the chokepoint — and there is **more than one**, because the defect *was* the second path |
| P2 | 1 | no mover outside the chokepoint carries the rules as live code |
| P3 | 2 | every refusing gate leaves the folder listing **byte-identical** AND returns a named gate and reason |
| P4 | — | armed-ness: a clear ticket still promotes, and a satisfied dependency does not refuse |

P3 is stated as a **conjunction** deliberately: each half without the other is a
defect wearing the other half's costume. A refusal that still shuffles files is
worse than no gate; a refusal that says nothing is the silent no-op invariant 2
forbids.

P4 is not optional. P1, P2 and P3 are **all** satisfied by a mover that refuses
everything — perfectly honest, and Expedite dead.

Non-vacuity, four breaks, each restored, failing-test counts measured:

| break | failing tests |
|---|---|
| move the file BEFORE consulting the gates | 4 |
| a refusal returns `{moved:false}` with no reason | 2 |
| the gates fail OPEN when the CLI is unreachable | 1 |
| the mover refuses every promotion | 3 |

## One thing for the architect to weigh

`PollAdapters.promoteTicketIfPaused` is now a **union**:
`Promise<boolean | PromotionOutcome>`, normalised in one place. That was chosen
so every existing boolean-returning stub in other tickets' tests keeps working
untouched — churning them would have added risk without adding value. If you
would rather see the union collapsed to the object shape, it is a mechanical
follow-up across about five call sites, and I would not argue against it.
