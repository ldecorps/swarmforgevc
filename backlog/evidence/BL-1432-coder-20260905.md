# BL-1432 — coder pass, 2026-09-05

## What was wanted

The land walk (`origin/main..tip`) grows forever: tip-pure replays land a
parcel's CONTENT under new SHAs on `main`, so QA's own review-merge commits
and main-sync merges never become main ancestors and never leave the
branch. 1839 commits ahead on 2026-09-05, growing a few per ticket, paying
3.5-4.5 minutes of git-subprocess cost on every land and inflating
`ENTANGLED_SIBLING` reports with sixty-odd done tickets. Human ruling
(re-opened, then confirmed): option 3, both mechanisms - bound the walk to
the parcel's own base (option 2), and re-point the QA branch to
`origin/main` after each successful, clean land (option 1).

## What landed

- **`swarmforge/scripts/task_scope_gate_lib.bb`**: `parcel-own-base`, a
  public wrapper exposing the same `last-handoff-commit`/`effective-base`
  notion `parcel-own-changed-paths` already computes for the send-time
  scope gate - never a second implementation of "this task's own base".
  `nil` on a task's first hop or an unreadable abandoned-base, both of
  which the caller falls back to `origin-main` for (only ever widens).
- **`swarmforge/scripts/land_step_lib.bb`** (option 2, the bounded walk):
  - `entangled-siblings` and `own-paths` each gained an optional trailing
    `walk-base` parameter, defaulting to `origin-main` (every existing
    caller/test unaffected). `walk-base` bounds the candidate walk
    (`ancestry-commits`) and the delivered-diff read
    (`full-delivered-paths`, via `delivered-attribution`); `origin-main`
    stays exactly what it was - the tree every landed/unlanded and
    approval verdict is read against (invariant 2: a narrower walk must
    never change what counts as landed).
  - `land-plan` gained an optional `:base` opts key (same convention as
    the existing `:origin-main` key, BL-1431). Omitted, it computes
    `(or (task-scope-gate-lib/parcel-own-base root task-ticket-id)
    origin-main)` automatically - production callers (`land_step_cli.bb`)
    need no change to get the bounded walk; a direct/test caller can pass
    `:base` explicitly.
- **`swarmforge/scripts/land_step_lib.bb`** (option 1, the re-point):
  `post-land-repoint!` - refuses (never runs `git reset --hard`) on an
  uncommitted change (`git status --porcelain` non-empty) or a parcel
  still in `in_process` (checked BEFORE the dirty check, mirroring
  BL-1421's own ordering - an in_process parcel's own mailbox file is
  untracked and would otherwise misreport as a generic "uncommitted
  change"), each named in a durable log
  (`.swarmforge/daemon/land-repoint.log`). On a verified-clean tree, moves
  the branch AND the worktree to `origin/main` and logs the old and new
  tip either way.
- **`specs/pipeline/steps/bl1432LandWalkRangesOverTheParcelSteps.js`**
  (new): drives the real `land_step_lib.bb` (via `bb -e` + `load-file`,
  the same pattern `bl1026StageBudgetStatedOnceSteps.js` already
  establishes) against a fresh fixture repo per scenario - never a
  reimplementation of the walk or the re-point.
- Unit coverage: 5 new assertions in `land_step_lib_test_runner.bb`
  (bounded-walk `:land`/`:replay` pair, the pre-existing unbounded
  fallback unchanged, `post-land-repoint!`'s three outcomes), 2 new in
  `task_scope_gate_lib_test_runner.bb` (`parcel-own-base`'s two cases).

## Declared invariants

1. **Walk cost is a function of the parcel, never the branch's age.**
   Demonstrated directly: `ancestry-commits` bounded to `:base` visits
   only the parcel's own commit (scenario 01, and the corresponding bb
   unit test's `:land` verdict where the SAME tip's unbounded walk
   misreads a stale sibling as entangled - the exact defect this ticket
   fixes, reproduced and then shown fixed in one test).
2. **What counts as entangled/landed/own is unchanged; a narrower range
   never hides a real sibling.** `origin-main` stays the tree every
   landed/unlanded verdict reads against - only the candidate range
   (which commits are inspected FOR a sibling) narrows. Scenario 02's own
   fixture proves the positive case: a sibling committed AFTER `base` is
   still caught (`:replay`, naming it), even though it is a live parcel
   ticket a bounded walk could in principle have missed had the bound
   been drawn wrong.
3. **Nothing in flight is ever discarded by the re-point.** `post-land-
   repoint!` refuses on either an uncommitted change or an in-process
   parcel, names the reason, and never touches the branch or worktree in
   either case (scenario 04, both Examples rows) - the `git reset --hard`
   only ever runs after both are verified clean.
