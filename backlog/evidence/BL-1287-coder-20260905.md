# BL-1287 — coder pass, 2026-09-05

## What was wrong

`extension/test/helpers/fixtureTunnelName.js`'s `leakedFixtureTunnelPids`
selected every temp-path cloudflared on the host with no scoping to the
asking run. `bl857TunnelOwnershipInvariants.property.test.js` calls it at
MODULE LOAD and SIGKILLs everything it returns, before its own first
assertion. The property lane runs `pool: 'forks'` with more than one
worker, so a concurrently-running sibling (`bl787NamedTunnelInvariants`,
which holds its own fixtures live for tens of seconds) can have its
fixtures killed out from under it by a file that has not started testing
yet. Measured at spec time: a process shaped exactly like a live bl787
fixture was selected by the real predicate 100% of the time it overlapped.

## What landed

- **`extension/test/helpers/fixtureTunnelName.js`**: `leakedFixtureTunnelPids`
  gains a second filter, after the existing temp-path/cloudflared/`run`
  check: the fixture's own tunnel name already encodes its creator's pid
  (`fixtureTunnelName()`'s own `sfvc-test-<pid>-...` shape), so the sweep
  reads it back (`creatingPidFor`) and skips any fixture whose creator is
  still alive (`isProcessAlive`). A fixture whose name doesn't carry this
  shape at all (no known live owner to protect) falls back to the
  pre-BL-1287 posture — selected — so this cannot make invariant 2 regress.
  Both new functions exported for direct testing.
- **`extension/test/helpers/fixtureTunnelName.test.js`** (new): focused
  unit tests for `creatingPidFor` (including the anchor-on-`run`, not
  merely-mentions-the-name case) and `isProcessAlive` (including pid 0 /
  negative pids never throwing or signalling this process's own group).
- **`extension/test/bl1287FixtureSweepScopingInvariants.property.test.js`**
  (new): the three declared invariants as genuine generative properties
  (P1/P2/P3 below), driving the real function against real spawned
  processes.
- **`specs/pipeline/steps/bl1287FixtureSweepSparesLiveRunSteps.js`** (new):
  acceptance step handlers, all 3 scenarios (4 runs).
- **`extension/test/bl1061TunnelFixtureIsolation.property.test.js`**: fixed
  a real regression this change surfaced in a PRE-EXISTING property test
  (see below) — its own "leaked fixture" synthetic lines used
  `fixtureTunnelName('leaked')`, which always embeds the CURRENT (live)
  test process's own pid as creator; under the new creator-liveness check
  that made every synthetic fixture look like a live sibling's, not a
  leaked one, and the property started failing. Added
  `fixtureTunnelNameWithCreator(creatorPid, label)` and a single
  once-computed dead pid (`spawnSync('true', [])`, reused across the whole
  property rather than respawned per generated case) so the synthetic
  fixtures honestly model "leaked by a run that is gone" under the new
  semantics. No other file in the tree calls `leakedFixtureTunnelPids` or
  `fixtureTunnelName` (`grep -rl`, confirmed exhaustive).

No change to `tunnel_ownership_lib.sh` or any other production script —
this ticket's own scope is entirely the test-harness sweep helper.

## Declared invariants (BL-654)

**Invariant 1** ("A fixture sweep only ever signals a pid whose creating
run is no longer alive; a fixture a live run still owns is never
selected, however its temp path or tunnel name is shaped.") — **P1** in
`bl1287FixtureSweepScopingInvariants.property.test.js`: randomizes creator
liveness (alive/dead) crossed with a random tunnel-name label shape,
spawns a REAL fixture accordingly, and asserts selection tracks creator
liveness alone.

**Invariant 2** ("The sweep still clears every fixture left by a run that
is gone, however that run died...") — **P2**: randomizes which signal
kills the creator (`SIGKILL`, the untrappable one; `SIGTERM`, a
cooperative one) and asserts the fixture is still selected either way.

**Invariant 3** ("No selection path can reach a cloudflared outside the
OS temp directory, however the tunnel names collide.") — **P3**:
randomizes whether an installed (non-temp-path) process's tunnel name is
identical to or merely similar to a real fixture's, and asserts the
installed one is never selected. Both share a DEAD creator pid
deliberately — a live-creator name would leave this property vacuous
(masked by invariant 1's own mechanism rather than exercising invariant
3's); this was a genuine gap caught and fixed during authoring (see
non-vacuity below).

**Non-vacuity**, each mutation run for real and restored byte-identical
(`diff` against a pre-break backup confirmed exact restoration):
- P1: dropping the `creatingPidFor`/`isProcessAlive` filter (selecting
  unconditionally on temp-path shape alone, the pre-BL-1287 behavior)
  failed on the very first generated case with `creatorAlive=true` —
  `"expected selected=false, got true"`.
- P2: forcing `creatingPidFor` to always return `null` (every fixture
  falls back to "unparseable, sweep it") happened to still pass P2 (a
  dead creator's fixture is swept either way under that fallback too) but
  FAILED P1 immediately — confirming P1 and P2 check genuinely different
  halves of the mechanism, neither masking the other.
- P3: **first draft was vacuous** — using `fixtureTunnelName()` (which
  always embeds the live property-test process's own pid) for the
  installed process's colliding name meant invariant 1's own
  creator-liveness check already excluded it regardless of the temp-path
  filter, so removing the temp-path condition did not fail the test.
  Caught by actually running the mutation (not merely asserting it would
  fail) — the established non-vacuity discipline this session, which
  exists exactly to catch this class of gap. Fixed by giving both the
  fixture and the installed process a shared DEAD creator pid (isolating
  the temp-path filter as the only thing protecting the installed one);
  re-run against the same mutation, now fails immediately —
  `"expected the installed-path pid ... to never be selected, got
  [...]"`. The acceptance step handler's scenario 02 carried the identical
  gap and was fixed the same way (see qa_e2e below).

**Reachability**: P1/P2/P3 each assert their own generator floor is
structurally satisfied (booleans and small constant sets over ≤12 runs
each, appropriate to real-process-spawning cost).

## A second guard, a second fix (BL-1280's mkdtemp migration)

The first commit attempt was refused by `check_property_suite_drift.sh`'s
own full-suite run: `bl1280MkdtempMigrationInvariants.property.test.js`
(a pre-existing, unrelated guard enforcing that every OS-temp-dir
allocation in the unit lane goes through the shared, sweep-registered
`mkTmpDir()` rather than a raw `fs.mkdtempSync(path.join(os.tmpdir(),
...))`) correctly flagged this ticket's own new
`bl1287FixtureSweepScopingInvariants.property.test.js:25`. Fixed by
routing `spawnFakeCloudflared`'s default temp directory through
`mkTmpDir()` instead. The `os.homedir()`-rooted "installed path"
directories (deliberately outside the OS temp directory, simulating an
installed binary) are untouched — `mkTmpDir()` itself always roots under
`os.tmpdir()`, so it isn't the right tool there and the guard correctly
does not ask for it. The acceptance step handler's own equivalent
temp-dir calls are outside this guard's scan scope (`extension/test/`
only) and outside vitest's own `afterEach` sweep mechanism (the
acceptance runtime is a plain `node --test` process, not vitest), so
`mkTmpDir()` would not add real cleanup there — left as a plain
`fs.mkdtempSync`, matching every other step handler in this tree.
