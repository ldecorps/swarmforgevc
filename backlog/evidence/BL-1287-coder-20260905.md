# BL-1287 — coder pass, 2026-09-05 (bounce fix)

## Bounce being answered

`backlog/evidence/BL-1287-bounce-20260905.md` (architect, commit `cef457dd50`):
`isProcessAlive` (`extension/test/helpers/fixtureTunnelName.js`) used a bare
`process.kill(pid, 0)` to decide whether a fixture's creating run was still
around. That answers "does some process with this pid exist and can I
signal it?", not "is it actually gone?" — a SIGKILLed process stays
signallable as an unreaped zombie until its subreaper collects it, so a
creator that had just been killed but not yet reaped was misreported as
alive and its leaked fixture was never swept, directly violating declared
invariant 2 ("the sweep still clears every fixture left by a run that is
gone, however that run died").

Architect's bounce reverted the whole parcel (coder `caf26a4c07` + cleaner
`97c297608d`) back to the pre-BL-1287 tree per Article 4.4 (multi-stage
blame bounces to the earliest role, inventory travels) — this pass
re-implements the ticket from that base with the defect fixed, not a patch
on top of the reverted commit.

## What landed

- **`extension/test/helpers/fixtureTunnelName.js`** (re-added): same
  `creatingPidFor`/`leakedFixtureTunnelPids` shape as the original pass,
  but `isProcessAlive` now treats a zombie as gone. There is no known
  command-line text to match identity against here (only a bare creator
  pid, unlike BL-1292's `fixtureLiveness.js#isAlive` which also confirms
  identity via `ps -o args=`), so the fix confirms liveness by **process
  state** instead: after `process.kill(pid, 0)` doesn't throw, `ps -o
  stat= -p <pid>` is read and a leading `Z` (zombie) is treated as gone,
  the same way a `ps` failure (pid fully reaped between the two checks) is.
  Also hardened `isProcessAlive` to refuse pid `0` and negative pids
  up front (never asks the kernel a process-GROUP question) rather than
  relying on `kill(0, 0)`'s incidental non-throwing behavior — the
  pre-existing unit test only pinned "never throws" for those inputs, so
  this is a strictly safer implementation of the same contract, not a
  behavior change the test suite depended on.
- **`extension/test/helpers/fixtureTunnelName.test.js`** (re-added, 7
  tests — 6 original + 1 new): adds "isProcessAlive answers false for a
  zombie process", using BL-1292's own `spawnZombie` helper
  (`fixtureLiveness.js`) to construct a genuine, `/proc`-confirmed zombie.
- **`extension/test/bl1287FixtureSweepScopingInvariants.property.test.js`**
  (re-added, 3 tests): invariant 2's property now drives THREE death modes
  instead of two — `SIGKILL`, `SIGTERM`, and `ZOMBIE` (the bounce's own
  case) — using the same "loop over named situations, `numRuns: 3` each,
  assert every situation was actually drawn" pattern
  `bl857TunnelOwnershipInvariants.property.test.js`'s own BL-1292 property
  already established, rather than inventing a new idiom.
- **`extension/test/bl1061TunnelFixtureIsolation.property.test.js`**
  (modified): same regression fix as the original pass — its
  invariant-2 property's synthetic "leaked" fixtures need an explicit
  dead creator pid (`fixtureTunnelNameWithCreator`), not
  `fixtureTunnelName()`'s own live-process-pid default, or the new
  creator-liveness check reads them as belonging to a live sibling and
  strands them unselected.
- **`specs/pipeline/steps/bl1287FixtureSweepSparesLiveRunSteps.js`**
  (re-added, unchanged from the original pass): the acceptance step
  handlers. Not given a zombie companion case — that would require a new
  Scenario Outline row in `specs/features/BL-1287-...feature`, and
  hand-authoring Gherkin is specifier/hardener territory, not coder's
  (constitution, coder role prompt "Does Not Own"). The zombie
  non-vacuity the bounce asked for is authored instead in the property
  test above, which IS coder's to author (BL-654) and is the file the
  bounce evidence itself points at as the mechanism of the finding.
