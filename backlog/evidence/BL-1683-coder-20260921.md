# BL-1683: the merge-drop guard maps renames and judges by new-path content — coder

## What changed

`swarmforge/scripts/merge_drop_guard_lib.bb`:

1. New `changed-paths-status` (`git diff -M --name-status base side`,
   parsed into `{:status :old-path :new-path}` rows) and `rename-map`
   (old-path → new-path, rename rows only) — the guard previously only had
   `changed-paths` (`--name-only`, no `-M`), blind to renames entirely.
2. New `diff-u0-refs` — diffs two arbitrary `<commit>:<path>` blob refs
   directly (verified this is valid git syntax: `git diff -U0
   <commit>:<pathA> <commit>:<pathB>`), needed because a rename means the
   two sides of a diff no longer share one path, and the existing
   `diff-u0` (`git diff -U0 from to -- path`) requires exactly that.
3. `findings-for-merge` now builds a rename map for BOTH the received and
   sender sides and, for each candidate path, resolves EACH side's own
   hunks (used for both "this side's own uncontested content" and "the
   other side's contested check") against THAT side's own renamed path
   when it renamed — not the old, vanished path, which a naive
   `base→side` diff at the old path reads as "every line deleted" (a
   rename artifact, not a real edit) and would spuriously CONTEST the
   other side's genuine edit at the same base position. Also resolves the
   path read FROM the merge commit's own tree to whichever side's rename
   applies (`merge-path`), so a real drop at a renamed path is reported
   AT THE NEW PATH, matching the ticket's own FIRM claim.
4. `findings-for-side`/`plus-minus` updated to take separate `from-path`/
   `to-path` arguments instead of one shared `path`, using `diff-u0-refs`.
5. `revert-excuses?` and the BL-1610 blob-identity excuse
   (`excused-by-blob-identity?`) are UNCHANGED, per the ticket's own FIRM
   claim — neither function's code was touched.

## A gap found while building the fixture (not shipped)

An early attempt at the fixture had the sender's own "append line 21"
edit land at the SAME base position as the received side's own 15-line
insertion (both "at the end of the shared stub"). The guard correctly (if
unhelpfully for that fixture) read the two as CONTESTING each other
(`contested?`'s own documented rule: two insertions at the same base
position ARE contested) — own-paths/hunk logic untouched, this was purely
a fixture-construction lesson, not a code change. The final fixture places
received's edit at the stub's FIRST line and the sender's append at the
stub's LAST line, genuinely disjoint base positions.
