## What changed (test-only, per the amended Scope)

- **Case 1** ("a clean approved commit lands..."): replaced the raw
  `origin_main() == $SHA` equality check with three assertions matching
  what a tip-pure replay actually produces: (a) origin/main's new tip is
  the sha the land itself printed as `LAND_PUBLISHED` (new `published_sha()`
  helper, parsed from the land's own output - never re-deriving it another
  way); (b) that published commit's one parent is the PREVIOUS origin/main
  (captured as `BEFORE_MAIN` before the land runs); (c) its tree is
  byte-identical to the approved commit's own tree (`git diff --quiet`,
  zero differences) - fetched into `$root` first, since `$PUBLISHED` lives
  only in `$origin` (the replay's own scratch pushed it directly) and
  `$SHA` lives only in `$root` (the approved commit itself is never
  pushed) - the two were never comparable in one repository before.
- **Case 5**'s second `run_land "$SHA"` call: widened the pass condition
  to also accept `replay!`'s own "nothing to commit" refusal (BL-1474) -
  the CORRECT outcome for a repeat land of an already-landed ticket+commit,
  per the amended ticket's own text ("Not in scope: ... a repeat land ...
  escalating 'nothing to commit' is not a defect"). The original
  fresh-publish check is kept alongside it (a genuine interruption on a
  slower host still passes too) - nothing already-passing is removed.

## Why the second case needed no NEW commit, only a widened assertion

The architect's own investigation (and the coder's prior spec-gap
analysis) established WHY: bash defers a trapped `TERM` until the
currently-running foreground `$(bb ...)` command substitution finishes,
so `land_main_publish.sh`'s own first (killed) run in case 5 always
completes fully before the kill has any effect - confirmed both via the
real test's own output (`LAND_PUBLISHED <sha>` present in `five.kill.out`
every time) and an isolated reproduction (a `bb -e '(Thread/sleep
4000)...'` inside `$(...)`, SIGTERM'd to the wrapper after 1s, still
prints its own completion line). The second `run_land` call for the SAME
SHA therefore always finds the content already on origin/main - "nothing
to commit" is the correct, expected answer, not a symptom needing a
fresh-commit workaround.
