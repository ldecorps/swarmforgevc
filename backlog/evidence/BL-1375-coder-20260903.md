## What changed

### 1. `swarmforge/scripts/land_step_lib.bb` — the narrowed refusal

`own-paths`' shared-path arm used to refuse whenever ANY unlanded sibling
co-owned a path. It now asks WHICH sibling, through a new
`ticket-approval-state`:

| sibling state | rides? |
|---|---|
| `human_approval: approved` | yes |
| `human_approval` absent | yes — `backlog-schema.md`'s "no approval needed", the same value `promotion_gates_lib.bb`'s own gate passes |
| present and not `approved` (pending/amending/rejected/unrecognised) | **no** |
| filed in `backlog/hold` | **no** (the folder decides ahead of the field: a held ticket can still read `approved` from before a human pulled it) |
| found in no tree / filed in two folders / unreadable | **no** |

Only a POSITIVE read of "approved" narrows anything; every unknown keeps
BL-1332's refusal. `read-human-approval` is `promotion_gates_lib.bb`'s own
reader, reused rather than re-implemented, so a quoted value or an inline
comment cannot be read differently here than at promotion.

`own-paths`/`land-plan` now also return `:passengers` — the approved unlanded
siblings whose lines ride on an included shared path.

### 2. The rider: the replayed tree is guarded BEFORE publish

`replay!` runs `check_feature_handler_registration.sh` against the tree it
just built, and refuses naming the passengers when it fails. Run **only when a
passenger actually rides**: with nothing riding the tree is this ticket's own
content on `origin/main`, and an already-inconsistent main would otherwise
start refusing every land — a second deadlock in place of the one being
dissolved.

`check_feature_handler_registration.sh` gained `--assume-main`. Without it the
guard's branch gate exits 0 on the scratch `land-replay/...` branch's NAME and
the land collects a pass it never performed — the vacuous-guard shape the
rider exists to prevent. The flag can only ever make the guard RUN where it
would have skipped; there is no path that changes what the checker decides.

The guard list is a `def` (`replayed-tree-guards`), so a second tree guard is
one entry, never a second call site. Each guard runs as its own process with
its status collected individually — BL-1242/BL-1252's rule, satisfied by
construction rather than by `set -e` discipline.

### 3. `land_step_cli.bb` — `PASSENGER_SIBLING <ticket-id>`

One line per passenger, so QA is never told a land is clean without being told
whose content rode with it.

## Two defects found only by running it against the live jam

Both were invisible from reading, and both would have shipped a fix that left
the queue exactly as jammed.

1. **The approval read must consult BOTH trees.** A sibling's ticket file
   MOVES on `main` when it lands. Reading only the checkout the land runs from
   (the QA branch) reported `unreadable` — hence blocking — for BL-1328,
   BL-1346 and BL-1351, whose work was already on `main`. `ticket-approval-state`
   now reads the worktree AND `origin/main`, and EITHER saying blocking blocks.
   That needs no judgment about which tree is fresher, and nothing one tree
   says can read away a hold the other is carrying.
2. **`backlog/done/` nests by milestone** (`backlog/done/M8/BL-....yaml`). A
   non-recursive listing finds nothing for every landed sibling. Both readers
   now recurse (`file-seq`; `ls-tree -r`).
