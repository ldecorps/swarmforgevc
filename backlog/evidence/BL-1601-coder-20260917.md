# BL-1601 — coder evidence, 2026-09-17

## What changed

`extension/test/telegramCursorOperatorExec.test.js`'s two `BL-1204` redeploy
tests spawn the real redeploy script `detached: true` + `child.unref()`
(the production module's own by-design shape - a redeploy outlives the
bot) and returned before the script wrote its marker. `tmpDirSetup.js`'s
afterEach then raced `fs.rmSync(dir, {recursive:true})` against the
still-running script, throwing `ENOTEMPTY` whenever the write landed
between the sweep's directory listing and its rmdir - a load-shaped
flake normalised by four roles across eleven days.

Fix (both halves of the ticket's "What is wanted"):
- The two tests now call the pre-existing `waitForFileSync(marker, {
  timeoutMs: 2000 })` helper (`extension/test/helpers/waitForFileSync.js`,
  BL-1063) after `executeOperatorVerb` and assert `.ok` - this also proves
  the real script ran, which the tests lacked before.
- `extension/test/helpers/tmpDir.js`'s `sweepPendingTmpDirs`/
  `sweepSharedTmpDirs` gain a bounded retry (`removeWithRetry`, 5
  attempts, 50ms synchronous sleep between them via the same
  `Atomics.wait` technique `waitForFileSync.js` already uses - exported
  as `sleepSync` from there, reused rather than duplicated) on
  `ENOTEMPTY`/`EBUSY`; the LAST attempt's error is rethrown exactly as
  before - never swallowed. `rmFn`/`sleep`/`attempts`/`delayMs` are all
  injectable (the ticket's own "existing fs seam or a rmFn parameter"
  direction), production callers pass none and get the real retry.

## Declared invariant (BL-654)

> "A fixture root that never empties still fails the run: after the
> bounded retries the sweep rethrows the same error, never returns
> quietly, so the retry can only turn a race into a pass, never a leak
> into silence."

`extension/test/bl1601TmpDirSweepRetryInvariant.property.test.js`: for a
generated number of failures-before-success (0-8) against the real
`sweepPendingTmpDirs` (5-attempt bound, `rmFn` injected) - within the
bound, the sweep succeeds after exactly that many calls and the root is
gone; at or past the bound, the sweep rethrows the SAME error code, after
exactly 5 calls, never more. Generator-reach asserted for both branches.

Non-vacuousness, verified by hand before forwarding: patched
`removeWithRetry`'s final `throw err` to `if (attempt >= attempts) {
return; } throw err` (a silent swallow on exhaustion) - the property
failed immediately (assertion on `threw` being non-null); restored, green
again.
