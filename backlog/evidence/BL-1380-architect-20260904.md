## Correctness read — the asymmetry with the Approve route

Read `classifyExpediteRulingRefusal` and `classifyApprovalRulingRequirement`
directly to verify the coder's stated design choice (refuse only on
`ruling-required`, let `unknown-option` proceed) actually matches the
ticket's own invariant wording, not a looser reading of it. Invariant 1
says: "a ticket with declared `ruling_options` and no ruling **on record**
never reaches `human_approval` approved" — and `classifyApprovalRulingRequirement`
returns `ruling-required` exactly when `ruling.trim()` is empty (no ruling
on record at all), while `unknown-option` covers the two cases where a
non-blank ruling text EXISTS but does not match a declared label (or
options are declared as empty but a ruling exists anyway). So refusing
only on `ruling-required` is not a looser implementation of the invariant
— it is the precise case the invariant names, and letting `unknown-option`
through correctly avoids re-litigating an answer that already exists,
which would be the BL-1083 over-correction the ticket explicitly warns
against. The gate runs before any write (`recordApprovalReply` is called
only past the check), matching the Approve route's own model.
