# BL-1379 — CODER PASS, 2026-09-04

## What was wrong

`park-plan` moved every ticket in `backlog/active/` except the run ticket into
`backlog/hold/` at initiation, and nothing ever moved them back. Article 3.1
makes `hold/` **human-held** — "never auto-promote from here; they sit until a
human moves them back" — so a mechanical, temporary park landed in the one
folder whose entire contract is that only a human empties it, and became
indistinguishable from a deliberate hold the moment the run ended. Five tickets
sat there from 12:02 on 2026-09-04 with nothing to notice.

## Built to the RULING, not to the acceptance — and why

`human_ruling` is **option 3**: restore to the prior folder, and mark each
restored ticket as needing a freshness check before it may be worked. The
feature file was written for option 1 (`restore to paused/`) and its scenario
02 still says so. The ticket anticipates this — "options 2 and 3 amend that
scenario alone" — and the amendment has not happened.

So scenario 02 FAILS on this branch, deliberately. Building to the stale
scenario would repeat BL-1309 exactly, where a parcel was built against a
ruling that had already been superseded. Raised to the specifier by priority-00
note; not resolved here, because rewriting the acceptance to match my code is
the wrong direction of fit.

**Acceptance: 7/8, the one failure being that mismatch.**

## Invariant 1 is structural, not checked

`unpark-plan` iterates the run's OWN park record and nothing else, so a ticket
a human put in `hold/` is not skipped — it is never considered. A reversal
driven by "everything in hold/" is the one implementation that breaks Article
3.1, and a unit row asserts the plan only ever ASKS about tickets it parked
(the `seen` atom), which is the row that would catch that rewrite.

The fixture carries a human-held `BL-9003` in EVERY shape, not only in the
scenario named for it. Measured across all six: it stays in `hold/` every time
and is named in no report.

## The record is recorded, not assumed

A `park-record.json` already existed but carried only ticket IDs — the origin
folder was implicit in "park-plan only ever parks out of active/". It now
carries each ticket's origin explicitly, alongside the existing keys so
anything reading `:tickets` is unchanged. That implicit uniformity is precisely
what the ticket names as the thing that would rot.

## Invariant 2, against a real ancestry check

Nothing is restored until the expedition's commit is an ancestor of `main`. The
fixture builds that difference REALLY — the unlanded shape puts the commit on a
side branch `main` cannot see — because a fixture that fakes the check cannot
exhibit the thing the invariant guards. Measured: nothing restored, both
tickets still in `hold/`, each reported `hold-not-landed`.

## Invariant 3: refuses rather than guesses

`skip-moved`, `skip-closed`, `skip-absent` are distinct answers, each reported
with its reason — "left alone" and "left alone because it was closed" are
different facts to whoever reads the handover. Idempotence is a consequence
rather than a special case: the second run finds the ticket already in
`active/` and answers `skip-moved`.
