implemented and tested at both writers:

- `gitCommitScopedFile.ts` (`commitScopedFile`): bounded lock-refusal
  retry (12 attempts, capped backoff, ~16.5s), verifies against HEAD
  (`isFileCommitted`) before reporting failure, never discards a real
  attempt's stderr (`onFailureDetail`/`CommitFailureReporter`).
- `commit_integrity_lib.bb` (`commit-with-integrity!`) /
  `commit_integrity_cli.bb`: same shape (`lock-refusal?`,
  `landed-sha-if-matching`, raised `default-max-retries` to 12), plus the
  front desk's third outcome ("landed in `<sha>` by another writer").
- Unit tests: `gitCommitScopedFile.test.js`, `blTopicStore.test.js`,
  `commitIntegrityRunner.test.js`, `telegramFrontDeskBotCore.test.js`,
  `commit_integrity_lib_test_runner.bb` (new BL-1475 cases).
- Property tests (BL-654, both declared invariants, non-vacuous - proven

- Acceptance: `specs/features/BL-1475-*.feature`, all 6 scenarios, step
  handler in the same parcel
  (`bl1475SharedCheckoutWritersRetryAndVerifySteps.js`, BL-233).

## Self-audit finding, fixed in this parcel

`commit_integrity_cli.bb`'s close-guard bookkeeping
(`abandon-inflight-for-ticket!`, `record-lean-ledger!`) used to run
whenever `commit-with-integrity!` reported `:success true`. Adding
`:landed-elsewhere` as a success outcome would have made that bookkeeping
re-run for a close this process never actually committed (another
writer's own commit already represents it, and that writer's own call is
the one that ran - or will run - the bookkeeping). Fixed: bookkeeping now
gates on `genuinely-committed?` (`:success` true AND not
`:landed-elsewhere`), never on `:success` alone. Verified: the existing
multi-ticket-close shell tests (`test_commit_integrity_cli.sh`) still
pass unchanged - a real close still runs its own bookkeeping exactly
once.

## Deliberately not done here (direction, not mandate)

The ticket's "How" section also suggests `repair-bl-topic-records.js`
batch still-dirty records into ONE commit rather than one per record
(its one-per-record cadence rejected 20/20 QA land attempts on
2026-09-07). No declared invariant or acceptance scenario covers this -
scenarios 01-05 are all about the two RETRY/VERIFY mechanisms, never
about `repair-bl-topic-records.js`'s own commit batching strategy, which
is a materially separate, larger change (its commit-per-record loop
would need restructuring into one multi-path commit). Left as a
follow-on: `repair-bl-topic-records.js` still functions correctly as the
backstop it already was, just not yet re-architected to batch.

The `gitCommitScopedFile.ts` "return true with the landing sha" direction
is also not implemented literally - `isFileCommitted` (already
existence+porcelain-guarded, avoiding the BL-390 nil-vs-nil trap) is used
instead of a raw porcelain check, and no sha is threaded back through
`commitScopedFile`'s own return value. No scenario needs a topic-record
commit to name a sha (only the front-desk path does, scenario 03, which
does name it) - this is a legitimate implementation-detail deviation, not
a missed requirement.
