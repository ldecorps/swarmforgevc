## Declared invariant (BL-654) — stated reason, no new property test

The declared invariant ("every fixture that ticks operator_runtime.bb
with the miniapp watchdog enabled provides, real or stubbed, every script
the recovery invokes") is a census claim over the repo's shell test
fixtures, not a property of a pure, testable module with a meaningful
randomizable input domain. The ticket's own census names exactly the
population it quantifies over — `grep -ln
'OPERATOR_MINIAPP_WATCHDOG_ENABLED=1' swarmforge/scripts/test/*.sh
specs/pipeline/steps/*.js` — and re-running that grep on the tree as it
stands after this commit still returns exactly the same two files:

```
swarmforge/scripts/test/test_bl1159_bridge_child_survives_without_crash_giveup_loop.sh
swarmforge/scripts/test/test_operator_runtime_tick.sh
```

`test_bl1159_...sh` already satisfies the invariant (line 18: `cp
"$SRC/stop_bridge_headless.sh" "$SRC/recover_miniapp_bridge.sh"` — a
stubbed router, present before this ticket and untouched by it);
`test_operator_runtime_tick.sh` now satisfies it via this commit's real,
unstubbed copy. There is no third member and no generator: the
population is exhaustively enumerable by the grep itself, not sampleable,
and the property has no input space to draw from beyond "does this exact,
finite set of files each carry the script" — the same "no meaningful
randomizable input domain" shape as BL-1212/BL-1221/BL-1263/BL-1291's own
stated-reason invariants. A future third fixture enabling the flag
without the router is a new-file risk this ticket's own scope note
already excludes handling (nothing else in the shell lane is reworked);
the census itself is the enforceable check, and it is restated here
rather than encoded as a property test because shell has no
mutation/CRAP/DRY/property tooling wired at all (BL-472 deferred).
