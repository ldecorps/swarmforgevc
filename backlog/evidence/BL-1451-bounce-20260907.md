# BL-1451 — hardener bounce, 2026-09-07

## D1: a stage entry's `healthDot`, if it holds any value other than
`green`/`yellow`/`red`, renders the literal string `"undefined "` at the
head of the ticket's caption line on the live board

**Failing command**: N/A — a runtime rendering defect, not a failing
test (no existing test drives a malformed `healthDot`). Reproduced
directly against the real, compiled render path:

```
$ node -e '
const { computePipelineBoard, renderPipelineBoardBody } = require("./out/concierge/pipelineBoard.js");
const board = computePipelineBoard({}, [], {}, {
  activeIds: ["BL-1"],
  ticketStageEntries: { "BL-1": { stage: "coder", status: "active", healthDot: "blue" } }
});
console.log(JSON.stringify(renderPipelineBoardBody(board)));
'
"   NS SP CO CL AR HD DC QA\n  1 X  .  .  .  .  .  .  .\n\nundefined 1 (no backlog entry)"
```

The caption line for ticket BL-1 begins with the literal text
`undefined ` instead of either a real dot or the bare display id.

**Commit tested**: `278f75046d` (this hardening worktree's tip,
architect's `1a8b134aa0` merged in — the coder's own `a101045f63`).

**First error excerpt**: see the reproduction above — `"undefined 1
(no backlog entry)"` where the caption should read either a real glyph
(`🟢`/`🟡`/`🔴`) plus `1 …` or, for an entry that carries no usable dot,
just `1 …` (invariant 2's own "renders exactly as today").

**Failure class**: `behavior` — the BL-317 shape named in the hardener's
own standing lessons ("a parser that returns the same value for absent
and unreadable cannot validate — probe it with a present-but-malformed
input"), here on the CONSUMER side rather than a parser: `HEALTH_DOT_GLYPHS`
is a `Record<TicketHealthDot, string>`, a closed three-key map, but
`gridCaptionLine`'s lookup (`pipelineBoard.ts` ~963-964) trusts
`row.stageEntry?.healthDot` to actually BE one of those three keys at
runtime. It is not guaranteed to be: `readTicketStageMap` →
`normaliseObjectStage` (`swarmState.ts` line 237,
`healthDot: entry.healthDot`) passes the field straight through from
`JSON.parse` with zero validation — a raw cast
(`value as Partial<TicketStageEntry>`) gives TypeScript's `TicketHealthDot`
union no runtime teeth at all. Any value the on-disk
`ticket-stage-map.json` carries in that field that is not exactly
`"green"`/`"yellow"`/`"red"` (a stale/newer bb-side vocabulary, a typo, a
partial write, a future 4th tier) reaches `HEALTH_DOT_GLYPHS[dot]` as
`undefined`, and the truthy-but-unrecognized `dot` still takes the
"render a dot" branch:

```
const dot = row.stageEntry?.healthDot;
const dotPrefix = dot ? `${HEALTH_DOT_GLYPHS[dot]} ` : '';
```

`dot` is truthy for `"blue"`; `HEALTH_DOT_GLYPHS['blue']` is `undefined`;
template-literal-stringifying `undefined` produces the literal text
`"undefined "`.

**Expected vs observed**: Expected — this ticket's own invariant 2 ("A
ticket with no entry, or an entry without a dot, renders exactly as
today") is the stated contract for "nothing usable to show"; a malformed
dot is exactly that case in spirit (there is no real health signal to
render) and should degrade the same way an absent dot does — no prefix
at all. Observed — a malformed dot instead corrupts the caption line with
literal `"undefined "` text, which is WORSE than doing nothing: it is
human-visible garbage on the operator's primary phone view (Article 1.10)
the moment the on-disk map ever carries an unrecognized `healthDot`
value, which is entirely plausible across a bb/TS boundary with two
independently-editable literal sets (the same class of risk the
engineering rules name explicitly: "A constant mirrored across a language
boundary needs a test asserting both literals agree", BL-897).

## Why every existing check missed it

- The acceptance feature's Scenario Outline 01 only exercises
  `green`/`yellow`/`red`; Outline 02's "without a dot" only tests
  ABSENCE, never an invalid PRESENT value
  (`bl1451BoardRendersStageEntriesSteps.js`, `KNOWN_COLOURS`/
  `KNOWN_ENTRY_KINDS` sets — both closed to the well-formed cases only).
- The property test's generator is `fc.constantFrom('green', 'yellow',
  'red')` for the "has a dot" arm and omits the field entirely for the
  "dot-less" arm (`bl1451PipelineBoardStageEntryInvariants.property.test.js`)
  — the malformed-but-present case is never drawn.
- BL-113 Gherkin mutation on Outline 01/02 only mutates the EXAMPLES
  TEXT the coder already wrote (green→Green, etc.), which can never
  synthesize a value outside the declared set.
- `normaliseObjectStage`'s own unit/property coverage (BL-670, landed)
  predates this ticket and was never asked to prove anything about a
  CONSUMER of the field it passes through.

## Remediation (direction, not mandate)

Guard the render side (the smallest, most local fix, and the one place
every consumer of `healthDot` ultimately goes through): in
`gridCaptionLine`, only emit the prefix when the value is actually a key
of `HEALTH_DOT_GLYPHS` —
`const glyph = dot ? HEALTH_DOT_GLYPHS[dot] : undefined; const dotPrefix
= glyph ? \`${glyph} \` : '';` — so an unrecognized value degrades to
"no dot", exactly invariant 2's own contract. A read-side guard in
`normaliseObjectStage` (validating `entry.healthDot` against the known
set before ever attaching it to the entry) is the more thorough fix,
since it also protects `row.stageEntry.healthDot` for any FUTURE
consumer (BL-940, the Art Director's brief) from the same trap — but
that touches BL-670's landed file outside this ticket's own diff, so is
offered as the stronger option rather than the mandate. Either way, add
a Scenario (or extend Outline 02) covering `healthDot: <something not
green/yellow/red>` asserting the caption renders exactly as the
no-entry/no-dot case, and extend the property generator's health-dot arm
with an occasional out-of-set string alongside the three real values.

Blamed role: **coder** (the new consumer code — `gridCaptionLine`'s
`HEALTH_DOT_GLYPHS` lookup — is this ticket's own diff, and its evidence
claims non-vacuity was proven by hand without exercising a malformed
value; cleaner and architect's own NONE passes also missed it).
