## A fixture detail worth recording

`write_role_launch_script`'s `role_script_dir` resolves to the real
`$SCRIPT_DIR` only when a role's own `worktree` field is `master` (or
`none`) — any other worktree name resolves to `$WORKING_DIR/.worktrees/
<name>`, which a minimal fixture (no real worktrees created) never
populates. The step handler's fixture pack conf therefore declares `window
coder claude master ...` — `master`, never `coder` — so the generated
script's embedded `bb` path actually resolves to this repo's own
`swarmforge/scripts/swarm_telegram_env_cli.bb`.

`specs/features/BL-1699-...feature` scenario 06 ("both are byte-identical
to what the same pack produced before this ticket") regenerates a Claude
seat's launch script against BOTH this checkout's current code and
`main`'s blobs (`git show`), asserting them byte-identical — a guard that
BL-1699's OWN aider-specific change never leaked into a Claude seat's
script. This parcel's own template edit (`write_role_launch_script`)
legitimately changes the generated output for EVERY role, Claude
included — so, run from THIS in-flight worktree (ahead of `main`, which
does not yet have this commit), that one scenario goes red: 9/10 of
BL-1699's own scenarios still pass; only the cross-commit byte-diff does
not. This is not a functional regression — it self-resolves the moment
this commit lands on `main` (both sides of the comparison would then
include the identical BL-1775 block again), the same way it would for
any ticket that touches this shared template while its own branch is
ahead of `main`. Not modified — the check is correct on its own terms
for a LANDED main; only running it against an un-landed sibling commit
produces this transient state.
