## What changed

- `specs/pipeline/steps/bl977SupervisorProgressSteps.js`: `mkSupervisorFixture`
  now ages `handoffd.pid` to `pidAgeMs` (default `STALL_MS + 30000`, the same
  age already used for the pending outbox mail) instead of leaving it at its
  freshly-written mtime — a fresh pid file reads as a newborn daemon under the
  2026-09-02 startup grace and grants `:healthy` before the wedge/marker
  branch is ever reached (BL-977 scenario 05's bug). A caller testing the
  grace boundary itself can pass `pidAgeMs: 0` to keep it fresh.
- `checkEnv()` in the same file now pins `SUPERVISOR_RESTART_BUDGET_COUNT` to
  `0`. Found empirically while verifying the pid-age fix alone: once the
  verdict reaches `:stalled`, the default budget of 2 sends the first two
  checks through `restart-daemon!` (which starts a REAL second
  `handoffd_supervisor.bb` process against the fixture root) rather than
  `alarm-and-halt!`, so scenario 05's "halted after two checks" assertion
  never fires even with the pid correctly aged. The shell lane's equivalent
  fixture (`test_handoffd_supervisor.sh`) already forces the same budget to 0
  for its analogous stalled-verdict case; this brings the JS fixture to the
  same posture. No change to `handoffd_supervisor.bb` itself.
- New `specs/pipeline/steps/bl1500WedgeCheckPidAgeSteps.js`: drives the real
  `--check-once` against the bl977 fixture shape (reused via exports added to
  that file) with the pid file's age as the one control variable (`older` ->
  `halted`/`1`, `younger` -> `healthy`/`0`), and runs the real BL-977 feature
  end to end (nested `node specs/pipeline/cli.js`) to prove all ten of its
  scenarios resolve from the checkout the run is in.

## Invariants (BL-654) — stated reason, no property test (both)

Both declared invariants are about this ticket's JS acceptance-fixture layer
and a Babashka production function, not a pure TypeScript module the
`extension/test/*.property.test.js` / `npm run test:properties` lane (the
only property-test harness this repo wires) can drive. This ticket's own
`constraints:` scope every allowed edit to the fixture file, the new handler
and its registration, the header comment, and the doc sentence — a new file
under `extension/test/` is outside that list, and Babashka/JS step handlers
have no mutation or property harness of their own (BL-472, engineering.prompt
"Startup Tools").

1. *"Every BL-977 scenario that drives the real `--check-once` presents a
   daemon whose pid file is at least as old as the oldest silence it
   stages... so no BL-977 verdict is ever decided by the startup grace."*
   — **stated reason, no property test**. This quantifies over which JS
   acceptance scenarios call `mkSupervisorFixture`/`ageHeartbeat`/
   `writeMarker` and with what arguments — a fact about hand-written test
   code, not a pure function's input domain a generator could sweep.
   Discharged instead by construction: `pidAgeMs` now defaults to the same
   age already used for the outbox mail inside `mkSupervisorFixture` itself,
   so every current and future caller of the shared builder inherits an old
   pid file unless it explicitly opts out (`pidAgeMs: 0`, today only
   BL-1500 scenario 01's "younger" row — the one caller deliberately testing
   the boundary this invariant protects). The real BL-977 feature run
   (BL-1500 scenario 02) proves scenarios 03 and 05 both still resolve
   correctly with this default in force.
2. *"The startup grace is neither widened nor narrowed... younger... reads
   healthy... older... halted exactly once across repeated checks."*
   — **stated reason, no property test**. The pure JS wrapper
   `evaluateHealth()` in `bl977SupervisorProgressSteps.js` never passes
   `:daemon-age-ms` to the real `evaluate-health` — the startup grace is
   observable only through `file-age-ms` on a real pid file via the REAL
   `--check-once` binary, not through the pure function's existing argument
   surface. Adding that parameter to reach it from a generated
   `*.property.test.js` would be a production-adjacent wiring change outside
   this ticket's `constraints:`, and driving real subprocess spawns from
   inside `extension/test/` would be the wrong toolchain for a Babashka
   production file with no property harness of its own. Discharged instead
   by the new Scenario Outline (`bl1500WedgeCheckPidAgeSteps.js` scenario 01):
   both sides of the boundary run through the REAL `--check-once` against the
   REAL fixture, and confirmed non-vacuous above (reverting the fix fails
   this exact scenario, not just BL-977's pre-existing one).
