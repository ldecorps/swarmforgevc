## A real design bug found and fixed during TDD

My first pass had `commitApprovalDecision` notify the Approvals topic
whenever `committed` was falsy — including when `adapters.commitApprovalWrites`
was simply **absent** (not wired), not just when it was wired-and-failed.
Running the existing test suite caught this immediately: `BL-434
approvals-standing-topic-02` (a fixture with no `commitApprovalWrites` at
all) started asserting a spurious "FAILED TO COMMIT" notification on an
otherwise ordinary successful approve. Fixed by distinguishing the two
cases explicitly — absent degrades silently (the same "new capability
defaults to a no-op" posture every other optional `PollAdapters` field in
this file already documents), only a genuine wired-but-failed commit is
loud. This is the correct behavior, not just a test accommodation: an
absent adapter means a deployment hasn't wired this capability yet, which
is not a durability failure to alarm about.

## Invariants (BL-654)

Both declared invariants are covered by
`bl892ApprovalCommitDurability.property.test.js`, EXHAUSTIVE over the 3
verdict kinds (approved/rejected/amending) x 2 real commit-CLI states
(present/absent) = 6 combinations, per
`bl886_vitest_orphan_reaper_supervisor_property_runner.js`'s own small-
fully-enumerable-space precedent. Every writer exercised is the REAL
production function (`recordApprovalReply`/`recordRejectionReply`/
`recordAmendReply`, `recordApprovalDecisionAndClose`/
`recordAmendDecisionAndClose`, `commitApprovalWrites`) against a REAL git
repo — a mocked commit adapter could fake "committed", but invariant 1's
own claim is specifically about `git show HEAD:<path>`, which only a real
git process can prove:

- **Invariant 1**: with the CLI present, `git show HEAD:<ticket path>`
  shows the NEW value after every verdict kind; with the CLI absent, HEAD
  still shows the OLD value (`human_approval: pending`) — the working tree
  alone is never treated as durable.
- **Invariant 2**: with the CLI absent, `git rev-list --count HEAD` is
  UNCHANGED after the failed commit attempt — no bare `git commit` ever
  sneaks in as a fallback.

Non-vacuity proven directly: a second test simulates the exact bug
invariant 2 forbids (a real bare `git commit -am` bypassing
`commit_integrity_cli`) and confirms the property's own `revCount` check
would flag it.
