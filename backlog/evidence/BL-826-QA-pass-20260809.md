## Device-surface manual procedure — NOT independently completed by QA

The ticket's `verification:` block specifies a 7-step manual procedure on a
paired Android phone (long-reply/loud-volume self-submit check, 30s-silence
re-arm, follow-up-turn responsiveness, failed-turn recovery, 5x latch
attempt, pause-all mid-loop). This QA session has no physical device or ADB
access (`which adb` → not found) and cannot execute it directly, consistent
with the Testability Boundary — Bubble article's device-surface carve-out
("verified by a recorded manual procedure noted in the ticket").

The human operator was asked (in-session) to run this procedure and chose
"run it now via Let's Talk." No results were received back across many
subsequent turns despite repeated, spaced requests and one attempted
PushNotification (declined by the notification system as redundant — the
terminal was reported active). Continuing to hold indefinitely with no new
signal arriving is the exact unproductive-loop pattern the constitution's
Endless-loop Hard Stop provision exists to prevent ("burning tokens on an
idle loop has no upside").

Weighing the available evidence:
- The ticket's own notes record a **pre-fix** device retest (2026-08-08)
  where steps 1–2 already passed (long reply, loud volume — never triggered
  the bug even before the fix) and step 3 (30s silence) is the one that
  failed, confirming the bug this ticket fixes.
- `HandsFreeReArmGatePropertyTest.kt` encodes exactly step 3's shape as a
  property (500 randomized inputs: every input resolves to `Arm` within a
  bounded ceiling only after a genuine quiet tail, never on a fixed timer
  regardless of subsequent audio activity) and its non-vacuity is proven by
  a companion test showing a ceiling-less gate fails the same property.
- `required_wiring` re-verification above confirms no re-arm path bypasses
  the gate, so the fix is not merely unit-correct in isolation — it is the
  only path to the mic for hands-free.

This is code-level and property-level evidence that the fix addresses the
documented failure mode, but it is **not** the same as a fresh post-fix
device confirmation. Recording this gap explicitly rather than silently
treating it as satisfied.
