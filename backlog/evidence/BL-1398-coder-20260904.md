# BL-1398 — coder evidence, 2026-09-04

Ticket: the commit-guard property fixture derives its guard set from
`run_commit_guards.sh` instead of listing the guards by hand.

## What shipped

- **`extension/test/helpers/commitGuardFixtureSet.js`** (new). Reads the
  runner and the two hooks at test time, parses their `run_guard <script>
  [args]` lines (comment lines skipped — a line that merely *mentions*
  `run_guard` is prose), and returns the files the fixture must carry, in
  chain order, with the arguments the chain itself passes each guard (so the
  BL-971 warming exec uses the real shape rather than a special case for
  `check_commit_size.sh`). It then walks `source`/`.` lines to pick up the libs
  those files need, bounded to `swarmforge/scripts` with a visited set.
  - **A guard the runner names but the tree lacks throws, naming it**
    (invariant 2) — never `continue`. A fixture that skipped it would run a
    chain narrower than production and still report green.
  - A *lib* referenced behind an `[[ -f ]]` test may legitimately be absent, so
    a missing lib is reported in `missingLibs` rather than thrown: the guard
    that wanted it still runs and says so itself. Guards and libs are not the
    same obligation and the code says which is which.
  - `runnerRel`/`readFile`/`exists` are seams so a test can point the
    derivation at its own runner copy. The live runner is read, never written.
- **`extension/test/bl632CommitTimeGuardInvariants.property.test.js`**: the
  hand-written `EXEC_FIXTURE_FILES` and its eleven `path.join` constants are
  gone; the set is `deriveCommitGuardFixtureSet({ repoRoot: REPO_ROOT }).files`.
  The template build, the hardlink warming and the per-case copy are unchanged
  — only the list moved. The two hooks stay explicit inside the helper: they
  are what git runs, not what the runner lists.
- The file also carries a **consumer-side cross-check** (`run_guard`, the
  required_wiring anchor): it re-reads the runner's own `run_guard` lines and
  asserts the fixture carries every guard they name. Two independent readings
  that must agree — a derivation that silently dropped a line would otherwise
  leave the fixture running a narrower chain than production and still report
  green, which is the failure this ticket exists to make impossible.

## The red this closes

`bl632CommitTimeGuardInvariants` was red on `main`: BL-1385's
`check_handler_module_graph.sh` joined the runner on 2026-09-04, the fixture
did not copy it, and every generated case died with
`No such file or directory ... (exit 127)`. The derived set now contains all
seven guards the runner names, `check_handler_module_graph.sh` included, and
the test is green. BL-1395's `check_bb_scripts_load.sh`, added to the chain
hours later, is picked up by the same derivation with no edit — the recurrence
this ticket predicted, already prevented.

## Declared invariants (BL-654) — both encoded

`extension/test/bl1398GuardFixtureDerivedSet.property.test.js`, runnable only
via `npm run test:properties`.

Generator reach is **constructed**: each case draws a base set of guard names
and derives its variant from it — the added guard is a name the base does not
contain, the removed one is drawn *from* the base, and invariant 2's absent
guard is a member of the named list whose file is deliberately not planted. So
every case is a real add, a real removal, or a real absence by construction,
and both directions of invariant 1 are asserted reached (`reach.added`,
`reach.removed`), not hoped for.

Non-vacuity, checked rather than asserted: invariant 1's removal case keeps the
dropped guard **on the tree** while removing it from the runner, so an
implementation that listed the scripts directory instead of reading the runner
fails it (probed directly: the listing and the runner-derived set differ).
Invariant 2's case plants the guard afterwards and re-derives cleanly, so the
refusal is the absence and not a seam that could never work.
