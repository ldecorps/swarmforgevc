## Defect found (D1) — class `invariant-unencoded`-adjacent correctness, NOT an architecture-rule/invariant violation

New file `specs/pipeline/steps/bl929LiveScreenPackLayoutSteps.js`,
`seedProjectRoot()` (line ~34): creates a fixture root via
`fs.mkdtempSync(os.tmpdir(), 'bl929-acceptance-')` in the Background step and
never removes it anywhere in the file — not in a `finally`, not in the last
`Then` step (the pattern this repo's own compliant step-handler files use:
`bl413StaleSandboxSweepSteps.js`, `bl458AcceptanceFixtureProcessLeakSteps.js`,
`bl460TmpSweepsBoundDeletesSteps.js`, `bl520RewrapLegacyWrappedSteps.js`,
`bl529TicketBranchMismatchGuardSteps.js`,
`bl607RoleClarifyingPollSteps.js`, `bl632CommitTimeGuardSteps.js`,
`bl633InvariantsSectionSteps.js`, `bl647RotationRouterLivenessSteps.js`).

This is a direct new violation of the "Fixture temp dirs are removed in a
`finally`" rule — adopted into `engineering.prompt` / the reference detail
file on 2026-08-18 from an **architect `rule_proposal`** (mine, raised after
the BL-921/BL-922 bounces the same session). The rule exists specifically so
this pattern stops being copied forward into new step-handler files; this
file copies it from `bl881ResidentPaneLiveCaptureTtlCacheSteps.js` (cited in
its own header comment as "same posture"), which predates the rule and is
itself non-compliant.

Confirmed empirically, not just by reading:
`node specs/pipeline/cli.js specs/features/BL-929-live-screen-follows-the-running-pack-not-the-resident-marker.feature`
— all 4 scenarios pass, and 4 new `bl929-acceptance-*` directories were left
under `$TMPDIR` afterward (24 total were already present on this host from
earlier runs of this exact code before this review pass; all 24 have been
removed as part of this review — cleanup, not evidence-of-fix).

## Remediation

Wrap the `^the Live Screen renders$` step's body
(`specs/pipeline/steps/bl929LiveScreenPackLayoutSteps.js`, `registerSteps`)
in `try { ... } finally { fs.rmSync(ctx.targetPath, { recursive: true, force:
true }); }`. That step already captures everything the four scenarios' `Then`
steps need (`ctx.snapshot`, `ctx.panes`, `ctx.rendered`) into plain in-memory
data before this file's other steps read it, so removing `ctx.targetPath`
there — even if `renderLiveScreen` itself throws — covers every failure path
in this scenario shape (the `Given` steps only write files, they do not read
`ctx.targetPath` back out afterward). This mirrors the established idiom in
the compliant files listed above (cleanup colocated with the step that owns
the fixture's last use), since this runner
(`specs/pipeline/runtime.js:runScenario`) has no scenario-level
after-hook to hang cleanup off instead.
