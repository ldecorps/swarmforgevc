# BL-567 Expeditor — design answers (specifier stage, hand-run)

Produced 2026-07-25 by the operator acting as specifier, with the swarm stopped.
This is stage 1 of the expeditor's own hand-run: the tool cannot build itself with
itself, so run #1 is human-driven and this document is its reference procedure.
BL-590 was parked to `hold/` to free the pipeline — see
`BL-590-parked-20260725.md`.

## Findings that change the shape before answering anything

**1. The prompt problem is already solved, and solved on the DATA side.**

BL-567's shape says the driver spawns each stage "with that role's prompt
(`.swarmforge/prompts/<role>.md`)". Reading that generated artifact would be a
mistake:

- It is a build output, not a source. `coder.md` is **62 KB** with mtime
  **Jul 23 08:19** — the last launch. Stale by two days right now.
- On a bare host it does not exist at all (cf. BL-628).
- **BL-546 landed a rule against it:** `prompt_engine_lib.bb` is "the single
  authority for all swarm prompt composition. **No swarm agent or launch script
  assembles prompt text directly**; every system-prompt artifact
  (`.swarmforge/prompts/<role>.md`) is produced through `compose` here."

So the expeditor must **compose fresh** via PromptEngine, not read the artifact.
And that is squarely on the data side of BL-567's own line: `compose` reads the
constitution articles, PIPELINE.md, the role prompt and pack/profile overlays —
all plain files under git — and resolves paths **from its own location, never
cwd**. It touches no mailbox, no tmux, no daemon.

This is a strict improvement on the ticket as written. Record it as a design
correction, not a detail.

**2. `task-injection` is the parcel replacement, and it is cache-shaped.**

`compose` takes `:task-injection` — "optional task text appended AFTER all
role/overlay content — never before or inside the stable chunk"
(`prompt_engine_lib.bb:220`). That is exactly what the expeditor needs in place of
a mailbox parcel: identical stable prefix per role (so prompt caching hits across
stages and across bounces), ticket-specific task appended at the tail.

**Gap:** `task-injection` is **lib-only**. `prompt_engine_cli.bb` does not expose
it (verified). Since BL-567 already allows `bb` for the driver, the driver should
`load-file` the lib directly rather than grow a CLI flag — fewer moving parts, and
no new public surface to keep compatible.

**3. Model/effort resolution is a two-line read, not a conf parse.**

BL-567 says "model, and effort (from the pack table)". In practice the launch
scripts do not read the pack conf at run time — the resolved values live in
`.swarmforge/launch/<role>.claude-settings.json`:

```json
{ "model": "claude-sonnet-5", "effortLevel": "xhigh",
  "skipDangerousModePermissionPrompt": true,
  "permissions": { "defaultMode": "bypassPermissions" } }
```

And this matters operationally: a conf edit alone is inert; the settings JSON is
what a session actually gets. The expeditor should pass `--settings <that file>`
exactly as the launch scripts do, falling back to composing one from the pack
table only if the file is absent (bare-host case). Same resolution as the online
pipeline, one file read, no reimplementation.

## Q1 — Fresh `claude -p` per stage, or one session re-prompted?

**Fresh per stage.** Confirming the ticket's own recommendation, with the
mechanism now known.

The reference invocation, from `.swarmforge/launch/coder.sh`:

```
claude --settings .swarmforge/launch/coder.claude-settings.json \
       --dangerously-skip-permissions \
       --remote-control SwarmForge-MonoRouter \
       --append-system-prompt-file .swarmforge/prompts/coder.md \
       -n 'SwarmForge Coder' "<task text>"
```

The expeditor's version differs in exactly three ways:

1. `-p` instead of interactive + drop `-n` and `--remote-control` (both are
   session/liveness machinery; `--remote-control` in particular re-registers an
   RC session, which is precisely the transport layer we must not touch).
2. `--append-system-prompt-file <composed temp file>` written from PromptEngine
   `compose`, instead of the possibly-stale generated artifact.
3. No `RESUME-ON-START` probe. That block shells `mailbox_dir.bb` to look for
   in-process parcels — forbidden machinery, and meaningless offline since the
   driver holds the stage state itself.

Keep from the launch script: `unset ANTHROPIC_API_KEY ANTHROPIC_AUTH_TOKEN`. This
is not incidental — the box authenticates a specific way and a stray key changes
which account is billed. Drop the Cerebras/Perplexity/Qwen remap blocks unless a
run explicitly asks for an alternate provider.

Why fresh-per-stage beyond the ticket's "context isolation" argument: the role
prompts are written for an agent that *is* that role, not one that used to be
another. A re-prompted session carries the previous role's reasoning into a review
gate — an architect that just wrote the code is not an independent reviewer, and
the whole value of the gate is independence. Bounces make it worse: the same
session would remember the defect it is being asked to find.

## Q2 — Where stage state lives, and how a bounce rewinds it

**Git is the state. The scratch dir holds only what git cannot.**

The online pipeline already carries stage products in git — every stage commits to
its own branch and hands forward a sha. The expeditor should not invent a parallel
state format; it should keep using commits, because that is what makes the
evidence bar identical rather than simulated.

```
.swarmforge/expedite/<BL-id>/
  run.json          driver state: stage order, current stage, bounce counts, shas
  <NN>-<role>/
    prompt.md       the exact composed system prompt (audit + reproducibility)
    task.txt        the task-injection text this stage received
    transcript.jsonl
    verdict.json    stage outcome: pass | bounce(target-stage, reason) | fail
```

`run.json` is the only thing that must survive a crash, and it is small and
append-shaped. Everything else is evidence.

**Bounce rewind:** a bounce does not rewind git. It records
`verdict: bounce(target, reason)` and re-enters the target stage with the bounce
reason as part of the next `task-injection`. The branch keeps moving forward —
which is the same thing the online pipeline does, and deliberately so: today's
post-mortem (BL-629/632) traced real damage to reverting bounced content out of a
review branch, and two architect `rule_proposal`s from BL-590 are open on exactly
that hazard. **The expeditor must not adopt the revert-on-bounce pattern.** Write
that into the runbook with the reason, or someone will "fix" it back.

Bounce counting is per (stage, ticket) with a bounded total. BL-590 is at five
architect send-backs today, all legitimate — so the bound must be generous enough
not to abort real convergence, and loud when hit. Recommend a default of 8 with
the count surfaced in the failure message.

## Q3 — Branch and worktree strategy

**A dedicated branch off `main`, in a dedicated worktree the expeditor creates
and owns.** Confirming the ticket's leaning, and today's incident makes it
non-negotiable rather than a preference.

```
branch:    expedite/<BL-id>
worktree:  .worktrees/expedite-<BL-id>   (created by the driver, removed on success)
```

Three reasons, one of them fresh:

1. **Never `main`.** This morning's incident was a role running its whole pass in
   the master checkout because `main` happened to be checked out there. A driver
   that operates on `main` reproduces it by design.
2. **Never the swarm's role worktrees.** They hold live branches and, right now,
   uncommitted work and stray claim sidecars. BL-567's own interlock refuses a
   dirty checkout it did not create; owning the worktree makes that check trivial
   instead of a judgement call.
3. **QA merges to `main`, exactly as online.** Preserves BL-247 (QA is the only
   integration point) with no special case — and stays compatible with BL-632's
   proposed commit-time guard, which will refuse non-QA commits on `main` from any
   role. An expeditor that wrote to `main` directly would have to be exempted from
   that guard, which is how guards die.

Interaction to state explicitly: **do not push.** `push-sweep!` is dead while the
swarm is stopped, and BL-630 wants publishing gated on QA-ancestry anyway. The
expeditor's QA stage merges to local `main` and stops; publishing is the operator's
call on the next boot.

## Q4 — Coordinator bookkeeping: inline or deferred?

**Inline, and minimal — and the boundary is already drawn for us.**

Deferring breaks use case 2 (offline operation): a ticket that reaches `done`
but whose yaml still says `active` leaves the backlog lying, and the next swarm
boot promotes against a false picture.

What "minimal" means concretely, because the coordinator does more than one thing:

| coordinator action | expeditor | why |
|---|---|---|
| move yaml `active/` → `done/` | **inline** | the ticket's own durable record; plain file move |
| set `status:`/`assigned_to:` | **inline** | same file, same reason |
| BL topic record | **defer** | writes a Telegram topic — front-desk machinery |
| briefing hooks | **defer** | the briefing runs on its own schedule and reads git |
| promote next ticket | **never** | one ticket, one run. Promotion is a queue decision and the expeditor has no queue |
| `pipeline_stage_cli.bb sync` | **defer** | board state for a live swarm; meaningless offline |

The machinery-independence rule means reimplementing the yaml move, not calling
coordinator code — and the yaml move is a `git mv` plus two field edits, which is
why this is acceptable rather than a slippery slope.

Everything deferred should be recorded in `run.json` as `deferred: [...]` so the
next boot (or a human) can see exactly what was skipped rather than inferring it.

## Q5 — `SWARMFORGE_SKIP_DAEMON`: excluded, and here is the sentence for the runbook

Excluded, as the ticket says. The runbook needs the *reason* stated in a form that
survives a future simplification pass:

> `SWARMFORGE_SKIP_DAEMON` makes handoff delivery synchronous instead of
> daemon-driven. It is tempting here because it removes handoffd from the picture —
> but it still **reads and writes `.swarmforge/handoffs/`**. The expeditor's
> premise is that the mailboxes may themselves be the broken thing (wedged
> parcels, stale claim sidecars, a starved queue — all three observed on
> 2026-07-25). Routing recovery work through the artefact under repair is how a
> recovery tool inherits the outage it exists to escape. The driver carries stage
> products in-process and in git; it needs no transport at all, so it must not
> acquire one.

## Interlock #1 is specified in a way that would refuse to run — found by stopping

BL-567's first safety interlock: *"Refuses to start if the swarm is live (real
socket check per `.swarmforge/tmux/*.sock` + handoffd pid)."*

Measured after a clean, verified full-stack stop on 2026-07-25:

```
tmux -S .swarmforge/tmux/1523266553.sock list-sessions
  -> no server running on .swarmforge/tmux/1523266553.sock
ls .swarmforge/tmux/*.sock | wc -l
  -> 1
```

**The socket FILE outlives the server.** `kill_all_swarm.sh` runs
`tmux kill-server` and deliberately leaves the file. So an interlock that globs
`.swarmforge/tmux/*.sock` reads a fully-stopped swarm as LIVE and refuses to
start — on the exact clean slate the expeditor exists to run on. The operator would
then reach for the override flag as a matter of routine, which is how an interlock
becomes decoration.

**Correction:** presence of the socket file proves nothing. Liveness is
`tmux -S <sock> list-sessions` exiting zero (server responds), plus a live
handoffd pid. Same shape as the recorded liveness lesson — glob the path to find
candidate sockets, then PROBE each one; never treat the file as the signal.

While confirming this, two processes also survived a stop that logged
"SUCCESS — clean slate": `./.swarmforge/operator/babysitterd.sh` (up 1d08h,
performs 5-minute sweeps that nudge agents) and the Operator agent (up 2d06h, 6
unprocessed events, whose job is to recover a swarm it finds down). Both are
exactly the class of process that can wake or relaunch things mid-run. So the
interlock's "handoffd pid" check is too narrow as written — it must also cover the
babysitter and the Operator, or the expeditor can be interfered with by a
supervisor that outlived the teardown. Ticketed separately as BL-637; the
interlock needs to be robust to it regardless of whether BL-637 ships first.

## Lifecycle in scope (operator ruling) — and why the two directions differ

The full park-and-stop becomes the expeditor's initiation, and it must bring
everything back at the end. This does not contradict "oblivious to swarm
machinery": that rule is about **dependence**, not **command**. Needing the
machinery to do your work is forbidden; commanding its lifecycle is the opposite
of needing it.

But teardown and restart are asymmetric, and conflating them would smuggle the
forbidden dependency back in through the exit code.

**Teardown blocks.** Park `active/` → `hold/` (never `paused/`, which
auto-re-promotes an approved ticket on restart); write the park record; stop with
no flags; then **probe** rather than trust — the measured 2026-07-25 stop printed
"clean slate" with two daemons alive. Failure to reach a verified clean slate
refuses the run. That is interlock #1 finally having teeth.

**Restart must not block.** Use case 1 is *fixing a broken swarm workflow*, so the
start path may BE what is under repair. If the verdict depended on a clean
restart, the expeditor would report failure on work it completed, and a start-path
defect would disable the recovery tool exactly when needed. The ticket is done when
QA stamps it and the yaml moves; the restart is a separate reported result whose
failure is loud and non-retracting.

Two consequences worth carrying into the driver:

- When the fix IS the start path, the restart phase becomes the **validation** of
  the fix — the first real user of the thing just repaired, with the expected live
  set as the assertion. Feature, not footnote.
- Stopping the stack kills the babysitter and the Operator, i.e. **the expeditor
  deliberately kills its own watchdog.** It therefore needs a bounded per-stage
  timeout and a loud terminal failure; nothing is left alive to notice it hang.

## Two things this design owes back to the ticket

1. **BL-567's `acceptance` item 1 wants machinery-avoidance "asserted by
   instrumentation, not inspection."** The hand-run must therefore produce that
   instrumentation, not just avoid the machinery by care. Cheapest honest form: run
   the driver under a wrapper that fails on any `open`/`exec` touching
   `.swarmforge/handoffs/` or `tmux`. Decide the mechanism during the hand-run —
   this is the one acceptance criterion a hand-run can quietly skip while looking
   complete, and it is exactly the "dry-run smoke test proves nothing" trap.

2. **The bootstrap admission.** The first traverse cannot be driven by the driver.
   Its transcript IS the reference procedure and should be committed as evidence,
   with an honest note that run #1 was human-driven — so nobody later reads the
   green result as proof the driver works.
