### Gap 1: the seat is DROPPED, not split into a second row

The ticket's description and `qa_e2e_procedure` both state the defect is two
rows — "two rows keyed `coder` and `coder@sonnet2`" — and the feature file's
narrative says the same. **That is not what the code does.**
`computeStageDwellReportForRoles` filters `roles.filter(r =>
PIPELINE_ORDER.includes(r.role))`, and `PIPELINE_ORDER`
(`swarmMetrics.ts:60`) holds bare stage names only. A non-bare seat fails
that filter and is dropped entirely.

Measured at the parent commit, fixture of two coder seats with two parcels
each plus one cleaner parcel:

```
rows: [ 'coder=2', 'cleaner=1' ]      <- the seat's 2 parcels are GONE
bottleneck: cleaner
```

So the stage is not split, it is **understated by silent data loss** — a
strictly worse defect than the one written down, and the qa_e2e's "confirm
two rows keyed coder and coder@sonnet2" can never reproduce. The ticket's
consequence 2 (wrong bottleneck, not just wrong label) is REAL and is what
this parcel fixes; only the stated mechanism was wrong.

### Gap 2: scenario 03's second clause is unsatisfiable

Scenario 03 asks for a fixture where "the coder seats together process slower
than every single-seat stage" AND "neither coder seat alone processes slower
than the slowest single-seat stage". `nameBottleneck` ranks on **median**
processing. A combined median can never exceed both inputs' medians, so if
the folded stage outranks cleaner then at least one seat alone must also
outrank it. The two clauses cannot both hold under median ranking.

The scenario's INTENT — a stage wrongly ranked below a faster one because its
dwell is not whole — is satisfiable and is asserted, via the real mechanism
(the drop): with the second seat dropped the coder stage reports its bare
seat's fast work only and cleaner is named; whole, coder is named. The
step handler for the unsatisfiable clause asserts what the fixture can
honestly establish (the bare seat alone is not the bottleneck, which is what
made the loss invisible) and says so in a comment. Not silently reworded.

## What was implemented

1. **The fold, before ranking** — `extension/src/metrics/stageDwell.ts`.
   `computeStageDwellReportForRoles` groups roster entries by
   `stageOfSeat(entry.role)` and filters on the FOLDED stage, so a seat no
   longer fails the PIPELINE_ORDER test. Each stage's seats' records are
   concatenated into one `buildStageDwellReport` call. The merge happens
   before `nameBottleneck` ranks, per the ticket's explicit warning that
   after it picks would leave consequence 2 intact.
2. **`nameBottleneck` folds defensively** — it is exported and ranks whatever
   rows it is handed, and naming a SEAT tells the coordinator to optimize
   something that is not a stage.
3. **Per-seat records untouched** (invariant 3) — `DwellRecord.role` stays the
   seat that worked the parcel. Folding is a reporting concern only.
4. **The ops seat-and-model view** (the ruling's second half) —
   `computeSeatDwellDetail` + `SeatDwellDetail` in `stageDwell.ts`, rendered
   by `formatSeatDwellDetail` in `tools/stage-dwell-report.ts`.
   - Deliberately NOT added to `StageDwellReportResult`: the bridge serves
     that shape on `/stage-dwell`, and the ticket's qa_e2e requires that
     payload carry no `@`. Ops surfaces may show seat detail; the optimizer
     payload may not. The seat rows ride the ops CLI's own `--json` instead.
   - Rendered only where a stage actually runs more than one seat, so a
     single-seat swarm's report is unchanged (same losslessness as the fold).
   - An unconfigured model reports `unknown`, never invented.

Reused `stageOfSeat`, exported from `swarm/swarmState.ts` by BL-1040 earlier
today, rather than adding a second TS seat-splitter. `stageDwell.ts` already
imported from that module, so no new dependency edge and no cycle.

## Invariants (BL-654) — three declared, four properties

`extension/test/bl1319StageDwellNamesTheStage.property.test.js`, 120 runs each.

**Generator reach, asserted not hoped for.** (a) Seat ids are CONSTRUCTED as
`<stage>@<suffix>` — the transformation the instrument conflated — with an
asserted floor, since a draw over bare stage names reaches a seat never.
(b) Extra seats are DERIVED FROM a stage already in the roster, so the
multi-seat collision the fold exists for is present by construction; an
independent draw would essentially never put two rows on the same stage.

**Non-vacuity, and one property that was VACUOUS until it was fixed.**
Breaking the fold (`stageOfSeat` neutered in the compiled module) left
invariant 1 PASSING — because with the fold gone the seats are dropped by the
filter again, so "no row carries an `@`" held for the wrong reason: the
seat's work was simply absent. Added the assertion that the folded rows
account for EVERY configured seat's parcels, which is what distinguishes
merging from hiding. Invariant 1 then fails against that mutation as it
should. Invariant 2 (losslessness) is correctly insensitive to that mutation,
so it was shown non-vacuous against a different one — a fold that over-merges
every stage onto one key — which it catches. All four properties now fail
against at least one deliberately broken implementation and pass restored.
