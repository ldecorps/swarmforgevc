# BL-1605 — coder, 2026-09-16

## What was wrong

`reverse_hop_lib.bb`'s `reverse-recipients` derives a git_handoff's
non-forwarding reverse copies from the sender's declared propagation mode
alone (back-one/back-all), with no awareness of the forward's own `to:`
recipients. The live pack declares the cleaner `back-one` and the
architect `back-all`, so an architect bounce `to: cleaner` made the
cleaner BOTH the forward recipient and (under back-all) an earlier
pipeline role — it received the forwarding file AND a non-forwarding twin
of the same send, in one batch. `swarm_handoff.bb`'s batch-aware send
gate (`inbound-non-forwarding?`) then refused the cleaner's own
re-forward for the whole batch until the coordinator's dropped-parcel
sweep chased it — fifty minutes, twice on 2026-09-16.

## The fix

- `reverse_hop_lib.bb`: new `remove-forward-recipients` — subtracts the
  forward's own recipients from a set of reverse candidates. The existing
  `reverse-recipients` (2-arity and 3-arity) is unchanged, so every
  existing caller and the bb property runner keep their exact prior
  behavior.
- `swarm_handoff.bb`: `reverse-roles` now takes the forward's
  `recipients` as a second argument and pipes `reverse-recipients`'s
  output through `remove-forward-recipients` before writing the reverse
  copies. The one call site (`write-handoffs!`) passes `(:recipients
  ctx)` — the same vector `with-non-forwarding`/`terminal-forward?`
  already read from `ctx` at that call site.

## Verification

- `swarmforge/scripts/test/reverse_hop_lib_remove_forward_recipients_runner.bb`:
  5 cases (a lone reverse candidate that IS the forward's own recipient
  empties; a forward hop to a later role leaves the reverse set
  unchanged; a back-all bounce to a middle role drops only that role;
  multiple forward recipients are all subtracted; no overlap passes
  through) — green.
- `specs/features/BL-1605-*.feature` via
  `specs/pipeline/steps/bl1605NoReverseCopyToForwardRecipientSteps.js` —
  drives the REAL `swarm_handoff.bb` (both self-audit calls) and
  `handoffd.bb --poll-once` against a real fixture swarm root with the
  live pack's exact propagation shape (cleaner back-one, architect
  back-all). 5/5 scenarios green:
  - `architect -> cleaner`: cleaner gets exactly the forwarding file, no
    non-forwarding twin; the reverse copy goes only to coder (architect's
    back-all set [coder, cleaner] minus the forward recipient cleaner).
  - `architect -> hardender`: unaffected forward hop — cleaner and coder
    both still get their merge-only copy, byte-identical to today.
  - `cleaner -> architect`: architect gets exactly the forwarding file;
    the reverse copy (back-one, the immediately preceding role) goes only
    to coder.
  - `cleaner -> coder`: back-one's sole reverse candidate (coder) IS the
    forward recipient — reverse set empties, nobody else gets a copy.
  - The batch-aware send-gate refusal for a non-forwarding inbound of
    ANOTHER task, in process, is unchanged.
- Regression: `reverse_audit_handoff_test_runner.bb` (19/19),
  `bl1299_reverse_hop_property_runner.bb` (500 runs, all reach floors
  met), `test_swarm_handoff_inbound_non_forwarding.sh` (3/3),
  `test_mailbox_only_delivery.sh` — all green, unchanged.
