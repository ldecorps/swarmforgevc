## Architecture review

- Two-layer boundary respected: `providerChatSeat.ts` is pure (no IO, no
  imports beyond its own types); `providerChatSeatLive.ts` does the fs/network
  IO and posting; the live adapter in `telegram-front-desk-bot.ts` is the only
  caller of `runProviderChatSeatTurn`. No agent/process spawned to bypass tmux
  (not applicable to this slice).
- Extension host owns all I/O: the map read, the fetch call, and the Telegram
  post all happen in `providerChatSeatLive.ts` / `telegram-front-desk-bot.ts`,
  never in a webview. No webview touched by this parcel.
- Dispatch hook (`attemptProviderChatSeatDelivery` in
  `telegramFrontDeskBotCore.ts`) is placed after the cursor-bridge exclusion
  and before the side-channel/subject-opening steps, mirroring
  `attemptCursorBridgeTopicExclusion`'s shape exactly — core decides + stops,
  live side performs. `PollAdapters.runProviderChatSeat` is optional so
  fixtures predating this seat keep working.
- Secrets: `apiKey` comes from `deps.env ?? process.env` only
  (`providerChatSeat.ts:80`); the map path is
  `.swarmforge/operator/provider-chat-topic-map.json`, gitignored runtime
  state, not the commit or the target working directory's tracked files.
  Confirmed by grep (`B_AI_API_KEY|api[_-]key` → one doc-comment hit only)
  and by invariant-2's property tests, which plant decoy credentials in three
  working-tree locations and assert none of them reach the outbound call or
  a posted message.
- Failure reporting: `completeWithProviderChat` throws
  `${url} answered ${status}: ${body}` — never a bare status code
  (BL-572/BL-662). The acceptance feature's Outline steps assert against the
  real failure shape (`answered 401: invalid api key`,
  `connect ECONNREFUSED ...`), not a passthrough/binary check.
