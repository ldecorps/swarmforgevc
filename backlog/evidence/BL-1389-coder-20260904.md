The two walks do not see the same set. The handler and the source file are
credited to BL-1367 alone by the per-path walk that `own-paths` decides with,
and are ABSENT from the per-sibling walk that the landed/unlanded verdict is
computed from. So the verdict was reached without ever looking at the two paths
it was about to decide. When those six read landed (at the then-current
origin/main `94be289136`), BL-1367 left `unlanded`, the exclusion branch
required `every? unlanded-siblings owners` and found false, and both files were
kept and rode into the replay under BL-1386's approval.

That is a sharper statement than "a sibling with one landed path can read
landed": the attributed set is not merely optimistic, it is a DIFFERENT set.
The fix follows the ticket's invariants unchanged.

## What changed

`swarmforge/scripts/land_step_lib.bb`

- `sibling-path-landed-fn` (new): (sibling, path) -> is THAT sibling's own
  contribution to THAT path on origin/main? BL-1354's own-lines question, asked
  where the exclusion decision is actually made. Fail-closed on every unread.
- `own-paths`' exclusion (invariant 1) now asks that question of the path.
  The pre-BL-1389 condition is kept as the first arm of an `or`: every owner
  being a known unlanded sibling still settles the path, needs no diff read,
  and is the common case. Only when the ticket-level verdict says the owners
  have landed is the per-path question asked - which is exactly the case that
  was fail-open.
- `landed-sibling-verdicts` (new): per sibling `{:landed? :deciding-path
  :paths}`. `landed-siblings` is now that answer as the set every caller
  before it expected, unchanged. It takes an `extra-paths-fn`, through which
  `land-plan` supplies the paths the per-PATH walk credits to a sibling and the
  per-sibling walk never reported - invariant 2's "every path attributed to it",
  made complete rather than assumed.
- `delivered-attribution` (new): the per-path attribution, computed ONCE per
  land and shared by both questions. Deferred behind a `delay`: a land with no
  entangled sibling never forces it, so a clean land pays nothing.
- `entangled-siblings` reports `:landed-paths` {sibling deciding-path}.

`swarmforge/scripts/land_step_cli.bb`

- `LANDED_SIBLING <id> <deciding-path>` and one `EXCLUDED_SIBLING_PATH <path>
  <sibling>` line per excluded path (invariant 3, and the ticket's
  `required_wiring` anchor). The report printed 17 landed names, 27 entangled
  names and not one path, which is why the false verdict was invisible until QA
  diffed the tip.

Two existing consumers parsed `^LANDED_SIBLING <id>$` anchored and would have
broken on the appended path: `extension/test/bl1308SiblingDetectorCoversReplay.property.test.js`
and `specs/pipeline/steps/bl1272LandedSiblingSteps.js`. Both were widened to
accept the optional path (BL-1006: the successor owns the sibling assertion it
falsifies). Neither assertion's subject changes - each still asserts the id
reaches the line QA reads.

## The declared invariants carry property tests (BL-654)

The ticket declares three invariants, so the parcel carries a coder-authored
executable property test for each:
`extension/test/bl1389UnlandedSiblingPathNeverRidesInvariants.property.test.js`
(`npm run test:properties` only, per the standard separation). It drives the
REAL `land-plan` - the whole decision, both walks together - over real git
fixtures.

**Generator reach, by construction rather than by draw.** The defect needs the
two walks to attribute DIFFERENT sets, and no random repository wanders into
that. It is built: the sibling's exclusive work reaches the tip on a MERGED
SIDE BRANCH (whose merge subject names no ticket), while its feature file and
ticket file are on the first-parent line AND on origin/main.
`task-tagged-changed-paths` walks `rev-list --first-parent`, so it sees only
those two and reads the sibling LANDED; `path-owner-tickets` walks
`git log -- <path>`, which sees every parent, so it credits the merged handler
and source to that same sibling. That is the 2026-09-04 BL-1367/BL-1386 shape
exactly. Each pass asserts the shapes it needed were actually built (three
approval states; both landed mixes).

Two false-reach traps were hit and fixed while building it, both of which made
the property pass against the DEFECT:

1. The all-landed shape left the sibling's ticket file off origin/main, so the
   sibling read unlanded for a reason the test did not intend.
2. More seriously: with the ticket file unlanded in the not-landed shape too,
   the FIRST-PARENT walk alone read the sibling unlanded, the pre-BL-1389
   predicate excluded the merged paths on its own, and all three properties
   passed against the broken code. Every path that walk attributes must be
   landed for the divergence to exist at all. This is the ticket's own
   generator-reach warning arriving in practice.

**Non-vacuity, after those fixes** (pre-BL-1389 behaviour restored by reverting
the exclusion `or` to `and` and dropping `land-plan`'s `extra-paths-fn`): all
three properties FAIL, and the failure prints the incident verbatim -
`landed: ["BL-9390"], landedPaths: {"BL-9390": ".../BL-9390-sibling.feature"}`,
with the sibling's handler in `ownPaths`. Restored: all three pass.
