## What was wrong

`merge_drop_guard_lib.bb`'s 4-arity head-bounded scan (`head..forwarded`)
excludes only what the sender's own HEAD-at-dequeue reaches. A merge an
UPSTREAM role made — reachable only through the RECEIVED commit's own
ancestry, never through anything the sender did after receipt — was still
a candidate: the documenter's four sends (BL-1599/1605/1607/1608,
2026-09-16 21:37Z–22:02Z) all named the cleaner's merge `6e5087cd43`,
excused only because the documenter happened never to touch
`extension/vitest.bl1599.stryker.config.mjs`; a role that DID edit a path
such an upstream merge one-sidedly resolved would have been refused for a
merge it never made and cannot redo.

## The fix

`swarmforge/scripts/merge_drop_guard_lib.bb`:
- `merge-commits` gains a 4-arity form: `(root bound forwarded
  also-exclude)`, building `git rev-list --merges --reverse <forwarded>
  ^<bound> ^<also-exclude>` (skipping the second `^` term when
  `also-exclude` is absent or equal to `bound`). The 3-arity form is
  unchanged (`bound..forwarded`, a single negative ref).
- `findings-between`'s 4-arity form now passes `received` as
  `also-exclude` whenever a `head` stamp exists, so the scan excludes
  merges reachable from NEITHER `head` NOR `received` — the merges the
  sender made since receipt, never one an upstream role made that arrives
  only through the received commit's own ancestry. The stampless 3-arity
  fallback (`received..forwarded`, a single bound) is untouched, per the
  bounce's own direction.
