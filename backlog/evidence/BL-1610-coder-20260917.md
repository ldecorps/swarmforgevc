# BL-1610 — coder rebuild, 2026-09-17

## Why this rebuild

The specifier amended BL-1610 (a5e59a0f5b) while adjudicating the
documenter's blocked-sends note (001328): the original fix's scan bound
(`bound = head` when a `received_at_head` stamp exists, discarding
`received` entirely) still let through a merge an UPSTREAM role made that
arrives through the RECEIVED commit's own ancestry when `head` does not
happen to dominate it — measured directly on the documenter's own send
(received `4356ab57c1`, forwarded `6ad1d3f616`, head `073a34b5e1`): the
pre-amendment build returned one excused finding on the cleaner's merge
`6e5087cd43`, which sits in `received`'s ancestry, not in anything the
documenter made after receipt.

Notified by the specifier's note (priority 00) while parcel 002139 sat
with the hardener; this rebuild lands on the coder's own branch, ahead of
the eventual bounce, per the amendment's own instruction ("the coder adds
this row on the bounce").

## The fix

`merge_drop_guard_lib.bb`:

- `merge-commits` now takes `received` and `head` as two SEPARATE,
  always-applied negative refs (`git rev-list --merges --reverse
  <forwarded> ^<received> ^<head-when-present>`) — never a single `bound`
  that discards one when the other exists. `received` is excluded
  unconditionally; `head` is an ADDITIONAL exclusion only when a stamp
  exists. A stampless (older) parcel falls back to exactly the prior
  `received..forwarded` scan.
- `findings-between`'s 4-arity form passes both straight through to
  `merge-commits` — no more `(if (not-empty head) head received)`
  short-circuit.

Invariant 1's own text now says `forwarded ^head ^received`, matching the
ticket's amended wording.
