# BL-1544 — coder pass (2026-09-12)

## What changed

`land_step_lib.bb`:

- New private helpers `leading-ticket-id` and `subject-attribution`,
  alongside `commit-ticket-id`. `leading-ticket-id` asks the strict,
  POSITIONAL question `commit-ticket-id`/`extract-ticket-id` never did:
  does the subject's own structure place a ticket id at the very start of
  the line (bare `TICKET-n: ...`, or one of this codebase's own three
  bookkeeping verb prefixes — `Close`, `Promote`, `Approve` — immediately
  before the id)? `subject-attribution` reports `{:ids #{...} :ambiguous?
  bool}`: a single id (or one that leads among several, e.g. "BL-1524,
  BL-1525, BL-1526: mint ...") is byte-identical to `commit-ticket-id`'s
  existing answer; a subject naming more than one id and leading with none
  is AMBIGUOUS — every named id rides as an owner.
- `path-owner-tickets` now runs each attributing commit through
  `subject-attribution` instead of `commit-ticket-id` alone, adding
  `:any-ambiguous?`/`:ambiguous` (`[{:commit :ids} ...]`) to its result
  alongside the existing `:owners`/`:any-untagged?`.
- `own-paths` gains one new `cond` clause, ahead of the existing BL-1389
  exclusion clause: when a path's attribution is ambiguous and the landing
  ticket is not among its owners, refuse (`{:paths nil :warning ...}`
  naming the commit(s), every id each names, and the path) rather than
  falling into the BL-1389 clause's silent exclusion. When the landing
  ticket IS an owner (a separate commit that itself leads with its id also
  touched the path), this clause does not apply and the path is kept
  through the existing logic, the ambiguous commit's other named ids
  riding as ordinary passengers. No change needed for "content already
  matches origin/main" (scenario 04): `full-delivered-paths` is a two-tree
  diff, so a path with no net change against origin/main is never in
  `delivered` in the first place and never reaches this decision at all.

`task_scope_gate_lib.bb` is untouched, per the ticket's own constraint —
its `subject-names-task?` (shape 2, the leading-id rule) already agrees
with `leading-ticket-id` by construction: nothing can occur earlier in a
string than position 0, so whenever `leading-ticket-id` finds a leading id,
`extract-ticket-id` (first-token-anywhere) finds that same id first. P2
below asserts this agreement directly.

`docs/how-to/BL-967-handoffd-cycle-stall-diagnosis.md`'s dropped BL-1525
paragraph and the doc-restore edit are the documenter's own tagged
BL-1544 commit, per the ticket's own "dropped paragraph rides THIS parcel"
section — not touched at this stage.

## Corpus measurement (the "leads with" grammar)

Per the ticket's own direction: measured `git log origin/main --format=%s
-500` before choosing the verb-prefix allowlist.

- Leading-word-then-id shapes found: `Approve` (31), `Promote` (17),
  `Close` (17) — all immediately followed by a bare ticket id and colon
  (the coordinator's/specifier's own promote/close/approve bookkeeping
  commits). `Update` occurs exactly **once**, and it is this ticket's own
  motivating incident (`a89a03ee45`, "Update BL-967 stall-diagnosis how-to
  for BL-1525's chokepoint fold"). `Update` (and every other verb) is
  therefore deliberately left OUT of the allowlist — including it would
  silently reintroduce the exact defect this ticket exists to close.
- Of the 500 subjects, exactly **4** name more than one ticket id and lead
  with none under the chosen `{Close, Promote, Approve}` allowlist:
  - `Accept hardender rule_proposal: ... mint BL-1519 epic + BL-1520/BL-1521 owner slices`
  - `Merge stranded coder note f35565394c into documenter (BL-1449: cite BL-1514 evidence).`
  - `Standing-red register: property allowlist rows for ... (coder note 2026-09-10 12:41Z)`
  - `Update BL-598 and BL-944 docs for dead-agent-events retirement (BL-1514).`

  All four are commits already on `origin/main` today, so this ticket's
  fix does not retroactively re-open any of them (own-paths is asked only
  of a FUTURE parcel's own `origin-main..commit` range); they are recorded
  here as the population this rule's stricter reading would flag going
  forward, per the ticket's own request to record the count.
- `BL-1524, BL-1525, BL-1526: mint ...` / `BL-1538 BL-1539 BL-1540 BL-1541:
  mint ...` style multi-id MINT subjects are unaffected: they lead with
  their first-listed id, so they are single-owner, exactly as
  `commit-ticket-id` already read them.
