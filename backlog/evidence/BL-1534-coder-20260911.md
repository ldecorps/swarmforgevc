## What changed

`extension/test/bl1373PathSetCacheInvariants.property.test.js` (`extension/src/`,
`swarmforge/scripts/`, and `specs/pipeline/steps/lib/babysitterSweepFixtureHelpers.js`
all untouched — `git diff main -- extension/src swarmforge/scripts
specs/pipeline/steps/lib/babysitterSweepFixtureHelpers.js` is empty):

- **Decisive by construction.** `decisivePairArb` draws `paths1` as a
  non-empty subset of the five constant prefixes, draws `x` FROM `paths1`,
  then draws `paths2` as a subset of the prefixes that remain once `x` is
  excluded — so `x` is in `paths1` and never in `paths2` on every draw.
  Invariant 1 and the cache-invalidation test both use it; no draw is spent
  discovering the pair happens not to be discriminating (the old skip for
  equal sets / no path-only-in-1).
- **Invariant 2** draws its unreported path from `OUTSIDE_PATHS` via
  `fc.constantFrom`, guaranteed disjoint from the five prefixes (asserted
  once at module load, so a future edit to either list fails loudly instead
  of silently reviving a vacuous draw).
- **The fail-open branch is gone.** The old `!finding1 && !finding2 ->
  return` ("might be OK if the sweep can't run in fixtures") no longer
  exists in any of the three tests. A finding from `paths2` (which never
  contains `x` by construction) is now always a hard `assert.fail` — a real
  cache/path-set bug, never tolerated as a flake. `grep -c "finding1 &&
  !finding2" extension/test/bl1373PathSetCacheInvariants.property.test.js`
  → `0` (per the ticket's own `qa_e2e_procedure` check; the decisive
  condition is written `if (finding1) reach.decisive += 1` instead of the
  retired literal shape).
- **Bounded, stated budget.** `numRuns = 5` for all three tests (comment at
  each site states the arithmetic): invariant 1 and the cache test do 2
  sweeps/draw → 10 sweeps ≈ 16 s at 1.6 s/sweep; invariant 2 does 1
  sweep/draw → 5 sweeps. All three inside the 20 s per-test timeout with
  headroom, down from up to 30 sweeps against the same timeout.
- **Reach counted and printed, not hoped for.** Each test tracks `{sweeps,
  draws, decisive}`, prints it as `BL-1534 reach map (<test>):
  <json>` (the BL-1371 `reach over N draws:` shape), then calls
  `assertReachFloor(reach, ['decisive'], 4, ...)` from the shared
  `test/helpers/reachFloors.js` — a run with zero decisive draws fails
  naming `decisive`, never passing silently.

## Verified non-vacuous (break-then-restore)

Per the ticket's own `qa_e2e_procedure` item 4: temporarily forced invariant
1's `paths1` stub to report no paths at all (`createStubScript([], ...)`
instead of `createStubScript(paths1, ...)`). Result: the property itself
still passed every draw (no hard invariant violation — `paths2` never found
anything either), but the run failed with `reach floor: BL-1534 invariant 1
decisive drawn 0 < 4` at `test/helpers/reachFloors.js:25`, exactly as the
ticket describes. Restored the stub call to `createStubScript(paths1,
...)` and confirmed the file is green again, 3 consecutive runs, no flake:

## Invariants (BL-654)

Both of BL-1534's declared invariants are encoded by the property test file
itself (it IS the deliverable this ticket bounds), not by a separate
property test of some other module:

1. "The file's verdict is a function of the code under test, not of host
   load" → the stated `numRuns`/sweep-count arithmetic per test (comments
   at each site) plus acceptance scenario 02, which reads the printed
   `sweeps` count from a real run and asserts it against the 10-sweep
   budget.
2. "No vacuous green" → `decisivePairArb`/`OUTSIDE_PATHS` construction plus
   `assertReachFloor(reach, ['decisive'], 4, ...)` in each test, plus
   acceptance scenario 03, which reads the printed `decisive`/`draws`
   counts from a real run. Non-vacuity demonstrated directly against the
   real file (see break-then-restore above), which is the closest thing to
   "a deliberately broken implementation" available when the artifact under
   test is itself a test file.
