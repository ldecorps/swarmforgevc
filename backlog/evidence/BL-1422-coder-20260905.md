# BL-1422 — coder pass, 2026-09-05

`done_with_current_task.bb` completed whatever sat in in_process and
immediately dequeued the next item, with nothing distinguishing a genuine
Work dispatch note from a chase/merge-up note at the moment of completion.
A role clearing a queue of chase notes with back-to-back
`done_with_current.sh` calls swept the dispatch out unread — BL-1384 was
blind-completed four times in one day this way, each costing a coordinator
round trip, the ticket still unworked. This session reproduced exactly
that pattern live against BL-1404/BL-1405/BL-1411/BL-1414 while draining a
flooded inbox before catching it via this very ticket.

## A cross-scenario git-history gotcha in the shell test's own fixture

The shell test reuses ONE fixture worktree across all 8 scenarios (cheaper
than a fresh `git init` per scenario). A commit is never undone, so a fixed
`dequeued_at` let scenario 02a's own `"BL-9001: did the work"` commit
satisfy scenario 05's LATER, unrelated Work note for the same ticket id —
first run of the new test failed 05 with 29 completions instead of 28.
Fixed by capturing a fresh `dequeued_at` immediately before each scenario
(with a 1s sleep guaranteeing separation at git's own commit-time
resolution), so no earlier scenario's history can satisfy a later one's
check. The JS acceptance handler sidesteps this entirely — it gives every
scenario its own fresh `mkProcessTmpDir` worktree.

## Declared invariants (BL-654)

Two of the three admit a pure encoding; the third is a live-host,
event-ordering property no fixture can construct without reproducing the
real daemon's dispatch machinery, and is recorded with a stated reason per
the ticket's own contract ("record a stated reason instead of a test when
a declared invariant admits no executable encoding").

- **Invariant 1 & 3** (combined: a Work note leaves in_process only with
  evidence or a stated reason; every non-Work note/git_handoff completes
  unaffected) — `work-note-completion-decision`'s full decision table, P1.
  Non-vacuous: broken by dropping the `(nil? ticket-id) :complete-plain`
  clause (falling through to the reason/evidenced?/refuse clauses even for
  a non-Work item) — every generated case with a nil ticket-id failed
  (114/500 in the broken run, exactly the nil-ticket-id bucket).
- **Invariant 2** (Work-note recognition is the one shared parser, no
  second regex) — P2: `work-note-ticket-id-from-message` must answer
  IDENTICALLY to calling `chase-sweep-lib/dispatch-trail-ticket-id`
  directly, for arbitrary message text. Non-vacuous: broken by adding a
  second regex (a bare leading `BL-\d+` with no Spec/Work verb) — every
  generated mention-only message ("BL-9001 active, spec-complete...")
  failed (63/500 in the broken run).
- **Not covered by a property test**: "Every non-Work note and every
  git_handoff completes exactly as today, AND the complete-then-dequeue
  contract of done_with_current is unchanged for them" — the
  complete-THEN-dequeue half of this (the `run-ready!` chaining, the
  ordering guarantee across a whole live queue) is an orchestration/timing
  property of the real daemon-driven mailbox, not a pure function this
  parcel could encode as a generator without rebuilding the real queue
  engine. The DECISION half (a nil ticket-id always plain-completes) IS
  covered by P1 above. The orchestration half is covered instead by the
  shell test's scenario 05 (a live one-item-at-a-time replay proving the
  burst behavior end to end) and the acceptance feature's own scenario 05.

**Reachability floors**: both P1 and P2's six coverage buckets (nil-ticket,
has-reason, evidenced-no-reason, the-refuse-case, dispatch-form messages,
no-match messages) measured 81-292 out of 500 — all well above the 50
(runs/10) floor.
