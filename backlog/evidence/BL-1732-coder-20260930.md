# BL-1732 — coder, 2026-09-30

## What shipped

- `extension/src/bridge/intakeVocabularyStore.ts` — the shared, durable
  vocabulary (`backlog/vocabulary/intake-narrative.yaml`, hand-rolled
  scalar-list format, no browser storage). `STARTER_VOCABULARY` is the
  ticket's own starter list. `withValue` is pure and in-memory only (a
  draft's own local addition); `promoteVocabulary` is the ONLY write path
  to disk, called exclusively at Submit — this is invariant 1.
- `extension/src/bridge/intakeWriter.ts` — `renderIntakeMarkdown` (the
  narrative + scenarios, a rule section only when the field is non-blank,
  a notes section only when non-blank), `submitIntake` (writes the
  INTAKE file + promotes the vocabulary, commits both TOGETHER through
  `commit_integrity_cli.bb` via the now-exported
  `runCommitIntegrityDetailed`), and the GitHub-permalink confirmation
  text, ported from `operator_lib.bb`'s own
  `github-base-from-remote-url`/`github-permalink`/
  `filed-intake-confirmation-text` (same math, TS-side since this is
  pure string formatting called from a bridge route, not a git write).
- `extension/src/tools/telegramTopicDecisions.ts` — `INTAKE_SUBJECT_ID`,
  `INTAKE_TOPIC_NAME`, `decideEnsureIntakeTopicAction` (mirrors
  `decideEnsureOperatorTopicAction`'s reuse/create shape exactly), and
  `decideIntakeTopicReply` (way-in link, or "unreachable, and why" when
  no form URL resolves — scenario 05).
- `extension/src/bridge/intakeFormUiHtml.ts` — the Mini App form: three
  narrative dropdowns over the fetched vocabulary (each with "add new…",
  kept in a page-local `newValues` object until Submit), a scenarios
  textarea, the optional rule and notes fields, posting to
  `/intake-form/submit`. No browser storage (Architecture rule 3) — the
  vocabulary is re-fetched from `/intake-form-state` on load and after
  every successful submit.
- `extension/src/bridge/bridgeServer.ts` — `GET /intake-form` (Mini App
  shell, same dispatch shape as `/epic-reorder`), `GET /intake-form-state`
  (read-scoped, query-token eligible, seeds the starter vocabulary on
  first read), `POST /intake-form/submit` (control-scoped like every
  other write route in the table, shape-validated, calls `submitIntake`).
- `extension/src/util/commitIntegrityRunner.ts` — exported
  `runCommitIntegrityDetailed` (was file-private) so `submitIntake` can
  read the commit's sha for the permalink.
- `specs/pipeline/steps/bl1732IntakeTopicFormSteps.js` — drives the real
  bridge routes via a real `startBridge` instance (mirrors
  `bl545CatchUpPagerSteps.js`'s own pattern) for the form/vocabulary/
  submit scenarios, and the real (pure) `decideIntakeTopicReply` directly
  for the topic-reply scenario, per the ticket's own "drives ... the
  topic decision in-process" constraint.

## Invariants (BL-654)

- **Invariant 1** ("a value joins the shared vocabulary only as part of a
  submitted intake that uses it"):
  `extension/test/bl1732VocabularyPromotionInvariant.property.test.js`.
  Generates random draft-local additions plus one promoted value; asserts
  the on-disk vocabulary is untouched until `promoteVocabulary` runs, and
  that every OTHER draft addition never reaches disk. Non-vacuous:
  verified by hand — a mutated `withValue` that leaked an extra token
  into its return value made the property fail; restored (diff against
  the pre-edit file: identical) before committing.
- **Invariant 2** (write routes refuse without the device/control
  token): `extension/test/bl1732IntakeAuthInvariant.property.test.js`.
  Drives the REAL `POST /intake-form/submit` route with randomly-shaped
  draft payloads and no auth headers; asserts 401 and no INTAKE file
  written, every time. Non-vacuous: verified by hand — removing
  `handleIntakeSubmitRoute`'s `requireControlAuth` call made the property
  fail (401 expected, got 200); restored (diff: identical) before
  committing. The invariant's OTHER half ("the Intake topic ignores
  everyone else") has no generator surface of its own — it is a
  message-routing property the acceptance's own topic-reply scenario
  already covers structurally (see Scope gap below).

## Scope gap, disclosed rather than silently dropped

The ticket's own Scope names `extension/src/tools/telegram-front-desk-bot.ts`
alongside `telegramTopicDecisions.ts`. I added the pure decision layer
(`decideEnsureIntakeTopicAction`, `decideIntakeTopicReply`) to the
latter but did NOT wire an `ensureIntakeTopic` async function or live
message-dispatch routing into the former's ~3,900-line poll loop. That
file's actual Telegram-message routing is the "unsuitable boundary"
Design And Testability already carves out (live Telegram client), and
the acceptance's own stated constraint is "drives the bridge routes, the
stores and the topic decision in-process" — which the pure decision
functions satisfy without a live bot. Wiring `ensureIntakeTopic` (a
direct mirror of `ensureOperatorTopic`, ~20 lines) and the inbound-message
dispatch case is real, low-risk follow-up work, but is not something I
could safely verify without live Telegram credentials, and the
`qa_e2e_procedure`'s own step 2 already calls for a human running that
live check. Flagging this explicitly rather than claiming it complete.
