## What was implemented — three layers, one predicate

1. **Writer — `land_step_lib.bb`.** New `record-land-approval!` appends one
   JSON line to `.swarmforge/land-approvals/<YYYY-MM>.jsonl` recording
   `{at, ticket, commit (the replay), source (the approved commit cited)}`.
   Appends, never truncates — a second land this month must not erase the
   first, or the predicate stops approving everything landed earlier. Refuses
   to write a record missing either sha, because the predicate reads such a
   line as corrupt and fails CLOSED: writing one would JAM the gate rather
   than open it. Returns `{:ok? bool}` and never throws.
2. **Wiring — `land_step_cli.bb`.** Records the mapping on the `:replay`
   success path, before announcing `LAND_REPLAY`. A failure to record is
   REPORTED (`LAND_APPROVAL_UNRECORDED` on stderr), never fatal: the land
   itself is sound, and an unrecorded land degrades to exactly the
   pre-BL-1334 behaviour (the sanctioned `--override`), never to a wrong
   approval.
3. **Reader — `is_qa_ancestor.sh`.** Collects the mapping and resolves it
   AFTER the bounce vetoes, in exactly the posture BL-1025's expedite store
   already established. This stays ONE predicate with one more approval path
   (BL-925 invariant 2), never a second definition.

Plus the consumer the ticket's scenario 03 names:

4. **`build_freshness_lib.bb` / `build_freshness_cli.bb`.** `code-drift-shas`
   no longer names a drift commit the shared predicate already calls
   approved; the CLI asks `is_qa_ancestor.sh --batch` (BL-1086: one process,
   stores read once) and passes the answer in as `:qa-approved?`. **This
   REMOVES an approval opinion rather than adding one** — the CLI previously
   decided the question itself with a merge-base walk, which is precisely the
   second-predicate the constraints forbid. `:qa-approved?` absent means
   unapproved, so an unanswerable predicate, an older CLI supplying no flag,
   and a genuinely unapproved commit all fail CLOSED alike.

## The mapping is not a rubber stamp — this is invariant 2's whole content

A land record grants approval ONLY when the SOURCE it names is itself
approved: the source must resolve, carry no bounce verdict in either store,
and be an ancestor of `swarmforge-QA`. A record naming an unapproved source
grants nothing and says so on stderr. Deliberately NOT a recursive call into
`answer_one`: a record whose source is itself a replay would otherwise chain,
and approval reachable through a chain of records is approval that spreads.

### A property of mine was VACUOUS, and the sweep is stronger for it

First cut had bounce states `{clean, source-bounced}`, where the bounced
source was NOT reachable from the QA ref. Deleting the bounce check from
`source_is_approved` entirely **left all 32 cases passing** — the source
failed the ancestry test anyway, so the veto was never what decided anything.
That is exactly BL-952's failure shape, and my property could not see it.

Added a third bounce state, `:approved-source-bounced`, which bounces a
source that IS reachable. The same break now fails. Recording this because a
green exhaustive sweep reads like proof, and this one was not proof of
invariant 3 until it covered a reachable-and-bounced source.

### Non-vacuity, all three, measured

- Remove the land-store consultation → **inv 1 fails** (2 cases: the approved
  replay, recorded, both bounce states).
- Approve on a record WITHOUT checking the source (rubber stamp) → **inv 2
  fails** (2 cases: the replay of a bounced parcel gains approval).
- Drop the bounce check from `source_is_approved` → **inv 3 fails** (1 case:
  the approved replay whose reachable source was bounced).

Each break restored; the sweep is green on the shipped code.

## Ordering is a RULE here, and my first expectation had it wrong

The sweep initially expected an unreadable store to dominate a bounce. It
does not, and should not: the predicate answers a bounce veto BEFORE raising
an unconsultable store, which it documents deliberately for the expedite
store ("a sha with a bounce on file answers a clean no even when this store
is unreadable"). A bounced sha is knowably not approved whatever else cannot
be read. I corrected the sweep's expectation to the documented rule rather
than "fixing" the predicate to match my first guess.
