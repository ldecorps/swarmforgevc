# BL-1352 — coder pass (2026-09-03)

GH-25's escalation reported an unusable transport into a status key nothing
read and a log line emitted once per tick — 7027 of them — while two role slots
sat wedged for four days. Both halves are fixed here.

## Visibility: a surface a human already runs

`role_ask_escalation_lib.bb` gains `escalation-transport-state`, the pure
three-way decision the ticket's scenario 01 asks for:

| transport | question waiting | state |
|---|---|---|
| configured | either | `ok` |
| unconfigured | none | `warn-unconfigured` |
| unconfigured | one or more | `fault` |

The middle row matters as much as the last: a signal that is permanently on
stops being read, which is precisely how the previous one died. A fault names
**every** waiting role, not just the first — a fault naming one of two gets
half-fixed.

`swarm_status.bb::ask_escalation` (the `required_wiring` anchor) reads that
state off the operator runtime's `status.json` and `./swarm status` renders an
"Ask escalation" row. The row is rendered **always**, even with nothing to
report: a row that appears only when something is wrong is a row a human never
learns to look for. An absent or unreadable status file reads as `unknown`,
never as healthy — a surface that cannot tell must not claim it can.

## The log flood

The per-tick `WARN ops issue unconfigured - no stamp` is **deleted**, not
quietened. `log-ask-escalation-transport!` writes the transport state on CHANGE
only, keeping its last state in `.swarmforge/operator/ask-escalation-transport.json`
— the same last-state pattern `write-babysitterd-watchdog-state!` already uses
in that file, deliberately rather than a second invention (the ticket asked
that it be read before inventing one).

## Rework on the cleaner's bounce D1 (2026-09-03)

**The finding was right.** Invariant 1's waiting set was drawn from
`fc.uniqueArray(maxLength: 3)` at `numRuns: 5`, so the empty-array case — and
therefore the `configuredIdle`/`unconfiguredIdle` reach floors — arrived by
luck. The cleaner measured a ~33% failure rate on `never exercised the
configuredIdle case`. A reach floor that fails a third of the time is the
mirror image of a vacuous one, and forwarding it would have shipped the
hardener and QA an intermittent red they did not cause and do not own fixing.

**Fix: all four corners are enumerated, not drawn.** The enclosing loops now
choose BOTH the transport and whether anything is waiting; only *which* roles
are waiting is generated (`fc.constant([])` on the idle arm, `minLength: 1` on
the other), with an assertion that the generator produced the arm it was asked
for. `numRuns` is 4 per arm — 16 cases against the previous 10, so breadth grew
rather than shrank. The header records D1 so the next reader knows why the file
is shaped this way.

This is the same class of defect the architect bounced on BL-1343 and BL-1323
earlier in this session; the discipline was applied up front in BL-1327,
BL-1332 and BL-1335, and this file predated my applying it consistently.

**Verified**: the property file ran green **15 consecutive times** against the
~1-in-3 red the bounce measured. Non-vacuity re-confirmed after the rewrite:
disabling the fault branch still fails invariant 1. The bb runner is ALL PASS
and the acceptance feature is 7/7 after restoring the parcel the bounce
reverted.

No production code changed in this rework — the defect was in the test's
generator, exactly as the bounce said. The parcel returns by reverting the
bounce revert, so the restore is explained by a revert rather than looking like
silently lost work.

## Two of my own earlier property tests, found red by this parcel's commit gate

Both were genuinely broken by later work on this branch — not load flakes —
and both are mine, so they are fixed here rather than left for a reviewer:

- **`bl1323StampOffInvariants` invariant 1** measured "did this parcel edit the
  code it reviews" over `origin/main...HEAD`, the whole branch. That was wrong
  the moment any LATER ticket touched a reviewed file: BL-1335 legitimately
  edits `handoffd.bb`, and BL-1323's invariant went red on work with nothing to
  do with the stamp-off. Now scoped to the stamp-off's OWN commits
  (`git log --grep BL-1323 origin/main..HEAD`), which is what the invariant
  always meant. An empty range returns early — the parcel having landed is not
  evidence that it edited something.
- **`bl1306AuditKeyBasisInvariants`** timed out at Vitest's 20 s default: each
  case is a git init plus two full `swarm_handoff.bb` invocations, which is
  seconds of real work. Given an explicit 180 s budget, and `numRuns` cut to 1
  per arm — the arms are enumerated, so repeating one buys wall-clock and
  nothing else. A property test that times out reports a red nobody can act on.
