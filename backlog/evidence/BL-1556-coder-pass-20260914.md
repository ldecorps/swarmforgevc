## Invariants (BL-654)

1. *"The number of bb processes a run of this file starts is bounded by its
   number of queries, never by its number of fast-check draws."* Encoded
   directly by feature scenario 02 / step handler
   `the shim counted at most 3 bb processes` — a real counting shim on
   PATH around a real subprocess run of the live file, the only way to
   observe this file's own process count (a reimplementation would prove
   nothing about the live file). This is process/environment behavior
   across a subprocess boundary, not a pure module a `fc.property` could
   exercise, so no separate `*.property.test.js` encodes it — the
   acceptance scenario IS the executable encoding (BL-654's own carve-out
   applies to a NEW property-test file, not to "no test at all"; here the
   invariant already has a real, executable, non-mocked check).
2. *"A fixture git step that exits non-zero stops the fixture and names
   itself; no later step runs on its result."* Encoded directly by feature
   scenario 04 — a real `git` shim that fails `push`, driving the REAL CLI
   as a real subprocess, asserting non-zero exit and that stderr names the
   failed step. Same reasoning as invariant 1: this is fixture/process
   behavior (a git subprocess's exit code propagating through `sh!`), not
   a pure function, so the acceptance-level real-subprocess check is the
   encoding rather than a new fast-check property.

Both invariants are therefore exercised as real, non-mocked, executable
checks in this same parcel (scenarios 02 and 04) rather than as
`*.property.test.js` files — recorded here per BL-654 rather than left
unaddressed.
