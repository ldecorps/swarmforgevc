## Invariants (BL-654)

1. "Overlapping live-screen captures for the same targetPath within the TTL
   share one synchronous walk." + 2. "After the TTL expires, or after
   clearResidentPaneLiveCache, the next capture performs a fresh walk." —
   one property test, `residentPaneLive.property.test.js`: for **any**
   sequence of poll-instant deltas (`fc.array` of `fc.integer({min:0,
   max:2*TTL})`, up to 15 polls, 200 runs), the number of real tmux walks
   the implementation performs must equal a plain greedy-TTL model's
   prediction (fresh walk exactly when the gap since the last real walk is
   >= TTL). Generator reach: deltas span `[0, 2*TTL]` by construction, so
   both cache-hit (including delta=0) and cache-miss (up to 2x TTL) paths
   are exercised on every run, not just plausibly. **Non-vacuous**:
   confirmed live — temporarily disabled the cache-hit branch
   (`if (false && cached && ...)`), recompiled, reran: fast-check found the
   minimal failing case immediately (`deltas=[0,0] expected 1 walks, got
   2`), then restored and reran green. No broken variant was ever committed.
2. (see above, folded into the same property)
3. "The Resident Spy Mini App poll interval does not routinely queue
   overlapping synchronous captures on the bridge event loop." — no
   separate property test; recorded reason in the property test file's
   header comment. `getResidentSpyUiHtml()` takes no arguments, so there is
   no input domain to generate over — an isolated property test would just
   restate a fixed assertion on a string constant. The actual protective
   *mechanism* this invariant describes is exactly what invariants 1/2's
   property test already proves for the worst case: delta=0 (requests
   arriving with zero gap, far faster than the real ~4s poll) still
   collapses to one real walk per TTL window, never one walk per poll. The
   real production wiring (poll=4000ms, TTL=5000ms) is checked structurally
   in two places: `residentPaneLive.test.js` (poll interval regex over the
   served HTML — not written, since no prior test file for this module
   existed; added via the new acceptance scenario instead) and the
   acceptance feature's third scenario, which asserts the served HTML's
   poll interval is >= 4000ms and `RESIDENT_PANE_CACHE_TTL_MS === 5000`
   against the real compiled modules.
