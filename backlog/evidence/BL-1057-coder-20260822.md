## Shape

Follows the existing checker shape the ticket's "How" section points at
(`babysitter_check.bb`, `master_checkout_drift_lib.bb`): `*_lib.bb` holding
every decision, a thin CLI that is argument parsing and I/O only, and
`test/*_lib_test_runner.bb`.

- **The inventory is DATA**, one vector of maps in the lib. Adding a sixth
  location is a one-row change, not a new code path. The CLI exposes it with
  `--inventory` so the acceptance step handlers BUILD their fixture host from
  the one declared inventory rather than keeping a second copy of it in
  JavaScript, where the two would drift.
- **Every `$HOME`-rooted base is an env seam** — `SWARMFORGE_TUNNEL_REGISTRY_DIR`
  (the one `tunnel_ownership_lib.sh` already established) and
  `SWARMFORGE_CLOUDFLARED_DIR` — and the repo root is injected rather than
  derived, so no lane ever reads the real `$HOME` and no fixture depends on
  where it was run from.
- **No git subprocess, no JSON parser, minimal dependencies**: it has to run on
  a half-migrated host with as little as possible working.

## Three decisions worth reviewing

**1. A per-role worktree is not a separate forge.** Run from
`.worktrees/coder`, a naive implementation reports the main checkout's paths
as STALE — two false findings for every role in the swarm. `main-checkout-root`
reads the worktree's `.git` FILE (`gitdir: <root>/.git/worktrees/<name>`) and
resolves to the forge's own root. Pure text, no git subprocess.

**2. `swarmforge.configPath` names a file INSIDE the checkout, not the root.**
The ticket's inventory table says both settings "name this repo root", but on
this very repo `swarmforge.configPath` is
`…/swarmforge/packs/full-forge.conf`. Equality would report a perfectly healthy
setting STALE forever — it did, until `describes-root?` was written to accept
the root or anything under it. The `/` separator in that prefix test is
load-bearing: without it a sibling checkout at `<root>-old` reads as inside
this one, which is precisely why the property's stale roots are near misses
derived from the real root rather than unrelated paths.

**3. "Present" means present AND READABLE.** `~/.cloudflared/config.yml`
existing as an unreadable entry is exactly "the check could not be run", and
the feature file requires BLOCKED for it. An existence-only check can never
produce that verdict, so every `:present` row reads its target.

## Settings files are JSONC, and a commented-out setting is not a setting

`extension/.vscode/settings.json` in this repo carries `//` comments AND a
trailing comma. A JSON parser reports it unreadable, and the doctor would say
BLOCKED about a healthy file. The lib does a targeted text scan instead, which
skips lines whose trimmed text starts with `//` — reading a commented-out
setting as live config would report a stale path the forge does not use. Same
rule `master_checkout_drift_lib`'s own text scan already applies to
commented-out `load-file` lines.

## Invariants (BL-654) — all three encoded, all five breaks proven

`swarmforge/scripts/test/bl1057_host_switchover_doctor_property_runner.bb`,
60 generated host states over a REAL temp filesystem (an injected write seam
nobody calls would prove only that the harness never called it).

| Invariant | Encoding |
|---|---|
| 1. never writes | the whole tree is fingerprinted (entry list, size, mtime, content hash) before and after every run; a creation, deletion, rewrite or touch anywhere fails it |
| 2. one entry, one verdict, BLOCKED never omitted | report length equals inventory length, ids match as sets, no duplicates, every verdict from the declared set — plus a state→verdict ORACLE (below) |
| 3. a non-OK finding is actionable | every non-OK finding must name a non-blank path and remediation, and the rendered report must carry that remediation |

Non-vacuity, each break applied to the lib, run, and reverted:

| Break | Fails |
|---|---|
| `verdict-for` returns `:ok` when a read fails | inv 2 — "could not be read and was reported :ok" |
| `run-doctor` filters `:ok` findings out of the report | inv 2 — "not one entry per declared location" |
| `describes-root?` drops its `/` separator | inv 2 oracle — "generated :stale and reported :ok" |
| a finding built without its row's `:remediation` | inv 3 — "is not OK and names no remediation" |
| the read seam does `slurp`-then-`spit` | inv 1 — "the doctor changed the tree it inspected" |

**One reach gap found and closed while proving this.** The first version of the
property asserted only structural properties plus "unreadable ⇒ BLOCKED", and
the `describes-root?` separator break PASSED against it — a location the
generator had made stale came back OK and nothing noticed. The fix is that the
generated state is now the ORACLE: every row's verdict is asserted against what
`build-host!` actually wrote for it. That is what turned break 3 into a
failure. Recording it because it is the exact failure mode BL-654's
generator-reach clause names, caught only by running the break.

Reach floors, asserted rather than hoped for and all met on the recorded run:
`{:ok 221 :blocked 81 :missing 89 :stale 29}`, each with its own floor. A state
set of four (`healthy / absent / stale / unreadable`) is drawn per location
because BLOCKED is not a coin flip on a real disk.
