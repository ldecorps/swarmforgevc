# BL-1851 coder evidence

## What was built

- `local_seat_tuning_report_lib.bb` (pure): groups a seat's requests into
  consecutive runs under the same (settings-fingerprint, served-signature)
  key, summarises each group (median ttft/prefill/decode/output/thinking-
  share, compressions per 10 requests and tokens saved, tool-call failure
  rate and the most-failing tool), and names what differs between
  consecutive groups' own settings/served.
- `local_seat_tuning_report_cli.bb` (thin IO): reads BL-1850's settings
  jsonl, every one of the seat's qwen session files, and the Ollama log;
  hands already-parsed data to the lib; renders the report as text.
  `bb swarmforge/scripts/local_seat_tuning_report_cli.bb <root> --seat <seat> [--since <iso>]`.
- Reused BL-1842's `local_seat_report_lib.bb` for every record parse
  (never a second parser, BL-1811/the ticket's own direction) - and
  extended it with `parse-ollama-loads` (every model load over the log's
  lifetime, not just the latest) since BL-1851's own scenario 04 needs
  the load *history*, which BL-1842 never needed.

## A pre-existing defect found and fixed in BL-1842's own code

While reading through `local_seat_report_lib.bb/parse-session-events`
(per the ticket's own "read through BL-1842's lib" direction) to reuse it
for per-request timing/tool-call data, I found its existing compression/
api-error reading was **silently wrong in production** - the same shape
of bug BL-1861's bounce just taught me to check for:

- A chat_compression row's real token counts live at
  `systemPayload.info.originalTokenCount`/`newTokenCount` - verified
  against every chat_compression row in every session file on this host
  (100% nested, 0% carrying a top-level `tokensBefore`/`tokensAfter`,
  which the old code read). `local_seat_report_cli.bb` has been printing
  `Compressions: N (->, ->, ...)` with no real numbers since BL-1842
  shipped.
- An API error is its own event, `qwen-code.api_error` - verified against
  real `qwen-code.api_error` rows on this host. The old code looked for a
  top-level `apiError:true` flag that no real record has ever carried, so
  `API errors: N` has always read 0 regardless of how many actually
  occurred.
- BL-1842's OWN unit test (`local_seat_report_lib_test_runner.bb`) and its
  acceptance step handler (`bl1842LocalSeatReportSteps.js`) both wrote the
  same idealized, never-real fixture shape the buggy code expected, so
  neither test could ever have caught this.

Fixed both reads to the real nested shape; fixed both fixtures (the unit
test and the acceptance step handler) to the real shape too; re-ran
BL-1842's own acceptance feature (3/3, unchanged) and its property test
(`bl1842LocalSeatReportReadOnlyInvariant.property.test.js`, unaffected -
it asserts only directory-tree read-only-ness, never field values).
Verified the fix against real session files on this host directly (see
below).

## A real tooling gap in the pinned Gherkin parser

Scenario 02 ("a group prints its time to first token...") carries a
step-level Gherkin DataTable. The pinned `swarmforge/vendor/aps`
`gherkin-parser` drops step-level DataTables entirely - confirmed by
running it directly and inspecting its own raw IR JSON, which carries no
table field for that step at all (an Examples: table, a DIFFERENT Gherkin
construct, IS supported and present elsewhere in the IR). Per
constitution ("never reimplement APS commands") this is not mine to
patch, and per my own role ("do not hand-author Gherkin") rewriting the
.feature file's scenario text to avoid a table is not mine to do either.
Noted to the specifier (priority 00) for their own awareness/future
tickets. Worked around transparently in the step handler: the three rows
the scenario's own table names are hardcoded literally (not re-derived,
not a second copy of any CLI/lib logic) since no tool in this pipeline
can deliver them to any handler as written.
