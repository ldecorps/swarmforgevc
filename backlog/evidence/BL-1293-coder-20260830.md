## A regression I caused and caught

First cut called the primitive with no merge guard. On a commit with fewer than
two parents its `diff-tree` is empty for an unrelated reason (a root commit, an
empty tree), so **BL-806's and BL-950's own acceptance suites went red** — 5 and
2 failures, refusing legitimate sends with the new wording.

The parent-count guard is part of the primitive's contract and already lived in
its sibling caller `no-dropped-work?`; the fix applies the SAME guard rather
than a second one, which is why `commit-parents` is promoted too. A regression
test pins the exact shape (`an empty root commit (no parents) fails open`).
Both sibling suites are green again: **9/9** and **6/6**.

## Declared invariant (BL-654)

> "A review role's forward carries content that role itself authored — its
> committed evidence file or its fix. A commit that introduces nothing of its
> own over its parents is never a pass, whatever its shape or subject."

Encoded in `review_forward_evidence_gate_lib_property_runner.bb`, this lib's
established property lane (the file's own header records it as BL-654
property-tested; the bb lane, not `*.property.test.js`, is the nearest existing
convention for a Babashka lib):

- the contribution fact joins the broad input space, with `nil` as a real value —
  it is what an unreadable commit produces and it must never block;
- the independent oracle gains a freshly-stated disjunct, not a copy of the
  gate's conjunction;
- **generator reach asserted, not hoped for**: the broad generator needs six
  independent draws to line up on the new shape, so a by-construction generator
  fixes sender/recipient/type to the gated hop and varies only the
  discriminating fields. The commit id is deliberately a DESCENDANT, never the
  received hash — an empty merge that also named the received hash would be
  caught by BL-806's old identity check and prove nothing about this one. Both
  the refused and the allowed shapes are asserted reached.

**Non-vacuity proven twice.** Reverting `blocked?` to identity-only:

| check | against the fixed gate | against the pre-fix gate |
|---|---|---|
| property runner | ALL PASS | **90 failures** |
| unit runner | ALL PASS | 2 failures |
| BL-1293 acceptance | 6/6 | **not ok 2, not ok 6** (4 pass / 2 fail) |

The identity-only decision is also kept in the property runner as a live mutant,
so a future regression to id comparison goes red rather than quietly green.

## Step 4 — the real BL-1224 commit is not an empty merge

`qa_e2e_procedure` step 4 asks to replay `b7d22b9ee` against `3bc1e28b53` and

The ticket's own declared invariant is "a commit that introduces nothing of its
own over its parents is never a pass". `b7d22b9ee3` DOES introduce something of
its own, so the mandated predicate cannot refuse it, and step 4 contradicts the
invariant and the direction rather than the code contradicting step 4.

Catching it would need a different question — "did this role commit evidence for
this task?" — which is a second notion of contribution, the exact thing
`approval_context` forbids growing here. **I did not do that.** The gate now
catches the clean-merge shape (the common one) and the unchanged-hash shape; the
conflict-resolving pass-through remains invisible to it. A `note` recording this
goes to the specifier with this parcel; it is a real, still-open hole and should
not be closed by silence.
