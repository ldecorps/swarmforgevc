## Architectural ruling this ticket required (not a side effect)

The ticket's `description` is explicit: whether `buildBridgeState`'s JSON
`/state` routes (`/pipeline`, `/agents`, `/backlog`, `/runlog`) should follow
the stream's narrowing, or keep full fidelity, "is a design call for the
architect pass; it must be a decided answer either way, not a side effect."

**Ruling: the JSON `/state` routes keep full fidelity. The projection
applies only at the two `/events` stream producers.** Confirmed as already
implemented this way — `stateForRoute`/`isStateRoute` in `bridgeServer.ts`
still call `buildBridgeState` directly (unchanged), and `streamSnapshot.ts`'s
`projectBridgeStateForStream` takes a `BridgeState` and returns a fresh
projected copy without mutating its input (verified by
`streamSnapshot.test.js`'s "the projection is a copy" test, and confirmed by
reading the function).

Rationale:
- The defect this ticket fixes is specific to the STREAM's broadcast cost:
  `broadcastSnapshotIfChanged` re-sends the whole frame to every connected
  SSE client on any backlog commit, and every 5-minute reconnect re-pays the
  full cost. The JSON routes are fetched once per page load
  (`holisticUiHtml.ts`'s `loadOnce`) — a single request, not a
  per-client-per-commit broadcast — so the bandwidth-multiplication problem
  this ticket targets does not apply to them with the same severity.
- Only one consumer of `/backlog` exists (`holisticUiHtml.ts`'s `loadOnce`),
  and it feeds the same `renderBacklogBoard` function the stream also feeds
  — which only reads `item.id`/`item.title` regardless of source. Narrowing
  `/backlog` would cause no CURRENT functional regression, but the JSON
  routes are a general-purpose state API with no established performance
  constraint of their own; narrowing them preemptively, with no consumer
  asking for it and no measured cost driving it, would be scope creep beyond
  the ticket's own bounded, reversible, low-risk framing ("Option 1... no
  consumer changes"). A future consumer of the JSON routes wanting richer
  per-item data is a live possibility the stream's consumers do not raise.
- This keeps the "narrow only what's proven safe to narrow" posture the
  human's ruling (option 1) established, rather than generalizing narrowing
  to a surface the ticket never measured or reasoned about.
