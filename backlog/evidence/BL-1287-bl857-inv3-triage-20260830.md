## Hypotheses tested and DISPROVED

**H1 — "the fixture is not yet visible to `pgrep -f` when the reap runs."**
Replicated `spawnFakeCloudflared`'s exact shape 60 times, pgrep'ing immediately
after `echo $!`:

    hits=60 misses=0

So exec latency is not the race. Disproved.

**H2 — "a sibling suite kills bl857's fixtures."** Every kill site was enumerated:

- `bl787NamedTunnelInvariants` — kills only pids it recorded itself (lines 70, 180)
  and via `killPidFile`. Its `stop_ancillary_services.sh` call is name-scoped
  through `isolatedEnv`.
- `bl1061TunnelFixtureIsolation` — calls `leakedFixtureTunnelPids` with a **fake**
  exec (line 194). Pure-filter test; signals nothing.
- `stop_ancillary_services.sh` — every kill is pidfile-scoped (lines 59–71, 199)
  or name-scoped (`tunnel_reap_orphans "$name"`, line 219); the two pgrep sites
  (lines 93, 97) are scoped by `$ROOT`.
- `bl857TunnelOwnershipInvariants:111` — the ONLY host-wide killer, and it fires at
  module load, before bl857's own first assertion, so it cannot reach bl857's own
  inv3 fixtures.

Disproved for the reported direction.

## What H2 DID surface — measured, and the reason BL-1287 exists

The same enumeration showed the sweep is unscoped in the *other* direction. A
process shaped exactly like a live `bl787` fixture — own temp dir
(`bl787-ready-prop-*`), own unique name from `fixtureTunnelName()`, creating run
still running — handed to the real predicate:

    sibling live fixture pid : 2702805
    selected by sweep        : YES — would be SIGKILLed
    total selected pids      : 2

`leakedFixtureTunnelPids` keeps any line matching
`tmpdir + \bcloudflared\b + / run \S/`, excluding only `process.pid`. Its own doc
comment claims it selects fixtures "leaked by an EARLIER run"; the predicate cannot
distinguish that from a concurrent sibling's live fixture. The lane is
`pool: 'forks'` with `maxForks > 1`, so the overlap is real, not theoretical.

## Open, NOT ticketed — needs QA's counterexample first

`isAlive()` is `process.kill(pid, 0)`, which returns **true for an unreaped
zombie**. inv3's reap SIGKILLs a fixture orphaned when its `bash -c` wrapper
exited, so the corpse waits on a subreaper before it stops answering signal 0, and
inv3 asserts within milliseconds. Measured window 7–8ms — but that number is
bounded by the probe's own poll cost (a `spawnSync` sleep), so the true width is
unknown. Plausible under a full lane; unproven. Deliberately NOT folded into
BL-1287: different file, different mechanism. BL-1061's own property-lane triage
split 1:4 on exactly this principle.

## Why this is not filed as "bl857 inv3 is flaky"

A ticket minted on a guessed mechanism is the BL-1061 failure mode — that ticket
named the wrong file and the wrong cause and had to be amended after the coder
measured its own base commit. BL-1287 claims only what was measured, and says so
in its `notes:`.
