# BL-1415 — coder pass, 2026-09-05

## What was wanted

The dropped-parcel sweep's stall clock read only a dispatch file's own
`created_at`/`enqueued_at` - never the recipient copy's `dequeued_at`/
`completed_at`. On 2026-09-05 two Work notes (BL-1384, BL-1402) waited
unread in the coder's inbox for over an hour, were dequeued and completed
within seconds of each other, and were reported as "possible drops" the
instant live mail cleared - because the clock, blind to the recipient's own
action, saw only the original 1h+-old creation time. The router correctly
refused the repair as DISPATCHED (a real trail existed), and `--force`
duplicated the route into a coder that was already working the ticket. One
of the two (BL-1384) really was dropped (a second dequeue raced the first
completion); the sweep could not tell the two cases apart because its
clock never looked at what the recipient did.

## What landed

- **`swarmforge/scripts/chase_sweep_lib.bb`**:
  - `handoff-event-ms-from-headers` - a new shared pure function: the
    freshest of `enqueued_at`/`created_at` (dispatch creation) AND
    `dequeued_at`/`completed_at` (the recipient copy's own action
    timestamps). `handoff-event-ms` (single-file reads, used by
    `newest-trail-event-ms`) and `build-dropped-parcel-trail-index`'s own
    inline derivation (the single-pass, perf-critical path BL-978 built)
    both now call this ONE function - BL-978 invariant 2 preserved by
    construction rather than by keeping two copies byte-identical by hand.
  - `ticket-dispatch-verdict` / `ticket-dispatch-verdict-in` - the new
    three-way question (`:dispatched`/`:dropped`/`:undispatched`), built
    directly on `decide-dropped-parcel?` UNCHANGED (invariant 1 - one
    predicate for the sweep, the CLI and the router). `:reason` for
    `:dropped` is `dropped-parcel-note-message` - the SAME text the
    sweep's own nudge already produces, so all three surfaces visibly
    agree without a duplicated message string.
  - `live-mail-trail-dirs` - the router's/CLI's own :new/:in_process
    scope-builder, mirroring `dispatch-trail-dirs`'s existing shape
    (handoffd.bb's private `dropped-parcel-live-mail-dirs` is unchanged -
    same scope, independently exposed here for this new caller).
- **`swarmforge/scripts/dispatch_trail_cli.bb`**: the `dispatched` command
  now prints `DISPATCHED`, `UNDISPATCHED`, or `DROPPED <reason>` (was a
  two-way DISPATCHED/UNDISPATCHED only), via `ticket-dispatch-verdict-in`;
  reads `dropped_parcel_stall_threshold_minutes` from `swarmforge.conf`
  the same way `handoffd.bb` does.
- **`swarmforge/scripts/route_backlog_to_coder.sh`**: three-way branch on
  the CLI's first word (`TRAIL_ANSWER`) - `DISPATCHED` refuses exactly as
  before; the new `DROPPED` case routes WITHOUT `--force`, printing the
  CLI's own reason (`TRAIL_REASON`) so the operator sees what is being
  repaired rather than having to guess at `--force`.
- **`specs/pipeline/steps/bl1415LostDispatchSteps.js`** (new): drives the
  real `chase_sweep_lib.bb` (via `bb -e`), the real
  `route_backlog_to_coder.sh`, and the real `dispatch_trail_cli.bb`
  (subprocesses) against a fresh fixture git repo per scenario.
- Unit coverage: 2 new bb assertions for the widened clock, 8 new for
  `ticket-dispatch-verdict`/`ticket-dispatch-verdict-in`
  (`dropped_parcel_test_runner.bb`); 1 updated source-lock assertion
  (`bl1097_router_dispatch_trail_test_runner.bb`, now names
  `ticket-dispatch-verdict-in` - the call the CLI actually makes); 3 new
  end-to-end shell scenarios (`test_bl1097_router_refuses_dispatched_ticket.sh`,
  scenarios 08-10: a long-completed dispatch routes without `--force`
  naming the reason, the CLI itself prints `DROPPED <reason>`, and a
  dispatch still unread past the threshold stays `DISPATCHED`).

## A live fixture-scoping bug caught and fixed before landing

The first version of `bl1415LostDispatchSteps.js`'s `runRoute()` shelled
out to the real `route_backlog_to_coder.sh` without setting `cwd` to the
fixture root - `swarm_handoff.sh` (which that script calls to actually
queue a route) resolves its OWN target via `git rev-parse
--show-toplevel` from the **process's** cwd, not from the `$ROOT`
positional argument, so the first run queued real (though gitignored,
non-persisting) handoff files into THIS session's own live
`.swarmforge/handoffs/coordinator/outbox/` instead of the fixture's.
Caught immediately from the log output naming the real repo's absolute
path instead of `/tmp/...`; fixed by passing `cwd: root` to every
`execFileSync` call that shells to the router (BL-1390's own class of
hazard, applied here). Verified clean on the next two runs:
`find /home/carillon/swarmforgevc/.swarmforge -name "*.handoff" -newer
.git -mmin -10` empty both times.

A second, related bug surfaced in the same debugging pass: the step
handlers first computed every fixture timestamp relative to a FIXED
historical instant (`2026-09-05T12:00:00Z`), but `route_backlog_to_coder.sh`
and `dispatch_trail_cli.bb` read the REAL wall clock (`System/
currentTimeMillis`, no injected clock) - so a "10 seconds ago" event was
actually many hours stale relative to the real clock the CLI/router
subprocess reads, misreporting a should-be-`DISPATCHED` fixture as
`DROPPED` (scenario 04 failed on the first run for exactly this reason).
Fixed by computing every timestamp from `Date.now()` instead, so the
fixture and the real subprocess agree within the run's own few seconds -
immaterial next to the scenarios' minute/hour margins.

## Declared invariants

1. **One predicate everywhere.** `ticket-dispatch-verdict`'s `:dropped`
   branch is `decide-dropped-parcel?` called unchanged; the router never
   re-derives the question from the mailboxes - it reads the CLI's
   printed verdict. Locked by `bl1097_router_dispatch_trail_test_runner.bb`'s
   updated source-lock assertion (18) and the acceptance feature's own
   scenario 05 (the CLI's reason matches the sweep's nudge text
   byte-for-byte, both built from `dropped-parcel-note-message`).
2. **The clock is the freshest of creation OR recipient action.**
   Demonstrated directly: `newest-trail-event-ms`'s new unit tests show
   `dequeued_at`/`completed_at` each individually override a much older
   `created_at`; scenario 02 (both Outline rows) proves a dispatch acted
   on 30 seconds ago is never a drop even though its own creation was 2
   hours ago.
3. **DISPATCHED/DROPPED/missing-data fail-closed exactly as BL-1301 has
   it.** `ticket-dispatch-verdict`'s unit tests cover live mail (always
   `:dispatched`), a trail too fresh to call stale (`:dispatched`), and a
   missing `newest-trail-ms` (`:dispatched`, never `:dropped` - BL-1301's
   own fail-closed posture, unchanged).
