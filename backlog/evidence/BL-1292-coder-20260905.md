# BL-1292 — coder pass, 2026-09-05

## What was wrong

`extension/test/bl857TunnelOwnershipInvariants.property.test.js`'s
`isAlive(pid)` decided every "did the reap kill it?" assertion with a bare
`process.kill(pid, 0)`, which answers "does some process with this pid
exist and can I signal it?" — not "is THIS fixture still running?" Two
mechanisms make those diverge, both likelier the busier the host is: a
SIGKILLed fixture stays signallable as an unreaped zombie until its
subreaper collects it, and a pid the reap just freed can be handed to any
of the thousands of processes a full property-lane run spawns. QA's
counterexample (`[prefixed, false]`, seed `-436553632`, path `12`) is
invariant 3's target-assertion firing this way.

## What landed

- **`extension/test/helpers/fixtureLiveness.js`** (new): the ONE shared
  `isAlive(pid, name)` — confirms the pid is signallable AND that
  `ps -o args= -p <pid>` still carries this fixture's unique tunnel name
  (POSIX, works on both supported OSes — the same portability lesson
  BL-1061 already paid for in this exact file; `/proc/<pid>/cmdline` is
  Linux-only). Also exports `spawnZombie(name)`, the real zombie-fixture
  construction both the property test and the acceptance step handler
  share (see below).
- **`bl857TunnelOwnershipInvariants.property.test.js`**: the local
  `isAlive` deleted; imports the shared one instead. All 6 call sites
  (invariants 1, 2, 3) updated to pass the fixture's own tunnel name —
  each site already had a `name`/`target`/`bystander` variable in scope,
  so this is a mechanical thread-through, no new fixture logic.
- **`specs/pipeline/steps/bl1292FixtureLivenessByIdentitySteps.js`**
  (new): acceptance step handlers, all 3 scenarios (6 runs).
- **New property test** (BL-654, see below) appended to the same file,
  after invariant 3.

No change to `tunnel_ownership_lib.sh` or any other production script —
per the ticket's own explicit framing, the production reap is not
implicated; only the test's own liveness question changes.

## Declared invariant (BL-654) — genuine generative property

**Invariant** ("A test's answer to 'is this fixture still running?' is
true only while THAT fixture is running: a zombie awaiting its reaper,
and a pid reused by an unrelated process, both answer false.") — the new
`property (BL-1292 invariant)` test iterates all four situations
EXPLICITLY (`still-running`, `zombie`, `unrelated-live-process`,
`absent-entirely`) — satisfied by construction, this codebase's own
established fix (BL-1062) for exactly this coverage-floor class — spawning
fresh REAL processes for each, never mocked or fabricated, and asserts a
reachability floor (every situation actually drawn, never omitted).

**Non-vacuity**, mutation run for real and restored byte-identical
(`diff` against a pre-break backup confirmed exact restoration): reverting
`isAlive` to the bare `process.kill(pid, 0)` form failed immediately on
the very first generated case — `"situation=zombie: expected
isAlive=false, got true"` — proving the property actually exercises the
identity check, not merely that some boolean comes back.

**Reachability**: all four situations are iterated explicitly (a `for`
loop over the full list, not `fc.constantFrom` sampling) with a
generator-reach assertion (`undrawn` must be empty) confirming none was
skipped.

## The genuine zombie, confirmed not inferred

`spawnZombie(name)` spawns a bash process that backgrounds a short-lived
child (renamed via `exec -a <name>`) and then itself sleeps for 5s without
ever calling `wait` on that child — the classic "parent alive, child
exited, nobody has reaped it yet" zombie window. Confirmed via
`/proc/<pid>/status`'s own `State: Z` line at authoring time (not inferred
from timing alone): a direct probe against this exact construction showed
`State: Z`, bare `process.kill(pid, 0)` reporting **alive: true** (the OLD,
broken answer), and the new identity-checked `isAlive` reporting **alive:
false** (the fixed answer) — the precise defect this ticket exists to
close, reproduced directly rather than assumed.
