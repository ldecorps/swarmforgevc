## What changed

- `extension/src/tools/bubbleSeat.ts` (new): the seat's whole decision, in the
  shape BL-1235's local seat already established.
  - **Invariant 1 is structural, not remembered.** The only `answer` variant
    the type can produce carries `via: 'front-desk-mirror'`. There is no
    variant on which the seat answers from a context of its own, so a second
    brain cannot be built out of this type without changing it — which is
    exactly the review a divergence deserves. A property asserts the source
    literal set is `['front-desk-mirror']` and nothing else.
  - **Invariant 2 is the first clause**, a hard gate ahead of everything else:
    a message outside the seat's topic returns `not-mine` before anything is
    considered, so no path exists on which the Bubble worker answers cursor's
    host topic or the front desk. A `not-mine` decision carries no `topicId`
    at all — there is nothing for a caller to post into.
  - `cursorBusy` is part of the input and deliberately UNREAD. It is there so
    the regression has a name and a test: waiting on it is the defect this
    ticket removes, and both a unit test and a property assert the decision is
    byte-identical whether cursor is mid-turn or idle.
  - `decideSeatWatch` covers BOTH seats, and a seat whose liveness could not be
    determined is reported rather than assumed alive — "could not tell" and
    "running" are the two answers a supervisor must never conflate.
- `extension/src/tools/telegramCursorBridgeLive.ts`: the Bubble topic is
  dispatched to its own worker BEFORE cursor's decision is consulted, from
  INSIDE the bridge's existing poll — the same posture the qwen seat uses, and
  the reason invariant 3 holds by construction: a bot token has exactly one
  getUpdates consumer, and this seat opens none.

## What this slice does NOT do, and what QA's live step still needs

The ticket's `qa_e2e` asks for a LIVE demonstration: occupy the Cursor seat
with a long turn and confirm from the phone that a Bubble message is answered
while that turn is in flight, with no 409s and no bridge restart. That is
QA's, and it is the half no fake can stand in for.

What this parcel ships is the decision, the dispatch point and the watchdog
report. The production answer source is an injected seam
(`runBubbleSeatTurnFn`): the bridge calls it for Bubble-topic messages, and
binding it to the front desk's own answering path is what makes the mirror
real at runtime. Wiring that seam to a live worker process (and the seat's
model/lifecycle choice, which the ticket notes should be made with the
measured ~2.8 tok/s local seat in mind) is deliberately not smuggled in here:
it is a live-agent concern, and this parcel keeps to what is testable without
booting one. The seam is present and dispatched, so the follow-up is a
binding, not a rebuild.
