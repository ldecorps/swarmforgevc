  `specs/pipeline/steps/bl871PropertyLaneWorkerPoolCapSteps.js`).

  budget instead of a bare literal — implementer's call.

## D2 — the property lane still times out on subprocess-heavy files, across repeated runs, on the ticket's own reference host

- **Failing command**: `cd extension && npm run test:properties` (run
  directly, not through the acceptance wrapper, to rule out D1's timeout as
  the cause)
- **Commit hash**: `052a1f4f0c`
- **First error excerpt** (run 2 of 3, `test/bl760DuplicateChainGuard.property.test.js`):
  ```
  × property: a send is always refused when any OTHER role already holds a
    live (new/ or in_process/) git_handoff for the same ticket id  101245ms
    → Test timed out in 20000ms.
  × property: a refused send writes nothing to the sender's outbox/sent...  162757ms
    → Test timed out in 20000ms.
  × property: a held parcel for a DIFFERENT ticket id never blocks a send...  152744ms
    → Test timed out in 20000ms.
  Test Files  1 failed | 72 passed (73)
  ```
  Run 1 of 3 instead failed `test/bl787NamedTunnelInvariants.property.test.js`
  (invariant 1) and `test/bl797MutationGateProbeCrashFallback.property.test.js`
  (120000ms timeout) — 3 failed files, 5 failed tests. Run 3 of 3 failed BOTH
  `bl760DuplicateChainGuard` (all 3 properties, `Test timed out in 20000ms`
  again) AND `bl787NamedTunnelInvariants` (invariant 1) together — 2 failed
  files, 4 failed tests. All three runs additionally logged 5 unhandled
  `[vitest-worker]: Timeout calling "onTaskUpdate"` RPC errors.
- **Failure class**: `behavior` (the ticket's own declared invariant 1 and its
  `qa_e2e_procedure` step 2 bar — "All 65 files must pass every run" across
  three runs — do not hold)
- **Expected vs observed**: expected 3/3 clean `test:properties` runs per the
  ticket's own procedure; observed 0/3, with a DIFFERENT file failing each
  time (bl797+bl787 → bl760 → bl760+bl787) — the same "moving failure"
  signature the ticket's own description cites as the pre-fix symptom
  (`bl760DuplicateChainGuard`, `bl787NamedTunnelInvariants`, and
  `bl805RotateGateOnUnfinishedInProcessParcel` are the exact three files named
  there). `bl805` did not itself fail in my runs, but the other two did,
  repeatedly.
- **Blamed role**: coder.
- **Remediation pointer**: `bl760DuplicateChainGuard.property.test.js` and
  `bl787NamedTunnelInvariants.property.test.js` both drive real subprocesses
  (`execFileSync`/`spawnSync` against `swarm_handoff.bb`, launcher/stop paths)
  per fast-check iteration. `vitest.properties.config.mjs`'s `maxForks`/
  `--max-old-space-size` cap bounds Vitest's OWN fork-worker count and each
  worker's V8 heap (confirmed working correctly in isolation — this ticket's
  own `bl871PropertyLaneWorkerPoolCapInvariants.property.test.js` invariant-1
  synthetic-load property passes cleanly every run, including inside the
  acceptance run above). It does not and cannot bound the CPU real child
  processes spawned BY a worker consume — three workers each shelling out to
  real `git`/`bb` processes can still oversubscribe 4 real CPUs. That is a
  plausible mechanism for why subprocess-heavy files remain the flaky ones
  post-fix while pure-JS property files in the same run are consistently
  green. Worth checking whether `bl760`/`bl787`'s own per-test `testTimeout`
  needs raising independent of the pool fix, and/or whether subprocess-heavy
  property files need a smaller effective concurrency than pure-JS ones on
  this host size. Scope call for whoever picks this up — the current fix's
  wiring itself (invariant 2, no hardcoded numbers, shared budget module) is
  correct and not in question.
