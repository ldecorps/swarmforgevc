# BL-1749 — coder pass, 2026-09-26

## What was built

BL-877 scenario 7 ("a host with no working liveness facility says so") was
red on this Linux host: the "a host on which no liveness facility can be
reached" step (`bl877PortableProcessLivenessSteps.js` ~line 241) forced only
`SWARMFORGE_LSOF_BIN` unavailable, on the premise that `/proc` is already
absent on the project's own macOS dev/CI host. On Linux, `/proc` is real, so
`proc_fd_scan_lib.bb`'s `proc-root` fell through to it, `procfs-available?`
returned true, and the sweep logged an ordinary scan line instead of
"liveness could not be determined this pass".

Fix: the same step now also sets `SWARMFORGE_PROC_DIR` to a nonexistent
path, the seam `proc_fd_scan_lib.bb` already reads (`proc-root`,
~line 48). Both facilities are now forced unreachable on any host. No other
Given in scenario 7 re-points either env var: `ctx.forceUserland` is only
set by the (unused-in-this-scenario) "a host running the X userland" step,
so `rootLiveProcessIn`'s `SWARMFORGE_PROC_DIR`-setting branch is not
reached for this scenario.
