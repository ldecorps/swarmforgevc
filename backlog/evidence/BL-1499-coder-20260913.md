# BL-1499 — coder pass

## Scope

`swarmforge/scripts/test/test_handoffd_notify_verified.sh`'s fake `tmux`
keyed its `capture-pane` reply on a raw call count (first call = BEFORE,
every later call = AFTER). Since `36ae0a8e23` the startup-notify path reads
the pane twice before any typing happens (the busy gate, then
`notify-agent!`'s own pre-inject check), so the count-based fake handed the
second probe the AFTER content before anything was ever typed — case 02
read the untyped wake text as already-pending input and never typed at all
(`got 0`, expected 1).

Fix: the fake now keys its reply on whether a `send-keys` call has
happened, not on how many `capture-pane` calls have happened. `TYPED_FILE`
is `touch`ed the first time any `send-keys` invocation is seen (a literal
`-l` type OR a bare `C-m`/`C-j` submit) and removed by `run_notify` each
scenario. `capture-pane` returns `BEFORE_STDOUT_FILE` while `TYPED_FILE` is
absent, `AFTER_STDOUT_FILE` once it exists. `CAPTURE_COUNT_FILE` is dropped
entirely (no longer needed for anything, diagnostic or otherwise).

Keying on `send-keys` broadly rather than on `-l` alone (the ticket's own
"How" section names `-l` specifically) is a deliberate widening: cases
03/04 both set `stacked?` true in `agent_runtime_inject.bb`'s
`notify-agent!`, which SKIPS the literal-send step entirely and recovers
(or doesn't) purely via the submit loop's `C-m`/`C-j`. Keying only on `-l`
left `TYPED_FILE` never set for either case, so case 04's recovery (before
= stuck, after = idle, expected to clear via a plain Enter) could never see
the AFTER content and would time out reporting a false failure. Verified
this concretely: an `-l`-only fake passes cases 01/02/03/05 but fails case
04 exactly this way; broadening to any `send-keys` call passes all five
without changing case 02's or case 03's assertions (case 03's AFTER file is
a byte-for-byte copy of BEFORE, so it is insensitive to which trigger flips
the marker).

## Invariants (BL-654)

Two declared invariants, both about the shell fixture's fake-tmux behavior
wired to a real `bb`-spawned daemon over a real tmux socket file and
real-clock retry sleeps (`agent_runtime_inject.bb`'s 150-200ms per-attempt
delays) — process/timing behavior of a Babashka daemon subprocess, not a
pure JS/TS module. Per the shared testability boundary (live tmux/PTY is
explicitly the environmentally-unsuitable case named in
`engineering.prompt`/`local-engineering.prompt`), and per the Invariants
contract's own carve-out ("a declared invariant [that] quantifies over
prose or process rather than a pure, testable module"):

**No `*.property.test.js` authored for either invariant.** Reasons, stated
per invariant:

1. "The fixture's pane content is a function of what has been typed into
   the pane, never of how many times it has been read" — this is a claim
   about a `bash` heredoc script's own branching, not a JS module fast-check
   could drive in-process. A property harness for it would need to spawn
   the fake `tmux` binary itself under `extension/test/`, outside any repo
   convention for exercising shell fixtures from the properties lane, for a
   fixture whose sole consumer is this one shell test file. Encoded instead
   by exhaustive case coverage inside the shell file (5 scenarios covering
   every {stacked, not-stacked} x {recovers, doesn't} combination) plus the
   probe-count-independence check above, which is exactly the generalization
   a property test would otherwise explore (arbitrary N of pre-send reads).
2. "BL-093's verified-submit contract is unchanged on the lost-Enter path"
   — this restates BL-093's own existing contract, unchanged by this
   ticket's constraint (`agent_runtime_inject.bb` untouched, diff empty per
   above) and already covered by BL-093's original test cases (this same
   file, unmodified assertions) plus this pass's case-02 contract check.
   Nothing in this parcel could regress it without also failing an existing
   assertion in this same file.

**DEGRADED GATE**: this diff is a shell fixture, a Gherkin feature file
(already authored at mint), and a step handler. No mutation/CRAP/DRY
tooling is wired for shell (engineering.prompt, Startup Tools); shell has
none wired at all, matching this ticket's own `mutation_cost: low` note.
No mutation/CRAP/DRY result is claimed because none was run.
