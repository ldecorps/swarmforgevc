## Change
- `process_table_lib.bb`:
  - `orphaned-by-parent?` (pure) is orphaned when there is no parent, the parent is PID 1, the
    parent is dead, or the parent is the learned adopter.
  - `adopter-from-probe` (pure) learns nothing when the probe's parent is unreadable, is still
    its starter, or is the reading process itself. A process that is its own subreaper must
    never read its own children orphaned.
  - `orphan-adopter-pid` probes through the bounded `daemon-cycle-guard-lib/sh!`: `sh -c 'sleep
    30 ... & echo "$$ $!"'`, so the sleep is orphaned below this process. It reads the sleep's
    parent and kills the sleep.
  - The result is cached per process with the adopter's start instant. An adopter that exits,
    or whose pid is reused, is re-probed rather than trusted. That covers a long-lived reaper:
    the Relay /init exiting at 02:40Z is exactly that case.
  - `parent-orphaned?` probes only when the parent is live and not PID 1, so the common path
    costs nothing new. It is still the one definition, and the three callers are unchanged.
- `test/lib/orphan_wait.sh` (new) provides `wait_until_orphaned <scripts> <pid> [tries]
  [interval]`. One bb process polls `process-table-lib/parent-orphaned?` itself, with no bash
  re-derivation. It also requires the process to be alive: the predicate reads a vanished pid as
  orphaned, and a reap asserted over a process that already died would pass vacuously.
- `test_onboarder_supervisor_tick.sh` (1 wait) and `test_handoffd_supervisor_job_reaper.sh`
  (4 waits: 04, 06, 07, 08) call it instead of polling `ps -o ppid=` for 1. Their pass/fail
  labels are unchanged.
- Handler `specs/pipeline/steps/bl1907SubreaperOrphanSteps.js`:
  - Scenario 01: a Python fixture becomes a child subreaper (prctl 36), starts starter → target,
    and runs the real predicate on the target as its own child (a reaper shares its adopter only
    below the same subreaper). It asserts the fixture really made the row's parent shape, then
    kills every pid it started in a `finally`, never by pattern.
  - Scenario 02: each standing test runs under a subreaper wrapper that, like a real adopter,
    reaps each adopted child as it exits. A zombie still answers `kill -0`, so without that the
    tests' "reaped" checks never pass. The wrapper kills anything left by pid. The roots are
    `trackedTmpRoot`.
