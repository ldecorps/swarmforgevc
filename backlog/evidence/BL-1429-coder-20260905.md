# BL-1429 — coder pass, 2026-09-05 (bounce fix)

## Bounce being answered

`backlog/evidence/BL-1429-bounce-20260905.md` (architect, commit `80e7616e08`):
`describeChangeReason`'s clearing branch credited the standing-red signal
for a clearing whenever `prior.standingRed` was merely PRESENT, without
checking it was ever the BINDING (lower) cap — the active branch already
runs that comparison (`standingCap <= reworkCap`), but the clearing branch
only checked truthiness. So a severe rework diagnosis (cap 0, the true
binding cause) clearing alongside a co-active but non-binding standing-red
signal (cap 1) got its clearing misattributed to the standing-red signal,
violating declared invariant 2 ("logged with the signal that caused or
cleared it").

Architect's bounce reverted the whole parcel (coder `d584d435c5` + cleaner
`bcf7d823c9`) back to the pre-BL-1429 tree per Article 4.4 — this pass
re-implements from that base (coder's original design plus cleaner's DRY
extraction, both recovered from git history) with the fix in place, not a
patch on top of the reverted commit.

## What landed

- **`extension/src/tools/emit-throttle-recommendation.ts`**:
  `describeChangeReason`'s clearing branch now computes the PRIOR tick's
  own `reworkCap`/`standingCap` the same way the active branch computes
  the current tick's, and only credits standing-red when it was actually
  `<=` the prior rework cap (i.e. actually binding). Otherwise it falls
  through to the original generic "rework diagnosis cleared - restoring
  the configured cap" wording — unchanged from the pre-BL-1429 shape.
- **`extension/test/emitThrottleRecommendationStandingRed.test.js`**: new
  test "a clearing names the diagnosis that was actually binding, not a
  merely co-active signal" — reproduces the bounce's own measured
  counterexample (severe rework at cap 0 + standing-red count signal at
  cap 1, both clearing together) and asserts the log names the rework
  diagnosis, not the red count.
- Everything else (`standingRedSignal.ts`, its unit tests, the property
  test, the step handler, `swarmforge.conf`, and cleaner's
  `standingRedRegisterFixture.js` DRY extraction) restored unchanged from
  the original coder + cleaner commits (recovered via `git show
  <sha>:<path>` from the reverted history) — none of it was implicated in
  the bounce.
