# BL-1633 — coder, 2026-09-18

## What was wrong and what replaced it

The per-file budget gate (`checkFileDurationBudget`, BL-1598) refused an
unregistered file at or above 1.5x the 7000 ms budget using only the
in-suite duration read from `npm test`'s own JSON report — measured while
the file shares the host with the lane's 10-11 concurrent forks. The
hardener measured `extension/test/telegramFrontDeskBotCli.test.js` (3.7-5.0
s alone after BL-1620's cut) at 8.0-19.7 s in-suite across eight `npm test`
runs with zero code change, six of eight over the 1.5x refusal line
(`backlog/evidence/BL-1620-hardener-20260918.md`): the gate's verdict flips
with the fork pool's contention, not the code.

**Pattern that replaced it**: `checkFileDurationBudget` gains an optional
fifth argument, `confirmAlone?: (file: string) => number | null`. Every
would-be new-pole (unregistered, at or above the 1.5x refusal line) is
confirmed with one solo measurement before the gate refuses it:
- confirmed **under** budget alone → moved from `offenders` to a new
  `contention` verdict list (`{file, durationMs, aloneMs, budgetMs}`); the
  run **passes**, and both durations are named in the report.
- confirmed **at or over** budget alone, or the confirmer returns `null`
  (timeout/failure — never treated as evidence of contention) → stays an
  offender, refused exactly as before.
- No confirmation runs for a file that already has a register row, or
  sits below the refusal line; each candidate is confirmed at most once
  per run (`confirmOffendersAlone`, extracted alongside
  `classifyRegisterRows` for the same CRAP-gate reason BL-1598 already
  states).

`recordTestDuration.js` defines and exports `confirmPoleAlone(file)`: one
`vitest run --dir <dirname> <basename> --reporter=json --outputFile=<tmp>`
under the SAME project config `npm test` itself runs under (globals:true
etc.), `timeout: 3 * PER_FILE_DURATION_BUDGET_MS`. `main()`'s own call to
`runGuardAgainstReport` now passes it as the real confirmer — one seam,
one live consumer, never re-spawned a second way.

## A real bug this parcel's own verification caught

`confirmPoleAlone`'s first draft resolved a relative `file` argument
against `ROOT_DIR` (`extension/`). In REAL use `file` is whatever
`runGuardAgainstReport` already loaded into `durations` —
REPO-ROOT-relative (`extractFileDurations` relativizes against the
register's repo root, e.g. `extension/test/telegramFrontDeskBotCli.test.js`),
never extension-relative. Joining that against `ROOT_DIR` double-prefixed
the path into one that does not exist, so `--dir` silently found nothing,
`confirmPoleAlone` returned `null` for EVERY real candidate, and `null`
counts as "over budget alone" by the FIRM — the exact refusal this ticket
exists to prevent, just moved one level down. A live `npm test` run
(2026-09-18, host load ~10) reproduced it directly:

```
2 new-pole offender(s):
extension/test/emitLifecycleSnapshotCli.test.js: 11.5s exceeds the 7.0s per-file budget
extension/test/telegramFrontDeskBotCli.test.js: 11.7s exceeds the 7.0s per-file budget
```

— while a manual solo run of each file measured 5.6-5.8 s and 4.0-5.0 s,
both well under budget. Fixed by resolving against `REPO_ROOT_DIR`
(`path.join(ROOT_DIR, '..')`) instead; re-running the guard against the
SAME stored report with the fixed confirmer:

```
passed: true
contention: [
  {"file":"extension/test/emitLifecycleSnapshotCli.test.js","durationMs":11502.9,"aloneMs":5595.8,"budgetMs":7000,"kind":"contention"},
  {"file":"extension/test/telegramFrontDeskBotCli.test.js","durationMs":11704.1,"aloneMs":4251.3,"budgetMs":7000,"kind":"contention"}
]
```

A fresh `npm test` after the fix printed `suite file budget OK: 626
files, all within 7.0s` with both files reported as contention (info,
not failure) — confirmed by two independent real `npm test` runs.
