## D1 — how-to doc misdescribes the 429 retry as bounded; the shipped code is deliberately unbounded

1. **Failing command**: `grep -n "bounded retry" docs/how-to/GH-24-coordinator-activity-telegram-feed.md`
2. **Commit hash**: `718bd15071` (my own merge of documenter's `728d880562`
   onto QA's worktree; the doc text itself was introduced by documenter
   commit `f2b9e0df68`, unchanged since).
3. **First error excerpt**:
   ```
   docs/how-to/GH-24-coordinator-activity-telegram-feed.md:36:
   honoring 429 `retry_after` with a bounded retry. An idle tick posts
   ```
   vs. the shipped implementation
   (`swarmforge/scripts/coordinator_activity_feed_post_lib.bb:29-47`,
   `send-with-rate-limit-retry!`):
   ```
   (defn send-with-rate-limit-retry!
     "...Mirrors retryOnRateLimit's own for(;;) shape (BL-342) - the
      loop is deliberately unbounded here too, same reasoning: giving up is
      ...
      loop's job to also cap."
     ...
     (loop []
       ...
       (if-let [retry-after (extract-retry-after-seconds body)]
         (do (wait-seconds! retry-after) (recur))
   ```
   and the coder's own bounce-fix evidence
   (`backlog/evidence/GH-24-coder-bounce-fix-20260906.md`): "the retry loop
   itself is deliberately unbounded too, matching `retryOnRateLimit`'s own
   reasoning: giving up is exactly the failure this contract exists to
   close."
4. **Failure class**: `behavior` (a documentation claim contradicts the
   actual, deliberately-chosen shipped behavior — not a docs-currency gap,
   a factual misstatement of a load-bearing design decision).
5. **Expected vs observed**: Expected the how-to to describe the retry as
   unbounded on a 429 (matching the code, its own comment, and the coder's
   evidence, all three of which agree and were written by two different
   roles independently arriving at the same description). Observed the
   how-to instead says "a bounded retry" — the opposite behavior. An
   operator reading only the how-to would wrongly conclude the surfacer
   gives up and silently drops a trace after some retry count, when by
   design it never gives up on a 429 (relying only on the daemon's own
   60s subprocess timeout as the outer safety net, not a retry-count cap).

**Blamed role**: documenter (Article 4.3 — a defect entirely in docs/
prose, no code fix needed below it).

**Remediation pointer**: `docs/how-to/GH-24-coordinator-activity-telegram-feed.md`,
the "Cadence and posting" section, the sentence ending "...honoring 429
`retry_after` with a bounded retry." — replace "a bounded retry" with
language matching the actual unbounded-on-429/immediate-report-otherwise
shape (e.g. "an unbounded retry — matching BL-342's own reasoning that
giving up is exactly the failure this contract exists to close; a genuine,
non-429 failure is reported immediately, never retried").
