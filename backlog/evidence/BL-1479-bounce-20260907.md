# BL-1479 — architect bounce, 2026-09-07

## D1: `park-ticket!`'s rollback on a commit refusal does not actually roll
anything back — the staged `git mv` is left in the shared checkout's index

**Failing command**: N/A — a wiring/logic gap, not a failing existing test
(no test in `bl1479_parked_active_sweep_test_runner.bb` or the property
runner exercises `park-ticket!`'s post-`git mv` commit-refusal branch at
all — both only cover the pre-mutation "not a git checkout" refusal).
Reproduced directly against the real, compiled `chase_sweep_lib.bb`:

```
(load-file "swarmforge/scripts/chase_sweep_lib.bb")
;; ... mkdtemp git root, one active ticket committed, own-script-dir
;; pointed at a stub commit_integrity_cli.bb that always exits 1 ...
(chase-sweep-lib/park-ticket! root item)
;; => {:success false, :reason "commit_integrity_cli.bb refused: "}

$ git -C <root> status --short
R  backlog/active/BL-9999-x.yaml -> backlog/paused/BL-9999-x.yaml
```

The rename stays **staged** after the reported failure. Isolating just the
rollback line:

```
$ git mv a/f.txt b/f.txt
$ git checkout -- a/f.txt b/f.txt
error: pathspec 'a/f.txt' did not match any file(s) known to git
```

`git checkout -- <path>` (no commit-ish given) reads from the **index**,
not `HEAD`; after `git mv`, the index has no entry at all for the old
path, so the command errors immediately for the old path and never even
reaches undoing the new path's staged add. `park-ticket!`'s rollback line
(`land_step_lib.bb`-adjacent code, `swarmforge/scripts/chase_sweep_lib.bb`
~line 2350) never checks this command's own exit status, so the failure is
silent — the function still returns `{:success false :reason "commit_integrity_cli.bb refused: ..."}`
as if the world were unchanged, while the working tree and index both
still carry the half-done move.

**Commit tested**: `9edb25a4c3` (this hardening worktree's tip merged into
architect — the coder's own `d78f9213c6`).

**Failure class**: `behavior` — an unexercised failure path that does the
opposite of what its own docstring promises ("rolls the staged mv back...
never leaves a half-renamed ticket staged in the shared index").

**Expected vs observed**: Expected (the function's own docstring and
invariant 2 — "a park changes a ticket's directory and nothing else... one
rename commit... byte-identical") — on any commit refusal, the checkout is
left EXACTLY as it was before `park-ticket!` was called: no staged rename,
nothing to accidentally sweep into an unrelated later commit. Observed —
the checkout is left with a staged, uncommitted rename indefinitely (until
some other process notices and cleans it up by hand), on the shared
checkout every role/daemon on this project explicitly must never leave
dirty (engineering.prompt Guardrails; the workflow rule's own "Clean Up
After Yourself"). The scenario is not hypothetical: the docstring's own
named trigger — a lock/verify-mismatch from a concurrent writer — is
exactly the shared-checkout contention this project's own memory of
recent incidents (index-lock races, concurrent-commit collisions) shows
recurs in exactly this kind of high-frequency daemon sweep.

**Why every existing check missed it**: the unit runner's only
`park-ticket!` case (`test_runner.bb` "park-ticket!: refuses against a
non-git root rather than mutating anything") exercises the pre-mutation
guard, never a mutation followed by a refused commit. The property runner
tests only the pure decision functions (`parked-active-condition`,
`parked-active-items`), never `park-ticket!`'s own real-git-mutation path.
The acceptance feature's park scenario exercises the ordinary
commit-succeeds path only. No fixture anywhere makes
`commit_integrity_cli.bb` refuse after a successful `git mv`.

## Remediation (direction, not mandate)

The correct undo of a `git mv old new` that has not yet been committed is
`git reset -- old new` (unstage both sides back to their `HEAD` state)
followed by `git checkout -- old` (restore the old path's working-tree
content, now that it is unstaged and matches the index/HEAD again) and
removing the now-untracked `new` path from the working tree (`fs/delete`
or equivalent — after the reset it is no longer tracked, so a plain
`git checkout --` cannot remove it). Verify the fix the same way this
bounce did: `git status --short` reads completely clean after a forced
commit refusal, not merely "the function returned `{:success false}`".
Add a test (unit is enough; the property runner does not need to reach
into real git) that forces `commit_integrity_cli.bb` to fail after a real
`git mv` and asserts the checkout is clean afterward — the missing case
that let this ship.
