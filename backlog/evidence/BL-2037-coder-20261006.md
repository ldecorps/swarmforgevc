# BL-2037 coder evidence (2026-10-06)

## What changed

A local-model seat's context window is too small to read a ticket, find
what to change, change it and check it in one session. This slice adds the
per-parcel phase record and the one command that reads and moves it; the
seat's own serve/restart wiring is BL-2038.

- `swarmforge/scripts/local_seat_phase_lib.bb` (new): pure transitions only.
  - `initial-record` (`arrange`, 0 failed, no notes); `render`/`parse`
    round-trip the on-disk text (`phase: X`, `failed: N`, then one `===`-
    delimited block per note).
  - `end-move record to`: legal only arrange->{arrange,act,assert} and
    act->assert (`end-targets`); every other `to` is refused (`:ok false`),
    record untouched by the caller.
  - `fail-move record`: legal only from `assert`. Under 2 failed asserts:
    returns to `act`, counting the failure. At 2 already: moves nothing
    (`:split true`), still `:ok true` - the CLI still appends the note and
    prints the split request; this is the ticket's own designed outcome,
    not a refusal.
  - `pass-move record`: legal only from `assert`, to `done`.
  - `append-note`: the only way the `:notes` vector changes - a plain
    `conj`, called by the CLI once per successful (`:ok true`) move,
    including the split case.
- `swarmforge/scripts/local_seat_phase_cli.bb` (new): IO only (thin
  wrapper over the lib, engineering rule). Reads/writes
  `.swarmforge/phase/<ticket>.md` relative to the invoking cwd (the seat's
  worktree). `show`, `end --to <phase> --notes <file>`, `fail --notes
  <file>`, `pass --notes <file>`. A refused move prints the reason to
  stderr and exits 1 without touching the file; a legal move (including
  the split case) appends the notes file's text, writes the record, and
  prints `{"phase":...,"failed":...,"path":...}` JSON (or, for the split
  case, `SPLIT_REQUEST <ticket>` to stdout, exit 0).
- `specs/pipeline/steps/bl2037LocalSeatPhaseRecordSteps.js` (new): binds
  the feature, landed in the same parcel (required_wiring). Runs the real
  CLI with `spawnSync('bb', ...)` against a `trackedTmpRoot` fixture
  worktree; the outline's `<outcome>` maps to the real command through an
  explicit table (`OUTCOME_TO_ARGS`), never passthrough.

## Invariants (BL-654)

Both of the ticket's declared invariants get a coder-authored property
test, `extension/test/bl2037LocalSeatPhaseRecordInvariants.property.test.js`:

1. "A record moves only arrange to arrange, act or assert; act to assert;
   assert to act on a failed assert while fewer than 2 have failed; or
   assert to done on a passed assert. Any other move is refused and leaves
   the record unchanged."
2. "Notes are only ever appended: every note a phase wrote is still in the
   record, in order, after every later move."

Both run the REAL `local_seat_phase_lib.bb` via one batched `bb -e` call
(load-file dominates a bb invocation; one call per draw buys no extra
coverage) over 300 random (phase, failed-count, pre-existing notes, op)
draws. REACH: phase drawn uniformly over all four phases including the
terminal `done` (which admits no move at all); `end`'s `--to` drawn over
five values so both real targets and three illegal ones are hit for every
current phase; failed drawn 0-3 so the `>= max-failed` branch and its
boundary are both reached. Generator-reach floors (>= 3 draws per branch)
are asserted directly, not hoped for.

Non-vacuity PROVEN at authoring time, three breaks, each restored
byte-for-byte after confirming RED (see the property test file's own
header for the exact break/restore log):
- `end-targets`'s `"act"` entry emptied: invariant 1 failed immediately
  (an act->assert move the CLI depends on reported refused), and invariant
  2 failed too (no note appended on what should have been a legal move).
- `fail-move`'s `>=` changed to `>`: invariant 1 failed on the first
  failed=2 draw (the split-request case was reported as a real phase
  change to `act` instead of staying in `assert`).
- `append-note`'s `conj` replaced with a prepend: invariant 2 failed on
  the first multi-note record (the new note landed first, not last).

## Manual verification (CLI smoke, scratch dir, not part of the suite)

```
$ bb local_seat_phase_cli.bb show BL-9001
{"phase":"arrange","failed":0,"path":".swarmforge/phase/BL-9001.md"}
$ bb local_seat_phase_cli.bb end BL-9001 --to act --notes n1.txt
{"phase":"act","failed":0,...}
$ bb local_seat_phase_cli.bb end BL-9001 --to assert --notes n2.txt
{"phase":"assert","failed":0,...}
$ bb local_seat_phase_cli.bb fail BL-9001 --notes n3.txt        # failed 0->1, back to act
{"phase":"act","failed":1,...}
$ bb local_seat_phase_cli.bb pass BL-9001 --notes n3.txt        # illegal from act
local_seat_phase_cli.bb: cannot pass from phase "act"           # exit 1, record unchanged
... (end->assert, fail, end->assert, fail again at failed=2) ...
$ bb local_seat_phase_cli.bb fail BL-9001 --notes n8.txt
SPLIT_REQUEST BL-9001                                            # exit 0, stays assert, failed stays 2
$ cat .swarmforge/phase/BL-9001.md
phase: assert
failed: 2
===
note1
=== ... (every earlier note, in order, "f4" last)
```
