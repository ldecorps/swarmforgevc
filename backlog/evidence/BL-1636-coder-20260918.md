split into the invariant's two independently-testable halves:
- Half 1: a synthetic handler file is an offender iff it mkdtemps without a
  recognised registration, for any combination (not just the acceptance
  feature's two fixed fixture handlers).
- Half 2: a root is removed iff it is older than the floor AND has no live
  owner, for any combination of age (0-72h) and owner-pid presence/
  liveness (not just the three fixed examples).

Non-vacuity (checked by hand, documented in the file): removed the

check from the reap — half 2 failed on the `hasOwner=true, ownerAlive=true,
age>=24h` branch (a live owner's old root wrongly removed). Both reverted,
re-verified green.

## Self-audit finding, 2026-09-19 (no behavior change)

`swarm_handoff.sh`'s AUDIT_REQUIRED challenge on the first send prompted a
re-read against the ticket's own invariants. Found: `reap_stale_tmp_roots.js`'s
`OWNER_PID_PATTERN = /(\d+)-/` takes the LEFTMOST digit-run in a name as the
"owner pid" - for a legacy directory outside this ticket's own
`trackedTmpRoot` convention (e.g. `bl1031-dir-<rand>`, `bl968-materialized-
<rand>` - both real entries on this host today), that leftmost run is a
ticket number, not a pid, and if it happens to coincide with some other
currently-alive process's pid, the reap skips a root it could safely have
removed. Considered and rejected a stricter end-anchored match (pid
required immediately before the trailing 6-char mkdtemp suffix): caller
prefixes to `trackedTmpRoot` vary in descriptive length, so anchoring
would fail to recognise a genuinely long-lived, still-owned root whose
prefix carries extra text - which risks the opposite and far worse
failure, deleting something still alive. The committed heuristic only
ever errs toward KEEPING a root it is unsure about, the same posture
`tmpDir.js`'s `isZombiePid` doc comment already states for the unit
lane's own sweep ("errs toward keeping a root it is unsure about") -
never loosened here beyond what that precedent already accepts.
Real-host impact today: negligible - live pids sampled during this
session (hundreds to thirty-thousands) don't fall in the current
ticket-number band (~900-1650), so no observed false retention; documented
here (rather than silently missed) since ticket numbers will keep
growing into that same pid range over time. Added a matching code comment
at the pattern's definition. No test change - this is a documented
precision tradeoff on the reap script's legacy-population handling, not a
defect in anything this ticket's own scenarios or invariant cover (both
test only the unambiguous no-digit and self-pid shapes).
