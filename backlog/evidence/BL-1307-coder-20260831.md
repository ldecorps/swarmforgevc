# BL-1307 — coder pass, 2026-08-31

Ticket: a review-forward gate that asks whether the ROLE produced anything,
not only what the COMMIT looks like. Human ruling in force: **refuse the
send**, like BL-806 and BL-1293 (ruling option 1, `human_approval: approved`).

## What was built

- `swarmforge/scripts/review_forward_evidence_gate_lib.bb`
  - `evidence-dir` / `evidence-path-for-ticket?` — the same shape
    `task_scope_gate_lib/own-evidence-path?` already reads (evidence dir +
    basename prefixed with the ticket id and a hyphen). Matching is on the
    TASK id, never the role name, per the ticket's "Task, not role".
  - `forward-carries-own-evidence?` — did the range `received..forwarded` ADD
    an evidence file for this task. `true` / `false` / **`nil` = could not
    evaluate**. The third fs-touching function in the file; `blocked?` stays
    pure and takes the answer, exactly as it takes the other two facts.
  - `blocked?` — one new disjunct, `(false? carries-own-evidence?)`. Only an
    explicit false refuses; `nil` and absent leave the send alone.
  - `refusal-message` — a third branch naming the role, the task, the commit,
    `backlog/evidence/<ticket>-<role>-<date>.md`, that an explicit NONE is a
    legitimate pass, Article 4.4, and the `reroute_reason` way out.
- `swarmforge/scripts/swarm_handoff.bb` — the live send path computes the new
  fact and feeds `blocked?` and `refusal-message` the same way it already
  feeds `forward-introduces-nothing-own?`. This is the `required_wiring`
  anchor: `swarm_handoff.bb::review-forward-evidence-gate-lib/forward-carries-own-evidence?`.

## Fail-open shapes (invariant 2), all returning nil

No project root · blank received or forwarded commit · a task name carrying
no ticket id · a git invocation that cannot answer · an **empty diff between
the two trees** (which covers a forward naming the received commit itself:
BL-806 owns that shape with its own wording, and reporting "no evidence" for
an empty range would take the refusal away from the gate that can explain it).

## Invariants (BL-654) — both encoded, non-vacuity proven

Invariant 1 (a forward adds an evidence file naming the task; incidental
content never satisfies it) and invariant 2 (the gate never refuses a send
whose inputs it could not read) are encoded in
`review_forward_evidence_gate_lib_property_runner.bb`:

- the independent oracle `expected-blocked?` gained a freshly-stated
  `adds-no-own-evidence?` clause (not a copy of the gate's conjunction);
- a **by-construction** generator fixes sender/recipient/type to the gated
  hop, uses a DESCENDANT commit id with `introduces-nothing-own? false`, so
  neither older fact can explain a refusal in that space — only the new one
  can. Both verdicts are ASSERTED reached (`evidence-refused-reached`,
  `evidence-allowed-reached`), never hoped for;
- a live pre-fix mutant (`commit-facts-only-blocked?`) is kept in the file
  and asserted to DISAGREE with the real gate on the BL-1224 shape.

**Non-vacuity, run by hand at authoring time:** deleting the
`(false? carries-own-evidence?)` disjunct from `blocked?` turned the property
suite red (45 failures) and the unit suite red (2 failures). Both were
restored to the adopted implementation before this commit.

## One sibling fixture changed, and why

`specs/pipeline/steps/bl1293ReviewForwardOwnWorkSteps.js`, row *"carries the
role's own fix" → allowed*: its fixture built a fix commit with **no**
evidence file, which Article 4.4 forbids unconditionally and this gate now
refuses. The row's contract is unchanged — BL-1293 judges that the commit
CONTRIBUTED the role's work rather than merging silently — so the fixture now
commits the fix **and** its evidence file, which is what a real review pass
does. This is a fixture correction, not a contract change: the ticket's
`approval_context` settled that matching is on the evidence FILE and not on
"does the diff contain a real fix", precisely because a fix-or-evidence rule
would pass `b7d22b9ee3`, the commit this ticket exists to refuse.

## Operational note for downstream roles (not a defect)

From this commit on, every cleaner/architect/hardender/documenter forward and
every QA approval hop must ADD its Article 4.4 evidence file for the task in
the range it forwards, or `swarm_handoff.sh` refuses the send with the message
above. That is the approved behaviour (the stall is the point), and the way
out is to write the file — including an explicit committed NONE for a clean
sweep. The coder hop is unaffected (`review-roles` does not contain `coder`,
and a fresh task has no received commit to measure against).
