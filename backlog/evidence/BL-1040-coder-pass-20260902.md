## What was implemented

BL-983 declared invariant 3 ("seat identity never escapes the mailbox layer")
and enforced it only on the FORWARD path. This closes the OBSERVATION path,
at all three leaking layers the ticket names.

1. **Source — `swarmforge/scripts/pipeline_stage_cli.bb`.**
   `role-for-observation` now folds through `handoff-lib/seat-stage` on BOTH
   branches. The `:sent` branch folds too, which the ticket's rescued draft
   did not do: a parcel may be ADDRESSED to a seat, not only held by one, and
   that branch reads the `to` header. `compute-stage-map`'s `role-order` is
   now `(vec (distinct (map seat-stage ...)))`, so a multi-seat stage occupies
   exactly one position in the precedence order `reconcile-stage-entries` uses.
   Reused the existing `seat-stage` chokepoint rather than a fourth
   hand-rolled `indexOf('@')`, per the ticket's direction.

2. **Reader — `extension/src/swarm/swarmState.ts`.** New exported
   `stageOfSeat`, applied inside BOTH `normaliseBareRoleStage` and
   `normaliseObjectStage`. Folding at the reader chokepoint rather than only
   in `invertTicketStageToRoleHeldTickets` is what closes the STALE-FILE case
   (qa_e2e step 5): the stage map is a file on disk that outlives its
   producer, so a map written before the source fix must still read
   correctly. Source-normalisation and reader-fold cover different
   populations of map and are not alternatives — the ticket says so and the
   acceptance run proves it.

3. **Renderer — `extension/src/concierge/pipelineBoard.ts`.**
   `heldRoleByTicketId` folds a seat key onto its stage. `roleHeldTickets` is
   a plain record any producer can hand in, and this function's
   `ALL_SWARM_ROLES`-only iteration was precisely the layer at which a leaked
   seat matched nothing and fell to the not-started sentinel.

### A regression this pass caught and fixed before forwarding

The first renderer implementation iterated `Object.entries(roleHeldTickets)`
and computed precedence by rank. That is behaviourally correct for
precedence and still broke two existing tests: the Map's INSERTION order is
read downstream as the board's row order, and iterating ALL_SWARM_ROLES in
pipeline order was what produced it. Recorded because the defect is
invisible from the fold's own tests — the final shape keeps the pipeline
-order outer loop and collects each stage's ids from every key folding onto
it, preserving both the "most downstream wins" rule and the row order.

## Invariants (BL-654) — three declared, three encoded

`extension/test/bl1040SeatIdentityObservationPath.property.test.js`
(coder-authored, `npm run test:properties` only). 4 properties, 300 runs each.

- inv 1 — no seat id survives the reader chokepoint, the held-role
  inversion, or a board column.
- inv 2 — a multi-seat stage takes exactly one board column, however many
  seats it has.
- inv 3 — a ticket held by any seat is never rendered as not-started.
- inv 1+3 — folding never lets a seat outrank a more downstream stage.

**Generator reach, asserted not hoped for.** (a) Seat keys are CONSTRUCTED
(`<stage>@<suffix>`) by the transformation the code conflated, so every
arrangement is a leak candidate; a uniform draw over bare stage names would
reach a seat id never. Asserted floor `reached.seatKeys >= RUNS`. (b) The
precedence property DERIVES the second holder's ticket from the first's —
the same id under an upstream seat and a downstream bare stage — so every
generated pair is a collision candidate by construction, not by luck.

**Non-vacuity, demonstrated.** With the fold broken in both layers
(`const at = -1`), properties 1/2/3 FAIL and the precedence one passes (it
tests ranking, not folding). With the fold restored and the pipeline-order
iteration reversed instead, the precedence property FAILS and the other
three pass. Each property was shown to fail against a deliberately broken
implementation, then the implementation restored.

## Acceptance handler notes

The handler EXECUTES the real production path rather than asserting on
source text: the actual `pipeline_stage_cli.bb` over a real on-disk
roles.tsv/mailbox fixture, and the actual compiled `computePipelineBoard` /
`invertTicketStageToRoleHeldTickets`. The fault under review was a fold that
could read correctly and never be consulted, which is exactly what a
source-text assertion cannot tell apart from a wired one.

The Scenario Outline validates `<holder>` against an explicit
`KNOWN_HOLDERS` map and throws on an unknown value — no passthrough.

The precedence scenario observes "one position in the order" through the
behaviour the order exists for: a ticket held by BOTH a seat and a genuinely
downstream stage resolves to the downstream one and yields exactly ONE
entry, which a stage occupying two positions could not guarantee.
