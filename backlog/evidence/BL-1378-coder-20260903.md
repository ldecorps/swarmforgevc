## Decisions worth the reviewer's eye

- **The mailbox decides first and decides alone.** A store that cannot be read
  does not break a close the mailbox already approved. Invariant 1 says the
  normal path is exactly as it was, and an unrelated corrupt file taking the
  pipeline's own close route down would be a worse defect than the one this
  fixes. Pinned by shell check `02c`. Every scenario in the feature that pairs
  a store problem with a refusal also states that the mailbox holds no QA
  handoff, so this reading is the feature's own.
- **`:absent` is not `:problem`.** A swarm that has never run the expeditor has
  no store, and that is the ordinary state of the world: the mailbox answer
  stands and the reason remains `missing-qa-approval` (scenario 06).
- **A corrupt line poisons the whole store, even beside a record that would
  have matched.** A store that cannot be trusted either way must not hand out
  the half of itself that happens to parse — the same posture
  `is_qa_ancestor.sh` already takes.
- **An unanswerable ancestry question gets its own reason**
  (`expedite-ancestry-undeterminable`), not "not on main". Both `main` and
  `origin/main` are consulted because either can be the stale one (BL-891),
  and a yes from either is a yes.
- **An allowed close now names the path that approved it.** A close that went
  through on an expedite record rather than a QA mailbox handoff is a
  materially different event, and a reader who cannot tell them apart cannot
  audit either.

## Self-audit (Article 2.3)

Two findings in the fixture, both fixed before forwarding:

1. **Scenario 01 asserted the wrong sha.** The approved commit was read back
   *after* `close_it`, which makes its own commit and moves `HEAD` — so the
   assertion was about whatever `HEAD` became rather than the commit the
   record actually named. It is captured before the close now, and compared in
   full rather than truncated.
2. **A failed fixture `git mv` was silent.** The guard would then have been
   deciding about a move that never happened and every assertion in that case
   would have been about nothing. The helper now fails loudly.

Also re-checked rather than assumed: `validate-close-allowed` returning
`:details` on an ALLOWED close breaks no existing consumer (V4, V5, V6 all
green), and the store reader poisons on a corrupt line **across** files as
well as within one — a later corrupt file refuses even when an earlier file
already matched, which is the same code path the unit test pins.
