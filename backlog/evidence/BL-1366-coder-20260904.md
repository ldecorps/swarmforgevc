# BL-1366 — CODER PASS, 2026-09-04

`land_main_publish.sh` has stated the caller protocol in its own header since
BL-1144 — "acquire the land lock first, rematch if advised, then push FF-only
(never force). Residual races rematch at most once then wait on the lock" — and
nothing implemented it. QA retyped that sequence after every approval.

## What was built

A `--land <task> <commit> [<issue-ref>]` mode on that same script, so the
protocol lives where it is documented. It adds no new git behaviour: every
primitive already existed.

The sequence, and where each invariant is enforced:

1. **The entanglement verdict first, before the lock.** `LAND_ESCALATE` stops
   the land without even taking the lock — that judgement is QA's, and taking
   it here would be the tool deciding what to land (invariant 3).
   `LAND_REPLAY` lands the replayed commit it names; `LAND_CLEAN` lands the
   cited one.
2. **The lock, bounded.** A deadline rather than a spin, and a held lock is
   reported and left exactly as found — never broken open.
3. **Push FF-only, never `--force`.** A rejection buys exactly ONE rematch onto
   the current origin tip and one more push; a second rejection stops the land
   (invariant 1). There is no retry loop, because a wrapper that retries a
   rejected push is one bad branch away from reaching for `--force`.
4. **The lock is released by a trap** on EXIT/INT/TERM (invariant 2). The
   failures that left the lock held historically were never the paths anyone
   enumerated, which is exactly why this is a trap and not a list of `return`
   sites.
5. A `GH-` ref closes its issue through the existing `issue_done.sh`; without
   one, no issue call is attempted at all.

## Verification

- `test_bl1366_land_is_one_command.sh` (new, standing) — the ticket's six e2e
  steps against real repositories with real bare origins: a clean land reaching
  origin/main with no force and no lock left; a moved origin rematched exactly
  once with the other role's landing preserved; an escalation leaving
  origin/main byte-identical, reported, non-zero, lock released; a held lock
  waited to a deadline (4s measured) with nothing pushed and the other lock
  untouched; a land killed mid-sequence leaving no lock and the next land
  succeeding; and both issue cases. **ALL PASS.**
- Acceptance on the BL-1366 feature: **9/9.**
- Stability: **10/10** green after the fix below, and 9/10 + 10/10 in the two
  batches before it.

### Non-vacuity, one mutation per declared invariant

- reach for `--force` on a rejection → the rematch scenario fails.
- drop the release trap → "the lock was left held".
- push past `LAND_ESCALATE` → "an escalation still pushed".

## A false positive in my own test, worth recording

One red run reported "the suite touched the live repository". It had not: I was
comparing this repository's `main` SHA before and after, and **other roles land
on main while the suite runs**, so their legitimate work was being attributed
to my test. The check now asserts what this suite could actually break — the
origin URL, which nothing else rewrites mid-run — plus that no live remote
points into the fixture directory. A shared branch's SHA is not a property of
this test at all.
