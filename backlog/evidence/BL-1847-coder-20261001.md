# BL-1847 — coder pass, 2026-10-01

## What was built

- `swarmforge/scripts/coordinator_mail_relay_lib.bb` (new): the pure
  parcel-summarizing/batching core. `relay-line` builds one text line for
  a parsed parcel (sender, type, ticket id if the parcel names one via an
  injected `extract-ticket-id-fn` - the real
  `chase-sweep-lib/extract-ticket-id` at the live call site, never a copy
  of its pattern - the first line of its message text, and the parcel's
  own file name). `relay-text` batches a tick's lines into ONE Telegram
  message bounded at 4096 chars: when every line fits it returns them
  all; when they do not, it keeps as many LEADING lines as fit plus an
  "and N more" trailer and reports `:kept` so the caller moves only those
  parcels, leaving the rest in `inbox/new/` for the next tick. A single
  pathologically oversized line is still sent once rather than dropped.
- `swarmforge/scripts/handoffd.bb`: new `coordinator-mail-sweep!`,
  wired to run EVERY tick (alongside `poll-once!`/`canary-sweep!`, not
  gated to the ~10-cycle chase cadence — a relayed QA approval sitting
  unrelayed that long would delay the ticket close guard that reads it).
  On a pack declaring `config coordinator_mode deterministic`
  (`coordinator-config-lib/deterministic-coordinator?`, unchanged), it
  lists the coordinator's `inbox/new/*.handoff` files in filename order,
  parses each with the existing `parse-message`, builds one relay line
  per parcel, batches them via `relay-text`, and — ONLY after the outbox
  append (`telegram-reply-outbox.jsonl`, `threadId: OPERATOR`) returns —
  moves exactly the `:kept` parcels to `inbox/completed/` via the
  existing `move-with-collision` (a plain file move, never a rewrite).
  Logs `coordinator-mail-relayed <count>` on success,
  `coordinator-mail-relay-error <detail>` on an outbox-write failure
  (which leaves every parcel in `new/`, since the move loop is inside the
  same `try` as the `spit`). A new `--coordinator-mail-sweep-once` CLI
  flag gives the acceptance/property drivers one deterministic pass with
  no background process, same convention as `--sweep-once`/
  `--chase-sweep-once`/etc.
- `swarmforge/scripts/test/coordinator_mail_relay_lib_test_runner.bb`
  (new): unit cases for `relay-line` (message-header path, body-fallback
  path, git_handoff task/commit fallback, no-ticket-id case, first-line-
  only truncation) and `relay-text` (fits, empty, overflow with correct
  `:kept`/trailer, and the single-oversized-line edge case). Registered
  in `swarmforge/scripts/test/suite-manifest.tsv`.
- `specs/pipeline/steps/bl1847DeterministicCoordinatorMailSteps.js` (new)
  and `specs/pipeline/steps/lib/bl1847TicketCloseGuardCheckCli.bb` (new):
  the acceptance driver. Every scenario drives the REAL
  `bb handoffd.bb <root> --coordinator-mail-sweep-once` over a disposable
  mkdtemp fixture (only a coordinator roles.tsv row — the sweep never
  reads any other role's row — no git repo needed, since the sweep never
  shells to git). Scenario 04's "outbox cannot be written" is a path
  seam (a directory sits where the outbox file must be, so `spit` throws
  a real EISDIR), never chmod. Scenario 03 drives the REAL
  `ticket_close_guard_lib.bb/qa-approved-ticket?` through a tiny CLI
  wrapper, proving a relayed QA approval still satisfies the actual gate
  the close commit reads.
- `extension/test/bl1847CoordinatorMailRelayInvariants.property.test.js`
  (new): a coder-authored property test (BL-654) for invariants 1 (the
  successful-write half — every parcel a relay line was written for also
  moves, none left behind or duplicated) and 2 (byte-identical content),
  driving the REAL `bb handoffd.bb ... --coordinator-mail-sweep-once`
  over a generated batch of 1-6 parcels (random senders from the real
  census pool, random message text, half the draws by construction
  prefixed with a `BL-<digits>` ticket id and half not). Invariant 3 is
  the UNCHANGED `coordinator-config-lib/deterministic-coordinator?`
  predicate, already exhaustively property-tested by
  `bl1846CoordinatorModeInvariants.property.test.js` — re-encoding it
  here would be a duplicate of that test, not a second invariant, so
  this ticket's own acceptance scenario 05 covers that this sweep
  actually consults it, and the evidence records that as the stated
  reason (BL-654's own escape hatch). **Non-vacuous, verified by hand**
  against two deliberately broken predicates (see below).

## Invariants (ticket's `invariants:` list, BL-654 coder-first authorship)

1. "A coordinator parcel moves to completed only after its relay line is
   written to the operator outbox; a failed write leaves it in new
   mail." The FAILED-write half is proven end to end by acceptance
   scenario 04 (real unwritable-path fixture) and by inspection (the
   move loop is the second statement inside the SAME `try` whose first
   statement is the outbox `spit` — there is no other move site). The
   successful-write half (every written-for parcel actually moves, none
   duplicated or stranded) is encoded by the property test's generator.
   **Verified by hand**: changed the move loop's `(take kept parsed)` to
   `(take (dec kept) parsed)` — the property test failed immediately
   (one parcel never moved); reverted (clean diff after, confirmed via
   `git diff`/grep for the break), reran green. Also reran the
   acceptance feature after the same break: 2 of 5 scenarios failed;
   reverted, reran 5/5 green.
2. "The sweep never edits or deletes a parcel: the file in completed is
   byte-identical to the one that arrived." Encoded directly by the
   property test (byte comparison before/after) and by acceptance
   scenario 01's own explicit byte-for-byte assertion.
3. "A pack whose conf does not declare coordinator_mode deterministic
   keeps its coordinator mailbox exactly as today." Covered by
   acceptance scenario 05 (the real sweep, real non-deterministic conf,
   mailbox untouched) and, at the predicate level, by BL-1846's own
   already-exhaustive property test over the same unchanged
   `deterministic-coordinator?` function — no new encoding needed here
   (stated reason, BL-654).
