## D1 / D2 — the identity-root argument was DEAD in both `conf-file-path` branches (M6, M7)

The existing BL-966 fixtures cannot discriminate `identity-root` from `project-root`,
for two different reasons — and this is the "**check that the fixture has not already
satisfied the condition the test claims to prove**" shape:

- **Persisted branch**: the fixture persists an **absolute** conf path, and `java.nio`'s
  `Path/resolve` returns an absolute second argument verbatim — so the root argument is
  discarded before it can matter. The lib's own docstring says a **relative** persisted
  path is a supported case (the original launch cwd); no test covered it.
- **Fallback branch**: the fixture writes the default conf into **both** checkouts with
  the **same cap (3)**, so caller-root and identity-root name files that are
  indistinguishable by content.

Both new tests make the two roots disagree on **disk content**, which is the only thing
an assertion can see:

- a **relative** persisted path `swarmforge/packs/rel.conf`, cap **9** at master and cap
  **4** in the linked worktree → from the worktree the cap must be **9**, and
  `conf-file-path` must be rooted at master (compared canonicalized: `mk-tmp` hands back
  `/var/folders/…` while `resolve-identity-root` canonicalizes through macOS's
  `/var` → `/private/var` symlink, so a raw prefix test fails on spelling, not rooting);
- **no identity at all**, default conf cap **8** at master and **2** in the worktree →
  from the worktree the cap must be **8**, and the fall-through must still be loud.

Why this matters beyond the mutant: BL-966 exists to stop the cap splitting per checkout.
With either mutant live, a worktree silently reads its **own** copy of the conf — the
exact class of defect the ticket was written to close — while every test stayed green.

## D3 / D4 — two overlapping guards, no isolating test (M2, M3)

`resolve-identity-root` accepts the git result only when
`(and r (zero? (:exit r)) (not (str/blank? common)))`. Real git either succeeds **with**
output or fails **with none**, so every fixture satisfies **both** conditions at once and
deleting **either** survived — my own accepted rule of 2026-08-13 ("overlapping guards
each need an ISOLATING test") reproduced exactly.

Real git cannot produce the discriminating pairings, so the subprocess seam
(`daemon-cycle-guard-lib/sh!`) is stubbed per case — the guards are what is under test,
not git:

- **exit 0, blank stdout** → must fall back to the caller's own root (isolates the
  blank-output guard; kills M3);
- **exit 1, non-blank stdout** → must fall back to the caller's own root (isolates the
  exit-code guard; kills M2).

Each stubbed case uses a distinct root string, because `resolve-identity-root` memoizes
in a `defonce` atom that outlives an individual assertion.
