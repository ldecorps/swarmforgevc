# BL-1358 — CODER PASS, 2026-09-04

Human ruling honoured as recorded: **option 1** — a timed-out mutant fails the
gate the same as a surviving mutant — and a **300-second** ceiling.

## Where the ceiling went, and why there

`runGeneratedTests`' `spawnSync` in `specs/pipeline/runnerAdapter.js` IS the
unbounded wait. The ticket's direction ("the ceiling belongs where the wait is,
so the kill can actually reclaim the worker") is exactly right: bounding the
worker's readline loop instead would have left the spawned `node --test` child
running behind a freed worker.

## What changed

`specs/pipeline/runnerAdapter.js`

- `DEFAULT_MUTANT_TIMEOUT_MS = 300000` and `resolveMutantTimeoutMs`, which
  reads an explicit `opts.timeoutMs` first, then `GHERKIN_MUTATION_TIMEOUT_MS`.
  An unparseable or non-positive value falls back to the default rather than
  disabling the ceiling — "no ceiling" is the state this ticket ends, and a
  typo in an env var must not reach it again.
- The spawn now carries `timeout`, `killSignal: 'SIGKILL'` and
  `detached: true`, and on `ETIMEDOUT` the whole PROCESS GROUP is killed
  (`process.kill(-pid, 'SIGKILL')`). `detached` is what makes that possible:
  spawnSync's own timeout kills the direct child ONLY, so a mutant that shelled
  out to a bb tool or a bridge would leave those descendants running — the scar
  this repo already carries as `kill -KILL -- -PGID`.
- The return value gains `timedOut` and `timeoutMs`, and `success` is false on
  a timeout: a mutant that never finished was not PROVEN killed.

`specs/pipeline/mutationWorker.js`

- A timed-out mutant is reported as `infrastructure_error` with
  `timed_out: true` and an error naming the mutant and the ceiling it exceeded.

**Why `infrastructure_error` and not a new outcome string.** The vendored
gherkin-mutator is pinned and must not be modified, and it understands exactly
three outcomes. `infrastructure_error` lands in the summary's `Errors`, which
`gherkinMutationClassify.classifyOutcome` already fails the gate on
(`survived > 0 || errors > 0`). So the ruling's option 1 is satisfied with no
change to the classifier and no string the pinned tool would not understand,
while invariant 1 holds: the timeout is neither `test_failure` (which would
claim the tests DETECTED it) nor `test_success` (which would claim it survived
a test that actually ran).

## Known trade-off, recorded rather than discovered later

`detached: true` puts the mutant in its own process group, so a Ctrl-C to the
harness no longer propagates to it by group signal. The mutant is now bounded
by the ceiling instead of running forever, so this is strictly better than
before — but it is a real behaviour change and the reviewers should see it
named rather than infer it from a flag.

### Non-vacuity, proved in both directions

- Ceiling removed (`timeout:` dropped from the spawn): the acceptance run
  **hangs** — observed at 304 seconds before it was killed by hand, which is
  the defect itself reproduced, not merely a failing assertion.
- Ceiling kept but the timeout folded into `test_success` (the precise
  invariant-1 violation the ticket forbids): the property pass FAILS fast while
  the no-hang control stays green.

### One fixture trap worth the next reader's time

The first hanging fixture did not hang at all. `await new Promise(() => {})` is
cancelled by node:test as soon as the event loop drains ("Promise resolution is
still pending but the event loop has already resolved"), so the child exited in
milliseconds and every timeout assertion failed against a CORRECT
implementation. A live `setInterval` is what keeps the loop alive, and that is
the shape of every real hang the ticket names — including the incident's own
20ms poll loop. Both the unit and property fixtures say so in comments.

The process-group assertion also needed a BOUNDED wait rather than an immediate
read: SIGKILL delivery is not instantaneous. It polls to a 5s deadline — an
unbounded wait there would have been this ticket's own defect, in its test.

## One thing the next reader should know, surfaced not swept

No standing entry point runs `specs/pipeline/test/*.test.js`. I looked for one:
nothing in `package.json`, `run_bb_suite.sh`, `suite-manifest.tsv` (which covers
the bb tree only) or the pipeline's own scripts runs that directory, and the
files already there — `runnerAdapter.test.js`, `endToEnd.test.js`,
`cli.test.js` — are in the same position. This PREDATES this parcel and is not
its to fix, so it is surfaced rather than folded in.

It does not leave this ticket's tests unrun: the acceptance step handler drives
`node --test specs/pipeline/test/bl1358MutantTimeCeiling.test.js` directly, so
every case above runs whenever the BL-1358 feature runs — which is the gate QA
and the hardener already execute. The property pass runs in the standard
property lane.
