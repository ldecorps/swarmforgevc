# BL-878 — coder pass (2026-08-11)

Implements: setsid-free daemon spawn for the nine handoffd wiring tests
under `swarmforge/scripts/test/` that previously unguarded `setsid` -
absent on stock macOS, this host included (`command -v setsid` returns
nonzero here) - which silently dies inside the backgrounded spawn job and
reads as a `wait_for_log` timeout rather than a named missing-tool error.

## Changes

- `swarmforge/scripts/portable_daemon_spawn_lib.sh` (new): one shared
  `portable_spawn_daemon_or_fail <required-interpreter> <cmd...>` -
  `setsid` when present, `nohup ... >/dev/null 2>&1` fallback otherwise
  (BL-802's own shape, matching the in-suite precedent already correct at
  `test_handoffd_role_context_clear_skip_rotation_router.sh:65`), PLUS a
  loud, foreground, named failure when the required interpreter itself
  (`bb`) cannot be resolved - never let that die silently inside the
  background job either (invariant 2). Ten call sites across eight scripts
  now source this one file rather than repeating the guard inline, so the
  guard's semantics cannot drift between sites (ticket's own constraint).
- `swarmforge/scripts/test/test_portable_daemon_spawn_lib.sh` (new): my own
  focused unit coverage of the shared primitive in isolation (a trivial
  stand-in interpreter, not a real daemon) - setsid-present branch taken,
  setsid-absent/nohup-fallback branch taken, missing-interpreter fails
  loud/named/fast (<=5s, well under any `wait_for_log`-scale timeout).
  Verified non-vacuous: reverting the fallback to a bare unconditional
  `setsid "$@" &` fails scenario 2 exactly as expected; reverting the
  interpreter pre-check fails scenario 3 exactly as expected; both
  reverted back before commit.
- Ten call sites, eight scripts, guarded (`test_handoffd_answer_file_drain_wiring.sh`
  x2, `test_handoffd_dead_letter_notify_wiring.sh`, `test_handoffd_cooldown_sweep_wiring.sh`,
  `test_handoffd_pause_auto_resume_wiring.sh` x2, `test_handoffd_resource_sample_wiring.sh`,
  `test_handoffd_push_sweep_wiring.sh`, `test_handoffd_role_context_clear_wiring.sh`,
  `test_handoffd_stuck_escalation_email_wiring.sh`) - `env`/extra-env
  prefixes preserved exactly per site, only the trailing `setsid bb ...`
  replaced with `portable_spawn_daemon_or_fail bb ... bb ...`. Cleanup
  (`kill "$DAEMON_PID"`, both branches) left unchanged: this host's
  non-interactive scripts run with job control off, so a backgrounded
  child inherits the shell's own process group and is never already a
  process-group leader - `setsid` therefore execs in place rather than
  forking (ticket's own `$!` subtlety note), so `$!` is the daemon's real
  pid in both branches, matching what the already-shipped model script
  already relies on.
- `specs/features/BL-878-setsid-free-daemon-spawn-in-wiring-tests.feature`
  (promoted from `.feature.draft`, unchanged Gherkin - pre-existing, not
  authored this pass) + `specs/pipeline/steps/bl878SetsidFreeDaemonSpawnSteps.js`
  (new) + `specs/pipeline/steps/index.js` + the ticket YAML's `acceptance:`
  pointer flipped to the live path, same commit (BL-233, per the coder
  prompt amendment landed just ahead of this ticket in `91cea1f5e`). Step
  handlers drive a REAL `handoffd.bb` subprocess through the REAL shared
  library against a disposable fixture root, mirroring
  `bl877PortableProcessLivenessSteps.js`'s "stub the facility, not the
  assertion" convention: "setsid present" is reproduced via a small stub
  binary (`exec "$@"`) prepended to PATH even on this real setsid-less
  host; "setsid absent" is simply the ambient, unmodified PATH.

## A second, independent, pre-existing defect this pass exposed but did not fix

Fixing the setsid blocker let six of the nine target scripts run to
completion for the first time on this host, surfacing a SEPARATE bug in
`swarmforge/scripts/handoffd.bb` itself: `chase-sweep-every-cycles` (=10,
`poll-ms`=1000, so ~10s+ between gated firings, more when several
subprocess-spawning sibling sweeps run ahead of a given one in the same
gated cycle - confirmed empirically, cooldown-sweep! is LAST in that
chain) gates seven sweeps (`dead-letter-notify-sweep!`,
`resource-sample-sweep!`, `push-sweep!`, `fleet-status-sweep!`,
`answer-file-drain-sweep!`, `pause-auto-resume-sweep!`, `cooldown-sweep!`)
that BL-617's own comment (`decd25110`, 2026-07-24) claims "keep running
unconditionally" - they do not; they are textually nested inside the same
`(when (zero? (mod cycle chase-sweep-every-cycles)) ...)` gate as
chase/dispatch-gap/unassigned-active/open-slot. `test_handoffd_push_sweep_wiring.sh`'s
own pre-existing comment ("a blind `sleep 6` here can land before the next
tick ever fires ... a pre-existing flake, not introduced by BL-630")
already documented this exact race independently and already carries the
correct fix (`wait_for_log`-based polling instead of a fixed sleep) for
its own two affected assertions - it just was never applied to the other
five scripts. Out of BL-878's own scope (a production `handoffd.bb`
cadence question, not the setsid spawn mechanism), so NOT fixed here;
reported to the specifier as a candidate new ticket (see the coder's
outgoing `note`). What IS in scope and done: the five affected scripts'
OWN "fires more than once" assertions (unchanged assertion, unchanged
threshold) now poll via a `wait_for_count` helper mirroring
`push_sweep_wiring.sh`'s own established pattern, instead of a blind
`sleep 6`/`sleep 11` that this pass proved (bumping to `sleep 20`
manually first, before implementing the poll, to confirm root cause) is
too short and non-deterministic given the real per-gated-cycle cost. This
is a reliability fix to the WAIT mechanism only, in files already touched
for the setsid fix - it changes nothing about what is asserted, honoring
the ticket's own "behaviour of the nine scripts must not change"
constraint.

## Acceptance (BL-112)

`specs/pipeline/scripts/run_acceptance.sh specs/features/BL-878-setsid-free-daemon-spawn-in-wiring-tests.feature`:
5/5 scenarios pass (setsid-present and setsid-absent daemon-starts rows,
setsid-present and setsid-absent no-daemon-survives-cleanup rows,
missing-tool-fails-loud), run twice to confirm stability. One bug in my OWN
step-handler harness surfaced and was fixed along the way, not a defect in
the shipped fix: the first attempt drove the real spawn via Node's
`execFileSync` with piped stdio, which hangs forever once the daemon
successfully backgrounds - the setsid branch does not redirect its own
stdout/stderr (matching production), so the long-lived grandchild inherits
the same pipe `execFileSync` is waiting to see closed, and that pipe never
closes while the daemon is alive. Fixed by setting `stdio:
['ignore','ignore','ignore']` on the spawn call and redirecting only the
one line of stderr this feature needs to a file inside the script itself.
No leaked processes or fixture directories after either run (`ps`/`lsof`
scoped to each run's own mktemp path).

## Invariants (BL-654)

Babashka/shell is one of the two stacks with no property-test framework
wired (engineering.prompt's Testability Boundary - Bubble section
documents the same gap class for Android/JVM unit tests; no Babashka/bash
equivalent to `*.property.test.js`/fast-check exists in this repo - see
BL-877's own coder-pass evidence for the same posture). Per the coder
role's own instruction for this case, each declared invariant's
verification is recorded here instead of a property test:

1. "A test that backgrounds a daemon leaves no daemon running after its
   own cleanup, on a host with setsid and on a host without.": verified
   two ways - (a) `test_portable_daemon_spawn_lib.sh` scenarios 1/2 spawn
   a real trivial daemon-shaped process through each branch and confirm it
   is killable/no-longer-alive after; (b) every one of the nine wiring
   scripts' own `trap cleanup EXIT` (unchanged this pass) was confirmed to
   leave no `bb .../handoffd.bb` process behind, scoped to that run's own
   fixture ROOT, across all nine individual runs.
2. "A missing external tool makes a test fail immediately, naming the
   tool - never as a downstream wait-loop timeout that reads as a slow or
   flaky daemon.": verified by `test_portable_daemon_spawn_lib.sh`
   scenario 3 (nonzero exit, tool name present in stderr, <=5s elapsed -
   proven non-vacuous by reverting the pre-check and watching it fail) and
   independently by the acceptance feature's own scenario 3 against the
   REAL shared library and a REAL (synthetic-name) missing interpreter.
