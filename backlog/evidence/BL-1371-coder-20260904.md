## Load order — checked before assuming a glob is safe

Discovery loads in file-name order; the array's order was insertion order.
Two measurements, both over the real tree:

- **No unscoped pattern is registered by two different files.** 947 files,
  13892 definitions, 5275 distinct unscoped patterns, 0 registered by more
  than one file.
- **Resolution is unchanged for every concrete step in the suite.** Resolved
  all 18164 non-placeholder Given/When/Then texts in `specs/features/` against
  both registries, comparing the OWNING FILE of the matched handler:
  `{ checked: 18164, unresolved: 1968, diffs: 0 }` (the 1968 are unresolved
  under both orders — outline placeholders and prose lines).

So order does not matter today. Several handler files carry comments claiming
"registered earlier in DOMAINS, so it wins"; none of those claims is load-
bearing under the measurement above. Stated rather than glossed: nothing
enforces that this stays true, and BL-1277's collision guard (which now reads
its file list from discovery) is what would catch a future file that broke it.

## The trade, stated

The array was explicit and greppable, and a file joined the suite only when
someone added a line. Under discovery a half-finished handler on a branch
joins by existing. That is acceptable only because invariant 2 holds: a file
that throws when required fails the whole load, naming the file, and NOTHING
is registered — `registerDiscoveredSteps` completes the load before it
registers anything, so a broken handler can never leave a partial registry
that runs some scenarios green.

## What else had to move, and why

- `extension/src/tools/featureHandlerRegistrationCheck.ts` (BL-1303 guard):
  reachability is now seeded with every discovered `*Steps.js` file. Without
  this the guard would have refused EVERY commit on `main`, because index.js
  no longer contains the require lines it walked.
- The guard is NARROWED, not deleted (the ticket asked for a decision, not a
  side effect): "registration lost while the handler file survives" cannot
  recur; "a ticket-named handler the registry cannot reach" and "a reachable
  handler executing an absent sibling script" still can, and are still
  refused. Recorded in the guard's own header and the assessor's docstring.
- `extension/test/helpers/stepCollisionGuard.js` (BL-1277): took its file list
  from `require.cache` children of index.js — now asks discovery. The reason
  that helper avoided a directory glob still holds and is preserved: the
  `*Only.js` focused entry points re-export another file's `registerSteps`,
  and discovery excludes them by suffix.
- `extension/test/helpers/materializedRegistryGuard.js` (BL-968): `plantOffender`
  no longer patches index.js (planting the file IS registering it) and refuses
  a name discovery would not pick up; its load probe now CALLS `registerSteps`,
  because requiring index.js alone no longer loads a handler — without that the
  guard reported a clean load for a tree whose handlers cannot load at all.
- `specs/pipeline/steps/bl726...Steps.js` asked whether index.js contains a
  require line; it now asks discovery whether the handler is returned.
- Fixtures whose "unregistered" case relied on a handler being absent from the
  array now use a name discovery does not return: the BL-1303 unit, CLI,
  property and acceptance fixtures, `test_check_feature_handler_registration.sh`,
  and `land_step_lib_test_runner.bb`.
- `required_wiring` in the ticket YAML updated IN-PARCEL, as its mint note
  required: the old anchor named the deleted array.
