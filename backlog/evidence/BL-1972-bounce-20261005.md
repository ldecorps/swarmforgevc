## D1 - CONFIRMED - invariant violation: the check crashes every Stryker sandbox dry run

- **Class:** invariant-unencoded (the ticket's own FIRM invariant: "never
  stops a run whose out/ was compiled after its sources, a Stryker sandbox
  included").
- **Blamed:** coder (`a0b390f7e0`) - production logic in
  `extension/test/helpers/staleBuildGuard.js`, wired via
  `extension/test/helpers/bl1972StaleBuildGuardSetup.js` into
  `extension/vitest.config.mjs`'s `globalSetup` (inherited by every
  `vitest.*.stryker.config.mjs`).
- **Repro:** scoped `stryker.config.json` to `vitest.bl1972.stryker.config.mjs`
  (include: `test/emitCostHealthSidecarCli.test.js`) and `mutate:
  ["out/tools/briefingSnapshotArgs.js"]`, ran `npx stryker run --concurrency
  1` inside `extension/`. The dry run crashed before any mutant ran:
  `Error: [stale-build-guard] extension/out/ is stale: src/benchmark/aggregate.ts, ...`
  (every `.ts` under `src/` named, not one or two - the whole tree).
  Reverted the scoped config and deleted the scratch
  `vitest.bl1972.stryker.config.mjs` after capturing this; `git status` on
  `stryker.config.json` is clean.
- **Root cause (verified in Stryker's own source, not guessed):**
  `node_modules/@stryker-mutator/core/src/sandbox/sandbox.ts`'s
  `fillSandbox()` copies every project file into the sandbox with
  `Promise.all(... this.sandboxFile(name, file) ...)` - fully concurrent,
  one write syscall per file, no timestamp preservation. Confirmed on a
  leftover sandbox from the crashed run: `src/benchmark/aggregate.ts`
  landed at mtime `1791192499351.67` and its compiled
  `out/benchmark/aggregate.js` at `1791192499271.67` - the source copy won
  the race by 80ms, on a file whose REAL repo mtimes are the other way
  round (out/ compiled after src/, same as every other pair checked).
  This is not an occasional race on one file; it reproduced across all
  three pairs checked (`aggregate.ts`, `bridgeServer.ts`,
  `briefingSnapshotArgs.ts`) and crashed the dry run outright before a
  single mutant ran.
- **Why no fixture/isolation issue:** this is not a flaky host-load
  artifact (load avg 6-9 on 20 cores, well under the 2x-cores busy
  threshold) and not a stale `.stryker-tmp` cache (ran
  `ensureStrykerSandboxSiblings.js` first, and the dry run fails before
  Stryker even reaches a cached incremental result - it is the very FIRST
  dry run invocation). It reproduces on a fresh sandbox every time because
  the cause is structural: Stryker's sandbox copy has no mtime-ordering
  guarantee at all, by design (plain concurrent file writes), so an
  mtime-comparison check cannot distinguish "really stale" from "copied in
  the wrong order this time" inside any Stryker sandbox, ever.
- **What this means for the fix:** the check needs to recognize it is
  running inside a Stryker sandbox and skip entirely there (mtime ordering
  is unobservable in that environment, not merely untrustworthy some of the
  time) - not a tuning fix, not a tolerance window. A path-based check
  (the sandbox's own files live under `.stryker-tmp/sandbox-<id>/...`, this
  project's configured and default `tempDirName`) is the shape other
  accepted rules in this project already use to recognize
  `.stryker-tmp` as this project's sandbox marker; whether that is the
  right mechanism is the coder's call to make and test, not mine to
  patch in on a hardening pass (production logic, not test hardening).
- **Failure scenario:** any later hardener pass on any OTHER ticket that
  tries to run Stryker at all, anywhere in this repo, crashes on its very
  first dry run the moment `extension/vitest.config.mjs`'s globalSetup
  (merged to `main`) reaches it - a correctness gate that silently disables
  every future mutation-hardening pass project-wide.
