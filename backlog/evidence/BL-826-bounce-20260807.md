## D1 — correctness defect (class: behavior, blamed role: coder)

**Claim**: the re-arm poll's FIRST check runs at a coarser, inconsistent
sampling interval than every later check, creating a blind window in which
real, continuous reply-audio activity can go completely unobserved — letting
the mic arm having witnessed only a sliver of true silence instead of the
declared quiet tail. This threatens invariant 1
("No path arms the microphone while Bubble's own audio can still reach it")
in exactly the variable-TTS-tail scenario this ticket exists to fix.

**Where**: `TalkEngine.kt::scheduleHandsFreeListen` /
`TalkEngine.HandsFreeListenPoll`.

**Mechanism**:
- `scheduleHandsFreeListen(delayMs, followsPlayback)` schedules the FIRST
  poll tick at `mainHandler.postDelayed(r, delayMs)`, where `delayMs` is
  always `AudioTurnRecorder.HANDS_FREE_POST_SPEECH_MS` (400ms) for the
  `onPlaybackDone` call site — the one path where `followsPlayback` can be
  `true`.
- `HandsFreeListenPoll` only samples `replyPlayer.isAudioActive()` AT poll
  ticks. `lastAudioActivityAt` starts at `waitStartedAt` and is advanced
  **only** on a tick where `playbackActive` reads true. It is never updated
  between ticks, and the interval before the FIRST tick (400ms) is much
  wider than every subsequent poll interval
  (`HandsFreeReArmGate.DEFAULT_POLL_INTERVAL_MS` = 150ms).
- Concretely: if real reply audio plays continuously from `waitStartedAt`
  until, say, t=390ms, then stops, the first poll (t≈400ms) observes
  `isAudioActive() == false` (correctly — audio *has* stopped by then) and,
  since this is the first and only tick so far, never sets
  `lastAudioActivityAt` away from its initial value (`waitStartedAt` = 0).
  `HandsFreeReArmGate.decide()` then computes `quietFor = 400 - 0 = 400ms >=
  quietTailMs(400ms)` and returns `Arm("quiet tail elapsed uninterrupted")` —
  even though the real quiet tail since the actual last audio (t=390) was
  only ~10ms, not 400ms.
- This is a genuine regression risk specifically in the narrow band where
  the physical playback tail ends shortly before the first sample
  (roughly the 250-400ms range) — shorter tails already resolved correctly
  under the old fixed delay, and longer tails are now correctly detected and
  extended by the poll loop once observed. The two-tier cadence (400ms then
  150ms) is what creates this specific asymmetric blind spot; a uniform
  cadence from `waitStartedAt` would shrink it to the size of one
  `pollIntervalMs` (150ms) instead of `delayMs` (400ms).

**Why the existing tests don't catch it**: `HandsFreeReArmGateTest` supplies
`lastAudioActivityAt`/`playbackActive` directly to the pure `decide()`
function — it never exercises how `TalkEngine` derives those values from
real polling. `HandsFreeReArmGatePropertyTest`'s main sweep starts its
simulated poll loop's `now` at `waitStartedAt` itself and advances by
`decide()`'s own `recheckAtMs` from the first call — it models a UNIFORM
poll cadence, not production's two-tier one (a large `delayMs` gap before
the first tick, then `pollIntervalMs` after). Neither test can see this gap
because both bypass `TalkEngine`'s actual scheduling.

**Remediation pointer**: make the first poll tick fire at the same cadence
as every later one (e.g. schedule the first check at
`HandsFreeReArmGate.DEFAULT_POLL_INTERVAL_MS`, not at
`AudioTurnRecorder.HANDS_FREE_POST_SPEECH_MS`, for the `followsPlayback =
true` path — `decide()`'s own ceiling/ recheck timing already governs how
long the overall wait can run, so this doesn't need to change the steady-state
timing, only the granularity of the first sample). Add a test that exercises
`TalkEngine`'s actual scheduling (not just the pure `decide()` function) with
a fake clock/handler, asserting that reply audio active up to just before a
poll tick is not silently invisible to the next `decide()` call — a
regression test for this specific quantization gap. `followsPlayback = false`
call sites are unaffected (gate arms immediately regardless of cadence) and
need no change.
