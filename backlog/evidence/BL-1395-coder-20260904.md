# BL-1395 — coder evidence, 2026-09-04

Ticket: a landed daemon script is booted before it is published.

## What shipped

- **`swarmforge/scripts/check_bb_scripts_load.sh`** (new). For every
  `swarmforge/scripts/*.bb` the tree's own HEAD commit changed, `bb -e
  '(load-file …)'` runs from **the tree's own scripts dir** with
  `*command-line-args*` empty, so a script that `load-file`s siblings picks up
  that tree's siblings and not the checker's (invariant 3). A refusal names the
  file plus the line and symbol SCI itself reported. `--all` analyses every
  script; babashka missing is a **refusal, not a skip**.
  - The discriminator is babashka's error banner, **not the exit code**: most
    scripts here are CLIs that print usage and exit when run with no arguments
    — they loaded perfectly, and failing them would make the guard refuse a
    healthy tree (observed on the first run against `hardening_debt_ledger_read.bb`).
  - `handoffd.bb` is excluded from the plain probe and **booted** instead
    (invariant 2), against a per-invocation `mktemp` root stamped with its
    owner pid and removed in a `RETURN` trap — never a blind prefix sweep
    (BL-1385/BL-1390).
  - No `set -e`: each file's status is captured and the whole set reported, so
    one broken script never masks the next (BL-1242/BL-1252).
- **`swarmforge/scripts/handoffd.bb`**: the bare `(-main)` at the foot is now
  `(when (= *file* (System/getProperty "babashka.file")) (-main))`, the idiom
  every other script uses, and the `project-root` top level no longer calls the
  exiting `usage` when the file is merely loaded. A load-file probe is now a
  pure analysis probe.
- **Wiring** (all three anchors were absent at mint; grep now returns them):
  `run_commit_guards.sh` runs the guard through `run_guard` (so a hand-splice
  on `main` meets it), `land_step_lib.bb` lists it in the replayed-tree guard
  set (so a replay meets it), and `handoffd.bb` carries `babashka.file`.
- **`specs/pipeline/steps/bl1395DaemonBootedBeforePublishSteps.js`**: the
  handler, with a module-scope memo so the e2e runs once for the whole feature
  rather than once per step (BL-1390's concurrency lesson).

## Declared invariants (BL-654) — all three encoded, none by prose

`extension/test/bl1395BbScriptsLoadGuard.property.test.js`, runnable only via

Generator reach is **constructed, not hoped for**: the caller's body is derived
from the callee's name, so every wrongly-ordered pair is a real eager-analysis
failure rather than one the generator has to stumble onto. Invariant 2's
generator emits daemon shapes whose defect sits **after** the early-exit top
level — the one region a load-only probe can never reach — and the test
**asserts** that non-vacuity in-line: it first proves a plain `load-file` sees
nothing wrong with the fixture, so a pass could only come from a guard that
actually boots. Each property also asserts the healthy mirror, because a guard
that refuses everything proves nothing.

## A second defect: my own test harness committed onto a live branch

The first attempt to commit this ticket failed with `cannot lock ref 'HEAD'`,
and the branch had gained a commit named `seed`. Cause, reproduced and then
fixed: git exports `GIT_DIR` and `GIT_INDEX_FILE` to its hooks, the commit
guard chain runs the changed-path gate, and that gate ran this ticket's new e2e
suite - whose fixture builder does `git init` + `add -A` + `commit -qm seed`.
Under an inherited `GIT_DIR` those act on the CALLER's repository, so the
fixture's commit landed on the live branch. Repaired with `git reset --mixed`
back to the merge commit; no work was lost and nothing was pushed.

Fixed in three places, and I checked which one was actually to blame rather
than assuming: the e2e suite and the property fixtures now `unset` the git
environment (they are the culprits - a pre-fix probe confirms the leak, and the
post-fix run leaves an ambient decoy repository untouched), and the guard
itself routes every git call through `git_clean`. The guard was NOT the
culprit - a pre-fix probe leaves the decoy alone - but its scrub is load
bearing for a different reason: under a leaked `GIT_DIR`, `git -C "$TREE_ROOT"
show HEAD` would list the CHECKER's changed files rather than the tree's,
inverting invariant 3 on the land-replay path.

Regression coverage: e2e checks 4b (the verdict still follows the tree under a
leaked `GIT_DIR`, and the leaked repository gains no commit) and the same pair
inside the invariant-3 property, against a decoy repository carrying pending
content - which is what the live incident needed to show itself.

## The property test found a real defect in the guard

Invariant 2 failed on its first run. The boot step accepted the daemon as
healthy when its output contained the marker `sweep-once done` — and babashka
**echoes the offending source in its `Context` block**, so a daemon whose last
line is `(println "sweep-once done")` prints the success marker *inside its own
analysis error report*. A marker-only check reads that as a healthy boot: the
exact false green this ticket exists to close, reproduced inside the guard
itself. Fixed by making an analysis banner a refusal whatever else the output
holds, ordered ahead of the marker check. Kept as e2e check 3b so it cannot
come back.
