## What changed

`swarmforge/scripts/check_property_suite_drift.sh` only. The suite run is
still captured to a `mktemp` file and still echoed to stderr; what changed is
that the file now outlives the read into `$OUT` (its removal moved onto the
EXIT trap the script already runs on every path, `on_interrupt`'s explicit
exit included), and the refusal path copies it aside before exiting 1.

- Retention dir: `$REPO_ROOT/.swarmforge/property-guard-refusals/` — the
  established home for local, gitignored runtime state, as the ticket's
  "How (direction, not mandate)" suggests.
- One file per refusal, `refusal-%06d-<UTC stamp>.log`. The index is derived
  from the names already in the directory, **not** from a clock: two refusals
  inside the same second must still order the way they happened, and
  `date +%N` does not exist on stock macOS (engineering.prompt targets
  /bin/bash 3.2). Pruning always keeps the newest, so the highest surviving
  index only ever grows.
- The refusal now prints
  `property-suite-guard: refusal output retained at <abs path>`.
- Bounded at 20 by default, `SWARMFORGE_PROPERTY_GUARD_REFUSAL_KEEP` for
  tests. That seam changes only how many logs are kept — never whether a
  commit is refused, and it is not a `*_FORCE_RESULT`-style bypass.
- The directory writes its own `.gitignore` containing `*`, so it is
  self-ignoring. Invariant 2 then holds **by construction** rather than by
  the surrounding checkout happening to carry a `.swarmforge/` rule.

Nothing about WHICH reds refuse, the reds themselves, or the exit codes was
touched — the three things the ticket puts out of scope.

## Declared invariants (BL-654)

Both declared invariants have a coder-authored executable property test in
the same parcel; neither needed a stated-reason exemption.

**Invariant 1** — a refusal retains this run's full output and names where.
Generator draws 1-4 real-shaped `FAIL <file>.property.test.js > <body>` lines
plus a deliberate 0-60KB pad. The pad is the generator-reach mechanism: an
arbitrary string generator essentially never draws kilobytes, and the
kilobyte case is the one the ticket was filed about (the 53KB
`properties.log` of 2026-08-22). Asserted reachability floor: at least one
run >16KB and at least one multi-line body, or the test fails on the floor
rather than passing vacuously. The assertion compares the retained file to
the injected body in full — a head/tail of the run would not satisfy it.

**Invariant 2** — nothing retained is ever commitable. Generator varies the
number of refusals (1-6), the bound (2-4) and **whether the fixture repo
carries a `.swarmforge/` ignore rule at all**. Floors asserted on all three:
at least one run over the bound, one under, and one in a tree with no ignore
rule. Beyond comparing `git status --porcelain` before and after, it runs
`git add -A` — the way a retained log would actually reach a commit — and
requires the status still be byte-identical.

### Non-vacuity, demonstrated then restored

- Invariant 1: retained the log but suppressed the "retained at" line →
  `AssertionError: the refusal named no retained-output path`. Invariant 2
  still passed, so the two are independent.
- Invariant 2: removed the self-ignoring `.gitignore`, leaving everything
  else intact → `AssertionError: retention changed what git sees in the
  working tree`, on the generated case with no outer ignore rule. Invariant 1
  still passed.
- Recorded honestly: the failing assertion in the second case is the
  `--porcelain` comparison, which fires before the `git add -A` clause for
  that defect. The `add -A` clause is the stronger teeth and is exercised on
  every passing run; it was not itself the first to fail.
- The script was restored and diffed byte-identical against the pre-break
  copy before committing; no `deliberately broken` marker remains.

## Self-audit finding, fixed before forwarding

The handoff self-audit caught one real defect in the first commit
(`f782498bed`), fixed in the follow-up commit on this branch.

`prune_refusal_logs` collected the log names into a bash array and expanded
`${#names[@]}` / `"${names[@]}"` over it. That array is legitimately EMPTY on
the common path (a first refusal, or any run under the bound), and an empty
array expansion under `set -u` is the BL-801 shape that breaks on the stock
macOS `/bin/bash` 3.2 engineering.prompt names as the target — a platform
this Linux host cannot exercise, so the green suite here was not evidence
either way.

The array bought nothing: the names carry a zero-padded index, so the glob is
already creation order. The function now counts with the glob and walks it
directly — no array, no `sort` subshell, one fewer moving part. Verified
directly under `bash -uo pipefail` against an empty directory.

Re-verified after the fix: shell suite 13/13, acceptance 4/4, property tests
2/2, BL-1202 4/4.
