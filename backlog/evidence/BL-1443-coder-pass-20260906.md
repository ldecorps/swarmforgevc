## What was implemented

1. `extension/test/helpers/tolerantTreeWalk.js` — `walkFilesTolerant(root, {
   excludeDirs, extension, withContent, encoding, fsImpl })`. Only the
   CONTENT READ (`readFileSync`) tolerates `ENOENT` (the file was listed,
   then removed before being read) and is skipped rather than thrown; any
   other read failure (`EACCES`, `EISDIR`, ...) throws, carrying the
   original error's `.path`/`.code`. Directory listing (`readdirSync`) is
   never wrapped — a vanished subdirectory is a listing error and throws,
   same as any other unexpected failure. Default exclusion set is bl874's
   own `EXCLUDED_DIR_NAMES`. `fsImpl` is the seam (never `chmod`, per the
   engineering rule against chmod-based failure simulation).

2. Nine property files carry an inline `readdirSync`-based recursive walk
   today (`grep -lE 'function walk|walk\(' extension/test/*.property.test.js`).
   Classified by what each one actually walks:

   | File | Walks | In scope? |
   |---|---|---|
   | `bl874PortableTimeInvariants.property.test.js` | `REPO_ROOT` (whole repo) | **Yes — required_wiring anchor** |
   | `tempDirTrapGuard.property.test.js` | `REPO_ROOT` (whole repo, byte-identical `findFunctionDefinitionFiles` shape to bl874's) | **Yes** |
   | `bl1060TelegramButtonUrlScheme.property.test.js` | `extension/out`, `extension/src` (live, non-fixture trees) | **Yes** |

4. `extension/test/bl1443TolerantTreeWalkInvariants.property.test.js` —
   coder-authored, one test per declared invariant (BL-654):
   - inv 1: generates 1-6 file trees (flat or one level nested), picks a
     random target file, and either makes it vanish (via the same
     `readdirSync`-spy shape as the acceptance scenario) or fails its read
     with a random non-ENOENT code (`EACCES`/`EISDIR`/`EPERM`); asserts the
     vanished case completes and excludes only that file, and the failing
     case throws naming that exact path and code.
   - inv 2: snapshots the walked tree's full path→content map before and
     after a read-only walk (an `fsImpl` exposing only `readdirSync`/
     `readFileSync` — no write-shaped method exists to call even by
     accident) and asserts it is unchanged; also builds a sibling directory
     sharing a NAME PREFIX with the walked root and asserts it is
     untouched — "never sweeps by prefix" (BL-1385/BL-1390), asserted, not
     assumed.
   Both confirmed **non-vacuous**: inv 1 was broken by swallowing every
   read error regardless of code (the EACCES/EISDIR case then failed —
   "expected the walk to fail... but it completed"), and inv 2 was broken
   by having the helper write a stray file into the walked root (the
   snapshot diff then failed, naming the stray file). Both reverted after
   confirming the red.
