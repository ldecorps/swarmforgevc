## What landed

`docs/how-to/BL-1320-add-or-remove-a-seat-of-a-bottleneck-stage.md`, covering
exactly what the ticket's "Wanted" list names and nothing more:

- the `window <stage>@<seat> …` line that adds a second seat, field by field,
  with its own worktree, model and tier — and the removal step, which is
  deleting that one line and nothing else;

  quoting the refusal `parse_config` actually prints;

  needs a `hard` seat, because above-tier work never lands on a lower-tier seat

  restating it.

## The page is executed, not asserted

The ticket's whole reason for wanting scenarios is that a prose-only how-to
rots silently. So `specs/pipeline/steps/bl1320SeatOperatorStepSteps.js`
extracts the window lines **from the page** and runs them through the REAL
parser — `source swarmforge.sh; parse_config`, the same harness
`test_coordinator_config_pack_override.sh` already uses. Nothing launches a
swarm: `parse_config` stops at the parse, which is both what the scenarios are
about and the only safe way to run this from an agent worktree.

The bare-seat scenario does the same in the negative: it builds a pack with the
extra seat and no bare seat, confirms the parser REFUSES, and confirms the page
quotes the refusal the parser actually prints. The tier scenario runs the
steward command the page prints against the real CLI, so a renamed subcommand
fails here instead of misleading an operator.
