# BL-1446 — coder pass, 2026-09-07

## What was wrong (recap)

`land_step_lib.bb`'s `land-plan` (BL-1432) bounded the attribution walk to
`walk-base` (the task's last recorded handoff commit). That boundary is
right for the send-time scope gate; wrong for the land step, twice:

1. `entangled-siblings`'s candidate walk (`ancestry-commits root walk-base
   commit`) never excluded anything reachable from `origin-main`, so a
   routine post-hop `git merge origin/main` pulled already-landed history
   into `walk-base..commit` and it was misread as a candidate sibling -
   `land-plan` returns `:replay` whenever `:entangled` is non-empty, even
   when every member is `:landed`.
2. `own-paths`/`delivered-attribution` were bounded to the SAME `walk-base`
   (via `(or walk-base origin-main)`), so a replay's own-path set held only
   the commits after the last hop - the coder/cleaner/architect/hardener
   work before it was silently dropped from the replay.

## Implementation

`swarmforge/scripts/land_step_lib.bb`:

- `ancestry-commits`: new optional 4th arg `exclude-also` - `git rev-list
  commit ^base ^exclude-also` instead of `base..commit`, so a caller can
  bound the walk to `base` (performance) while STILL excluding anything
  reachable from a second boundary.
- `entangled-siblings`: passes `origin-main` as that 4th arg on its own
  internal candidate walk - a commit already reachable from `origin-main`
  is never a candidate sibling, whatever `walk-base` is (invariant 1). The
  candidate walk itself stays bounded to `walk-base` (BL-1432's own cost
  profile, paid on every land, is unchanged).
- `own-paths` (8-arg arity) and `land-plan`'s own `attribution` delay: both
  now read `full-delivered-paths`/`delivered-attribution` from
  `origin-main`, never `walk-base` - restoring `own-paths`'s own
  pre-BL-1432 docstring ("this ticket's own changed paths since
  origin/main"). `walk-base` is still accepted as a parameter for
  arity/call-site compatibility with `land-plan` but is no longer read as
  a diff boundary. This only runs on the rare `:replay` path (never forced
  when `entangled` is empty, the common `:land` case), so widening it back
  to `origin-main` does not reintroduce BL-1432's original per-land cost.

## Invariants (BL-654) — stated reason, no property test (all three)

All three declared invariants quantify over `land_step_lib.bb`'s own git
ancestry-walk behaviour (`ancestry-commits`, `entangled-siblings`,
`land-plan`) - a Babashka mechanism that shells out to real `git` over a
constructed repository, not a pure, testable JS module `test:properties`'
fast-check generators could drive. Per the Startup Tools rule ("Babashka/
Clojure... have NO mutation/CRAP/DRY wired... gated only by their own
unit-test suite") this file's own gate is
`land_step_lib_test_runner.bb`, not the JS property lane - the same
carve-out BL-1448's own evidence used for its shell fixture, and the
established pattern this codebase already uses for `land_step_lib.bb`
specifically (`bl1431_one_land_plan_one_tip_property_runner.bb` and its
five siblings are Babashka-native generative checks, never
`*.property.test.js` files).

- **Invariant 1** (a commit reachable from origin/main is never a candidate
  sibling, whatever the walk base) is exercised directly by scenario 01 and
  scenario 03 (syncs 1, 2): each proven non-vacuous above.
- **Invariant 2** (the bounded walk's verdict and own-paths equal the wide
  walk's) is exercised directly by scenario 03's own three Outline rows
  (0, 1, 2 syncs) plus scenario 01's "wide walk agrees" assertion - the
  ticket's own boundary examples, all four non-vacuous.
- **Invariant 3** (the candidate walk still visits only the parcel's own
  commits) is unchanged by this fix - `walk-base` still bounds the
  candidate walk exactly as BL-1432 left it, only the extra `origin-main`
  exclusion is new - and is exercised by BL-1432's own pre-existing
  regression tests in the same file (`land-plan (no :base): the old
  parcel's commit is misread as an entangled sibling` /
  `land-plan :base - the SAME tip, bounded, sees nothing before base`),
  both still passing unmodified.

## Notes for the next role

- The ticket's own "How" text says the acceptance handler "drives the same
  fixture through `land_step_cli.bb`" (direction, not mandate). This
  handler instead calls `land-step-lib/land-plan`/`replay!` directly via
  `bb -e`, matching the sibling ticket's own precedent
  (`bl1432LandWalkRangesOverTheParcelSteps.js`) exactly - `land_step_cli.bb`
  has no flag to force the "wide" `:base`, and adding one would be new CLI
  surface this ticket never asked for. The real CLI entry point IS still
  exercised, separately: the "real incident, rebuilt from the actual
  commits" verification above runs `land_step_cli.bb` directly against a
  throwaway clone of this repository.
- `own-paths`'s 8-arg arity still accepts `walk-base` as a parameter for
  call-site compatibility with `land-plan` (which still threads it through)
  but no longer reads it for the diff boundary - flagged in a code comment
  at both read sites removed.
- A test-fixture-only hazard, not a production one: writing `.swarmforge/`
  content via `spit` into a fixture whose `commit!` helper runs `git add
  -A` risks that content being swept into an unrelated line's commit and
  then deleted by a later checkout back. Both the babashka test runner's
  `record-handoff!` and the new acceptance handler's `recordHandoff`
  exclude `.swarmforge/` via `.git/info/exclude` for exactly this reason -
  worth keeping in mind for any future `land_step_lib.bb` fixture that
  seeds the handoff archive.
