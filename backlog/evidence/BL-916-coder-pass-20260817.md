## Invariants (BL-654)

The ticket declares two invariants. Neither gets a coder-authored
`*.property.test.js` — both admit no executable encoding in that lane, for
the reason stated per-invariant below (per the coder prompt's Invariants
section: "record a stated reason in the parcel instead of a test").

1. **"The overlay service never starts the Talk panel activity directly...
   because a background start of a non-exported dialog activity is exactly
   what the platform drops after a cold start."**

   This quantifies over Android component wiring (`Intent`, `Activity`
   classes — real `android.*` types in the relevant signatures), not a pure,
   testable JS/TS module. Per BL-769, Bubble has no property-test lane at
   all — only plain-JUnit pure-logic and a recorded manual procedure for
   device-surface behaviour, and this invariant is squarely device-surface
   (which component a running `Service` starts, and how the platform treats
   that start after a cold start with no foreground activity). No JVM
   pure-logic seam exists for "which activity does this PendingIntent
   target" either — it is Kotlin source structure, not a computable
   function. The closest executable encoding is what Scenario 01's own
   structural guard already does — pins `openTalkPanel()` to target
   `MainActivity` and never name `TalkPanelActivity` — which is exactly the
   negative-space half of this invariant, checked on every acceptance run.
   The positive half (a background start of `TalkPanelActivity` is actually
   dropped by the platform) is unreachable outside a real device, so it is
   covered only by the ticket's `qa_e2e_procedure` step 2.

2. **"No fix for one freeze reintroduces another... each is only observable
   as 'the bubble is frozen'."**

   This is explicitly a process/prose invariant over three independently-
   observable device freeze modes that all present identically to the user
   — not a property of any single pure module. There is no generator to
   construct here (there is nothing to sample; the three freezes are three
   fixed, already-diagnosed defects, not a state space). The regression net
   for this invariant is the combination of all five acceptance guards added
   this pass (scenario 01 guards the cold-start freeze, 02 guards the
   trampoline target staying launchable, 03 guards the splash freeze, 04
   guards the panel-dismiss freeze, 05 guards the same splash freeze's theme
   config) plus `qa_e2e_procedure` steps 2-4, which the ticket requires be
   run together in one device pass specifically so a fix for one freeze that
   silently reintroduces another cannot be missed by only checking the freeze
   currently being worked on.
