## The re-measured overhead (qa_e2e item 3's own basis)

BL-1801's own 105,000-character measurement was qwen's UNSCOPED default
(28 tools) - already over a 32768-token window with no prompt at all.
Re-measured live with the six-tool `.qwen/settings.json` in place, same
method (a loopback fake OpenAI-compat endpoint, node http, capturing the
first request body; `qwen --auth-type openai -y -m test -p "<63-char
marker>"`, confirmed `qwen --version` 0.22.2), but under the **real
operator HOME** this time (per the ticket's own instruction - that is
what a seat actually runs with, not a clean temp HOME):

- `tools` array: 6 entries (`edit`, `glob`, `grep_search`, `read_file`,
  `run_shell_command`, `write_file`) - confirms the settings file was
  honoured, not merely present; 14,522 characters.
- `messages` (system prompt + qwen's own injected system-reminder
  blocks), marker text excluded: 34,847 − 63 = 34,784 characters.
- **Total: 49,306 characters.**

This host's real `~/.qwen` carries fewer skills/memories than whatever
host the ticket's own mint measurement ran on (its clean-HOME baseline
for this same six-tool settings shape read 51,727) - real-HOME overhead
is environment-dependent, which is exactly why the constant needs a
safety margin rather than either raw number verbatim. Set to **55,000**,
above both measurements, and matching the ticket's own illustrative
figure ("At 55,000 characters of overhead plus the coder's compact card
... the first turn is about 21,100 tokens") - confirmed live: the
acceptance run's own gate output for an 8,192-character prompt file
reads `WARN: ... (21064 tokens) is more than half its 32768-token
window`, not a refusal.

No live Ollama is running in this sandbox (`ollama serve` unreachable),
so `qa_e2e_procedure` item 3 (`local_model_window_gate_cli.bb check`
against a REAL served window) could not be run here - deferred to QA's
own e2e pass, per the ticket's own item ownership. Item 1, 2 and the
`--context-length`-fallback shape of item 3 are all covered by the
acceptance suite itself (scenario 03 drives the real CLI the same way,
just without a live served window).

## Invariant

"The launch never writes or reads-and-rewrites the operator's own
`~/.qwen`; a seat's qwen settings exist only in that seat's working
directory, and only for a local-model seat." No separate property test:
this is bash/zsh, with no `*.property.test.js`-style generator
infrastructure wired for it (Engineering "Startup Tools" - only
TypeScript has that lane). Checked instead by an explicit unit case in
`test_bl1829_local_model_qwen_settings.sh` ("never writes under HOME,
only the given worktree" - runs the writer with `HOME` pointed at a
throwaway directory and asserts nothing appears under it) and by the
call site itself, scoped unconditionally to `agent == "local-model"`
(verified by reading `write_role_launch_script`: no other branch calls
`write_local_model_qwen_settings`, and scenario 02 exercises this
directly against a real `claude` seat in the same fixture).
