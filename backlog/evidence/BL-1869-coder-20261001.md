## A pitfall hit while building the fixture (worth recording for whoever next touches this handler)

The first rewrite gave every closed ticket `mutation_cost: low`. That made
`reworkObservatorySource.ts`'s `classesByTicket` attribute every bounced
record's `topTicketClass` to `"low"` - a single repeated class across all
bounced records, which `reworkDiagnosis.ts`'s `describeLikelyCause` reads
as a concentrated, attributable cause. `classifyRemediationDisposition`
then classifies that `'escalate-only'`, and `classifyThrottleSeverity`
returns `null` for any `'escalate-only'` verdict - so the throttle never
fired at all (scenarios 01/02/03/05 all printed the configured cap, never
the throttled one). Fixed by dropping `mutation_cost:` entirely from the
fixture's ticket files, so `topTicketClass` stays `null` and the
no-concentration circuit-breaker path (Article 3.5's own sanctioned knob)
is the one actually exercised.

`node extension/out/tools/emit-throttle-recommendation.js <root>` run on

peak RSS. (The ticket's mint-time figure was 32s/1670 records; the gap is

briefing**, both via the SAME unbounded, full-history

specifier.** Not fixed here (out_of_scope: "bounding the depth CLI ...
is a ticket of its own").

### c. Failure path

Reproduced in-process and end-to-end via a mkdtemp root: pre-seeded
`.swarmforge/coordinator/throttle-recommendation.json` with a stale
`severe`/`recommendedCap: 0` shape (simulating "an earlier run"), then
made `.swarmforge/telemetry/` uncreatable (`chmod 555` on `.swarmforge`
itself, leaving `.swarmforge/coordinator` writable) so
`persistReworkSignal` inside `refreshReworkSignal` throws EACCES.

- `node extension/out/tools/emit-throttle-recommendation.js <root>`:
  exits 1, `Fatal error: EACCES: permission denied, mkdir
  '.../.swarmforge/telemetry'` - confirms `main()`'s un-try'd
  `refreshReworkSignal` call propagates a throw.
- `effective_backlog_depth_cli.bb <root>` (the real promotion
  entrypoint): logs `throttle-recommendation refresh failed, exit=1
  ...`, then **prints `0`** - the min of configured (3) and the STALE
  severe recommendation already on disk, confirmed unchanged afterward
  (`{"recommendedCap":0,"severity":"severe",...,"updated_at":"2026-07-16T..."}`).

This confirms the concern: ANY exception anywhere along
`refreshReworkSignal`'s call chain (not just the "no git repo" case this
hotfix's happy path already fixes) silently falls back to whatever stale
recommendation is already on disk - exactly the stale shape the hotfix
exists to remove, just reachable via a different trigger (any write
failure under `.swarmforge/`, not only a never-refreshed signal).
**Confirmed - sending a note to the specifier.** Not fixed here (no probe
fix is in scope; this is a new finding beyond the two the ticket named,
reported the same way).
