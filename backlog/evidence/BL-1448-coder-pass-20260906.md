## Invariants (BL-654) — stated reason, no property test (both)

Both declared invariants quantify over `test_property_suite_drift_guard.sh`'s
own runtime behaviour: a bash integration fixture that copies files and
spawns bash subshells, not a pure, testable JS module. Unlike BL-1409's
wiring check (`propertyGuardIsWired`, a JS shim reading files that a
fast-check generator could drive in milliseconds per case), no JS layer
mediates this mechanism - the guard-copy construction and the suite's case
bodies are the whole of it. A property test would need to spawn the real
suite (measured ~43s per run above) once per generated case; that cost and
shape belong to the acceptance/integration gate already exercising it, not
`npm run test:properties`.

- **Invariant 1** (no case reads the live TSV, so the live file may hold any
  rows) is exercised representatively by the acceptance feature's Scenario
  Outline over the live-file row count (0, 1, 3 - the ticket's own boundary
  examples) plus scenario 02 (a live row naming the fixture's *non*-
  allowlisted red, `pipelineBoard`): all four pass identically, which is the
  direct experiment the invariant describes, run through the acceptance gate
  the ticket already specifies rather than a generated JS property.
- **Invariant 2** (the fixture's allowlisted and non-allowlisted names are
  disjoint by construction) is structural, not generative: every allowlist
  row `install_guard_copy_with_allowlist` ever writes comes from its own
  call's `"$@"`, and grepping every call site in the suite
  (`grep -n install_guard_copy_with_allowlist test_property_suite_drift_guard.sh`)
  shows the seven calls pass only `bl632CommitTimeGuardInvariants`,
  `alertTelemetry`, `crossFileDuplicationCheck`, `hostActivityFeed`,
  `pilotAcceptanceGate`, or nothing - `pipelineBoard` (the suite's
  non-allowlisted fixture red) never appears as an argument anywhere.
  Disjointness holds by that construction, not by a runtime check with a
  pass/fail domain to range a generator over.
