# BL-1698 — coder pass, 2026-09-25

## The fix

All six of the ticket's "What is wanted" points, against BL-1697's
`swarmforge/scripts/local_parcel_driver_lib.bb`/`local_parcel_driver_cli.bb`:

1. **Resume.** The ticket parcel flow is split so the merge is
   resumable: `start-ticket-parcel!` now merges once, immediately
   persists `{:phase "post-merge" ...}`, then calls the new
   `continue-after-merge!` (red-check through typing the instruction,
   itself persisting `{:phase "awaiting-model" ...}` **before** typing).
   `drive-tick!` gains a `"post-merge"` branch that calls
   `continue-after-merge!` directly (never re-merges) and dispatches an
   escalated hold to `resume-from-hold!` (point 2) instead of parking
   unconditionally. A new `resume-writable-sweep!` restores write
   permission on every spec file named by every persisted driver record
   under `.swarmforge/local-driver/*.json` (every seat, not just the
   current tick's) — wired as the one true "driver starts" entry point
   (`resume!`), called once from `handoffd.bb`'s own `-main` right after
   `self-heal-stale-stubs!`, and exposed to the CLI/tests via a trailing
   `resume` argument.
2. **Hold release by answer.** `resume-from-hold!` calls the new
   `answer-available?` (the sole sanctioned entry point,
   `extension/out/tools/deliver-role-answer.js --role <role>`, BL-1244 —
   never a direct read of `role-answers/<role>.json`), types ONE fix
   request carrying the answer text via `answer-fix-request-text`, and
   re-arms the gate for exactly one more try (`fixTurnsUsed` set to
   `fixTurnsLimit - 1`).
3. **Hold release by operator.** `release-hold!` (new), a driver CLI
   verb (`local_parcel_driver_cli.bb release <root> <checkout> <role>
   <seat-id> <complete|retry>`) that never types into the pane:
   `complete` completes the parcel with no `git_handoff` and clears the
   record; `retry` just clears the record.
4. **Mechanical mail.** `start-new-parcel!` now classifies the served
   mail before assuming it's a ticket: `qa-merge-up-note?`/
   `merge-up-commit` (pure, matches handoff-protocol.md's own Article
   2.5 shape) and the `non-forwarding: true` header both route to the
   new `mechanical-mail!` (merge, then `seat done` — no model turn, no
   handoff; a conflict escalates using `"mail"` as the pseudo-ticket id,
   same posture as a ticket's own merge-conflict path).
5. **Any other note.** Routes to the new
   `ask-or-escalate-to-coordinator!`: `seat ask` (execs `role_ask.bb`,
   output passed straight through); when the role's own ask slot is
   already taken (`{:asked false :reason "already-pending"}`), the same
   text goes to the coordinator instead via `seat note` (its own 80-char
   bound).
6. **babysitterd.** No production change: `babysitter_nudge_lib.bb`'s
   pre-existing `aider-agent?` check (the 2026-09-21 "never nudge an
   aider coordinator" rule) already unconditionally withholds every
   nudge to any aider-provider seat, which already covers the driver's
   coder seat — confirmed, not re-implemented. Scenario 06 is a fresh
   assertion of existing behaviour, reusing BL-1697's own dedicated
   daemon test (`test_handoffd_driver_seat_injection_skip.sh`) rather
   than a second copy of the same mechanism.

## Two bugs found and fixed while wiring this up

- `answer-available?`'s `daemon-cycle-guard-lib/sh!` call omitted `{:dir
  checkout}` — `sh!`'s own opts-first calling convention
  (`split-sh-args`) means an opts map passed anywhere but first is never
  applied, so `node deliver-role-answer.js` ran with THIS bb process's
  own cwd, not the seat's checkout. Fixed: `(daemon-cycle-guard-lib/sh!
  {:dir checkout} "node" deliver-js "--role" role)`.
- `drive-to-end!`'s loop checked `(:escalated state)` **before** ever
  ticking, so an already-escalated hold (exactly requirement 2's own
  starting state) never got a single tick to attempt
  `resume-from-hold!` — the loop just returned immediately. Fixed with a
  `prev-escalated?` accumulator: an escalated hold still gets one tick
  before the loop treats it as terminal; a hold that becomes escalated
  freshly during the loop still stops after one further (harmless) tick,
  same as before this ticket.
- `resume-from-hold!` re-armed `:fixTurnsUsed` but never `:fixTurnsLimit`
  in the written state — harmless when the original escalation state
  already carried it (a real gate escalation always does), but an NPE in
  `run-gate!`'s `(< fixTurnsUsed fixTurnsLimit)` for a state with none
  (a pre-chat-setup red-check escalation, which never HAD `:fixTurnsLimit`
  to begin with). Fixed by defaulting and re-writing it explicitly.

## Invariants (BL-654)

- Invariant 1 ("no spec file... is left without write permission once
  the driver's first pass completes"): coder-authored property test,
  `extension/test/bl1698LocalParcelDriverResumeAndRelease.property.test.js`
  — generates 0-4 driver records (0-3 spec files each, a mix of
  already-writable/locked-444, some records with no `:specFiles` at all —
  the pre-chat-setup shape) and asserts `resume-writable-sweep!` leaves
  every named file writable. Non-vacuity checked directly: disabled
  `restore-spec-writable!`'s body (`(when false ...)`), reran — failed
  immediately; restored the real source, reran — 2/2 green. A second
  test proves the sweep reads records rather than chmodding everything
  in sight (an unrecorded locked file stays locked).
- Invariant 2 ("every mail... ends in exactly one of...") quantifies
  over the real dispatch through real git/seat subprocesses for four
  mail shapes — not a pure module a generator can drive. Stated reason
  recorded in the property test file's own header, same disposition
  BL-1697's own invariant 2 used: encoded by the acceptance feature's
  nine scenarios, which run the real driver against a real throwaway
  checkout for every one of the four mail shapes.
