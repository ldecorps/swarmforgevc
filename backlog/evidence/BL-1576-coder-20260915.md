# BL-1576 — coder pass, 2026-09-15

## What landed

`swarmforge/scripts/merge_drop_guard_lib.bb` — a new send-time gate wired
beside BL-1213's `parcel_rollback_guard_lib.bb` in `swarm_handoff.bb`. It
walks the merge commits reachable from a `git_handoff`'s forwarded commit
and not from the sender's own received commit (via BL-806's
`review-forward-evidence-gate-lib/received-commit-for-task` — no second
reader of that in_process `commit` header), and for each merge's two
parents, parses `git diff -U0 <base> <side> -- <path>` into hunks. A hunk
one side made is a finding only when the OTHER side never touched it (not
merely "close to it" — adjacent ranges are explicitly not contested, the
incident's own 33-38-vs-39-39 shape); for each side's uncontested hunks, a
`+`/`-` line in `diff(side, mergeCommit)` matching a line that side itself
removed/added is a dropped-hunk finding, excused by a `This reverts
commit <sha>` reachable from the forwarded commit naming a commit that
touched the path since the merge base (the BL-490/BL-495 convention
BL-1213 also honours).

The pure decision core (`parse-hunks`, `contested?`, `uncontested-hunks`,
`lines-lost`) is fully separated from the git reads, per BL-654 and the
constraints' own direction, so the hardener's mutants land on the
predicate rather than on process plumbing.

A read-only CLI entry point ships in the same file (`bb
merge_drop_guard_lib.bb <project-root> <received-commit> <forwarded-commit>`,
guarded to run `-main` only when this file is the one bb was invoked with
directly — safe to `load-file` as a pure library the rest of the time),
printing one JSON line per finding for QA's own live-objects check
(qa_e2e_procedure step 2).

`specs/pipeline/steps/bl1576MergeDropGuardSteps.js` lands in the same
commit as `specs/features/BL-1576-a-forward-is-refused-when-a-merge-dropped-one-sides-uncontested-hunks.feature`
per BL-233/BL-1371; discovered automatically by `specs/pipeline/steps/index.js`
(no manual registration line). Merge commits in every scenario are built
with `git commit-tree` for exact, deterministic content control (one
scenario — "git's own clean auto-merge, no conflict raised" — instead
drives a real `git merge --no-edit`, the fixture's hunks spaced so it
auto-succeeds with no conflict).

## Declared invariants (BL-654) — all three encoded as executable property tests

`swarmforge/scripts/test/bl1576_merge_drop_guard_property_runner.bb`:

- **Invariant 1** ("computed from git objects... never from any working
  tree"): a real-git-fixture case with a dirty, uncommitted edit that
  would flip the verdict to "no finding" if the working tree were read;
  asserted the committed sender-verbatim finding survives unchanged.
- **Invariant 2** ("a line one side changed is a finding only when the
  other side never touched that hunk... a genuine same-line conflict is
  never refused... a revert excuses it"): two generative sub-properties —
  `contested?` against a brute-force per-base-line overlap/symmetry check
  (2000 runs), and `lines-lost` against a brute-force set-intersection
  definition over random removed/added/diff line sets including blank-line
  noise (2000 runs) — plus the incident's own adjacency shape and the
  same-position-insertion clause asserted directly.
- **Invariant 3** ("bounded to merges reachable from forwarded and not
  from received, and to the paths those merges' parents changed since
  their merge base — never a full-tree walk, never past received, never a
  merge the sender did not make"): two real-git-fixture cases — a
  pre-existing merge (before the ticket's own received commit) with the
  identical droppable shape is never inspected; a path neither merge
  parent touched since base is never flagged even when the merge commit's
  own tree independently differs there too (the full-tree-walk
  temptation).

Non-vacuity proven by hand at authoring time (also true of
`merge_drop_guard_lib_test_runner.bb`'s own two sed-mutation checks, run
and restored, not left in the tree): relaxing `contested?`'s overlap
check to `false` fails 6 assertions across both the unit runner and the
property runner (including the scenario-02 contested-pick and the
invariant-3(a) pre-existing-merge case going wrongly green-when-wrong);
relaxing `revert-excuses?` to always `false` fails the scenario-04 revert
case; scoping `merge-commits` to `--all` instead of `<received>..<forwarded>`
fails invariant 3(a). All three restored before this commit.
