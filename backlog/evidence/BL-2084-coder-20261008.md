## Bugs found and fixed in the salvaged lib

The ticket named two (`.toInstant` on an `Instant`, which has no such
method). Running `briefing-window` after fixing those two surfaced two
more, both confirmed empirically (`bb -e` against the loaded lib, per the
ticket's own "run after every edit" direction) before being fixed:

1. `local-date-of` and `briefing-window` both called `.toInstant` on the
   `Instant` `Instant/parse` returns — `Instant` has no such method
   (nothing converts an Instant to itself). Fixed: pass the `Instant`
   straight to `LocalDate/ofInstant`, exactly as the ticket's own
   remediation says.
2. `briefing-window`'s `-> ` chain called `(java.time.LocalDateTime/atTime 0 0)`
   — `atTime` is an INSTANCE method on `LocalDate` (returns a
   `LocalDateTime`), not a static method of `LocalDateTime`; threw
   `No matching method atTime found taking 3 args`. Fixed: `.atTime 0 0`.
3. The same chain then called `(.toInstant zone)` on the resulting
   `LocalDateTime` — `LocalDateTime.toInstant` takes a `ZoneOffset` (a
   FIXED offset), not a region-based `ZoneId` like `ZoneId/systemDefault`'s
   usual `Area/City` shape; threw
   `ZoneRegion cannot be cast to ZoneOffset`. Fixed: `.atZone zone`
   (→ `ZonedDateTime`) then a no-arg `.toInstant` (needs no offset at all).
4. `briefing-day-rows` combined its three per-kind bucket maps
   (`{date -> {:requests [...]}}`, `{date -> {:compressions [...]}}`,
   `{date -> {:tool-calls [...]}}`) with a plain `(merge m1 m2 m3)` — a
   SHALLOW merge, so a date present in more than one bucket kept only the
   LAST map's value for that date, silently dropping the earlier kind's
   events. This is the exact failure the ticket's own description names
   for the SECOND salvage attempt (`refs/swarmforge/salvage/BL-2084`) -
   it is present in the FIRST salvage (the one taken) too. Fixed:
   `merge-with merge` — a shared date key is resolved by merging the two
   inner `{:kind [...]}` maps (each carries exactly one kind key per
   date, so the inner merge never itself collides) instead of one
   replacing the other.

All four fixes verified non-vacuous by hand: each was temporarily
reintroduced (or, for #4, replaced with a direct `merge`) and `bb -e`
against the loaded lib reproduced the exact original failure, then
restored.

## --briefing mode (local_seat_tuning_report_cli.bb)

`settings-record-seats` lists seats by settings-record FILE STEM under
`.swarmforge/local-agent/seat-settings/*.jsonl` — never by inverting a
qwen directory name (the ticket's own direction and the salvage's
documented bug); `gather` already maps a seat name FORWARD to its qwen
directory. For each such seat, `gather` runs once (reusing every existing
`--qwen-home`/`--qwen-projects-dir`/`--ollama-log` option), its
requests/compressions/tool-calls are filtered into `briefing-window`'s
`[start-ms end-ms)`, and a seat with at least one request in the window
gets a `### <seat>` heading and a markdown table with one row per
host-local date it made a request (a date with only a compression or
tool-call, no request, is not a row). No seat with a request in the
window -> the exact single line `No local-model seat ran in the last <N>
days.`. `--seat` mode is untouched (same `gather`/`build-report`/`render`
path as before).

## Declared invariants (BL-654)

Both property-tested in
`extension/test/bl2084LocalSeatBriefingInvariants.property.test.js`,
driving the REAL CLI over a real mkdtemp fixture:

1. "The briefing section is read-only to produce and the same records
   always print the same section." — a SHA-256 hash of every file under
   the fixture root, before and after a `--briefing` run, must be
   identical (read-only, proven against the fixture's own data rather
   than trusting the claim); two runs over the same fixture must print
   byte-identical output (determinism).
2. "Every number in the section comes from a record; a field no record
   carries prints as unknown, never as 0." — four deliberately
   CONSTRUCTED day shapes (BL-1062/BL-2083's "constructed, not sampled"
   rule: the space is small and exactly about a nil-vs-zero boundary, so
   it is enumerated, not drawn at random): no tool-calls at all (failure
   rate must read "unknown"), tool-calls that all succeed (a GENUINE 0%,
   never "unknown"), tool-calls with some failing (neither "unknown" nor
   "0%"), and zero compressions (a genuine `0`, never "unknown" -
   compressions-per-10-requests is always computed once any request
   exists).

Non-vacuity, both invariants, proven by hand before this commit:
invariant 1 — temporarily had `run-briefing!` write a stray file; the
read-only check failed, naming it. Invariant 2 — temporarily coerced a
`nil` tool-call-failure-rate to `0` before formatting; the
"no-tool-calls-at-all" case failed (`expected "unknown", got "0%"`). Both
reverted before this commit.
