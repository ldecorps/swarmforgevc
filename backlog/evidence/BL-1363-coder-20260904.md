## What was built

`swarmforge/scripts/close_ticket.sh` — the mirror of
`promote_and_route_next.sh`, reusing its shape rather than inventing one:

- **Every id resolves BEFORE anything is staged** (invariant 2). A partial
  close is worse than no close — the id that did not move stays active forever
  with nobody looking for it — so one unresolvable id refuses the whole batch
  with nothing moved and nothing staged.
- **The same snapshot/rollback discipline** promotion has (BL-1028): the index
  entries and file contents for exactly this close's paths are captured before
  the `git mv`, and a refusal restores them. Never a blanket `git reset`, which
  on the shared master checkout would discard other roles' staged work.
- **The refusal is obeyed, never overridden.** The integrity CLI's own output
  is passed through, its two refusal shapes are read the same way promotion
  reads them (`CLOSE BLOCKED` with no JSON, versus `"reason"` / `FAILED (…)`),
  and there is no raw-commit fallback — the specific failure BL-1028 recorded.
- **The subject names every id** the approval satisfied (Article 2.6).
- **It never promotes** (invariant 3).

### Non-vacuity, one mutation per invariant

- override the refusal with a raw `git commit` — BL-1028's exact defect → P1
  fails ("a refused close moved 1 ticket(s)").
- `continue` past an unresolvable id instead of refusing the batch → the
  partial close is caught immediately.
- promote the paused ticket on the way out → P3 fails.

## What the close guard taught the fixture, worth recording

The real `commit_integrity_cli.bb` refuses a close with no QA approval on
record (`ticket_close_guard_lib.bb`'s `qa-approved-ticket?`: a QA `git_handoff`
or `note` in the coordinator's mailbox naming this id). My first fixture had no
mailbox, so every "successful close" scenario was actually exercising the
refusal path — and passing scenario 2 for the wrong reason. The fixture now
provides what a real close has: a coordinator mailbox carrying QA's own note.

The e2e also runs the FIXTURE's copy of the script, not this repository's:
`close_ticket.sh` resolves its helpers from its own location, so running this
repo's copy would consult this repo's integrity CLI and the stubbed-refusal
scenario would never be reached.
