## What was built (round 1)

- `extension/test/helpers/landStepLibSession.js` (new): `startBbSession(libPath)`
  spawns ONE long-lived `bb` process that `(load-file ...)`s
  `land_step_lib.bb` once, then answers one Clojure expression per line
  read from stdin, printing `{"ok" true "value" ...}` or `{"ok" false
  "error" ...}` as one JSON line per answer. `ask(expression)` writes a
  line and resolves the matching line back off a FIFO queue (one
  `readline` listener, one pending-queue shift per response - requests
  are never pipelined out of order because the test itself never sends a
  second expression before the first resolves). `close()` ends stdin and
  kills the child in every caller's `finally`.
- `extension/test/bl1343ReplayNeverDropsOwnPathInvariants.property.test.js`:
  the old `ask(root, expression)` (one `spawnSync('bb', ['-e', ...])` per
  draw, reloading the 4071-line lib every time) is replaced by one
  `startBbSession(LAND_STEP_LIB)` per test, called before the two
  `SHAPES` loops and `session.close()`'d in a `finally` after them. Both
  tests became `async`/`fc.asyncProperty` so each draw can `await
  session.ask(...)`. `ownPaths`/`landPlan` now take the session as their
  first argument instead of re-deriving a fresh `bb` call. Every draw
  still sends its own expression, built from its own `root`/`headOf(root)`,
  over the stdin pipe - no answer is cached, stubbed, or reused across
  draws (invariant 2).
- `specs/pipeline/steps/bl1865Bl1343PropertyBudgetSteps.js` (new): drives
  the real file three times through the real `vitest.properties.config.mjs`
  CLI with `--reporter=json` for scenario 01 (fastest-of-three per test,
  by `assertionResults[].title`); reads the file's own source for
  scenario 02 (exact SHAPES array, the `runsPerCell(27, SHAPES.length)`
  constant, and that both tests reference it - a matcher that finds
  nothing fails loud, BL-1445); drives the real
  `standing_red_register_cli.bb` plus a live read of
  `backlog/{paused,active,done}` for scenario 03's "present while open,
  absent once done" check. `vitest.properties.config.mjs` always prints
  one `[property-lane-budget]` line to stdout before the JSON reporter's
  own line (module-body `console.log`, same process/stream), so every
  parse here takes `out.trim().split('\n').pop()`, never a bare
  `JSON.parse(out)`.

## A performance finding — the 8000 ms bound is not reliably met on this host (flagged to specifier)

The prescribed remedy (load `land_step_lib.bb` once per test, not once
per draw) is implemented exactly as directed and the FIRM invariants hold
(same draws, same assertions, no caching across draws, `propertyLaneTimeoutMs(20000)`
unchanged). It delivers a real, large improvement - the guaranteed ~26-29
reloads at ~1.0-1.1 s each that dominated the old 18424/15558 ms totals
are gone. But the remaining per-draw cost (`buildRepo`'s own ~2-10 git
spawns per draw plus `land-step-lib/own-paths`/`land-plan`'s own internal
git calls, run fresh every draw by design, invariant 2) is itself larger
than the 8000 ms ÷ 27 draws ≈ 296 ms/draw headroom the ticket's "40% of
20000 ms" math implicitly assumed once the reload cost was paid once.
Measured typical per-draw cost after the fix is ~340-530 ms, not ~110-210
ms. On this host, outside one unusually quiet window (batch A), four of
five three-run batches did not clear 8000 ms for invariant 1 (closest
miss: 9320 ms, batch D, the acceptance scenario's own live drive).

This is not a logic defect - `buildRepo` and `land_step_lib.bb`'s own
per-draw git calls are both out of this ticket's scope (constraints:
`swarmforge/scripts` unchanged; "leave the fixture side alone unless
measurement shows it matters" - it does, but changing it is a call for
the specifier, not this remedy). Flagged by `note` (priority 00) to the
specifier with this evidence's path; forwarding anyway since the prescribed
remedy is correctly and fully implemented and is a large, real
improvement over the pre-fix numbers in every batch measured.

## Invariants (ticket's `invariants:` list, BL-654)

Neither declared invariant quantifies over a generated input domain - both
describe a single, non-varying fact about this one file's own structure
(which draws/assertions it runs; where each draw's answer comes from),
not a production behavior whose violation could hide in some corner of
an input space a generator would need to reach. Per BL-654's carve-out
("When a declared invariant admits no executable encoding ... record a
stated reason ... instead of a test"), neither gets a NEW coder-authored
`*.property.test.js`; both are encoded directly against the real,
committed file instead:

1. "Each test ... runs the same 27 draws, 9 per shape, and the same
   assertions ..., and each keeps `propertyLaneTimeoutMs(20000)` as its
   budget." Stated reason: this is a static fact about the file's source,
   true or false for the whole file at once - no input varies it, so
   generation adds nothing a source read does not already establish.
   Encoded by the acceptance feature's scenario 02, which reads the
   committed source and pins the census (exact `SHAPES` array, the
   `runsPerCell(27, SHAPES.length)` constant, and that both tests
   reference it by name - BL-1445, a matcher that finds nothing fails
   loud rather than passing vacuously).
2. "Every draw's answer comes from `land_step_lib.bb` as loaded from the
   tree under test, ... no draw's answer is cached, stubbed or reused for
   another draw." Stated reason: `landStepLibSession.js` has no memoization
   path to fuzz against - `ask()` always writes the caller's own
   expression to the child's stdin and resolves the next stdout line off
   a FIFO queue; there is no key, no map, no branch that could return a
   stale or substituted answer for a different draw's root/commit, so no
   generated input could exercise a caching bug that the code structure
   does not admit. Verified by code reading (this file's own diff) rather
   than a property test for that reason, and indirectly by every draw's
   assertions passing against ITS OWN generated fixture in every run
   recorded above (a cached/reused answer from a different draw's fixture
   would fail those assertions, since each draw's `root`/`commit` differ).
