## The fix

Both fixtures replace their hand-`cp` lists with `copy_bb_closure`, sourced
from `lib/bb_closure_copy.sh`, naming the real entry points
`promote_and_route_next.sh` drives:

| fixture | entry points named |
|---|---|
| `test_promote_and_route_next_priority.sh` | `promotion_gates_cli.bb` |
| `test_promote_and_route_next_no_limit_depth.sh` (both `ROOT` and `ROOT2`) | `promotion_gates_cli.bb`, `backlog_depth_cli.bb`, `backlog_depth_conf_path_cli.bb`, plus `effective_backlog_depth_cli.bb` for `ROOT` only — `ROOT2` deliberately omits it to keep forcing the fallback branch, exactly as the hand list it replaces did by simply not `cp`-ing that one file |

`effective_backlog_depth_cli.bb`, `backlog_depth_cli.bb` and
`backlog_depth_conf_path_cli.bb` are named explicitly because
`promote_and_route_next.sh` SHELLS to them directly (lines 107-113) — no
load-file walk from `promotion_gates_cli.bb` alone reaches them.
`copy_bb_closure` accepts multiple entry points for exactly this shape
(its own docstring: "a fixture sometimes needs a sibling script its subject
SHELLS to rather than load-files").

Each fixture also preflights every entry point it copied with
`assert_bb_closure_present` (`lib/bb_fixture_load_guard.sh`, BL-1279's own
discipline) before asserting any behaviour — invariant 2.

`promote_and_route_next.sh`, `promotion_gates_cli.bb` and the libs are
untouched (`git diff --stat` on those paths is empty), matching the
`human_approval`'s FIRM constraint.

## bbFixtureClosureGate.js: extended for a multi-entry-point fixture

BL-973's `FIXTURES` map assumed one `entry` string per fixture; every
existing enrollee still declares one. `test_promote_and_route_next_no_limit_depth.sh`
is the first fixture with several. `effectiveList`/`missingFromList` now
treat `spec.entry` as a list uniformly (`entryList()` wraps a bare string),
so the shell-copy invocation runs `copy_bb_closure` with every declared
entry and the closure check unions all of them. Regression-checked: every
pre-existing `FIXTURES` entry (single-string) still resolves with an empty
`missing` list, unchanged. Proved the guard fires: added one load-file edge
to a scratch copy of `promotion_gates_lib.bb` and confirmed both new
fixtures report it `missing` (paste in commit; not repeated here).

Both fixtures enrolled as `kind: 'shell-copy'`. `bb_load_closure_agreement_test_runner.bb`
(BL-897, JS/bb parity) still passes.

## Invariants (BL-654) — stated reason, no property test

Both declared invariants are about SHELL FIXTURE / bb-subprocess behaviour
tied to real process execution and a disposable filesystem root, not a
pure, testable module a generator can drive — the exemption the coder
Invariants section names ("quantifies over prose or process rather than a
pure, testable module"). There is no pure function here to property-test;
`computeClosure` (the nearest pure piece) is BL-973/BL-1279 infrastructure
already exercised by `bb_load_closure_agreement_test_runner.bb`, and this
ticket's invariants are about the FIXTURES' own behaviour, not that parser.

Both invariants are instead encoded behaviourally, with the real mechanisms,
in the acceptance feature: invariant 1 (full closure, no hand-named file) by
scenarios 01 and 02; invariant 2 (a load failure reports itself, passes no
check) by scenario 04, non-vacuously (removes a real file from a real
closure, runs the real guard).

**2. BL-1173's deprecator freshness gate blocks BOTH of BL-1480's own
fixtures even after the closure fix.** Once the bb subprocess loads,
`promote_and_route_next.sh` reaches the Article 3.6 freshness gate
(landed 2026-08-27, one week after these fixtures last worked and three
weeks after BL-966 first broke their closure — nobody has exercised this
gate against an isolated fixture root before). It resolves
`$ROOT/extension/out/tools/deprecate-check.js` against the FIXTURE root,
finds nothing, and fails closed to `hold` — the candidate never leaves
`backlog/paused/`, so both fixtures' assertions on `Promoted BL-...` would
fail regardless of the closure fix.

The real `deprecate-check.js` cannot travel into these shell fixtures — it
requires a compiled `extension/out/` tree and its own multi-module
`require` graph (confirmed: copying just the one file throws
`Cannot find module './swarm-metrics'`), which is exactly the kind of
heavyweight dependency these lightweight shell fixtures have no way to
build or partially copy. Added
`swarmforge/scripts/test/lib/deprecate_check_allow_stub.sh` — a minimal
fake reproducing only the narrow, stable contract
`promote_and_route_next.sh` consults at both call sites (run directly:
one JSON line, exit 0; required: exports `interpretFreshnessCliOutput`
per `extension/src/tools/deprecate-check.ts`'s documented pure contract) —
the same "stand in for a mechanism downstream of what this test verifies"
posture already used in both fixtures for `route_backlog_to_coder.sh`.
This does not touch `promote_and_route_next.sh`; the fixtures test
priority ordering and the no-limit depth sentinel, not the deprecator.

I judged this within the coder's authority to add (test infrastructure
only, no production file touched) rather than a spec-amendment blocker,
and did not hold the ticket for adjudication — but it is a real widening of
the fix surface beyond what the ticket's `human_approval` anticipated, so
flagging it here explicitly for the architect/QA to weigh in on if they
disagree with that call.
