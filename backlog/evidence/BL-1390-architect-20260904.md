## Safety read — the hook itself

Read `swarmforge/git-hooks/post-commit` and `post_commit_push.bb` in
full, given this installs on every worktree via the existing
`core.hooksPath` config:

- Bounded by `timeout "$BOUND_SECONDS"`, exits 0 unconditionally, and the
  bb runner's own `-main` is wrapped so it can never propagate a non-zero
  exit into git — a post-commit hook cannot fail a commit and this one
  cannot stall one beyond the bound either.
- `linked-worktree?` correctly reads `--git-dir` vs `--git-common-dir`
  divergence (git's own answer) rather than path arithmetic, and fails
  CLOSED (treats an unreadable answer as linked, so it pushes nothing) —
  confirmed this means MY OWN commits on `swarmforge-architect` never
  trigger a push attempt (linked worktree AND non-`main` branch, doubly
  safe).
- The three self-caught defects (wrong repo resolution via
  `$PWD`/`--show-toplevel` vs the hook file's static location; a failed
  fetch still reading stale "ahead" counts; `git fetch origin main`
  leaving `origin/main` stale so the explicit refspec
  `+refs/heads/main:refs/remotes/origin/main` was needed) are exactly the
  kind of subtle correctness issues this class of infrastructure invites,
  and all three are now covered by their own test scenarios.
- `push-main!` never uses `--force`; the daemon's periodic sweep now
  delegates to the identical function (invariant 3, confirmed by reading
  `handoffd.bb`'s `push-sweep-push!` directly), so hook and sweep cannot
  diverge on what counts as safe.
