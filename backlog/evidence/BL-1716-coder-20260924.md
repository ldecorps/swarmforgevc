# BL-1716 — coder pass, 2026-09-24

## What landed

`swarmforge/scripts/land_step_lib.bb` (`replay!` only, per Scope):

- **`process-start-ms`**: pid's current start time in epoch ms, or nil
  when not running - re-querying it for the same still-running pid always
  answers the same value, which is what lets a REUSED pid be told apart
  from the run that actually made a leftover scratch.
- **`replay-scratch-owner-record-path` / `write-replay-scratch-owner-record!`
  / `read-replay-scratch-owner-record`**: a `{pid, start-ms}` JSON record
  written the moment a fresh worktree+branch is created, at a SIBLING
  path of the scratch directory (`<id>.owner.json`), so it is never
  mistaken for parcel-authored content.
- **`stale-scratch-age-bound-ms`** (env `SWARMFORGE_LAND_REPLAY_STALE_SCRATCH_HOURS`,
  default 2.0h) / **`scratch-age-ms!`** / **`branch-ref-age-ms!`**: the
  age fallback for a RECORDLESS leftover (predates this fix, or died
  between `worktree add` and the record write) - directory mtime when a
  directory exists, else the branch's own loose-ref mtime (a branch can
  survive with NO directory - see "Discovered while wiring" #1).
- **`stale-scratch-decision`**: the pure core (BL-654's declared
  invariant - see below). `{:action :proceed}` when there is nothing to
  reap, or a leftover whose record proves dead, or a recordless leftover
  past the age bound; `{:action :refuse :owner-pid pid-or-nil}` — FIRM —
  when the record proves the owner alive, or nothing can establish it.
- **`replay!` itself**: before building, checks BOTH a leftover worktree
  directory AND a leftover branch (see #1 below) for the SAME id, reads
  its owner record, and applies `stale-scratch-decision`. A refusal
  leaves the leftover completely untouched (FIRM) and returns
  immediately, naming the live pid or "an unestablished owner". Otherwise
  it reaps any leftover (`cleanup!` + `drop-branch!`) before building
  fresh, and records ITS OWN pid+start-ms right after the new `worktree
  add -b` succeeds. The create-failure reason now carries git's own
  stderr text (scenario 03). On a TRUE success, only the worktree
  DIRECTORY is removed (`remove-worktree-dir!`) - the branch AND its
  owner record both survive on purpose (see #1); on a refused-after-
  success outcome (the passenger tree-guard path), the record is removed
  alongside the branch since both are being thrown away together.

## Discovered while wiring

1. **A branch can survive a killed run with NO leftover directory - my
   first design missed this entirely.** I originally checked only
   `(fs/directory? scratch)` for a leftover. Reproducing the ticket's own
   cited symptom against `test_bl1366_land_is_one_command.sh`'s case 5
   (kill `land_main_publish.sh` 2s after launch) showed: the underlying
   `bb land_step_cli.bb` process is NOT killed by that SIGTERM at all -
   **bash defers a trapped signal until the current foreground command
   substitution finishes** (confirmed directly: a `bb -e '(Thread/sleep
   4000) ...'` inside `$(...)` still prints its own completion line after
   the wrapping script is SIGTERM'd and its own trap has already fired -
   the child is untouched, and the parent's trap only runs once bash's
   own wait on the substitution returns). So on THIS class of host, land-1
   in case 5 always completes its own FULL sequence before anything is
   interrupted - `LAND_PUBLISHED <replayed-sha>` reliably appears in its
   own output. Its `land-replay/<id>` branch survives that success (by
   design - QA's own land action reads it), but the WORKTREE DIRECTORY is
   already gone (removed by that same successful run's own cleanup). A
   second, redundant land of the SAME ticket+commit then hit exactly the
   ticket's own quoted symptom: `worktree add -b` failing on the
   surviving branch, with NO leftover directory to have ever detected.
   Fixed by checking `branch-exists?` OR `dir-exists?` for "is there a
   leftover", and (see #2) by keeping the owner record ALIVE alongside a
   surviving branch so a LATER re-land can tell it apart from one a
   still-running replay owns.
2. **The owner record must survive success alongside the branch, or the
   "record present, owner dead" fast path never fires for exactly the
   scratch it exists for.** My first pass deleted the owner record
   inside the SAME `cleanup!` used everywhere, including the success
   path - so a surviving branch's record vanished with it, leaving a
   FUTURE re-land attempt with NO record and only the age-bound fallback
   (which reads "too young" seconds after a fresh success and correctly,
   but unhelpfully, refuses with an unestablished owner instead of
   recognizing this run has already finished and its old pid is long
   dead). Split `cleanup!` into `remove-worktree-dir!` (directory only)
   and `remove-owner-record!`; the true-success path now calls
   `remove-worktree-dir!` alone, while every failure path (including a
   refused-after-success passenger-guard outcome, where the branch is
   ALSO being dropped) still calls the full `cleanup!`.
3. **A residual, OUT-OF-SCOPE gap the fix above newly exposes:** once
   scenarios 1-2 above are fixed, case 5's second `run_land` call no
   longer hits `worktree add -b`'s branch collision at all - it builds a
   fresh replay scratch successfully, then finds its own-paths already
   byte-identical to origin/main (since land-1's own successful replay
   already pushed that exact content) and reports `replay!`'s own,
   pre-existing (BL-1474) "nothing to commit" refusal. `land_main_publish.sh`
   wraps that as "entangled tip ... specifier adjudication needed" -
   whether a REPEAT land of an already-landed ticket+commit should
   instead report a benign no-op success is `land-plan`'s /
   `land_step_cli.bb`'s decision, both explicitly **out of this ticket's
   own Scope** ("Not in scope: land-plan and land_step_cli.bb (BL-1713,
   landing first)"). Confirmed this residual case-5 line and the
   PRE-EXISTING, unrelated case-1 SHA-drift line are BOTH present
   identically with this ticket's WHOLE diff stashed out (`git stash
   push -u`, re-run, `git stash apply <sha>` to restore) - see the
   dedicated spec-gap note sent alongside this parcel.
