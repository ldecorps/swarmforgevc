### Reading scenario 04 ("nowhere-to-start-from-is-loud")

Its Given is `no SWARMFORGE_TOOLING_ROOT` (the env var), and its Then
demands the refusal name **both** places looked. Those two only reconcile
if the fixture still gives the launcher a tooling root to find — via the
target's own pack conf (the "relaunch" fallback), never the env var. So the
step for that Given writes `config tooling_root <dir-without-the-
entrypoint>` into the target's own `swarmforge/swarmforge.conf` while
leaving `SWARMFORGE_TOOLING_ROOT` itself unset. This is deliberately the
SAME fallback path scenario 01 already proves swarmforge.sh populates from
a real pack conf — scenario 04 exercises a caller that skips swarmforge.sh
entirely (a bare `bash launch_front_desk.sh`, closer to a relaunch) and
still gets the pack-conf-derived tooling root. A target with truly nothing
configured anywhere keeps the exact pre-BL-1757 single-path refusal
(invariant 1) — proven by the pre-existing smoke tests in
`test_launch_front_desk.sh`/`test_start_stop_cursor_bridge.sh`, not
re-tested by this scenario.

## Self-audit finding: required_wiring checks literal file text, not what a sourced lib does

`pre_qa_gate_lib.bb`'s wiring gate (`str/includes? content pattern`) checks
the CITED file's own raw text for the literal pattern string. My first
commit resolved `SWARMFORGE_TOOLING_ROOT` entirely inside
`tooling_root_lib.sh` — `launch_front_desk.sh`/`start_cursor_bridge.sh`
never spelled the variable name themselves, even though sourcing the lib
does make each launcher's own process actually read it. That would fail
both `required_wiring` entries at the gate despite being functionally
correct. Fixed by having each launcher read
`${SWARMFORGE_TOOLING_ROOT:-$(tooling_root_resolve "$ROOT")}` directly —
the env var is read in the launcher's own text first, falling through to
the lib's own (harmless, re-checks the same var) conf-fallback only when
unset. No behaviour change; re-ran every test above after this fix, still
green.
