`collect_deletions`'s `--no-renames` → `-M` is the minimal correct change:
git's default similarity threshold already distinguishes a real move (the
`R<NNN>` status the existing `status == "D"` filter already excludes) from
a rewrite-that-keeps-the-name (still reports `D`+`A`, correctly still
flagged). No new threshold tuning needed.

`ticket_id_for_path`/`introducing_commit_for_path` merged into one
`attribution_for_path` is itself a cleanup over the pre-fix shape: the two
functions duplicated the same "ask HEAD, fall back to MERGE_HEAD" logic
independently, which is exactly how they drifted out of sync (id's fallback
condition was narrower than commit's). Resolving both together from
whichever side actually names a ticket removes that duplication rather than
just patching around it.

The `commit<TAB>id` field-order fix (never `id<TAB>commit`) is backed by a
genuinely subtle, well-documented reproduction of a bash `read` gotcha
(a leading empty field is silently swallowed with `IFS` set to an explicit
tab; a trailing one is not) — this is exactly the kind of non-obvious
invariant worth a comment, and the comment is already there.

No duplication, no structural concerns. `docs/how-to/BL-1242-merge-deletion-guard.md`
is correctly left to the documenter per the pipeline's own division of
labor (the ticket names it as part of the direction but it is
