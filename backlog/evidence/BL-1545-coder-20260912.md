## Invariants (BL-654)

All three of BL-1545's declared invariants are statements about this
shell test's own assertion structure and ordering (which value an
assertion reads, in what sequence, and that its git fixtures cannot
escape their own mkdtemp) — not about a pure, generator-drivable
production module. None admits a generative property-test encoding
without re-implementing the shell script's control flow in JS merely to
generate inputs for it, which the ticket's own `constraints:` and
`out_of_scope:` (BL-1516 remains the systematic, repository-wide root-proof
backstop; this ticket "proves the one file it edits") argue against. Stated
reason recorded here per BL-654, in place of a property test:

1. *"reads `:paths`, never the printed whole map"* — a structural property
   of which shell variable an assertion is built from. Verified instead by
   the negative control above (the old whole-map grep genuinely trips on
   BL-1389's `:excluded` key; the fix reading `:paths` alone does not) and
   by the acceptance handler independently checking the real
   `OWN-PATHS-DELIVERED` / `OWN-PATHS` output.
2. *"pins both ends... asserts non-empty range before any absent check"* —
   an ordering property of printed `ok`/`FAIL` lines in one script run.
   Verified by the oracle negative control (demonstrates the vacuous pass
   this ticket exists to close) and by acceptance scenario 03's ordering
   assertion (`rangeIdx < firstAbsentIdx`) against the real run's output.
3. *"creates no ref/commit/working-tree change... every fixture root is
   proven"* — a property of interaction with the live filesystem/git state
   under a hostile `GIT_DIR`/`GIT_WORK_TREE`, exercised concretely (not
   generatively) by acceptance scenario 04 and the root-proof negative
   control above.
