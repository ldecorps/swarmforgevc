## D1 — `deliverRoleAnswer`'s refuse-a-mismatch guarantee is unreachable from the real note-delivery path a role actually receives (behavior, HIGH)

**Failing command (repro):**
```
grep -rn "deliver-role-answer" swarmforge/ extension/src extension/out docs/how-to \
  | grep -v '\.test\.\|\.map:'
```
**Result:** only `extension/src/tools/deliver-role-answer.ts` (its own
definition) and `docs/how-to/BL-1201-*.md` (prose telling a human to run it
manually). Nothing else in the repo — no role `.prompt` file, no shell
wrapper, no Babashka script (`role_ask.bb` and friends have no counterpart
that consumes `role-answers/*.json` or calls this CLI), no change to
`composeRoleAnswerNoteMessage` — references or invokes it.

**Commit hash tested:** `ec5a92c9bb` (working tree merged to
`swarmforge-QA` at merge commit, this worktree).

**First error / evidence excerpt:**
```ts
// extension/src/tools/telegram-front-desk-bot.ts:1650-1652 (unchanged by this ticket)
export function composeRoleAnswerNoteMessage(role: string, text: string): string {
  return fitsInlineInRoleAnswerNote(text) ? text : `answer ready: ${roleAnswerFilePointerPath(role)}`;
}
```
This is the literal note text a role receives — byte-identical to before
the ticket. It still points straight at the raw
`.swarmforge/operator/role-answers/<role>.json` file, with no mention of
the new CLI or any instruction to run it. The documenter's own how-to
concedes this directly: "That direct-read path still exists as a file on
disk, but reading it directly no longer applies the correlator check... Use
the CLI instead" — i.e. the fix's enforcement is opt-in, gated entirely on
a role happening to already know (from documentation it was never told to
read) to run a CLI instead of following the note it was actually sent.

**Failure class:** `behavior` (honest label per Article 4.4's table — an
intent/invariant mismatch, not a compile/unit/acceptance red; every unit
and acceptance test for `deliverRoleAnswer` and its CLI genuinely passes,
because they call the function/CLI directly rather than reproducing how a
role actually arrives there).

**Expected vs observed:** Expected — per the ticket's own firm approval
context ("a role must refuse one it cannot match") and invariant 1 ("a role
never consumes one whose question it cannot match to its own pending
question") — that the actual live consumption path a role follows on
receiving an "answer ready" note enforces the correlator check. Observed —
the note text and every role-facing surface are unchanged from before this
ticket; a role (AI or human) acting on the note as literally written still
reads the raw file directly, exactly the read that produced the original
five-day-stale-answer incident, and gets none of `deliverRoleAnswer`'s
refuse/consume guarantees. The new mechanism is correct and reachable
*from a test or a human who has read the how-to doc*, but not from the
production note-delivery path any role actually receives — the same
"correct in isolation, invoked by nothing real" shape as BL-149, and the
same shape architect already found once this ticket (D1/D2, now fixed) at
one remove closer to production.

**Remediation pointer:** `composeRoleAnswerNoteMessage` /
`roleAnswerFilePointerPath`, `extension/src/tools/telegram-front-desk-bot.ts`
(~line 1650). The minimal closure: change the pointer-path note text itself
to instruct running the CLI (e.g. `answer ready: run
node extension/out/tools/deliver-role-answer.js --role <role> (do not read
.swarmforge/operator/role-answers/<role>.json directly)`) rather than a bare
file path — this is the same file and function this ticket already
modifies, not new surface. If a note-text change alone is judged
insufficient (e.g. an AI role could still ignore prose in a note the way
the original incident's role ignored no correlator at all), escalate to
specifier as a spec-gap for how enforcement should reach role prompts —
but the note-text gap itself is a plain wiring omission in code already
inside this ticket's own domain, so routing to specifier first is not
warranted until the minimal code fix is tried.
