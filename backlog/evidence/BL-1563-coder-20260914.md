## Goal 4 (PROBE only - recorded, not fixed): `recipient-is-home` is overridable, exact fixture

Confirmed live via the CLI: `forward-target=coder`, `forward-reason=recipient-is-home`,
`router-preferred=hardender` -> `{"target":"hardender","reason":"router-preferred"}`.
So when the departing role's own forward decision already names the home
role as a *confirmed* recipient (`:recipient-is-home` - "coder held the
parcel it just pushed to itself" cannot really happen operationally the way
the goal frames it, but the CODE PATH is real: any `forward-rotate-target`
result whose target equals home-role, for ANY reason including a genuinely
confirmed one, is treated identically to "no parcel to follow" by
`resolve-empty-mailbox-target` - the function only branches on
`(not= target home-role)`, never on *why* the target is home), the resolver
still asks the router and can send the resident elsewhere. This is exactly
what the ticket's goal 4 flags: "a confirmed recipient... stands" (per the
hotfix commit message) is true only when the recipient is NOT home; a
confirmed recipient that happens to BE home is silently treated as "no
parcel to follow." Consistent with the chase sweep's own eventual
redirect, but a design choice made silently. Recorded per the ticket's
instruction - refutation (if the human meant recipient-is-home to stand) is
a note to the specifier, never an in-parcel change.

## Goal 5 (PROBE only - BL-1558 owns the fix): router-preferred hops are mislabeled `handoff-forward`, confirmed by code trace

Traced the label path for a `router-preferred` hop end to end:
- `ready_for_next.sh` (lines ~26-31): when `ROTATE_TO != HOME_ROLE` it sets
  `REASON=rotate-forward` and exports `SWARMFORGE_ROTATION_REASON=rotate-forward`
  before exec-ing `rotate_to_role.sh`.
- `rotate_to_role.bb` -> `handoff-lib/respawn-as!` -> its `do-respawn!` calls
  `(rotate-resident-to! target-role "handoff-forward")` (`handoff_lib.bb:1341`)
  - an EXPLICIT literal reason argument, not `nil`.
- `rotate-resident-to!`'s `emit-reason` is `(or reason (System/getenv
  SWARMFORGE_ROTATION_REASON) default-reason)` (`handoff_lib.bb:1283-1285`)
  - the explicit `"handoff-forward"` argument always wins first, so the
    wrapper's `SWARMFORGE_ROTATION_REASON=rotate-forward` env var is dead
    code on this call path; it is never read.

So every rotation telemetry row for a `router-preferred` hop - not just a
`forward-recipient` one - reads `handoff-forward`, matching the ticket's
description of the 08:46Z QA->cleaner row. Confirms the ticket's framing
exactly: BL-1558 (rotation label dropped by `respawn-as!`) owns this,
scoped to whether a distinct label for router-chosen hops is worth adding
to BL-1558. Not fixed here.
