# BL-1673: the lane scan never counts the process doing the scanning — coder

## What changed

1. `swarmforge/scripts/lane_process_lib.bb`, `lane-running?`: excludes the
   scanning process's own pid (`(.pid (java.lang.ProcessHandle/current))`)
   before classifying any process-table row. `lane-process-pattern` and
   `project-scoped-process?` are unchanged.
2. `extension/test/bl1652HandoffdRespawnReadingsWiring.test.js`,
   `loadHandoffdAndRun`: the form is now written to a temp file (the
   file's own existing `mkTmpDir` helper + `writeFileSync`) and run as
   `bb <file> <root>`, never `bb -e <form> -- <root>` - an `-e` form is a
   literal argv element, so a form naming a fixture worktree put that
   path on the probe's own command line. Found and fixed along the way:
   a bb FILE invocation does NOT consume a `--` separator the way `-e`
   does (`bb file.bb -- root` → `*command-line-args*` is `("--" "root")`,
   not `("root")` — confirmed empirically against bb directly), so the
   `--` had to come out, not just move; every heartbeat-file read broke
   until it did (caught by the existing `heartbeat-age-seconds` cases,
   which regressed under the naive `bb file -- root` shape before this
   was found).
3. `extension/test/laneProcessLib.test.js` gains `the scan never counts
   its own process`: a bb probe whose `-e` form names the worktree and
   whose trailing arg carries a `.stryker-tmp/` token (probe B from the
   specifier's adjudication evidence) - red before the fix, green after.
4. New `specs/pipeline/steps/bl1673LaneScanNeverCountsItselfSteps.js`
   drives the pre-minted feature (mint `88f0acf751`): scenario 01 (three
   argv shapes: no lane-pattern token, a `.stryker-tmp/` token, and a real
   `run_acceptance.sh`-named child with cwd under the worktree, probed
   through a file so its own argv names nothing); scenario 02 (handoffd's
   `role-lane-running?` under the same `.stryker-tmp/`-token shape);
   scenario 03 (the real `laneProcessLib.test.js` file run through vitest
   `--reporter=verbose`, asserting the named case is among the passes -
   the default reporter only prints an individual test's own name when it
   is "slow enough", collapsing fast passes into the file-level count, so
   a by-name census pin needs `--reporter=verbose` to be reliable).

## Invariant (BL-654)

Declared: "lane-running? never counts the process performing the scan,
whatever that process's own command line matches or names; every other
process is classified exactly as today." Same disposition as BL-1658's
materially identical invariant: `lane-running?` scans the REAL, host-wide
process table with no injectable seam (by design - this is a host-wide
OS scan, not a pure function over a supplied list), so a fast-check
property would have to spawn real OS processes per draw to mean anything,
which the acceptance feature's own scenarios already do for the three
shapes that matter (no token, a self-matching stryker-shaped token, and a
real other lane process) plus the daemon's own read (scenario 02) - all
against the real bb binary and the real process table. That Scenario
Outline is already this invariant's coder-authored executable test; no
separate `*.property.test.js` file adds anything. No stated-reason note
needed beyond this record, matching BL-1658's own precedent
(`eae448e6c9`).
