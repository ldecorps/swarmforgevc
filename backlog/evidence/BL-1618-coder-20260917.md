# BL-1618 — coder pass, 2026-09-17

## Self-audit correction

`current_in_process_task`'s first draft found the role's newest in-process
handoff with `find "$inbox" -name '*.handoff' | sort | tail -1` — sorting
FULL PATHS. `handoff-lib/handoff-files-with-batches` (BL-1313), the reader
every other newest-match consumer in this swarm uses, sorts every
candidate — top-level or inside any `batch_*` directory — by FILENAME
ALONE. A batch-nested file's own `batch_<ts>/` path segment can make a
full-path sort rank it above or below a top-level file for reasons that
have nothing to do with either file's own priority/timestamp prefix, so a
batch role (cleaner, hardender) holding more than one in-process task
could have this script ask `review_forward_evidence_gate_lib.bb` about the
WRONG task's received commit — silently wrong changed-path facts, never a
visible error. Caught during the self-audit before the real send (no
scenario in the ticket's own acceptance feature exercises a multi-task
batch mailbox, so nothing else would have caught it). Fixed by shelling
directly to `handoff-lib/handoff-files-with-batches` and reading the
LAST result's own `task:` header, instead of reimplementing the sort in
bash — the same primitive `swarm_handoff.bb`'s `inbound-non-forwarding?`
and BL-1612's own two send-time-gate readers already trust.

## The fix

`swarmforge/scripts/verify_lanes.sh [role] [--plan]`: one lane table
(`plan_for_role`), shared byte-for-byte between `--plan` (prints the plan,
runs nothing) and the real run (executes exactly that plan, sequentially,
stopping at the first failed lane and naming it in the verdict) —
invariant 1 by construction, since both modes call the SAME function.

- Role defaults to `$SWARMFORGE_ROLE`; an `@`-seat (`coder@2`) maps to its
  stage (`coder`) via `${RAW_ROLE%%@*}`. An unknown stage is refused (exit
  2), never run-everything.
- Lane table (human ruling A): `coder` — compile, unit, properties,
  acceptance-own, always; `cleaner`/`architect`/`documenter` — compile
  always, `unit` only when the parcel's own changed paths (since the
  received commit, or `origin/main` with none) touch `extension/src` or
  `extension/test`, `properties` only when they touch a
  `*.property.test.js` file, acceptance-own always; `hardender` —
  compile, unit, mutation, acceptance-own, always; `QA` — compile, unit,
  changed-path, properties, acceptance-own, always.
- Changed-path facts reuse `review_forward_evidence_gate_lib.bb`'s own
  `received-commit-for-task` (BL-806, BL-1612's batch-aware fix) against
  the role's own current in-process parcel's `task:` header — the SAME
  resolution the send-time gates use, never a second reader. No parcel (or
  none matching) falls back to `origin/main`.
- The ticket's single `acceptance:` feature is read from
  `backlog/active/` or `backlog/paused/` by the ticket id parsed off the
  same task name.
- `changed-path` (QA's own lane) surfaces the changed production paths
  (excluding docs/backlog/generated) rather than selecting or running a
  specific test itself — Article 4.5's own gate has no dedicated automated
  selector yet ("day-one tooling is manifest grep + judgment", per the
  amendment's own Non-goals), and this ticket's constraints forbid
  changing that gate; the lane is informational, never fails on its own.
- `npm` and `run_acceptance.sh` are invoked by bare name (PATH-resolved),
  not a hardcoded path — the same shape the acceptance/shell fixtures use
  to shadow both with recording fakes; `run_acceptance.sh` falls back to
  the real `specs/pipeline/scripts/run_acceptance.sh` when nothing shadows
  it on PATH (production has no `run_acceptance.sh` on PATH today).

## BL-654: the two declared invariants

`swarmforge/scripts/test/bl1618_verify_lanes_property_runner.bb`:

- Invariant 1 ("the plan... is byte-for-byte the sequence it runs"): for
  10 role/property-touched fixture combinations, the REAL `--plan` output
  is cross-checked against the REAL recorded sequence of fake-npm /
  fake-run_acceptance.sh invocations from an ACTUAL (non-`--plan`) run of
  the identical fixture — two independent observations of the same
  script's two modes, never one restating the other. (Required seeding a
  plausible in-process parcel per fixture so `acceptance-own` has
  something to resolve — without one, `CURRENT_TASK` is empty and the
  lane fails open/skips by design, which the property caught immediately
  as "plan says acceptance-own, run never called it" until fixed; the
  seeded parcel's own `commit:` had to be the fixture's real baseline SHA,
  not a placeholder, or `DIFF_BASE` becomes unresolvable and every
  changed-path signal this same property depends on goes silently blank —
  a second thing the property itself surfaced before landing.)
- Invariant 2 ("the property lane appears in no plan for cleaner,
  architect, documenter or hardender unless... a `*.property.test.js`
  file... always in QA's... and the coder's per the ruling"): an
  EXHAUSTIVE sweep of all 6 roles × {a property test file changed, none
  changed} — 12 states, small enough to enumerate completely — checked
  against an independently-expressed oracle (a plain `case`, not the
  script's own `plan_for_role` restated).

Proven non-vacuous by hand before committing: swapping the RUN mode's
`properties` lane to invoke plain `npm test` instead of `npm run
test:properties` fails invariant 1 on every role whose plan includes
`properties` (6 of 10 cross-checks); dropping `properties` from the
coder's own printed plan fails invariant 2 on both coder cases; both
reverted before landing.
