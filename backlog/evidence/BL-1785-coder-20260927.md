## A finding: `git mv` does not create its own destination directory

Building the fixture's "sibling ticket... moved from backlog/active/ to
backlog/done/M8/" step, a bare `git mv backlog/active/X backlog/done/M8/X`
failed ("fatal: renaming ... failed: No such file or directory") until
`backlog/done/M8/` was `fs.mkdirSync`'d first - unlike a plain filesystem
rename or `git add -A` after `fs.renameSync`, `git mv` itself never
creates the destination's parent directory. Noted in the step file at the
call site.

## A finding: git's cherry-pick rename detection has a real similarity floor

Building scenario 02's fixture (a record already on the done copy),
`git cherry-pick -x` on the stray produced a genuine `modify/delete`
conflict instead of the expected "previous cherry-pick is now empty"
outcome, with a bare one-line ticket body (`id: BL-9787\n`, 12 bytes).
Measured directly: git's rename detection compares the stray's PARENT tree
against the TARGET tree by content similarity, and a one-line record
addition to a 12-byte file drops that ratio under git's ~50% default
threshold - the SAME fixture shape with a realistic multi-line ticket body
(id/title/milestone/type/status/etc., ~7 lines) cherry-picks clean and
correctly reports the by-then-already-landed patch as empty. This is a
fixture-realism artifact, not a production defect: every real ticket YAML
is well over 50 lines, so a one-line record addition never approaches this
floor in practice. Fixed by giving the fixture's sibling ticket a
realistic multi-line body throughout.

## A finding: the Examples table's row 1 "other path" could never be named

Scenario 03 row 1 used `swarmforge/scripts/bl9785_fixture_lib.bb` as the
disqualifying "other path", committed alongside an edit to the sibling's
own (allowed) `backlog/active/` file in the SAME commit. Measured
directly against the real code: `land-plan`'s own path-refusal loop
(`land_step_lib.bb` ~line 1826) walks `full-delivered-paths` - a plain
`git diff --name-only origin-main commit`, which git always returns in
tree (lexical) order - and returns on the FIRST disqualifying path it
finds; it does not collect or report every one. `backlog/active/...`
always sorts before `swarmforge/scripts/...`, so the escalation always
named the sibling's OWN (allowed-in-isolation) ticket file path, never the
actual disqualifying code path the scenario means to prove. Row 2
(`backlog/active/BL-9786-another-ticket.yaml`) happens to sort BEFORE
`backlog/active/BL-9787-fixture.yaml` (9786 < 9787) and so passed by
lexical coincidence, not because the mechanism differs.

This is pre-existing behavior (a single-first-match refusal, not a
collect-every-violation report) that the ticket's own "How" never asked to
change, and changing it would be real scope creep into a heavily-commented,
multiply-cited per-path loop several OTHER tickets' own scenarios depend
on verbatim. Corrected the one Examples cell instead - `android/bl9785_fixture.txt`
(a real top-level directory in this repo, confirmed: `ls -d */` lists it),
which sorts before `backlog/active/...` and is measured to be named
correctly - same disqualified-content kind (code/other, distinct from row
2's ticket-file kind), same commit shape, same assertions, only the exact
path value changed. Per the ticket's own INVEST note ("fixture shapes are
direction"), and the step handler's `OTHER_PATH_KNOWN_VALUES` updated to
match.
