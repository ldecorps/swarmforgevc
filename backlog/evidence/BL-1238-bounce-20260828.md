## D1 — `swarmforge/scripts/test/test_idle_clear_respawn.sh` scenario 01 is
host-dependent, not deterministic (failure class: `behavior`, blamed role:
coder — the test is new authorship in this ticket)

Scenario 01 fakes `tmux` by prepending a fixture `$FAKE_BIN` to `$PATH` and
expects the real-flow call chain (`done_with_current_task.bb` →
`process/exec` of `ready_for_next_task.sh`) to invoke that fake tmux for the
new `capture-pane -S -400` call this ticket adds to
`idle_clear_fullness_cli.bb`'s `own-pane-capture-lines`.

`ready_for_next_task.sh` carries shebang `#!/usr/bin/env zsh`. Invoked via
that shebang (not via `zsh -f`/`zsh -c`), zsh unconditionally sources
`~/.zshenv` even for a non-interactive script run. On any host where the
executing user's `~/.zshenv` prepends real tool directories onto `$PATH`
(mine does: `~/.local/bin`, `~/.npm-global/bin` — and `~/.local/bin/tmux` is
a real tmux binary), that re-prepend lands ahead of the test's `$FAKE_BIN`,
so the REAL system tmux runs instead of the fixture fake. Reproduced
directly:

```
$ bash swarmforge/scripts/test/test_idle_clear_respawn.sh
FAIL: 01: expected a respawn-pane call for the enabled role, log:
```

Instrumented `own-pane-capture-lines`'s `sh!` call and confirmed the real
tmux was invoked and errored against the fixture's fake socket path:

```
:err no server running on /tmp/tmp.cx962n9zc3/fake.sock
```

`read-context-fullness` therefore returns `proxy-percent nil` (fullness
`:unavailable`), which — correctly, per the ticket's own invariant 2/locked
decision — refuses to respawn. So the pure decision logic is NOT at fault;
the TEST's PATH-based fake-tmux injection is not robust to the zsh dotfile
sourcing that happens on this re-exec path.

This is not a new failure mode for this codebase — it is the exact,
documented hazard this project already guards against elsewhere. See the
comment at `swarmforge/scripts/test/test_bl1069_tmux_server_version.sh:11`:
"`zsh -f` (no rcs: `~/.zshenv` re-exports real credentials over fixture
values...)", and the same `zsh -f` isolation used in
`test_alternate_runtime_launch.sh`, `test_local_model_seat.sh`, and
`test_resume_on_start.sh`. Those tests invoke zsh directly
(`zsh -f -c "..."` or `zsh -f "$launch_script"`) so they can pass `-f`.
`test_idle_clear_respawn.sh` scenario 1 can't do that directly because the
fake-tmux call is reached through `done_with_current_task.bb`'s
`process/exec` of `ready_for_next_task.sh`'s own shebang line — but the same
class of isolation is still available and just wasn't applied: setting
`ZDOTDIR` to a directory with no `.zshenv` (or an empty tmp dir) for the
whole test run neutralizes the exact hazard, since zsh honours `ZDOTDIR`
from the inherited environment even when invoked via shebang.

Before this ticket, `maybe-clear-at-idle-boundary!` never shelled out to
tmux at all (it only checked `idle-clear-enabled?`), so this hazard existed
in the codebase's general pattern but had no code path in
`test_idle_clear_respawn.sh` that could actually trip it. BL-1238 is the
first ticket to route a real tmux subprocess call through this exact
re-exec'd-zsh-script path in a test, so this is new-in-parcel breakage, not
a pre-existing repo-wide failure (checked: `grep -rl
test_idle_clear_respawn backlog/` — no ticket already covers this).

**Remediation:** set `ZDOTDIR` (to `mktemp -d` or similar, with no
`.zshenv`) for the whole `test_idle_clear_respawn.sh` run, matching this
project's own established `zsh -f`-equivalent isolation convention. Confirm
by re-running the test on a host/user whose `~/.zshenv` prepends a real
`tmux` ahead of `PATH` (or simulate by temporarily prepending a decoy `tmux`
in `~/.zshenv` locally) and confirming scenario 01 still passes with the
isolation in place.
