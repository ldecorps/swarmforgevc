## Invariants (BL-654) — stated reason, no property test (both)

Both declared invariants quantify over which step-handler source files exist
under `specs/pipeline/steps` and how each one's own hand-written spawn code
decides one environment variable — a fact about test-infrastructure source
text, not a pure module's input domain a `fast-check` generator could sweep.
This repo's only property-test harness (`extension/test/*.property.test.js`,
`npm run test:properties`) drives TypeScript modules under `extension/`; this
ticket's `constraints:` scope every allowed edit to one existing step
handler, one new step handler and (documenter's) one doc sentence — a new
file under `extension/test/` is outside that list, and Babashka/JS step
handlers have no mutation or property harness of their own (BL-472,
engineering.prompt "Startup Tools").

1. *"BL-1318's acceptance verdict never depends on whether
   `PACK_STAFFING_SKIP_GATE` is present in the ambient environment... the
   feature's result with it unset equals the result with it set to 1 and
   with it set to 0."* — **stated reason, no property test**. The variable's
   only three meaningful states for this handler are `1`, `0` and unset
   (whatever else a pane might export is never a value the launcher's own
   gate logic branches on beyond truthiness); Scenario Outline 01 already
   enumerates that closed domain exhaustively inside the same parcel — a
   generator would sweep a domain a property test can't meaningfully widen.
   Structural discharge: both spawn sites now `delete` the variable before
   applying any explicit override, so no third spawn site can silently
   reintroduce ambient inheritance without also failing scenario 02's grep.
2. *"The override scenario (BL-1318 row 04) stays the only place the
   override is on in that handler, and it turns it on explicitly for that
   scenario alone."* — **stated reason, no property test**. This is a
   structural fact about one file's source (how many places assign
   `PACK_STAFFING_SKIP_GATE` to a truthy value), which scenario 02's own
   grep-based check already verifies at test time via the same mechanism
   BL-1445 uses for its shell-lane sibling (an `assignmentLines`-style count
   would be redundant here: `runRealParse`'s only truthy assignment is
   `extraEnv`'s own key, reached only when `ctx.override` is set, which
   scenarios 01/02/03/05/06/07's own step definitions never set).
