# BL-2069 — coder evidence, bounce fix (2026-10-08)

QA bounce (`backlog/evidence/BL-2069-QA-20261008.md`, commit 0a0c21c0c7)
found two defects, both in `briefing_email_lib.bb`. Both fixed in this
commit.

## D1 — the heal commit was not cheap

`send-unsent-briefings!`'s heal block called the injected `:commit-marker!`
adapter unconditionally every sweep. `commit-with-integrity!` still runs a
real `git add` + `git commit` through this checkout's `core.hooksPath`
pre-commit hook even when the result is `:nothing-to-commit` (byte-identical
marker) — QA measured that hook alone at ~7.5s per no-op attempt against
handoffd's own ~2.4-minute sweep cadence, stalling the poll loop on every
sweep with nothing to heal. The comment above the call called this
"cheap" — it was not.

**Fix**: a new `marker-uncommitted?` function (working-tree marker content
vs `commit-integrity-lib/default-show` at HEAD, via
`commit-integrity-lib/default-read`/`default-rev-parse-head` — never a
second lock-wait loop) decides whether there is anything to heal. Wired as
a new optional `:marker-uncommitted?` adapter (1-arg, called with
`briefings-dir` exactly like `:commit-marker!`), consulted before the heal
attempt; omitting it (every caller/test predating this fix) falls back to
the original unconditional attempt. `handoffd.bb` wires the real function
alongside `:commit-marker!`.

## D2 — commit-sent-marker! threw inside a linked worktree

`commit-sent-marker!` derived the working-tree root from
`commit-integrity-lib/absolute-git-dir` (the GIT DIRECTORY) via
`(fs/path git-dir "..")`. For a plain checkout `git-dir` is `.git`, and
going up one level happens to land on the work tree — but for a LINKED
worktree `git-dir` is `.git/worktrees/<name>`, and going up one level
lands on `.git/worktrees` (not a work tree at all, not even a git
directory on its own). `git -C .git/worktrees rev-parse --show-toplevel`
then fails, `(:out ...)` is `""`, and `(str/trim "")` is `""` — truthy in
Clojure — so the `(when git-dir ...)` nil-check never caught it.
`commit-with-integrity!` then threw on `:project-root ""`, and an earlier
pass had removed the try/catch that used to convert that into
`{:ok false :reason ...}` — so `send-unsent-briefings!` skipped
`briefing-sent` and the rest of that sweep's mailable batch entirely.

**Fix**: `resolve-briefings-project-root` now runs
`git rev-parse --show-toplevel` with `:dir` directly INSIDE the work tree
(`briefings-abs`) — never derived from the git directory at all. A linked
worktree's `.git` is a file (a `gitdir:` pointer), and git resolves
`--show-toplevel` correctly from inside either layout, so no special-casing
is needed. The result is accepted only when the subprocess exits zero AND
its output is non-blank (`str/blank?`, not a bare nil-check) — the actual
bug's exact shape. The removed try/catch is restored around the whole
1-arity body: `commit-sent-marker!`'s own docstring has always promised it
never throws.

`commit-sent-marker!` and the new `marker-uncommitted?` now share this
resolution (`resolve-briefings-project-root`) and the marker-relative-path
derivation (`marker-rel-path`), factored out so the two checks can never
answer "what is this marker's path" two different ways.

  counts `:commit-marker!` invocations (`commitMarkerCalls` in its JSON

  existing `extension/test/bl2069BriefingMarkerCommittedInvariants.property.test.js`

  that wants the call count.

**Non-vacuity, both fixes, proven by hand before this commit**: D1 —
temporarily replaced the new gate condition with a bare `true`, reran the
unit runner: the "NO commit attempt" test failed (`expected 0, got 1`);
restored, reran clean. D2 — temporarily reintroduced the old
`absolute-git-dir` + `(fs/path git-dir "..")` derivation, reran: both
linked-worktree assertions failed (`{:ok false}`, the old bug reproduced
and correctly caught by the restored try/catch rather than crashing the
runner); restored, reran clean.
