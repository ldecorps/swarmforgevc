# BL-1604 — coder pass, 2026-09-17

## What landed

`swarmforge/scripts/land_step_lib.bb` — a pure function `rows-to-restore`
plus an impure orchestrator `restore-other-tickets-registry-rows!`, called
from `land-plan`'s `:replay` build right after `write-tree-from-paths!`
overlays the landing ticket's own tip onto the scratch worktree (checked
out off `origin-main`), and BEFORE the replay commit is made — a restored
row rides the SAME land, never a second commit.

For each of the two shared registry files (`backlog/standing-reds.tsv`,
`swarmforge/scripts/property_suite_standing_allowlist.tsv`), it reads
origin/main's own copy (`git show <origin-main>:<path>`, fail-closed on an
unreadable ref or blob) and the replay tree's current copy, and appends
back every origin/main row whose owner is an open ticket other than the
landing one and whose key (the `file` column, or the allowlist's `owner
BL-<n>` rationale token) is absent from the replay tree — byte-identical,
origin order preserved. Open ticket ids come from `qa_hold_lib.bb`'s
`open-ticket-ids-for` (backlog/paused + backlog/active basenames) — the
one reader per the ticket's own direction, no second one written here.

`land_step_cli.bb` prints one `REGISTER_ROW_RESTORED <registry> <file>
<owner>` line per restored row, reading the literal from a new
`land-step-lib/register-row-restored-prefix` def rather than duplicating
the string at the print site — this also satisfies the ticket's own
`required_wiring` entry naming the literal in `land_step_lib.bb`.

The byte-identity replay-completeness check (`replay-completeness-offenders`)
is exempted for exactly these two registry paths — the sanctioned
divergence this ticket exists to create — every other own-path keeps the
unchanged full check.

## Declared invariants (BL-654) — both encoded as executable property tests

`swarmforge/scripts/test/bl1604_registry_row_restoration_property_runner.bb`
(2000 generative runs against `rows-to-restore`, seeded RNG, same
no-shared-framework convention as `bl1576_merge_drop_guard_property_runner.bb`):

- **Invariant 1** ("a land never reduces another open ticket's
  ownership"): `rows-to-restore` checked against an independent
  brute-force filter (owner open AND owner != landing AND key missing
  from replay) across random origin-line sets and a random replay-keys
  subset drawn independently of row construction order.
- **Invariant 2** ("the landing ticket's own rows are never protected
  from itself"): asserted DIRECTLY inside the same generative draw (never
  left to the aggregate equality check to catch by accident) — a
  landing-owned row missing from replay-keys must never appear in the
  result. The fixture deliberately puts the landing ticket's own id
  INSIDE `open-ticket-ids` (it is realistically open on origin/main until
  the coordinator's post-QA bookkeeping closes it), so the `(not= owner
  task-ticket-id)` clause is the only thing invariant 2 can be riding on
  — a first draft that left the landing id out of the open set passed
  even with that clause deleted, and was caught and fixed before this
  parcel forwards.

Both reachability floors (an open-other row missing from replay was
generated; a landing-owned row missing from replay was generated) are
asserted, never assumed. Non-vacuity proven by hand: deleting the
`(not= owner task-ticket-id)` clause fails invariant 2 immediately;
deleting the `(contains? open-ticket-ids owner)` clause fails invariant 1
immediately. Both restored before this commit.

`specs/features/BL-1604-a-land-never-carries-another-tickets-register-row-removal.feature`

fixture repo, same pattern as `bl1481SharedPathContentCheckSteps.js`. One
fixture bug was found and fixed while getting this green: `writeActiveTicket`

point the fixture's own Background claims it does. Fixed by making
`writeActiveTicket` commit atomically; all 5 scenarios pass.
