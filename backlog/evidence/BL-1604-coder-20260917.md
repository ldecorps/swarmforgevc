# BL-1604 — coder, 2026-09-17

## What was wrong

`land_step_lib.bb`'s tip-pure replay (`write-tree-from-paths!`) applies
each of a landing ticket's own paths WHOLE from the cited tip. For the two
shared registries every ticket edits — `backlog/standing-reds.tsv` and its
mirror `swarmforge/scripts/property_suite_standing_allowlist.tsv` — "whole
from the tip" meant a row another OPEN ticket owns, missing on the branch
for any reason (a merge on a batch branch, a stale worktree, never a
deliberate drain), was silently deleted from `main` by whichever parcel
landed next: BL-1548's land (2c1c44e2cc, 2026-09-16) removed BL-1595's
still-open register row this way, the register then read the red as
unowned, and BL-1429 dropped the intake cap to 1.

## The fix

`swarmforge/scripts/land_step_lib.bb`:
- `registry-rows-to-restore` — the ticket's own pure core: given origin
  rows, replay rows, the landing id and the open-id set, returns the
  origin rows whose owner is open and not the landing ticket, and whose
  `:file` is missing from the replay — exactly the rows a land must put
  back. A row owned by the landing ticket or by anyone not in `open-ids`
  (closed or absent) is never returned (the drain/retirement rule stays
  untouched).
- `register-tsv-rows`/`allowlist-tsv-rows` — raw-row readers for the two
  registries (owner from column 3 for the register, from the free-text
  `owner BL-<n>` token for the allowlist), each row carrying its exact
  source line (`:raw`) so restoration is byte-identical, never a
  re-serialization.
- `registry-restore-plan`/`restore-registry-rows!` — the impure half:
  reads both trees (`registry-blob-text` off `origin-main` via git,
  `registry-tree-text` off the scratch worktree's own filesystem, each
  absence-as-valid/failure-as-nil per this file's existing `blob-lines`
  convention), resolves `open-ids` from `origin-main`'s own
  `backlog/paused`/`backlog/active` trees, and appends any missing rows
  before the replay commit — printing `REGISTER_ROW_RESTORED <registry>
  <file> <owner>` per row. An unreadable registry on either side (or an
  unreadable open-id set) refuses the WHOLE replay, never a partial one.
- `replay!` — runs the restore right after `write-tree-from-paths!` and
  before the commit, so a restored row rides in the SAME commit as the
  ticket's own content; a refusal here fails the replay exactly like every
  other pre-commit refusal in this function. Returns `:register-restored`
  (the report lines) and `:register-restored-paths` (which registries were
  actually touched).
- `land-plan` — threads `:register-restored` into its `:replay` result,
  and excludes any `:register-restored-paths` from BL-1447's own
  post-build completeness check (`replay-completeness-offenders`): a
  registry a restore actually modified is EXPECTED to differ from the
  cited tip's own blob there, and that sanctioned divergence must never
  read as a dropped path. Every other path stays fully covered by that
  check, unchanged.
- `land_step_cli.bb` — prints each `:register-restored` line in the
  `:replay` branch; docstring updated.

Injection seams (`registry-restore-fn` on `replay!`,
`blob-text-fn`/`tree-text-fn` on `restore-registry-rows!`) follow this
file's own existing convention (BL-1481's `content-blocked-fn`) for the
one case no real git fixture can construct without corrupting the
repository: an unreadable blob.

## Invariants (BL-654)

Both declared invariants are encoded as one coder-authored, non-vacuous
property test:
`extension/test/bl1604RegistryRestoreInvariants.property.test.js`, driving
the real `registry-rows-to-restore` via
`swarmforge/scripts/test/bl1604_registry_restore_property_runner.bb`
(batched stdin/stdout, the BL-1003 convention — a bb process per draw is
dominated by `load-file`-ing this file's own dependency chain). 80 random
trials per run; reachability floors assert the generator actually produces
an open-other row missing from the replay, a landing-owned row missing,
and a closed/absent-owned row missing, every run.

Non-vacuity (recorded in the parcel commit): dropping the `(not= (:owner
row) landing-id)` clause first passed FALSE GREEN, because the generator's
`open-ids` did not yet include the landing ticket itself (a real gap —
open-ids there excluded it for an unrelated reason and the break rode
free). Widening `open-ids` to include the landing ticket (realistic: a
landing ticket is ordinarily still active on origin/main too) made the
same break go RED. Restored, property holds.
