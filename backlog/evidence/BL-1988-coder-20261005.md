## Helper review: `extension/test/helpers/hotfixLedgerDecision.js`

`uncommittedDecision(repoRoot, ledgerText, commit)` encodes exactly the
invariant's three cases:

1. Row undecided (`isDecided` false) → `null` (pass).
2. Row decided AND matches `git show HEAD:backlog/hotfix-ledger.yaml`'s row
   for `commit`, field-for-field (`state`/`human_decision`/`decided_at` via
   `decisionFields`), AND that committed row itself carries a human decision
   (`human_decision: approved|waived` with `decided_at` not null) → `null`
   (pass).
3. Row decided but either HEAD carries no human decision for it, or the
   live row's decision fields diverge from HEAD's → failure message naming
   the row.

No ledger row found for `commit` → failure message (the same failure shape
the old inline three-assertion checks produced on an empty extraction, so
no behavior regresses for that case).

Checked against `backlog/hotfix-ledger.yaml`'s real schema: `state`,
`human_decision` and `decided_at` always move together in the committed
ledger (`certified`↔`approved`, `waived`↔`waived`, `pending`/`stamp-open`↔
`null`) — there is no committed case where a legitimately decided row's
decision fields could diverge from HEAD while still being the same
decision, so the exact-match comparison in case 2 does not produce false
negatives against real ledger data.

## For the specifier: five features' step wording

`BL-1333`'s "Then both ledger rows for the reviewed commits still read
'pending'", `BL-1342`'s and `BL-1346`'s "Then the ledger row for the
reviewed commit still reads 'pending'", and `BL-1560`'s and `BL-1563`'s
"Then the ledger row for the reviewed commit carries no human decision"
now describe only the in-flight-review case. After a human certifies the
reviewed commit — exactly the case this hotfix exists to let pass — the
row no longer reads "pending" and does carry a human decision; the
scenario still passes only because the step binding's real assertion
checks `uncommittedDecision(...) === null`, not the literal prose anymore.

I think these are worth rewording (e.g. "carries no decision beyond what
HEAD's committed ledger records as the human's") so the Gherkin text
matches what is actually enforced post-certification — leaving it as-is
risks the same gap recurring: a future reader "fixing" the step binding
back toward the literal "still pending" wording would reintroduce this
exact red. Not blocking this stamp-off either way; the specifier's call.
