# BL-1419 — coder pass, 2026-09-05

## What was wanted

Human, verbatim: "first job: reflow text in daily breigin email. also make
it better looking overall." The briefing markdown is hard-wrapped at ~74
columns; `markdown_to_html_lib.bb`'s renderer turned every non-blank line
into its own `<p>`, so a wrapped paragraph, list item, quote, or bold span
fragmented into many broken elements on a phone mail client. Wanted:
block-aware reflow (consecutive wrapped lines join into one element) plus
a bounded, inline-styled phone layout for the HTML part, with the
plain-text part unchanged.

## What landed

- **`swarmforge/scripts/markdown_to_html_lib.bb`**: the renderer is now
  block-aware. New predicates `list-item-line?` ("- "), `blockquote-line?`
  ("> "), `list-continuation-line?` (indented, non-blank, not itself a
  list item), and `paragraph-continuation-line?` (non-blank, not the start
  of any other block type) let the main loop consume a whole run of
  consecutive lines belonging to one block before rendering it, joining
  with single spaces where the wraps were - a paragraph becomes one `<p>`,
  a run of "- " lines (with their indented continuations) becomes one
  `<ul>` of `<li>`, a run of "> " lines becomes one `<blockquote>`.
  Headings and GFM tables are untouched (already single-line/block
  constructs). `render-inline-markdown` gained a backtick-span rule
  (`` `code` `` -> `<code>`) alongside the existing `**bold**` -> `<strong>`
  one - both now apply to the JOINED block text, so a bold span that wraps
  across two source lines closes as one `<strong>` instead of leaving one
  side with an unclosed `**`.
- **`swarmforge/scripts/briefing_email_lib.bb`**: new `render-briefing-html`
  wraps the rendered body (and, when present, the diagram section's html)
  in a bounded single-column phone layout - a system font stack, every
  block element's spacing/type style carried INLINE via a literal
  open-tag string replace (`tag-inline-styles`, since
  `markdown-to-html-lib` only ever emits these tags bare), a header naming
  the briefing and its date before the first section, and the diagrams
  section under its own "Diagrams" heading after the body (BL-393's own
  body-then-diagrams ordering, kept). `compose-and-send-one!` now calls
  `render-briefing-html` instead of the bare `render-markdown-to-html` +
  the old `merge-diagram-html` (removed, now dead - `render-briefing-html`
  absorbs its job). The plain-text part (`content`) is untouched by any of
  this - it is composed and passed to `:send-email!` exactly as before.

## Declared invariants

1. **"A line break inside a markdown block never survives into the HTML
   part as an element boundary"** - the block-aware loop above; proven by
   the new unit tests (`markdown_to_html_test_runner.bb`) and acceptance
   scenario 01 (Outline: paragraph/blockquote/bold-span all join).
2. **"Every style the HTML part depends on is carried inline... complete
   with every `<style>` block removed"** - `render-briefing-html` never
   emits a `<style>` block at all (`tag-inline-styles` + literal
   replace); proven by `briefing_email_test_runner.bb`'s new invariant-2
   test (asserts no `<style` substring AND that stripping any would be a
   no-op) and acceptance scenario 04.
3. **"The plain-text part is byte-identical to the composed markdown"** -
   unchanged code path; proven by the pre-existing `content`-is-plaintext
   contract plus a new dedicated unit test and acceptance scenario 05.
