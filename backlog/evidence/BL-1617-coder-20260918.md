# BL-1617 coder pass

## Declared invariants - encoding

Invariant 1 ("the guard's reading of a subject is the land step's ... never
a second parser") is encoded by mirroring, not re-deriving: the guard's
`TICKET_PREFIXES="BL|GH"` and its leading-verb match
(`close|promote|approve`, any case) are the literal shapes of
`pipeline_stage_lib.bb`'s `known-ticket-prefixes` and `land_step_lib.bb`'s
`leading-verb-prefixes`. The shell test's scenario 10 (BL-897) asserts
both literals agree by reading them out of the live `.bb` files and
grepping the guard's own source for the matching shape - a drift on
either side of the boundary is a red test, not a silent divergence.

Invariant 2 (refuses only on a non-main branch, and only closed/unknown/
ambiguous; an unreadable origin/main warns and commits) is encoded
directly in the guard's control flow (branch check first, untagged-subject
early exit, ambiguity check, then closed/unknown via `git ls-tree`, with
the `ls-tree` failure path warning and exiting 0) and covered by the
shell test's scenarios 01-09 and the acceptance feature's 8 scenarios.

## What was wrong, and the fix

`land_step_lib.bb` attributes each path in a landing ticket's tip by the
first ticket id in the subjects of the commits that touched it, and
refuses (BL-1546) a path whose every owner is closed on origin/main -
correct, but an hour after the fact, on whichever parcel happens to carry
the stray path next. On 2026-09-16 a documenter commit subject-tagged
`BL-1576: evidence - ...` (BL-1576 closed) rode every documenter-lineage
tip and blocked two QA-approved lands (BL-1608, BL-1607) on 2026-09-17
until the specifier landed the file onto main by hand. A second land
refused the same day on `93f2031c3b` ("Revert fb9a53751e's wrongly-
reintroduced BL-1185/BL-1608 standing-red row") - two ids, no leading one,
read AMBIGUOUS, and BL-1185 had no ticket file anywhere on origin/main
(dropped by the 2026-08-28 reset), which the BL-1481 shared-path check
reads as unreadable and fails closed.

`swarmforge/scripts/check_closed_ticket_subject.sh` (new, wired into
`swarmforge/git-hooks/commit-msg` after `check_bounce_revert_scope.sh`,
`|| status=$?`, unmasked): on a branch other than `main`, extracts every
named ticket id from the commit subject (mirroring `extract-ticket-ids`)
and the leading id if the subject's own structure positions one at the
start, optionally after `close`/`promote`/`approve` (mirroring
`leading-ticket-id`/`leading-ticket-id-pattern`), reproduces
`subject-attribution`'s three answers (untagged: commit; one id, whether
leading or merely named alone: check it; several named with none leading:
refuse as AMBIGUOUS, naming every id), then for a single resolved id
reads `git ls-tree -r --name-only origin/main -- backlog/` and refuses
when that id's ticket file is found under `backlog/done/` and no other
folder there (closed, BL-1546) or under no folder at all (unknown there,
BL-1481's failure shape) - warning and exiting 0 when the `ls-tree` itself
fails (an unreadable origin/main, never treated as "closed").

## A near-miss during this pass

An initial `git reset --hard HEAD~1` after the first live probe (intended
only to drop the probe commit) silently reverted the two TRACKED files
this parcel had edited in the working tree (`commit-msg`,
`suite-manifest.tsv`) back to their pre-parcel content - `git reset
--hard` resets tracked files to the target commit regardless of
uncommitted changes; only the two new UNTRACKED files survived. Caught by
re-reading both files before committing (their edits were simply absent),
redone, and re-verified in full before this commit. No stray commit or
content loss reached git history at any point.
