# BL-1779 — coder pass — 20260926

## What changed

### Item 1 — an undeclared root never reads a fleet creds file or writes the primary-root record

- `swarmforge/scripts/swarm_identity_lib.bb`: new `declared-swarm-name`
  accessor — nil when `.swarmforge/swarm-identity` is absent or carries no
  `swarm_name` key, never defaulted to `"primary"` the way `own-swarm-name`
  is for every other caller.
- `swarmforge/scripts/fleet_telegram_creds_lib.bb`: extracted the shared
  "env-fallback or refuse" tail (`env-fallback-or-refuse`, private) out of
  `resolve-telegram-creds`, then added `resolve-telegram-creds-undeclared`
  — the undeclared-root entry point, which never calls `read-fleet-creds`
  at all and resolves only through `env-fallback-allowed?` (BL-622,
  unchanged), using the primary swarm name only for that comparison (the
  same value an undeclared root's env-fallback eligibility already used
  before this ticket). New `undeclared-root-refusal-message` — a kinder
  refusal than the per-swarm `refusal-message` (per the ticket's own "How"
  point 3), pointing at `./swarm` or channel provisioning instead of naming
  a swarm that does not exist yet.
- `swarmforge/scripts/front_desk_supervisor.bb`: computes
  `declared-swarm-name` alongside the existing `swarm-name`; skips
  `ensure-primary-root-recorded!` entirely when nil, and dispatches
  `resolved-telegram-creds` to `resolve-telegram-creds-undeclared` instead
  of `resolve-telegram-creds` when nil. Every other use of `swarm-name` in
  the file (env-fallback eligibility inside the undeclared path,
  `conflicting-swarm`, refusal messages) is untouched.
- `swarmforge/scripts/fleet_telegram_creds_cli.bb` (**scope addendum** —
  see below): same declared/undeclared dispatch, so the CLI reports the
  exact same answer the real supervisor would for a given root — never a
  rosier one for a debug probe.
