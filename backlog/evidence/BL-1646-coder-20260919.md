# BL-1646 coder evidence

## What was built

- `swarmforge/scripts/check_standing_red_register.sh`:
  - `added_or_changed_lines()` now subtracts every line already present in
    `HEAD`'s own version of the file, and — when `.git/MERGE_HEAD` exists —
    `MERGE_HEAD`'s own version too (new `inherited_lines()` helper), before
    handing the candidate `+` lines to each source's own judgment loop
    (invariant 2). Applies uniformly to all three sources (register,
    ledger, allowlist) since it lives in the one shared reader.
  - The ledger section is restructured from a flat `while` loop over
    candidate `- parcel:` lines into a block parser: it reads the FULL
    staged ledger content in order, tracks each row's `parcel` and
    `file_set` together, and judges a row only when its own `- parcel:`
    line is a member of the (now merge-aware) new-lines set. A row's
    ownership is resolved FIRST through the staged register's own
    `(hardening, file_set)` join (`ledger_row_owned_by_register`, the same
    join `standing_red_register_lib.bb`'s `build-report` uses) and only
    falls back to the row's own bare parcel id when the join finds no
    owner (invariant 1).
- `swarmforge/scripts/test/test_check_standing_red_register.sh` (new): 5
  cases on a real `git init` fixture under mkdtemp — a merge inheriting an
  owned row passes (the join); a merge inheriting an unowned row still
  passes (inherited, never authored); a linear commit adding a genuinely
  new unowned ledger row is refused; a linear commit adding a genuinely
  new register row naming a closed ticket is refused (regression); a
  linear commit adding a ledger row for an open ticket by its own bare
  parcel id still passes (regression).
- `specs/pipeline/steps/bl1646RegisterGuardLedgerJoinSteps.js` (new): the
  feature's 6 scenarios, driving the real guard against a real git
  fixture (main + role branches, forked before main gained the ledger
  row — the exact 2026-09-19 shape).

## Bug found and fixed during acceptance authoring

Scenario 04's own Given step ("the staged register names the open ticket
BL-4343 as owner...") is shared, word-for-word, with scenario 01's — but
01 is a merge scenario (register row lives on `main`, inherited by the
merge) and 04 is a LINEAR-commit scenario on `role` (which never merges
`main`, so a row committed only to `main` never reaches it). First draft
committed the ownership row to `main` only; scenario 04 failed with
"register names no open owner" even though the Given step had run.
Fixed by committing the SAME row to both `main` and `role` in that one
Given step, since its own text does not say which branch is relevant —
both are made true.
