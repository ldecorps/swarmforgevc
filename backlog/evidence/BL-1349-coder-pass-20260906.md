## Why each file was slow (real cost, not incidental)

- **onboarderLauncherPidGuard**: the `__LIVE__` branch (weight 3/10) hits
  `launch_onboarder.sh`'s `OLD_PID_FILE` fast-decline and returns almost
  instantly. The other three branches (weight 7/10 combined) fall through
  to a real `nohup bb onboarder_supervisor.bb … &` plus a poll-for-pid-claim
  loop — a real babashka JVM start, measured at ~6s/run on this host under
  the live swarm's normal concurrent load. This is exactly the IO the
  ticket's invariant 2 permits reducing sample count for.
- **bl1252CommitGuardAggregationInvariants**: all 5 properties `spawnSync`
  the real `run_commit_guards.sh` against bash-stub guards every run — real
  IO, cheap per-call (~25ms) but multiplied by 120 runs × 5 tests.
- **bl787NamedTunnelInvariants invariant 3**: NOT the launcher, the fake
  cloudflared, or the fake caffeinate — those resolve near-instantly.
  `stop_ancillary_services.sh`'s own `stop_ancillary_services_main` stops
  ALL FIVE lifecycle components (babysitterd, front-desk, onboarder,
  operator-runtime, tunnels) every run, and three of those five carry real
  unconditional `sleep 1` calls even though this fixture never starts them.
  That is production script behavior (real graceful-shutdown timing), out
  of this ticket's scope to edit — so the fixed ~4.9-6s/run floor stays,
  and numRuns is the only lever left.

## BL-654 invariant obligation

This ticket declares two `invariants:`, both about the SHAPE of the change
to existing property tests (no deletion, no weakening; sample-count
reduction only on IO-spawning properties) — not about new production-code
behavior. There is no new pure module for a coder-authored property test to
encode. The obligation is discharged instead by the ticket's own acceptance
scenario 02 ("no property is deleted to meet the budget"), which the new
step handler enforces mechanically (diffs each tuned file's `test(...)`
names and `fc.property(`/`fc.assert(` call counts against `HEAD`) — the
same kind of stated-reason carve-out as BL-1426's "parcel touches no other
file" invariant, except here the check IS executable, just via the
acceptance gate rather than a `*.property.test.js` file.

## Reach tradeoff, stated plainly

- `onboarderLauncherPidGuard`: numRuns 15→2. With weight 3/10 on the LIVE
  branch, 2 draws will sometimes miss it entirely (no explicit
  `assertReach` in this file, before or after this change). Measured worst
  case (both draws land in the expensive branch) is a consistent ~12.1s,
  comfortably under the 15s budget with margin.
- `bl1252`: numRuns 120→60. `CLEAN_PLAN`/`SUITE_ONLY_PLAN` are drawn
  directly at p=0.1 each (unchanged); missing one in 60 draws is
  `0.9^60 ≈ 0.18%` per branch — the file's own `assertReach` calls make a
  miss loud, not silent.
- `bl787` invariant 3: numRuns 6→2. A single run now covers at most 2 of
  the 4 (mode, keepalive) combinations rather than reliably all 4 — the
  most severe reach reduction of the three, forced by the fixed
  unconditional-sleep floor described above. No `assertReach` existed here
  before or after.
