## D1 — the fixture fix does not actually turn the test green; it only
moves the failure from case 03 to case 04

**Class:** test-isolation / incomplete-fix (the ticket's own stated
acceptance, "the test is green on main," is not met).

**Command:** `bash swarmforge/scripts/test/test_openrouter_provider_support.sh`
(run twice for reproducibility) from this worktree, commit `7ee58e3a91`
(coder's BL-1791 commit) merged in.

**Excerpt:**
```
PASS: 01: empty SWARMFORGE_OPENROUTER_ROLES keeps first-party auth; key never on disk
PASS: 02: listed roles use OpenRouter Skin; unlisted keep first-party; key never on disk
PASS: 03: role routing follows SWARMFORGE_OPENROUTER_ROLES membership
FAIL: 04: conf --model must still reach the settings JSON, got: {
  "model": "claude-sonnet-5",
  ...
}
```
The script uses `set -euo pipefail`; `fail()` calls `exit 1`. On `main`
(pre-BL-1791), case 03 fails FIRST, so the script exits there and case 04
never runs — this is why case 04's own defect was never observed until
now. BL-1791's fix correctly clears case 03, but the script still does
not reach "All BL-523 OpenRouter provider-support tests passed." — it now
fails at case 04 instead. The ticket's own "What is wanted" states the
test must be green on main; it is not, after this parcel.

**Root cause (confirmed, not a regression from BL-1791's own edit):**
`write_claude_settings_file` (swarmforge.sh) calls `resolve_role_model`,
which shells out to `model_factory_cli.bb resolve-model <role>
<pack-model>`. That CLI's `factory-state-dir` defaults to
`$MODEL_FACTORY_STATE_DIR`, or else **this repo's own real**
`.swarmforge/model-factory/` (`model-factory-store/repo-root`) — never
the test's own `$ROOT4` fixture root, because the test's zsh subshell
never sets `MODEL_FACTORY_STATE_DIR`. This worktree carries a real,
live `.swarmforge/model-factory/assignment.json` (gitignored runtime
state from actually running as the cleaner seat), which pins `documenter`
to `claude-sonnet-5` — so `resolve_role_model` returns that instead of
the fixture conf's `deepseek/deepseek-chat`, and case 04's grep fails.

**Confirmed not a logic bug — a missing fixture isolation flag.** Setting
an isolated state dir makes the passthrough correct again:
```
$ MODEL_FACTORY_STATE_DIR=/tmp/empty bb swarmforge/scripts/model_factory_cli.bb \
    resolve-model documenter "deepseek/deepseek-chat"
deepseek/deepseek-chat
```

**Precedent already in this test suite** for exactly this isolation, on
the sibling `MODEL_STEWARD_STATE_DIR` env var (same
`model-factory`/`model-steward` family, same repo-root-default shape):
`swarmforge/scripts/test/test_pack_staffing_gate.sh` sets
`MODEL_STEWARD_STATE_DIR="$STATE_DIR"` before every `bb "$CLI" ...` call
so it never reads this repo's real runtime state. `test_model_factory_cli.sh`,
`test_model_factory_runtime_wiring.sh` and
`test_remote_control_launch.sh` do the same for `MODEL_FACTORY_STATE_DIR`.
`test_openrouter_provider_support.sh` never sets `MODEL_FACTORY_STATE_DIR`
at all, so it is exposed to whichever real overlay happens to exist in
whatever worktree runs it — different roles' worktrees (each running
the live swarm) may see different results, or none at all, depending on
their own `.swarmforge/model-factory/assignment.json` contents at the
moment the test runs.

**Why this is not a nit:** BL-1791's own approval_context and "What is
wanted" name "the test is green on main" as the acceptance bar; per the
cleaner's own review discipline (never downgrade a guardrail/behavior gap
to a nit without checking the call site — done above), this is a real gap
against the ticket's own explicit acceptance criterion, not a hypothetical.

**Remediation pointer (not applied here — coder's domain, same file the
parcel already touches, no `swarmforge.sh` edit required — the ticket's
own FIRM invariant is preserved):** export
`MODEL_FACTORY_STATE_DIR="$ROOT4"` (or a dedicated empty tmp dir) around
case 04's `zsh -c` invocation, mirroring
`test_pack_staffing_gate.sh`'s `MODEL_STEWARD_STATE_DIR="$STATE_DIR"`
pattern. Worth checking whether cases 01–03's own `zsh -c` blocks need
the same isolation for robustness (they currently pass in this worktree
only because none of them assert on `documenter`'s or another
overlay-affected role's resolved model — `role_uses_openrouter`
membership and `unset ANTHROPIC_API_KEY` don't route through
`resolve_role_model`).
