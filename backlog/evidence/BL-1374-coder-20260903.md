# BL-1374 — coder pass, 2026-09-03

A sync merge is not credited with its passengers.

Built to the recorded ruling (`human_ruling:`): **option 3, both** — the code
fix here, the discipline rule the specifier's to write.

## The mechanism, corrected by measurement

The ticket names `own-commit-changed-paths :delivered` as the over-inclusion.
Driving that shape in a fixture shows **no defect**: git's path-scoped history
walk (`path-attributing-commits`) already elides a merge that is TREESAME to a
parent on the path, so a sync merge that merely carried a passenger through is
invisible to the attribution. A probe of exactly the ticket's described shape
returned `{:owners #{"BL-9002"}}` — clean.

The shape that actually bites is the **clean auto-merge**. When both sides
changed the same file in different places, the merge result differs from
**both** parents, so the walk *does* report the merge, and its subject decides
the owner of content its merger never wrote.

Measured on the live tip that produced the report, `5d4486eb08` ("Merge main
into swarmforge-QA for BL-1309 human_approval restore"):

| question | answer |
|---|---|
| `git diff-tree --cc --name-only` | names BL-1296's *and* BL-1309's ticket files |
| the same command **with its patch** | **not one hunk** — the merge authored nothing, anywhere |
| owners of `BL-1296-…yaml` before this parcel | `#{"BL-1296" "BL-1309" "BL-1328"}` |
| owners after | `#{"BL-1296"}` |

So `--cc`'s *name list* is not the discriminator — it names every path whose
result differs from all parents, which a clean auto-merge does without the
merger writing a line. The **dense combined patch** is: git's own
simplification drops exactly the hunks that match a parent.

## The fix

`land_step_lib.bb`:

- `merge-authored-paths` — the paths a merge produced a `diff --cc` / `diff
  --combined` header for, i.e. actually wrote a line at. nil (never `#{}`) on
  an unreadable read, this file's fail-open convention.
- `path-owner-tickets` now keeps a merge as an attributing commit **only**
  where that merge wrote something. Non-merge commits are untouched, and an
  unreadable combined diff propagates as blindness rather than as "the merge
  wrote nothing".

This is `sibling-own-line-changes`' rule ("a merge authors no lines of its
own") applied to the delivered side, with the one exception a merge genuinely
can author — a conflict it resolved — kept, because invariant 3 forbids
dropping any path the ticket's own work changed.

## Declared invariants (BL-654)

| # | Invariant | Property | Non-vacuity |
|---|-----------|----------|-------------|
| 1 | a genuine entanglement is still refused | **P1**, both directions — a real shared-file edit is refused naming the sibling, **and** a land with no genuine entanglement is not refused at all | restored the pre-fix crediting → **7 FAIL P1/P2/P3** |
| 2 | detection stays as wide as today | **P2** — every sibling whose work is on the tip and not on origin/main is still reported as unlanded | (same break) |
| 3 | no path the ticket's own commits changed is dropped | **P3** — every own path is in the replay set or the run refused; plus a merge that really resolved content still owns that path | made merges own nothing → **10 FAIL** in properties, **3 FAIL** in the unit suite |

Two vacuity traps were found and closed while proving this, both in my own
tests:

- **P1's first half alone is satisfied by a fix that refuses everything.** The
  pre-fix break produced *zero* property failures, because every assertion that
  mattered was guarded by "if the run replayed" and the buggy code refused. The
  runner now carries `:entanglement-expected?` **out of the fixture builder**
  and asserts the no-false-refusal direction too.
- **Unit case 05 passed with merges owning nothing**, because its fixture had
  no own path: every delivered path was then excluded as a sibling's and the
  *different* BL-1343 refusal fired, wearing the same face. The fixture now has
  own work, and the assertion names the shared-path refusal specifically.

**Generator reach** is asserted: all four fixture shapes, plus specifically the
shared-and-refused case (P1's first half) and a passenger-only case that
actually replayed (P1's second half). The shared path is **constructed** — this
ticket's edit is derived from the passenger's own file rather than drawn beside
it, since two independently drawn filenames would collide essentially never.

## `qa_e2e_procedure` step 5, answered rather than assumed

> Construct, if one exists, a case where a path reaches the branch ONLY via a
> merge and the parcel must still replay it. If none can be constructed, record
> that finding.

**Such a case exists and is preserved.** A merge that resolves a conflict
writes content neither parent holds — it reaches the branch only via that
merge. That is fixture case 05 in the unit runner and the `:resolved-merge`
shape in the property runner, and it is exactly why the fix is "a merge owns
only what it wrote" rather than `sibling-own-line-changes`' flat "a merge owns
nothing". Breaking that exception fails three unit assertions and ten property
checks.

The related shape the ticket worried about — content reaching the branch on an
*earlier* merge — is already safe by a different mechanism: `own-paths` builds
its set from `full-delivered-paths`, the two-tree diff against origin/main
(BL-1315), so attribution only ever *excludes*. That is BL-1315's own case 06,
still green.

## Self-audit (Article 2.3)

**One efficiency fix.** `path-owner-tickets` is asked once per delivered path,
and each call read the whole merge's combined diff again — on a tip with many
paths and a few merges, the same diff dozens of times, on the land step's
critical path that the BL-1309 ruling already made the everyday one. The read
is memoized per `(root, commit)` now, the same posture `own-paths`' own
`blocking-for` takes. Safe by construction: a commit sha addresses its content,
so the answer for a given sha cannot change under the memo.

**On the declared `required_wiring` anchor.** It names
`land_step_lib.bb::own-commit-changed-paths` as "the delivered-side path set
this ticket narrows". The measurement above says otherwise: the over-inclusion
is in the attribution walk (`path-owner-tickets`), not in
`own-commit-changed-paths`, and that is where the narrowing landed. The anchor
string is present in the file either way (it is discussed in five places), so
the gate passes — but it passes for the wrong reason, and saying so is more
useful than quietly satisfying it.

Routing the fix through `own-commit-changed-paths :authored` was considered and
**rejected on evidence**: that semantic is `--cc --name-only`, which is exactly
the list this ticket proves over-reports. Using it would have reinstated the
defect under a better name.

**A finding this parcel does not fix.** The same over-report means
`own-commit-changed-paths :authored` credits a clean auto-merge's combined
paths as "authored" for the two send-time gates (BL-1297's scope gate and
BL-1240's unregistered-test gate). Those gates fail *closed* on it — an
over-wide authored set makes them stricter, never permissive — so nothing is at
risk and it is out of this ticket's scope. Surfaced here so whoever meets a
puzzling scope-gate refusal on a merge has the reason in hand.
