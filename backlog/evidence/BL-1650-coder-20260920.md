# BL-1650 coder evidence (QA bounce fix, D1)

## What was wrong

`land_step_lib.bb`'s `replay!` (the BL-1650 items 1-2 stray-cherry-pick
loop, ~line 2139) treated ANY nonzero `git cherry-pick -x` exit
identically to a real content conflict: `--abort` and fail the whole
replay closed (`LAND_ESCALATE`). Git also returns nonzero, with "The
previous cherry-pick is now empty, possibly due to conflict resolution" on
stderr and a pending `CHERRY_PICK_HEAD`, when the stray's content is
ALREADY present on the target tree under a different commit - the
everyday shape once a stray of this kind has been hand-landed once (QA's
own reproduction: BL-831's evidence file, landed by the specifier's manual
`cherry-pick -x` on 2026-09-19, then hit BL-1650's own new automation the
next day trying to land it again). That is not a conflict; it is exactly
the "already landed" case the ticket's own FIRM constraint describes for
the sibling-scoring side of this same fix ("an ancestor whose every path
is byte-identical to main ... is reported as landed, never as entangled")
- applied here to the cherry-pick side, which had no such handling.

## The fix

- `cherry-pick-already-applied?` (new, pure): true when a cherry-pick
  result's stderr matches git's own "previous cherry-pick is now empty"
  message - the same signal QA's own reproduction observed directly.
- The stray-cherry-pick loop now branches three ways: a clean cherry-pick
  records `:landed-sha` as the new commit as before; an already-applied
  one runs `cherry-pick --skip` (clears the pending `CHERRY_PICK_HEAD`,
  content is already there) and records the SAME entry shape with
  `:already-applied? true` and `:landed-sha` = the tree's current tip
  (unchanged - nothing new was committed); anything else still `--abort`s
  and escalates exactly as before.
- `land_step_cli.bb` prints `LAND_STRAY_EVIDENCE_ALREADY_LANDED <sha>
  already at <landed-sha> <paths>` for the already-applied case instead of
  `LAND_STRAY_EVIDENCE_LANDED <sha> -> <landed-sha> <paths>` - distinct
  and equally auditable (invariant 2's "nothing lands silently"), since no
  new commit with an `-x` trailer was actually made for it.

## Tests

- `land_step_lib_test_runner.bb`: new case reproducing D1 exactly (a
  stray committed on a role branch, origin/main separately carrying the
  SAME path+content under a different commit before the landing ticket's
  own tip) - asserts `:action :replay` (not `:escalate`), the stray is
  still recorded in `:stray-landed` with `:already-applied? true`, its
  `:landed-sha` is origin/main's own tip (not a new commit), and the
  sibling still reads `LANDED_SIBLING`. **Non-vacuity verified by hand**:
  reverted the fix to a scratch copy, reran - 6 assertions failed exactly
  as expected (the stray dropped out of `:stray-landed` entirely, the
  action became `:escalate`); restored the real fix, reran clean.
- `specs/features/BL-1650-...feature` scenario 05 (new) + step handler
  additions in `bl1650LandStepPureEvidenceStraySteps.js`: drives the real
  `land_step_cli.bb` end to end on the same fixture shape, asserts
  `LAND_REPLAY` (exit 0), a `LAND_STRAY_EVIDENCE_ALREADY_LANDED` line
  naming the stray's own commit and path, no `LAND_STRAY_EVIDENCE_LANDED
  ` (fresh-land) line, and `LANDED_SIBLING`, never `ENTANGLED_SIBLING`.
- Ran the full existing battery unaffected: `land_step_lib_test_runner.bb`
  (all pre-existing cases plus the new one), the BL-1650 acceptance
  feature (5/5), BL-1546's own acceptance feature (4/4, re-verifying the
  closed-owner-refusal side this fix does not touch), both registration
  guards (`check_test_file_registration.sh`,
  `check_feature_handler_registration.sh`), and the full property suite
  (`npm run test:properties`).

## FIRM constraints held

- Fail-closed posture unchanged for a genuine conflict: the `:else`
  branch (`--abort` + escalate) is untouched.
- The classifier (`cherry-pick-already-applied?`) is pure; the git call
  and the `--skip` recovery live beside the existing cherry-pick loop's
  own git calls, same as the ticket's own "How" direction.
- The step handler edit lands in the same commit as the feature edit
  (BL-233).
