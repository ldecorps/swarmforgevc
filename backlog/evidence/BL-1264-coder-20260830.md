# BL-1264 — coder pass, 2026-08-30

An absent approval context is an absent key.

## 1. Pre-fix baseline (qa_e2e_procedure step 1)

From `extension/`, before any change:

```
CURSOR_API_KEY=fixture-key npx vitest run test/backlogDashboard.test.js
 × a live active ticket with human_approval: pending appears in needsApproval with its id and title
+     approvalContext: undefined,
      Tests  1 failed | 46 passed (47)
```

The recorded diff is the extra own key, exactly as the ticket predicts.

## 2. Root cause confirmed (step 2)

`extension/src/metrics/backlogDashboard.ts` — the two halves read together:

```ts
export interface NeedsApprovalEntry {   // :42-46
  id: string;
  title: string;
  approvalContext?: string;             // optional
}

.map((item) => ({                       // :157-165
  id: item.id,
  title: item.title,
  approvalContext: item.approvalContext,  // unconditional
}));
```

The optional marker is the tiebreaker and it points at the producer. The
test imports `node:assert/strict`, so `deepEqual` is `deepStrictEqual`, under
which an own key valued `undefined` is not an absent key.

## 3. The fix

A conditional spread: the property is emitted only when
`item.approvalContext !== undefined`. Deliberately `!== undefined`, not a
truthiness test — an empty-string context is a real value the ticket carries
and must survive (pinned by its own unit test and by the property's
`emptyContext` reach requirement). No sentinel, no empty string, no null in
place of a missing context.

The file's own "explicit rather than absent" comment at :63-68 was read
before applying anything: it is about `needsApproval` and `notDoneCount`
being always present at the TOP LEVEL so both surfaces can render a no-data
state. It says nothing about a per-entry optional field, and the entry's own
type declares the opposite. A comment on the fix says so, so the next reader
does not have to re-derive it.

Nothing else moved: the filter, the interface, the top-level posture, the
schema version and the shape of `backlog.json` are untouched, and the test
was not relaxed.

## 4. Unit tests (step 3)

Four added to `test/backlogDashboard.test.js`, all asserting with
`hasOwnProperty` rather than truthiness — a truthiness check passes for BOTH
shapes and would prove nothing:

- no context → own keys are exactly `['id', 'title']`;
- with a context → the key is present and carries the value;
- an EMPTY-STRING context is kept, not pruned — only `undefined` means absent;
- the serialised form is identical to the pre-fix shape's.

47 → 51 tests in that file, all green.

## 5. Declared invariant (BL-654) — executable

`extension/test/bl1264OptionalKeyAbsenceInvariants.property.test.js`,
`npm run test:properties` lane. 3 properties, all pass, driving the REAL
compiled `computeNeedsApproval`.

Generator reach, asserted every run: `noContext`, `withContext`,
`emptyContext`, and `mixed` (one list holding both kinds). The no-context
state is the one that matters — the unconditional copy and the conditional
spread AGREE whenever a value exists, so a generator that only produced
tickets with contexts would pass against the defect. Tickets without a
context are built with the property genuinely absent, never set to
`undefined`, which is the shape a YAML file without `approval_context:`
actually produces.

The second property is the invariant stated in full generality: no entry
carries ANY own key valued `undefined`, not just this one.

Non-vacuity: restoring the unconditional copy fails 2 of the 3 properties.
The third (serialised forms identical) passes either way BY DESIGN — it is
the property that explains why `backlog.json` never carried the key, so its
passing under both shapes is the point, not a gap.

## 6. Artefact unchanged (step 4)

pending tickets — one with a context, one without — and requires

would mean the real context was lost; twice would mean the absent one leaked.
