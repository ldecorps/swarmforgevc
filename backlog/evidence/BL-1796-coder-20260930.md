  exactly as before when `named-base?` is false).

## Invariant check

Two declared invariants:

1. "A seat whose own active launch CLI names an OpenAI-compatible base
   ... is respawned onto that base's provider, or onto no cloud provider
   for a local base, never onto a provider named only by a flag in the
   respawning process's environment." - encoded directly: scenario 01
   (5 cases, local bases under every one of the four flags) and scenario
   02 (4 cases, a named cloud host under a DIFFERENT flag) in the
   acceptance feature above; both drive the real generator and the real
   lib, no reimplementation.
2. "A seat whose launch script names no base, or that has no launch
   script, gets exactly the respawn environment it gets today." -
   scenario 03 (Claude, no base, takes the flag) plus the full regression
   set above (BL-1495 scenario 03's own no-launch-script case, and
   `test_handoffd_auth_observe_wiring.sh` 02's no-launch-script case) -
   both pre-existing contracts stay green unchanged.

No separate property test: both invariants quantify over a small,
already-enumerated set (four cloud hosts × the flag that names a
different one, plus the two `named-base?`/`not named-base?` arms), which
the acceptance's 10 cases and the regression suite's own pre-existing
cases already cover exhaustively - a fast-check property over the same
finite space would not strengthen either check.
