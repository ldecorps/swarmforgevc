# BL-1493 — coder evidence, 2026-09-16

## The fix

`context_telemetry_store.bb` gains `latest-event-for-role`: reads the
log's TAIL in successively doubling bounded chunks (`RandomAccessFile`),
starting at `initial-tail-chunk-bytes` (64 KB) and capped at
`default-tail-window-bytes` (8 MB, about a day of events at the ticket's
own measured volume). A role whose row sits near the tail — the common
delivery-hop case — resolves on the FIRST, smallest chunk; the window
only grows when that attempt finds nothing. A `*read-tail-chunk*`
dynamic var is the read primitive (mirrors `chase_sweep_lib.bb`'s
`*read-handoff-file*` seam) so the acceptance CLI can count bytes without
duplicating the chunk-growth logic.

`llm_cost_ledger_lib.bb`'s `latest-role-usage-from-context-events` now
calls this instead of `read-events!` + filter + sort + last. The returned
record shape is byte-for-byte identical; `read-events!` itself is
unchanged for its other callers.

## Scenario 01's own claim, verified directly

Built a 200000-row / 24 MB fixture with `cleaner`'s only occurrence 50
rows from the end (matching the acceptance scenario exactly) and counted
bytes via the `*read-tail-chunk*` seam:

```
result: {:role cleaner, ...}
bytes read: 65536 of 23999996 = 0.27%
```

Well under the ticket's 5% bound — the first (smallest, 64 KB) chunk
already reaches the row.

## Declared invariant — coder-authored property test

`swarmforge/scripts/test/bl1493_usage_lookup_bounded_property_runner.bb`
(BL-654, coder-authored first pass), two properties over randomly
generated logs (fixed-seed `java.util.Random(1493)`, 60 trials):

- **P1** (within-window-matches-full-read): for a role whose last
  occurrence lies within a window sized from that occurrence's own byte
  offset plus a margin covering the preceding line (constructed so the
  target line can never be the window-edge line the reader
  unconditionally drops), `latest-event-for-role`'s answer equals the
  reference "full read, filter, sort, take last" computation.
- **P2a/P2b** (outside-window-or-absent-yields-nil): a window sized to
  land strictly before a role's only occurrence, or a role absent from
  the log entirely, yields nil.

Non-vacuity checked by hand (see the runner's own header comment for the
three specific breaks tried and restored): reversing the scan order and
dropping the role filter each reliably fail the properties; the
window-edge line-drop guard's own failure mode is a documented design
note (not reliably reproduced by this ASCII-only generator — the
acceptance scenario's real NUL-tail case is the reliable check for that
path).
