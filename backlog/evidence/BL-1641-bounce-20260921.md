## D1 — `mainHasBriefing` fails OPEN on a git read error, contradicting its
own documented contract and the ticket's FIRM invariant

`extension/src/tools/night-closing-ceremony-run.ts`:

```js
function mainHasBriefing(target: string, dayKey: string): boolean {
  try {
    execFileSync('git', ['cat-file', '-e', `main:${briefingRelPath(dayKey)}`], {
      cwd: target,
      stdio: 'pipe',
    });
    return true;
  } catch {
    return false;
  }
}
```

The function's own comment, immediately above it, states the intended
contract:

> Absent on main: the check must fail closed on any git error (including
> "not a repository") - a broken read must never read as "safe to write".

The implementation does the opposite. `git cat-file -e main:<path>` exits
non-zero both when the path is genuinely absent AND on any other git-level
failure (corrupted/missing `main` ref, `GIT_DIR` misconfiguration, a
transient I/O error, git itself failing to run). The `catch` block collapses
every one of those into `false` ("briefing absent"), which is exactly "safe
to write" — the opposite of fail-closed. `false` is the value that lets
`landDocumenterBriefing`/`composeHeadlessBriefing` proceed past their
early-return guard and commit a new `docs/briefings/<day>.md`.

Empirically confirmed (repo root, not committed):

```
$ git cat-file -e main:docs/briefings/2026-09-18.md   # file present
exit: 0
$ git -C /tmp/nonexistent-dir cat-file -e main:docs/briefings/2026-09-18.md
fatal: cannot change to '/tmp/nonexistent-dir': No such file or directory
exit: 128
```

Any of these non-zero-for-a-reason-other-than-absence outcomes reads,
today, as "main does not have the briefing" and clears the way to write —
onto a `target` that, per the ticket's own git-safety pattern
(`rev-parse --git-common-dir`, BL-1390), is exactly the kind of shared
checkout where a transient git failure is plausible, not hypothetical.

**Why this is in scope for this parcel and not a pre-existing condition
being merely inherited:** `mainHasBriefing` is new in this commit, written
FOR this ticket's FIRM constraint ("a briefing main already has is never
replaced or rewritten, whether or not its email went out") and invariant 1
("The ceremony never adds, replaces or rewrites a docs/briefings/<day>.md
that main already has"). The bug is the single guard that constraint rests
on, getting its own stated contract backward.

**Coverage gap, not just the bug:** neither the acceptance feature
(scenario 03 exercises only the *successful*-detection case, where
`git cat-file -e` genuinely succeeds) nor the declared-invariant property
test (`bl1641EnsureBriefingInvariants.property.test.js`) drives
`mainHasBriefing` through a git-error path — the property test's own
comment says invariant 1a is intentionally left to the acceptance e2e
because it "quantifies over real repository state," but the e2e itself
never induces a read failure. So the property this ticket declares is not
actually pinned against its own most direct violation.

**Fix shape (direction, not mandate):** swap the `catch` block's return to
`true` (fail closed: an unreadable check is treated as "main might already
have it," so no write happens), and add a test that forces `git cat-file
-e` to fail for a reason other than path-absence (e.g. an unreadable/
corrupted `.git`, or stubbing the exec call) and asserts `landDocumenter
Briefing`/`composeHeadlessBriefing` both return null/false rather than
writing.
