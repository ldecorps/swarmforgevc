## Careful read of the change

- `classifyApprovalRulingRequirement` is pure and total over the four
  outcomes the ticket names (`ok` with/without options declared,
  `ruling-required`, `unknown-option`), and `recordApprovalReply`'s widened
  optional `ruling` parameter is validated by the CALLER, never inside the
  writer itself — confirmed by reading `computePausedPagerApproveOutcome`,
  which calls the classifier before ever reaching the writer, and by the
  coder's own note that rescuing an unvalidated caller inside the writer
  would hide the exact defect class this ticket exists to catch.
- `recordApprovalReply` routes through the SAME pre-existing
  `rulingHumanApprovalText`/`approveHumanApprovalText` pair the bot's
  callback path already used — one writer, not a parallel one, satisfying
  invariant 1's "an approval PATH, never a second definition" shape (the
  same posture this session's other tickets built on today).
- Invariant 2 (an existing ruling is never overwritten) is upheld
  structurally: `recordApprovalReply` only ever calls
  `rulingHumanApprovalText` when a NEW `ruling` argument is passed; a plain
  approval (`ruling` undefined) always takes the `approveHumanApprovalText`
  branch, which never touches the `human_ruling:` block. Confirmed against
  `HUMAN_RULING_BLOCK_PATTERN`'s replace only firing inside
  `rulingHumanApprovalText`.
- Invariant 3 (no-options ticket behaves exactly as before) holds because
  `classifyApprovalRulingRequirement` returns `{kind: 'ok'}` immediately
  when `options.length === 0` and no `ruling` was sent, taking the same
  `approveHumanApprovalText` path as pre-parcel code.
