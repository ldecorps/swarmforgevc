## D1: a second liveness check that can disagree with `./swarm status`/`./swarm ensure` (firm constraint violated)

The ticket's constraints section is explicit and marked firm:

> Do not write a second liveness check. `operator-healthy?` is the one that
> `./swarm status` and `./swarm ensure` already agree on; a watch that
> decides differently would produce a runtime that status calls dead and
> the watch calls fine, or the reverse.

and the "How" section:

> Reuse `operator-healthy?`/`ensure-operator!` rather than writing a second
> liveness check that can disagree with `./swarm status`.

The parcel does not do this. `swarm_ensure.bb:282` (`operator-healthy?`)
and `swarm_status.bb:169` (`daemon-from-pid`, used for the
`"operator-runtime"` row) both resolve liveness via bare
`pid-alive?`/`ProcessHandle.isAlive` — no command-line check. The new
`operator_runtime_watch_lib.bb:70-91` (`runtime-alive?`/`healthy?`)
deliberately adds a command-line check
(`operator-runtime-cmdline?`) so a pidfile naming a **live but unrelated**
process (pid reuse) reads as DOWN. That extra check is correct per this
same ticket's own required scenario (`dead-runtime-is-restarted-01`, row "a
pidfile naming an unrelated pid"; qa_e2e step 3: "Pid reuse is the case a
naive `kill -0` check gets wrong") — but it makes the watch a **second,
stricter** liveness check, exactly what the constraint forbids, and the two
now disagree on precisely the case the ticket calls out.

Concrete divergence: operator_runtime.bb crashes, its pid gets reused by
any other process before the watch's own interval fires. In that window:
- The new watch correctly reads DOWN and restarts (this parcel's fix
  working as intended).
- `./swarm status` still reports the runtime alive (bare pid check).
- Worse, a human running `./swarm ensure` during that same window sees
  `operator-healthy?` = true and skips repair — reproducing this ticket's
  own root cause (a down runtime that nothing restarts) through the one
  path the constraint was written to keep trustworthy.

This is not a hypothetical scope gap; the coder's own comment in
`operator_runtime_watch_lib.bb:16-20` names the conflict directly
("swarm_ensure.bb's own operator-healthy? is intentionally left
untouched... strengthening that shared check would false-DOWN an
established, passing fixture") and resolved it unilaterally in favor of
scenario correctness over the firm constraint, without a `note` to the
specifier/architect flagging the tension.

I checked the "outside this ticket's scope" claim rather than taking it on
faith: `test_swarm_ensure.sh`'s `make_fixture` (called by all 48 scenarios
in that file) seeds a default "operator healthy" baseline via `echo "$$" >
runtime.pid` — the test script's own pid, whose command line is never
`operator_runtime.bb`. That is the one fixture the coder's comment refers
to, and it is shared infrastructure, not per-scenario duplication — a fix
touches it once, not 48 times.

### Remediation
Make `operator_runtime_watch_lib.bb`'s `healthy?`/`runtime-alive?` the
**one** true operator-runtime liveness check, reused by all three
consumers instead of duplicated:
1. `swarm_ensure.bb`'s `operator-healthy?` (`:282`) load-files
   `operator_runtime_watch_lib.bb` (both already `load-file` several
   sibling libs the same way — precedented, no circularity) and delegates
   to `operator-runtime-watch-lib/healthy?` instead of the bare
   `(pid-alive? (operator-pid))`.
2. `swarm_status.bb`'s `"operator-runtime"` row (`:214`,
   `daemon-from-pid`) does the same, rather than the generic bare
   `pid-alive?` path used for the other daemon rows (front-desk,
   babysitterd, cursor-bridge are out of scope here — narrow this to the
   operator-runtime row only).
3. Update `test_swarm_ensure.sh`'s `make_fixture` "operator healthy by
   default" stanza (and the two other spots that seed a specific operator
   pid, `:266`/`:474`, already using an intentionally-dead `999999` so
   those are unaffected) to fake a process whose command line contains
   `operator_runtime.bb` — mirrors the pattern this ticket's own
   `bl993_watch_survives_runtime_death.sh` and property runner already use
   for a real fixture process — so the shared "operator is healthy"
   baseline stays true under the strengthened check.
4. Re-run `test_swarm_ensure.sh` in full (48 scenarios) after the fixture
   change to confirm no other scenario silently depended on the old bare
   check.

This keeps the cmdline-aware check the ticket's own required scenario
needs, while restoring the single-source-of-truth the constraint demands —
`./swarm status`, `./swarm ensure`, and the new watch all agree again,
including in the pid-reuse case.
