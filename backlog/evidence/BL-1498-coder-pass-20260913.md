## Invariants (BL-654) — stated reason, no property test (both)

Both declared invariants quantify over the behavior of external processes
(zsh's own startup-file sourcing across a shebang-spawned script; the real
`handoffd_supervisor.bb`'s health/grace decision through its real
`--check-once` entry point) rather than a pure, generator-drivable module
this parcel introduces or changes:

- Invariant 1 ("no zsh script the supervisor test spawns reads the
  operator's own zsh startup files") is a claim about zsh's own semantics
  (`ZDOTDIR` redirection) interacting with an arbitrary, unbounded set of
  possible operator `~/.zshenv` contents — there is no pure module here to
  draw generated inputs against; the claim is discharged by acceptance
  scenario 01 above, which stages a HOSTILE startup file (an adversarial
  example by construction, not a fuzzed one) and asserts the real fixture
  still reaches the fake tmux through the real `swarm-cleanup.sh`.
- Invariant 2 ("the startup grace is neither widened nor narrowed") is a
  claim that this parcel changes NOTHING about `handoffd_supervisor.bb` —
  the constraint section and the empty `git diff` above are the direct
  evidence, and the existing `handoffd_supervisor_startup_grace_test_runner.bb`
  (BL-1342's own 7-assertion regression suite, unmodified) is the
  standing property/contract test for the grace's behavior itself. This
  ticket is scoped to never touch that file (constraints, "the startup
  grace keeps BL-1342's contract exactly"); authoring a second, competing
  property test for a contract this parcel deliberately does not touch
  would test somebody else's invariant, not this ticket's change.

Acceptance scenario 02 (Outline, both examples) is the closest thing to
an executable encoding of invariant 2 that stays in scope: it drives the
real `--check-once` path across both sides of the stall window and reads
the real resulting state, rather than asserting on the shell fixture's
own log.
