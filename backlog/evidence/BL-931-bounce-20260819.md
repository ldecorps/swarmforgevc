builds an isolated git-repo fixture and it is never removed anywhere in the

have followed (`bl413StaleSandboxSweepSteps.js`,
`bl458AcceptanceFixtureProcessLeakSteps.js`,
`bl460TmpSweepsBoundDeletesSteps.js`, etc. — cleanup colocated with the
step that owns the fixture's last use).

## Remediation

Same shape as the BL-929 remediation. This scenario has 3 `Then`-only
scenarios and one 2-example Scenario Outline, all sharing `seedFixture()`
from Background; the natural point that has already captured everything
downstream `Then` steps need (`ctx.result`/`ctx.rotationOutcome`/etc. —
whatever the "When the resident rotate helper is invoked" step populates)
is that same When step. Wrap its body in `try { ... } finally {
fs.rmSync(ctx.root, { recursive: true, force: true }); }` so removal
happens regardless of which step throws afterward, matching the idiom this
repo's compliant step-handler files already use. `swarmforge/scripts/test/`
Babashka fixtures are unaffected — check whether they already clean up via
their own shell-side helpers; this finding is scoped to the JS acceptance
step handler only.
