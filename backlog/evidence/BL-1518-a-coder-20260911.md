## What this parcel does

1. `swarm_handoff.bb` calls a new `draft-root-guard!` (line ~113) right
   after the "draft file exists" check and before any sender/mailbox logic,
   refusing (exit 1, `HANDOFF_DRAFT_OUTSIDE_ROOT`) when the draft path does
   not lie under the resolved project root — before any write.
2. `handoff_draft_root_guard_lib.bb` is the pure decision: `outside-root?`
   (containment at a path-separator boundary, never a bare string prefix)
   and `refusal-message` (names both paths). Both take already-canonical
   absolute path strings; the impure caller does the one `fs/canonicalize`
   each side needs.
3. `extension/test/telegramFrontDeskBotCli.test.js`: the two BL-607 tests
   and the BL-1203 dedup test stop using `use staging please` as answer
   text (now `sample answer alpha` / `sample answer gamma`); a new BL-1518
   test drives the real CLI with an explicit wrong `cwd`/`SWARMFORGE_ROLE`
   (the actual mutation-escape shape) and asserts refusal + nothing queued
   under either fixture, then a second real invocation with correct
   cwd/env delivers normally.
4. Feature file rewritten to 3 scenarios (draft under root sends normally;
   draft under an unrelated second project is refused; draft under a
   sibling directory sharing the root's name as a text prefix is still
   refused) with step handlers in
   `specs/pipeline/steps/bl1518HandoffDraftRootGuardSteps.js`, driving the
   real CLI against real fixture projects (same discipline as
   `bl1205HandoffRefusesAMassDeletionForwardSteps.js`).
5. No change to `enqueueRoleAnswerNote` itself: the ticket's "How" section
   directs "prefer deriving the root from the draft's location when cwd
   disagrees... over a new flag", which is what the CLI-side guard already
   does for every caller — the fix belongs in the CLI, not the one call
   site, and production `cwd`/`env` there were already correct.

## Non-vacuity (BL-654: "show it fails against a deliberately broken implementation, then restore it")

Both invariants encoded in `bl1518_handoff_draft_root_guard_property_runner.bb`
were proven non-vacuous by breaking `handoff_draft_root_guard_lib.bb` in
place, re-running, and restoring (verified `git diff` empty after restore
each time):

- **Invariant 1** (refuse outside, allow inside): `outside-root?` forced to
  never report outside (`(not (or true (= ...)))`). Result: the plain unit
  runner failed its 4 `outside-*` assertions; the property runner failed
  `P1` on every `:outside-*` shape drawn ("a draft that lies outside the
  root was treated as inside"). Restored → both green again.
- **Invariant 2** (verdict depends on nothing but the (draft, root) pair,
  no hidden cwd/env channel): `outside-root?` made to return a coin-flip on
  `System/nanoTime` half the time. Result: the plain unit runner still
  passed (it only calls the function once per case) but the property
  runner's `P2` failed immediately (seed 7, first case) — "the same
  (draft, root) pair produced different verdicts across calls". This is
  exactly why P2 exists as a *repeated-call* check rather than relying on
  the unit runner's single-call assertions to catch non-determinism.
  Restored → green again.

## Front-desk-bot restarts, 2026-09-10 18:00-18:16 UTC — attribution

The ticket's description asks whether the same mutation run (or its load)
is what took the live front-desk bot down that evening, given four
`front-desk-supervisor` restarts landed within seconds of the run-launch
times already on record. `reports/mutation/mutation.json` from that
evening does not exist (the ticket's own notes record the coder deleted it
before each run), so this is read entirely from
`.swarmforge/operator/front-desk-supervisor.log` on the master checkout.

**Restarts, all four `stalled bot no poll heartbeat within 90000 ms`:**

| stall detected (UTC) | restart (UTC) | attempt | nearest mutation run launch |
|---|---|---|---|
| 18:03:36.47 | 18:03:40.62 | 1 | 18:01:19 (+2m17s) |
| 18:08:25.64 | 18:08:29.84 | 2 | 18:06:33 (+1m53s) |
| 18:11:07.52 | 18:11:11.67 | 3 | (mid-run; no fresh launch logged this close — the 18:06:33 run was still active) |
| 18:13:35.44 | 18:13:41.63 | 4 | 18:11:44 (+1m51s) |

All four fall inside the mutation run's active window (~18:01-18:16) and
each is the *only* supervisor event of any kind (other than heartbeats) in
its surrounding minutes.

**Base rate, for comparison** (`grep "stalled bot" front-desk-supervisor.log
| cut -c1-10 | sort | uniq -c`): most days show 1-2 stalls total (2026-08-28:
1, 08-30: 2, 08-31: 1, 09-06: 2, 09-08: 2, 09-09: 1); 09-07 had 5;
08-29 had 57 (a separate, much larger known incident, not this one).
2026-09-10 had **6** stalls total — the four above, plus one at 15:50:53
and one at 22:14:50, both well outside the 18:01-18:16 mutation window and
each isolated (no other stall within hours either side).

**Conclusion: the run's load is what took the bot down for these four
restarts.** Four of the six stalls that day cluster with ~16x the day's
background density inside the exact 15-minute span the coder's
`stryker.bl1441bl620.config.json` run (and its immediately preceding
interrupted session) was active, each restart landing 1m51s-2m17s after a
run launch — consistent with the heavy, multi-process Stryker mutation
run saturating host CPU enough to starve the bot's own poll loop past its
90-second heartbeat window. The other two stalls that day (15:50, 22:14)
sit outside any mutation-run window and match the day's otherwise-normal
background rate, so mutation load is not implicated as the SOLE cause of
every stall ever recorded — only of the four inside this run's window.

Per the ticket's own framing ("if it is [the same test set or the run's
load], it is in scope, and if it is a separate cause it becomes its own
defect by note to the specifier"): this is the run's load, so **no
separate defect note was sent** — it is recorded here as in-scope
observation. Nothing in this ticket's "What is wanted" asks for a fix to
the bot's own resilience to host load or to the supervisor's 90s timeout;
that would be a distinct, larger slice (resource isolation between a
mutation run and live pipeline processes on a shared host) if the
specifier later decides it is worth its own ticket — this parcel does not
mint one on a hypothesis alone.
